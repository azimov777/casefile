# Tracker

Бэкенд таск-трекера: REST API для фронтенда и MCP-сервер для агентов.
Что и зачем строим — `docs/CONCEPT.md`, правила разработки — `docs/CONVENTIONS.md`.

## Требования

Docker и Docker Compose. Больше ничего: Python, зависимости, миграции, тесты и линтер
живут в контейнерах. Установка Python на хост-машину не поддерживается и не нужна.

## Быстрый старт

```bash
cp .env.example .env          # необязательно: у дев-контура есть значения по умолчанию
docker compose up -d          # поднимает PostgreSQL и сервер
docker compose run --rm migrate   # применяет миграции
docker compose run --rm init      # заводит владельца и печатает его первый токен
curl http://localhost:8000/health
```

Ответ здорового сервиса:

```json
{"status": "ok", "version": "0.1.0", "environment": "local", "database": "ok"}
```

Документация API — http://localhost:8000/docs, схема — http://localhost:8000/openapi.json.

## Доступ к API

Все маршруты `/api/v1` требуют токена — исключений нет. Вне защиты остался только `/health`:
он для Docker и мониторинга и в контракт с фронтендом не входит.

```bash
curl -H "Authorization: Bearer trk_..." http://localhost:8000/api/v1/actors/me
```

Первый токен взять неоткуда, кроме командной строки: выпустить его через API нельзя, потому
что API уже требует токен. Это и делает `docker compose run --rm init` — заводит
актора-владельца и печатает его секрет. Команда идемпотентна: повторный запуск второго
владельца не создаёт, но выпускает новый токен, и это же способ вернуть себе доступ.

Токен показывается **один раз**: в базе лежит только его хеш, восстановить секрет нельзя.

Дальше акторы и токены заводятся через API — одним и тем же механизмом для людей и агентов:

```bash
# завести агента
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"type": "agent", "key": "release_bot", "display_name": "Релизный бот"}' \
     http://localhost:8000/api/v1/actors

# выпустить ему токен (секрет виден только в этом ответе)
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"name": "ci"}' \
     http://localhost:8000/api/v1/actors/release_bot/tokens

# отозвать токен
curl -X DELETE -H "Authorization: Bearer $TOKEN" \
     http://localhost:8000/api/v1/actors/release_bot/tokens/$TOKEN_ID
```

Системный актор (`system`) создаётся миграцией, от его имени работают автоматика и фоновые
процессы. Через API он защищён: его нельзя изменить и нельзя выпустить ему токен.

## Очереди и справочники

Очередь — контейнер конфигурации процесса: свой набор типов задач, свои значения по умолчанию,
свои локальные статусы и резолюции. Ключ очереди (`TRK`) неизменяем — на нём построены ключи
задач (`TRK-123`).

```bash
# создать очередь: без указаний она комплектуется глобальными справочниками и готова к работе
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"key": "TRK", "name": "Трекер"}' \
     http://localhost:8000/api/v1/queues

# конфигурация целиком: типы, статусы, резолюции и поля одним запросом
curl -H "Authorization: Bearer $TOKEN" http://localhost:8000/api/v1/queues/TRK/config

# архивация вместо удаления: очередь с задачами удалить нельзя
curl -X POST -H "Authorization: Bearer $TOKEN" \
     http://localhost:8000/api/v1/queues/TRK/archive
```

Статусы, типы задач и резолюции — редактируемые данные, а не зашитый список. Начальный набор
(`open`/`in_progress`/`closed`, `task`/`bug`/`epic`, `done`/`rejected`/`duplicate`) создаётся
миграцией такими же обычными записями: их можно переименовать, отключить и дополнить своими.

Запись справочника либо **глобальная** (доступна всем очередям, адресуется голым ключом `open`),
либо **локальная** для очереди (адресуется с префиксом: `TRK.in_review`).

```bash
# свой статус только для этой очереди
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"key": "in_review", "name": "Ревью", "category": "in_progress", "queue": "TRK"}' \
     http://localhost:8000/api/v1/statuses

# чем можно пользоваться в очереди: глобальные записи плюс её собственные
curl -H "Authorization: Bearer $TOKEN" \
     'http://localhost:8000/api/v1/statuses?queue=TRK'
```

У каждого статуса обязательно есть **категория** — `new`, `in_progress` или `done`. На неё
опираются доски, прогресс проектов и автоматика, поэтому статус можно переименовать, ничего не
сломав. Сменить категорию у статуса, в котором стоят задачи, нельзя: это задним числом
переопределило бы, какие задачи считаются закрытыми.

Статус, которым пользуются, не удаляется — запрос отклоняется с кодом `status_in_use`. Порядок
такой: сначала перенести задачи, потом удалить. Ненужный, но исторически важный статус
правильнее не удалять, а отключить (`PATCH` с `is_active: false`) — история изменений останется
читаемой.

```bash
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"target_status": "open", "queue": "TRK"}' \
     http://localhost:8000/api/v1/statuses/TRK.in_review/move-issues
```

Ключи адресуются без учёта регистра (`trk.in_review` найдёт ту же запись), а вот придумать
кривой ключ при создании нельзя: ключи очередей — латиница в верхнем регистре, ключи
справочников — snake_case в нижнем.


## Кастомные поля

Разным процессам нужны разные атрибуты: у бага — серьёзность, у релиза — версия сборки. Поля
описываются в реестре и хранятся в `values JSONB` задачи, поэтому **новое поле не требует
миграции**. Область действия как у справочников: глобальное поле адресуется голым ключом
(`business_value`), локальное — с префиксом очереди (`TRK.severity`).

```bash
# перечисление, только для багов этой очереди, со значением по умолчанию
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"key": "severity", "name": "Серьёзность", "value_type": "enum", "queue": "TRK",
          "issue_types": ["bug"], "is_required": true, "default_value": "minor",
          "options": [{"key": "minor", "name": "Мелкая"},
                      {"key": "critical", "name": "Критическая"}]}' \
     http://localhost:8000/api/v1/fields

# какие поля есть у задачи такого типа в этой очереди
curl -H "Authorization: Bearer $TOKEN" \
     'http://localhost:8000/api/v1/fields?queue=TRK&issue_type=bug'
```

Типы значений: `string`, `text`, `number`, `date`, `datetime`, `boolean`, `enum`, `actor`
(ссылка на актора), `issue` (ссылка на задачу). Любое поле может быть множественным
(`is_multiple`) — тогда оно хранит массив значений того же типа.

Формат записи в JSONB зафиксирован в докстринге `app/domain/fields.py` и обязателен для всех:
его читают история изменений, поиск и автоматика. Ключ в `values` — это **ссылка** на поле, а
не его ключ, иначе глобальное `severity` и локальное `TRK.severity` затирали бы друг друга.

Что нельзя менять: ключ поля (под ним лежат значения в задачах) и — у поля, в котором уже есть
данные, — тип и множественность. Переименование, обязательность и порядок показа меняются
всегда. Удалить поле со значениями нельзя: его **скрывают** (`PATCH` с `is_hidden: true`) —
поле исчезает из конфигурации очереди, но данные и история остаются читаемыми.

Валидатор значений возвращает **все** замечания сразу, а не первое: фронт подсвечивает всю
форму за один ответ, агент исправляет запрос за одну попытку.

```json
{"error": {"code": "field_values_invalid",
           "message": "Custom field values failed validation",
           "details": {"fields": [{"field": "TRK.severity", "reason": "required",
                                   "allowed": ["minor", "critical"]},
                                  {"field": "TRK.due_on", "reason": "invalid_date",
                                   "expected": "YYYY-MM-DD"}]}}}
```


## Задачи

Задача — центральная сущность. Системные поля (статус, тип, исполнитель, дедлайн, приоритет,
теги) живут отдельными колонками, всё остальное — в `values JSONB` по реестру полей. Ключ
(`TRK-123`) выдаёт счётчик очереди, он неизменяем и никогда не переиспользуется — даже после
удаления задачи.

```bash
# создать задачу: тип и статус берутся из настроек очереди, если не указаны
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"queue": "TRK", "summary": "Починить выдачу ключей", "priority": "major",
          "tags": ["release"], "deadline": "2026-09-01T12:00:00+03:00",
          "values": {"TRK.severity": "critical"}}' \
     http://localhost:8000/api/v1/issues

# частичное обновление: меняются только переданные поля
curl -X PATCH -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"status": "in_progress", "version": 1}' \
     http://localhost:8000/api/v1/issues/TRK-1

# назначить исполнителя и подписать наблюдателя
curl -X PUT -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"assignee": "alice"}' http://localhost:8000/api/v1/issues/TRK-1/assignee
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"actor": "release_bot"}' http://localhost:8000/api/v1/issues/TRK-1/followers
```

**Переданный `null` очищает поле, отсутствующий ключ — не трогает.** Различаются они на уровне
типов, а не договорённости: `null` осмыслен у `assignee`, `deadline` и `resolution`, а у
названия его прислать нельзя — схема не даст. Значения кастомных полей обновляются по тому же
правилу, но проверяется всегда полный набор, поэтому снять обязательное поле частичным
обновлением не получится.

**Версия защищает от потерянных изменений.** Клиент присылает ту, которую видел; если задачу
успели изменить, ответ — `409 version_conflict` с текущей версией, а не молчаливая перезапись.
Версию можно не присылать — тогда проверки нет. Растёт она только на **фактических**
изменениях: поле, переданное со значением, равным текущему, ничего не меняет.

```json
{"error": {"code": "version_conflict",
           "message": "Issue was changed by someone else",
           "details": {"key": "TRK-1", "expected": 1, "actual": 2,
                       "hint": "re-read the issue and retry"}}}
```

Список задач (`GET /api/v1/issues?queue=TRK`) — простое перечисление с курсорной пагинацией.
Полноценный поиск с фильтрами и языком запросов — отдельная задача дорожной карты.

Что задача не отпускает: очередь с задачами нельзя удалить (её архивируют), статус с задачами
нельзя удалить и нельзя переопределить его категорию, поле со значениями нельзя удалить и
нельзя сменить ему тип. Во всех случаях ответ — `409` с числом задач в `details`. Саму задачу
тоже нельзя удалить, пока на неё ссылается кастомное поле другой задачи: сначала снимают
ссылки — иначе в чужом значении остался бы ключ, за которым ничего нет.


## Связи и иерархия

Связи соединяют задачи: блокировки, дубликаты, декомпозиция. Каждый тип имеет обратную
сторону, но **связь хранится один раз** — вторая сторона вычисляется при чтении. Двух строк на
одну связь в базе нет, поэтому им не из чего разойтись.

| Прямая | Обратная | Смысл |
|---|---|---|
| `relates` | `relates` | Просто связано |
| `depends_on` | `blocks` | Задача не может начаться, пока не сделана другая |
| `subtask_of` | `parent_of` | Декомпозиция и вложенность |
| `duplicates` | `duplicated_by` | Дубликат |

```bash
# TRK-3 зависит от TRK-2 — то же самое, что «TRK-2 блокирует TRK-3»
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"type": "depends_on", "issue": "TRK-2"}' \
     http://localhost:8000/api/v1/issues/TRK-3/links

# связи задачи: со стороны TRK-2 та же строка называется blocks
curl -H "Authorization: Bearer $TOKEN" http://localhost:8000/api/v1/issues/TRK-2/links

# дерево подзадач, с ограничением глубины
curl -H "Authorization: Bearer $TOKEN" \
     'http://localhost:8000/api/v1/issues/TRK-6/tree?depth=2'

# удалить связь — она исчезает у обеих задач сразу
curl -X DELETE -H "Authorization: Bearer $TOKEN" \
     http://localhost:8000/api/v1/issues/TRK-3/links/$LINK_ID
```

**Эпик — это тип задачи, а не тип связи.** Задачи входят в эпик обычной иерархической связью,
поэтому у задачи один родитель, а не «родитель и отдельно эпик». Вопрос «в каком эпике задача»
решается подъёмом по цепочке родителей: у эпика родителя не бывает, и он всегда корень.

Иерархия защищена тремя правилами, и каждое отвечает своим кодом:

| Ситуация | Код |
|---|---|
| Такая связь уже есть — в том числе заведённая с другой стороны | `409 link_already_exists` |
| У задачи уже есть родитель | `409 link_parent_exists` |
| Связь замкнула бы кольцо на любой глубине | `409 link_cycle_detected` |
| Родителя пытаются дать эпику — или эпиком делают подзадачу | `409 epic_cannot_have_parent` |
| Задачу связывают с самой собой | `422 link_self_reference` |

**Дерево ограничено, и об обрезке оно говорит.** Глубина задаётся параметром `depth`
(по умолчанию 3, потолок 10), а число узлов в одной выдаче — потолком в коде. Узел, чьи дети не
поместились, приезжает с `has_more_children: true`: урезанное дерево не выдаёт себя за полное.

Изменение связей попадает и в историю **обеих** задач, и в шину событий — типами `link.created`
и `link.deleted`. Удаление задачи уносит её связи каскадом; отдельных событий об этом нет,
подписчику достаточно `issue.deleted`.


## Обсуждение, чеклисты и теги

Комментарии — основной канал общения человека и агентов вокруг задачи. Комментарий агента,
человека и автоматики — **одна сущность**, различаемая типом актора: отдельной ленты для
служебных сообщений нет, и читателю не приходится склеивать две.

```bash
# написать реплику: упоминания @ключ_актора разбираются при сохранении
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"body": "Починил выдачу. @release_bot собери сборку"}' \
     http://localhost:8000/api/v1/issues/TRK-1/comments

# лента задачи, страницами
curl -H "Authorization: Bearer $TOKEN" http://localhost:8000/api/v1/issues/TRK-1/comments

# правка и мягкое удаление
curl -X PATCH -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"body": "Починил выдачу, тесты зелёные"}' \
     http://localhost:8000/api/v1/issues/TRK-1/comments/$COMMENT_ID
curl -X DELETE -H "Authorization: Bearer $TOKEN" \
     http://localhost:8000/api/v1/issues/TRK-1/comments/$COMMENT_ID
```

**Упоминания разбираются один раз, при сохранении**, и лежат отдельным полем `mentions` — на
них подпишутся уведомления. В поле попадают только существующие акторы: `@nobody` остаётся
обычным текстом. Следствие, о котором стоит знать: актор, заведённый позже комментария, в его
адресаты задним числом не попадёт.

**Цепочек ответов нет.** Ответ выражается цитатой отрывка в Markdown и упоминанием того, кому
отвечают: лента остаётся плоской, читается сверху вниз и листается курсором.

**Удаление мягкое.** Реплика остаётся в ленте плашкой — `body: null`, `is_deleted: true`, — а
текст стирается из базы. Дыра в обсуждении хуже плашки: соседние реплики теряют контекст, а
ушедшее уведомление начинает ссылаться в никуда. Повторное удаление и правка удалённого
отвечают `409 comment_deleted`.

### Чеклист

Лёгкая декомпозиция там, где заводить подзадачи избыточно: у пункта нет ни статуса, ни
процесса — только текст, галочка, место в списке и необязательные исполнитель с дедлайном.

```bash
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"text": "Прогнать тесты", "assignee": "release_bot"}' \
     http://localhost:8000/api/v1/issues/TRK-1/checklist

# отметить выполненным: кто и когда — проставляются вместе с галочкой
curl -X PUT -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"is_done": true}' \
     http://localhost:8000/api/v1/issues/TRK-1/checklist/$ITEM_ID/done

# переставить: место задаётся соседом, `after: null` — в начало списка
curl -X PUT -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"after": null}' \
     http://localhost:8000/api/v1/issues/TRK-1/checklist/$ITEM_ID/position
```

**Перемещение меняет одну строку.** Порядок держится на разреженных позициях — целых числах с
большим шагом между соседями, — и новая позиция вычисляется между соседями по месту вставки.
Сплошная нумерация переписывала бы весь список на каждое перетаскивание карточки. Когда зазор
между соседями исчерпан, список перенумеровывается целиком: это единственная операция
чеклиста, которая трогает больше одной строки.

Позиции наружу не отдаются — клиенту нужен порядок, а не координата. Чеклист возвращается
целиком, без курсора: число пунктов ограничено (100), поэтому страница всегда одна.

### Теги

Свободные метки, живущие в самой задаче. Справочника тегов нет: тег появляется вместе с первой
задачей и исчезает вместе с последней.

```bash
# словарь заведённых тегов: по алфавиту, с числом задач; ?query= ищет подстроку
curl -H "Authorization: Bearer $TOKEN" 'http://localhost:8000/api/v1/tags?query=rel&queue=TRK'

# точечное добавление и снятие — не требуют присылать весь набор
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"tags": ["backend"]}' http://localhost:8000/api/v1/issues/TRK-1/tags
curl -X DELETE -H "Authorization: Bearer $TOKEN" \
     http://localhost:8000/api/v1/issues/TRK-1/tags/release
```

Внутри задачи теги сравниваются без учёта регистра, первое написание побеждает: `Release`,
добавленный к задаче с меткой `release`, не создаёт второй метки — иначе получились бы два
разных фильтра про одно и то же. Полная замена набора по-прежнему доступна через
`PATCH /issues/{key}` с `tags`; точечные операции нужны, чтобы не читать задачу целиком и не
затирать метку, поставленную параллельно.

**В поиске метка сравнивается точно** (`tags: Release` не найдёт `release`), и это осознанное
исключение: `tags @> '["release"]'` ложится на GIN-индекс, а приведение регистра по элементам
массива — ни на какой, то есть регистронезависимый фильтр означал бы чтение всей таблицы задач
на каждый запрос. Канонические написания берутся из словаря выше — он и есть источник
существующих меток. Нужна нечёткость — есть вхождение: `tags: ~ rel`.

Обсуждение и чеклист попадают и в историю задачи, и в шину событий — типами `comment.created`,
`comment.updated`, `comment.deleted`, `checklist.item_added`, `checklist.item_checked`,
`checklist.item_unchecked`, `checklist.item_updated`, `checklist.item_moved`,
`checklist.item_removed`. В журнал задачи идёт отрывок комментария, полный текст — в событие.


## Поиск и язык запросов

Два способа спросить одно и то же. Строка на языке запросов — главный путь агента: её можно
передать, сохранить и положить в правило автоматики. Структурный фильтр — путь формы поиска
во фронтенде. Оба сводятся к одному внутреннему представлению, поэтому одинаковые по смыслу
запрос и фильтр дают **идентичный** результат.

```bash
# язык запросов
curl -H "Authorization: Bearer $TOKEN" -G http://localhost:8000/api/v1/search/issues \
     --data-urlencode 'query=queue: TRK and status: open and assignee: me() and deadline: <= today()' \
     --data-urlencode 'fields=summary' --data-urlencode 'fields=deadline'

# тот же отбор структурным фильтром
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"filter": {"queue": ["TRK"], "status": ["open"], "assignee": ["me()"],
                     "deadline_to": "today()"},
          "fields": ["summary", "deadline"]}' \
     http://localhost:8000/api/v1/search/issues
```

**Операторы:** `=`, `!=`, `>`, `>=`, `<`, `<=`, `~` (содержит), `!~`, `in`, `not in`. Оператор
можно не писать — тогда это равенство, а несколько значений через запятую превращают его во
вхождение в набор: `status: open, in_progress`.

**Функции:** `me()` — тот, кто спрашивает; `today()`, `now()` — точка отсчёта на стороне
сервера; `empty()` — значения нет. У дат бывает сдвиг: `today() - 7d`, `now() + 12h`
(единицы `d`, `w`, `h`, `m`).

**Связки:** `and`, `or` и скобки; `and` связывает крепче. Значение с пробелом, со словом языка
или с временем внутри пишется в кавычках: `text: "выдача ключей"`,
`deadline: >= "2026-08-28T10:00:00+00:00"`.

**Поля.** Системные адресуются именем (`queue`, `key`, `status`, `status_category`,
`issue_type`, `resolution`, `priority`, `summary`, `description`, `author`, `assignee`,
`followers`, `deadline`, `tags`, `project`, `created_at`, `updated_at`), кастомные — ссылкой
(`severity` у глобального, `TRK.severity` у локального). Отдельно есть `text` — вхождение
подстроки сразу в название, описание и ленту обсуждения.

Ошибка разбора называет **позицию и причину**, а не просто «неверный запрос»:

```json
{"error": {"code": "invalid_search_query",
           "message": "Search query cannot be parsed",
           "details": {"query": "queue TRK and status: open", "position": 6,
                       "reason": "expected_colon", "token": "TRK", "expected": [":"]}}}
```

**Сортировка и выдача.** `sort=-deadline` — по убыванию; сортировать можно по `created_at`,
`updated_at`, `deadline`, `priority`, `summary` и по одиночным кастомным полям. Порядок всегда
доопределяется идентификатором задачи, поэтому страницы устойчивы при параллельных правках.
`fields=` оставляет в ответе только названные поля — это не оптимизация, а способ не съесть
контекст агента сотней полных задач; ключ приходит всегда, а ссылка на кастомное поле
(`fields=TRK.severity`) оставляет в `values` только его.

Пустой запрос — законный: он означает «все задачи». Имя, занятое системой, но ещё без фильтра
(`links`, `comments`), отвечает отказом с причиной `not_searchable`, а не молча ищет в JSONB.

### Сохранённые фильтры

Именованный отбор, который переиспользуют фронт, MCP и автодействия. Хранится **описание**, а
не результат, и ровно одним способом: либо строкой запроса, либо списком условий.

```bash
# сохранить
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"name": "Мои горящие",
          "query": "assignee: me() and deadline: <= today() and status_category: != done",
          "sort": ["-priority"]}' \
     http://localhost:8000/api/v1/filters

# запустить: это параметр поиска, а не отдельный маршрут
curl -H "Authorization: Bearer $TOKEN" -G http://localhost:8000/api/v1/search/issues \
     --data-urlencode "saved_filter=$FILTER_ID" --data-urlencode 'fields=summary'

# сузить сохранённый фильтр ещё одним условием
curl -H "Authorization: Bearer $TOKEN" -G http://localhost:8000/api/v1/search/issues \
     --data-urlencode "saved_filter=$FILTER_ID" --data-urlencode 'query=tags: release'
```

Функции вычисляются в момент запуска, а не сохранения: `me()` означает «мои» для каждого, кто
запускает фильтр, а `today()` — сегодня. Описание проверяется при сохранении целиком, поэтому
опечатка в имени поля становится ошибкой сразу, а не пустой выдачей через неделю.


## Проекты и портфели

Надочередной слой планирования. Очередь отражает процесс команды, проект — результат, ради
которого работают несколько команд: он собирает задачи **из разных очередей**, а портфель
объединяет проекты и другие портфели. Это разные оси, поэтому проект — отдельное поле задачи,
а не свойство её очереди.

```bash
# портфель и проект внутри него
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"key": "platform", "name": "Платформа", "status": "in_progress"}' \
     http://localhost:8000/api/v1/portfolios

curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"key": "alpha", "name": "Доставка", "portfolio": "platform",
          "start_date": "2026-01-01", "end_date": "2026-06-30"}' \
     http://localhost:8000/api/v1/projects

# состав: задачи из разных очередей одним запросом
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"issues": ["TRK-1", "TRK-2", "OPS-1"]}' \
     http://localhost:8000/api/v1/projects/alpha/issues

# убрать задачу из проекта — сама задача остаётся жить в своей очереди
curl -X DELETE -H "Authorization: Bearer $TOKEN" \
     http://localhost:8000/api/v1/projects/alpha/issues/TRK-2
```

**Прогресс не хранится, а считается.** В карточке проекта лежит доля задач в статусах
категории `done`, посчитанная в момент запроса; у портфеля она сложена по задачам **всех** его
проектов-потомков, на любой глубине вложенности:

```json
{"data": {"key": "platform", "progress": {"total": 4, "done": 3, "ratio": 0.75},
          "projects_count": 1, "portfolios_count": 1}}
```

Сумма по задачам, а не среднее от детей: портфель отвечает на вопрос «сколько работы под ним
сделано», и мелкий проект, закрытый целиком, не должен двигать это число как крупный. У
проекта без задач `ratio` равен `null`, а не нулю: «нечего считать» и «сделано 0%» — разные
вещи. Колонки с процентом готовности в схеме нет и не будет — задачу закрывают из REST, из
MCP и массовым переносом статуса, и хранимая доля разошлась бы с реальностью в первую же
неделю.

**Список задач проекта — это поиск.** Отдельного набора фильтров у него нет: работает тот же
язык запросов, та же сортировка, тот же выбор полей и тот же курсор, а условие `project`
приклеивается по `and`.

```bash
curl -H "Authorization: Bearer $TOKEN" -G \
     http://localhost:8000/api/v1/projects/alpha/issues \
     --data-urlencode 'query=status_category: != done and priority: >= major' \
     --data-urlencode 'fields=summary' --data-urlencode 'sort=-deadline'
```

Тем же именем проект адресуется и в общем поиске: `project: alpha`, а `project: empty()`
находит задачи вне проектов.

**Состав портфеля** отдаётся одним упорядоченным списком, где проекты и вложенные портфели
различаются полем `kind`, — а не двумя коллекциями в одном ответе:

```bash
curl -H "Authorization: Bearer $TOKEN" \
     http://localhost:8000/api/v1/portfolios/platform/content
```

**Статус проекта — самостоятельное поле** (`not_started`, `in_progress`, `paused`, `done`), а
не функция от статусов задач: проект бывает приостановлен при полностью закрытых задачах.

**Вложенность без циклов.** Портфель кладётся в портфель через `PUT
/portfolios/{key}/parent`, проект переносится через `PUT /projects/{key}/portfolio`; `null`
вынимает объект наверх. Кольцо запрещено на произвольной глубине — отказ
`portfolio_cycle_detected`, как `link_cycle_detected` у иерархии задач.

**Удаления нет — есть архив.** `POST /projects/{key}/archive` убирает проект из рабочих
списков: новых задач он не принимает, но уже собранные остаются, прогресс продолжает
считаться, а поля правятся. Возврат — `POST /projects/{key}/unarchive`; оба идемпотентны.

## Доски

Доска — рабочий экран: она берёт задачи **сохранённым фильтром** (задача 12), раскладывает их
по колонкам и хранит собственный порядок карточек. Своих условий отбора у доски нет
намеренно: второй способ описать отбор разошёлся бы с языком запросов, и одна и та же доска
показывала бы разное во фронте и в автодействии.

```bash
# фильтр, который доска показывает
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"name": "Задачи TRK", "query": "queue: TRK"}' \
     http://localhost:8000/api/v1/filters

# доска с колонками: колонка — это набор статусов, а не один статус
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"name": "Доска команды", "saved_filter": "<uuid фильтра>",
          "columns": [{"name": "Открыт", "statuses": ["open"]},
                      {"name": "Работа", "statuses": ["in_progress"], "wip_limit": 2},
                      {"name": "Закрыт", "statuses": ["closed"]}]}' \
     http://localhost:8000/api/v1/boards

# задачи одной колонки — страницей, с выбором полей
curl -H "Authorization: Bearer $TOKEN" -G \
     "http://localhost:8000/api/v1/boards/<uuid>/columns/<uuid колонки>/issues" \
     --data-urlencode 'fields=summary' --data-urlencode 'fields=assignee'
```

**Доска собирается покомпонентно, а не одним ответом.** Одна доска тянет тысячи задач, и
оболочка ответа кладёт под `data` ровно одну коллекцию: карточка доски отдаёт настройки и
колонки, каждая колонка — свою страницу со своим курсором и своим `fields`. Счётчиков задач в
колонке нет — курсорная пагинация не считает `total`, а отдельный `COUNT` по фильтру доски
самый дорогой запрос API. `wip_limit` — то, что доска показывает, а не то, что она стережёт:
перемещение карточки идёт переходом воркфлоу, и второй запрет поверх него означал бы, что
одно и то же изменение статуса проходит из карточки задачи и отклоняется с доски.

**Перемещение карточки между колонками — это переход воркфлоу.** Доска не пишет статус
напрямую, поэтому через неё нельзя обойти ни одну проверку процесса:

```bash
# отказ, если такого ребра в графе нет: 409 transition_not_allowed
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"column": "<uuid колонки>"}' \
     http://localhost:8000/api/v1/boards/<uuid>/issues/TRK-3/column

# закрытие требует резолюции — она принимается тем же запросом
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"column": "<uuid колонки Закрыт>", "resolution": "done"}' \
     http://localhost:8000/api/v1/boards/<uuid>/issues/TRK-3/column
```

Если в колонке несколько статусов, целевой обязан назвать вызывающий (`"status": "TRK.review"`):
угадывать значило бы переводить задачу в статус, которого никто не просил.

**Порядок карточек задаётся соседом.** Отдельный маршрут, потому что перестановка не меняет
задачу вовсе: версия не растёт, история не пополняется, статус не трогается.

```bash
# в начало списка
curl -X PUT -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"after": null}' \
     http://localhost:8000/api/v1/boards/<uuid>/issues/TRK-4/rank

# сразу за TRK-4;  {"before": null} ставит в самый конец
curl -X PUT -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"after": "TRK-4"}' \
     http://localhost:8000/api/v1/boards/<uuid>/issues/TRK-2/rank
```

Позиция наружу не отдаётся: место задаётся соседом, а внутреннее число разреженной шкалы
клиенту знать незачем — при перенумерации доски все они меняются, сохраняя порядок. Задача,
которую никто не двигал, стоит там, где встала по времени создания: строки ранга у неё нет, а
позиция всё равно есть.

## История изменений и события

Каждое изменение задачи оставляет два следа, и оба пишутся **в той же транзакции**, что и
сама правка: запись в журнале изменений и событие в outbox. Откат транзакции уносит все три
разом — состояния «уведомление ушло, а изменение откатилось» в системе не бывает.

```bash
# история задачи: кто, когда, с какого значения на какое
curl -H "Authorization: Bearer $TOKEN" \
     http://localhost:8000/api/v1/issues/TRK-1/changelog
```

```json
{"data": [{"id": "...", "issue": "TRK-1", "actor": "owner",
           "event": "issue.status_changed",
           "changes": [{"field": "status", "before": "open", "after": "in_progress"}],
           "created_at": "2026-08-27T19:58:48.884Z"}],
 "meta": {"next_cursor": null, "has_more": false}}
```

Порядок хронологический, от старого к новому; первая запись у любой задачи —
`issue.created` с пустым списком изменений: у создания нет «было». Значения хранятся
ссылками на момент события (`open`, `TRK.open`, ключ актора), поэтому переименованный или
удалённый статус не портит историю задним числом.

Типы событий: `issue.created`, `issue.updated`, `issue.status_changed`, `issue.assigned`,
`issue.deleted`, `status.issues_moved`, `link.created`, `link.deleted`. Словарь открытый —
следующие задачи дописывают свои в `app/domain/events.py`. Тип выводится из действия, которым
сценарий проверял права, чтобы имена действий и имена событий не разъехались.

**Событие самодостаточно.** В нагрузке лежит снимок задачи после изменения и список
«было → стало»: подписчику не нужно идти в базу за контекстом — пока событие ждало
обработки, задачу успели изменить ещё раз.

**Массовый перенос задач между статусами устроен несимметрично.** Запись в истории получает
каждая перенесённая задача, а событие рождается одно на весь перенос
(`status.issues_moved` со списком ключей). История ведётся по задаче, и дыры в ней быть не
должно; шина же кормит автоматику и уведомления, где сотня одинаковых `issue.status_changed`
означала бы сотню уведомлений об административной операции.

### Воркер событий

Рассылку ведёт **отдельный сервис Compose** `worker`, а не поток внутри веб-процесса: поток
размножился бы вместе с репликами API, и каждое событие обработалось бы несколько раз.

```bash
docker compose logs -f worker          # что обрабатывается прямо сейчас
docker compose restart worker          # после правки кода подписчиков: автоперезапуска у него нет
```

Свойства, на которые можно рассчитывать:

- Событие обрабатывается в собственной транзакции и захватывается `FOR UPDATE SKIP LOCKED`.
  Процесс, убитый посреди работы, не теряет событие — оно снова становится необработанным.
- Падение одного подписчика не мешает остальным: каждый идёт во вложенной транзакции, и
  откатывается только его работа.
- Повтор идёт **только по тем подписчикам, кто ещё не отработал** — их имена копятся в
  `delivered_to`. Упавший вебхук не заставит автоматику сработать дважды.
- Пауза перед повтором растёт (`TRACKER_OUTBOX_RETRY_DELAY`, удваивается до потолка). После
  `TRACKER_OUTBOX_MAX_ATTEMPTS` попыток событие помечается недоставленным и больше не берётся.
- `docker stop` доводит текущее событие до конца и завершает процесс — за секунду, а не по
  истечении отведённого времени.

Подписчик объявляется декоратором и попадает в реестр при импорте своего модуля:

```python
from app.domain.events import EventType
from app.services.event_bus import EventEnvelope, subscribe


@subscribe(EventType.ISSUE_ASSIGNED, name="notifications")
async def on_assigned(session: AsyncSession, event: EventEnvelope) -> None:
    # Всё нужное — в самом событии: снимок задачи после изменения и что поменялось.
    assignee = event.payload["issue"]["assignee"]
    session.add(Notification(actor_key=assignee, issue_key=event.object_key))
```

Модуль дописывается в `SUBSCRIBER_MODULES` (`app/services/event_bus.py`) — ядро шины и
воркер при этом не трогаются. Подписка без указания типов означает «все события».


## Автоматика

Правила пишутся **кодом** и лежат в репозитории (`app/automation/rules/`). В базе хранится
только их состояние: включено ли правило, к какой очереди привязано, с какими параметрами
работает. Поведение меняем правкой кода, включаем и настраиваем — через API, без перезапуска.

Три формы:

| Форма | Чем запускается | Пример |
|---|---|---|
| **Триггер** | событие из шины | «родителя закрыли — разобраться с подзадачами» |
| **Автодействие** | расписание, отбирает задачи фильтром | «задачи без движения неделю — напомнить» |
| **Макрос** | ручной вызов по конкретной задаче | «оформить как релизную» |

### Как это выглядит снаружи

```bash
# какие правила есть, что они умеют, включены ли
curl -H "Authorization: Bearer $TOKEN" \
     http://localhost:8000/api/v1/automation/rules

# включить, ограничить очередью и настроить — без перезапуска процессов
curl -X PATCH -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"is_enabled": true, "queue": "TRK",
          "params": {"mode": "close", "resolution": "done"}}' \
     http://localhost:8000/api/v1/automation/rules/close_children_with_parent

# запустить макрос по задаче
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"issue": "TRK-3", "params": {"tags": ["release"]}}' \
     http://localhost:8000/api/v1/automation/rules/prepare_release/run

# журнал срабатываний: что сработало, что пропущено и почему
curl -H "Authorization: Bearer $TOKEN" \
     'http://localhost:8000/api/v1/automation/runs?issue=TRK-3'
```

Ответ списка правил показывает обе половины сразу: неизменяемое объявление из кода (`kind`,
`events`, `schedule_seconds`, `query`, `params_schema`) и изменяемое состояние из базы
(`is_enabled`, `queue`, `params`, `saved_filter`). По `params_schema` интерфейс строит форму
настройки — это обычная JSON Schema, объявленная в модуле самого правила.

Заводить и удалять правила через API нельзя: правило — это код, а строка состояния
появляется сама при старте процесса. **Новое правило приезжает выключенным** — включённое с
выкладкой начало бы менять задачи в ту же минуту, когда его ещё никто не настроил.

### Как добавить своё правило

Это самая частая операция при эксплуатации. Четыре шага.

**1. Написать функцию с декоратором** в новом файле `app/automation/rules/my_rule.py`:

```python
from pydantic import BaseModel, Field

from app.automation.context import RuleContext
from app.automation.registry import rule
from app.domain.automation import RuleKind
from app.domain.events import EventType


class Params(BaseModel):
    model_config = {"extra": "forbid"}

    assign_to: str = Field(description="Actor key to assign the issue to")


@rule(
    key="assign_on_start",
    name="Назначить исполнителя при старте",
    kind=RuleKind.TRIGGER,
    events=(EventType.ISSUE_STATUS_CHANGED,),
    params=Params,
)
async def assign_on_start(ctx: RuleContext) -> None:
    if ctx.target.assignee is not None:
        ctx.skip("already_assigned")
    await ctx.assign(ctx.params.assign_to)
```

**2. Дописать модуль в `RULE_MODULES`** (`app/automation/registry.py`). Больше нигде ничего
менять не нужно: ни движок, ни воркер, ни планировщик про конкретные правила не знают.

**3. Перезапустить процессы**, которые правило исполняют. Автоперезапуска по правке кода у
фоновых процессов нет — он есть только у uvicorn:

```bash
docker compose restart worker scheduler
```

**4. Включить и настроить** через `PATCH /api/v1/automation/rules/assign_on_start`.

Что нужно знать, когда пишете правило:

- **Действовать только через `ctx`.** Каждое действие контекста — обёртка над тем же
  сценарием, который зовут REST и MCP, поэтому правило проходит проверки воркфлоу, пишет
  историю задачи и порождает события. Правило, пишущее в базу напрямую, обходит всё это.
  Набор действий: `update`, `set_status`, `transition_to_category`, `assign`, `comment`,
  `add_checklist_item`, `link`, `create_subtask`, `reparent`.
- **Смена статуса идёт через воркфлоу.** Ребра в графе нет — правило падает с
  `transition_not_allowed`, и это видно в журнале. Если нужен мягкий вариант,
  `transition_to_category` вернёт `None` вместо исключения, когда подходящего перехода нет.
- **Рассуждать категориями, а не ключами статусов.** `done` работает и там, где закрывающий
  статус называется `released`.
- **Смотреть в `ctx.changed_fields()`, а не только на тип события.** `issue.status_changed`
  может нести вместе со статусом ещё и смену исполнителя, а кастомное поле меняется обычным
  `issue.updated`.
- **Массовый перенос задач между статусами `issue.status_changed` не даёт.** Он приходит
  одним событием `status.issues_moved` со списком ключей — это осознанное решение, чтобы
  сотня задач не означала сотню срабатываний. Правилу, которому такие переносы важны, надо
  подписаться и на этот тип и разобрать список самому.
- **`ctx.skip(...)` прерывает правило и откатывает всё, что оно успело сделать.** Это его
  смысл: «условие не выполнено, меня здесь не было». Если работа уже сделана и надо просто
  выйти — обычный `return`.
- **Переподчинение — два шага.** Родитель у задачи ровно один, и попытка завести второго даёт
  `link_parent_exists`, а не переносит задачу. Для этого есть `ctx.reparent`.
- **Правило выполняется от системного актора**, а настоящий инициатор лежит в
  `ctx.initiator` и попадает в журнал срабатываний.

### Отбор задач у автодействия

Автодействие отбирает задачи **тем же поиском**, что и API: строка на языке запросов из
объявления либо привязанный сохранённый фильтр. Второго толкования фильтра в системе нет —
иначе правило работало бы не на том наборе задач, который показывает интерфейс.

Функции языка вычисляются в момент запуска, поэтому `updated_at: <= today() - 7d` означает
семь дней от сегодняшнего дня, а не от дня выкладки, а `assignee: me()` — актора, от имени
которого идёт правило. Поменять набор задач без правки кода можно, привязав сохранённый
фильтр:

```bash
curl -X PATCH -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"saved_filter": "dde16776-90e8-45ad-879a-e3bf008169bf"}' \
     http://localhost:8000/api/v1/automation/rules/nudge_stale_issues
```

Две оговорки. `me()` в отборе автодействия означает **системного актора**: расписание никем
не инициируется. И привязка правила к очереди складывается с отбором отдельным условием, а не
дописывается в строку текстом.

### Планировщик

Автодействия будит **отдельный сервис Compose** `scheduler`. Он обязан быть в
**единственном экземпляре**: две реплики выполнят каждое автодействие дважды. Воркер событий
так масштабировать можно, планировщик — нет.

```bash
docker compose logs -f scheduler       # какие правила отработали и по каким задачам
docker compose restart scheduler       # после правки кода правил
```

Каждое правило идёт в своей транзакции, срок следующего запуска считается от момента
выполнения (а не от пропущенного срока), и за один тик правило обрабатывает не больше
`TRACKER_AUTOMATION_BATCH_SIZE` задач — остальные ждут следующего.

### Защита от зацикливания

Правило меняет задачу → рождается событие → срабатывает правило. Без защиты первая же пара
взаимных правил положила бы систему. Защит три, и каждая ловит своё:

| Защита | Что ловит | Настройка |
|---|---|---|
| Реакция на себя | правило поймало собственное событие | всегда включена |
| Глубина цепочки | A изменил → сработал B → изменил → сработал A | `TRACKER_AUTOMATION_MAX_CHAIN_DEPTH` |
| Лимит на задачу за окно | волна законных событий по одной задаче | `TRACKER_AUTOMATION_RATE_LIMIT`, `..._RATE_WINDOW` |

Признак «это изменение сделано автоматикой» и глубина цепочки едут **в полезной нагрузке
события** (ключ `automation`): между изменением и его последствием стоит outbox, и другого
канала нет. Отсутствие ключа означает, что изменение сделал человек или агент.

Сработавшая защита — не тишина, а строка в журнале со статусом `skipped` и причиной
(`self_triggered`, `chain_depth_exceeded`, `rate_limited`). Вопрос «почему правило не
сработало» задают чаще, чем «что оно сделало».

### Журнал срабатываний

Пишется на каждое **рассмотренное** срабатывание, а не только на успешное: выключенное
правило и чужая очередь записи не дают, а вот «посмотрел и решил ничего не делать» — даёт.

```json
{"data": [{"rule": "close_children_with_parent", "issue": "TRK-1",
           "trigger": "event", "status": "success", "reason": null,
           "actions": [{"action": "set_status", "target": "TRK-2",
                        "from": "in_progress", "to": "closed"}],
           "initiator": "owner", "chain_depth": 1, "duration_ms": 21}]}
```

`initiator` — тот, чьё действие привело к запуску; сами изменения идут от системного актора,
и в истории задачи автором стоит `system`. Связка «правило X, запущено из-за действия актора
Y» читается отсюда: `GET /api/v1/automation/runs?issue=TRK-2`.

Ошибка правила изолирована: она не роняет ни соседей, ни обработку события — и попадает в
журнал со статусом `failed` и текстом причины. Неудачный **макрос** отвечает тем же `200` с
`status: failed`, а не пятисоткой: проброс исключения откатил бы транзакцию вместе с записью
журнала, то есть с единственным следом неудачи.

## Уведомления и инбокс

У каждого актора есть персональная лента событий. Она живёт в базе, поэтому работает
независимо от того, подключён ли клиент прямо сейчас: агент забирает накопившееся, когда
проснётся, а не теряет его.

```bash
# что мне пришло
curl -H "Authorization: Bearer $TOKEN" http://localhost:8000/api/v1/notifications

# только непрочитанное
curl -H "Authorization: Bearer $TOKEN" \
     'http://localhost:8000/api/v1/notifications?is_read=false'

# разобрал ленту целиком
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{}' http://localhost:8000/api/v1/notifications/read

# отметить только эти
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"notifications": ["6c6e17f7-..."]}' \
     http://localhost:8000/api/v1/notifications/read
```

Запись несёт и текст, и идентификаторы. Текст — человеку, идентификаторы — агенту: по ним он
решает, браться ли за задачу, не разбирая строку.

```json
{"data": [{"id": "6c6e17f7-...", "event_type": "issue.status_changed",
           "object_type": "issue", "object_key": "TRK-1", "issue": "TRK-1",
           "body": "TRK-1 status: open -> in_progress",
           "details": {"issue": "TRK-1", "queue": "TRK", "scope": "assignee",
                       "fields": ["status"], "status_from": "open",
                       "status_to": "in_progress"},
           "count": 1, "is_read": false}]}
```

`scope` — **почему** уведомление пришло, и это самая адресная из ролей: реплика «@bob,
посмотри» по задаче, где Боб и так исполнитель, придёт ему как `mention`, а не как
`assignee`. «Меня позвали лично» и «изменилось что-то в моей задаче» — разные поводы
вмешаться.

### Кто и что получает по умолчанию

Без единой настройки уведомления получают автор, исполнитель, наблюдатели и упомянутые —
по событиям своих задач; руководитель и участники — по событиям своего проекта или
портфеля. Исполнитель **пункта чеклиста** тоже: у пункта свой исполнитель, и он может не
совпадать с исполнителем задачи.

Собственные действия не уведомляют: иначе агент, обновивший задачу, немедленно разбудит сам
себя своим же изменением. Это настройка подписки (`notify_own_actions`), а не жёсткое
правило.

Повторы схлопываются. Десять правок одной задачи за минуту дают **одну** запись со
счётчиком `count`, а не десять писем; окно задаётся `TRACKER_NOTIFICATION_DIGEST_WINDOW`.
Прочитанная запись в склейку не берётся — дописать в неё событие значило бы изменить
увиденное задним числом.

### Подписки

Подписка нужна, чтобы **расширить** набор (следить за очередью, проектом, чужой задачей или
всем потоком) либо **выключить** роль по умолчанию.

```bash
# следить за всей очередью TRK, но только за созданием задач
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"scope": "queue", "scope_key": "TRK", "event_types": ["issue.created"]}' \
     http://localhost:8000/api/v1/notifications/subscriptions

# больше не уведомлять меня о задачах, где я наблюдатель
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"scope": "follower", "is_enabled": false}' \
     http://localhost:8000/api/v1/notifications/subscriptions
```

Области: `all`, `queue`, `project`, `issue` (требуют `scope_key`) и `author`, `assignee`,
`follower`, `mention`, `member` (ключа не требуют — они про роль в событии).

Две вещи, которые легко понять неправильно:

- **Пустой список подписок означает «всё по умолчанию»**, а не «мне ничего не приходит».
- **Удаление выключенной подписки на роль возвращает уведомления.** Строки, которая их
  гасила, больше нет. Чтобы не получать их, подписку держат выключенной.

Опечатка в типе события отвергается (`invalid_subscription`): иначе получилась бы подписка,
неотличимая от исправной и никогда не срабатывающая.

### Ожидание новых уведомлений

Основа инструмента ожидания в MCP: вызов блокируется до появления уведомления или до
таймаута.

```bash
curl -H "Authorization: Bearer $TOKEN" \
     'http://localhost:8000/api/v1/notifications/wait?timeout=30'
```

```json
{"data": {"notifications": [], "waited": 30.0, "timed_out": true}}
```

Пустой ответ с `timed_out: true` — **не ошибка**: по коду ответа отличить «ничего не пришло»
от сбоя нельзя, он в обоих случаях успешный. Таймаут ограничен сверху
(`TRACKER_NOTIFICATION_WAIT_MAX_TIMEOUT`), и запрос сверх потолка отвергается, а не
срезается молча — иначе клиент решил бы, что уведомлений не было, хотя его просто перестали
ждать.

Опроса базы в цикле здесь нет. Уведомление рождается в воркере — другом процессе, — поэтому
основной канал оповещения `LISTEN/NOTIFY` PostgreSQL: `pg_notify` уходит в той же
транзакции, что и запись, и доставляется при её фиксации. Редкий контрольный опрос
(`TRACKER_NOTIFICATION_WAIT_POLL_INTERVAL`) страхует от оборванного соединения слушателя.
Соединение с базой на время ожидания не удерживается: транзакция закрывается, пока вызов
спит, иначе пять ждущих агентов исчерпали бы пул.

### Уведомление из правила автоматики

У правила два способа заговорить с человеком, и они не взаимозаменяемы. Комментарий виден
всем, кто читает задачу; уведомление адресовано одному и живёт в его ленте.

```python
await ctx.notify(ctx.target.assignee, "Дедлайн завтра", reason="deadline")
```

Отправленное видно в журнале срабатываний. Уведомление в адрес системного актора не
отправляется — правила ходят от его имени, и его инбокс никто не читает; в журнале это
видно пометкой `skipped: system_actor`, а не тишиной.


## Вебхуки

Инбокс — канал для агентов внутри трекера. Наружу события уходят вебхуками: подписка на
адрес, подпись секретом, повторы и журнал доставок.

```bash
# завести подписку на весь поток
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"name": "release-bot", "url": "https://ci.example.com/hooks/tracker"}' \
     http://localhost:8000/api/v1/webhooks

# только события одной очереди и только смены статуса
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"name": "ops-watch", "url": "https://bot.example.com/hook",
          "scope": "queue", "scope_key": "OPS",
          "event_types": ["issue.status_changed"]}' \
     http://localhost:8000/api/v1/webhooks
```

Область — `all`, `queue` или `project`; у двух последних обязателен `scope_key`. Пустой
`event_types` означает «все типы»: вебхуку обычно нужен весь поток. Ролевых областей
(«я исполнитель») у вебхука нет и быть не может — у адреса нет актора.

**Секрет отдаётся один раз**, в ответе на создание. Дальше в API приходит только маска
(`secret_hint`) — по ней две подписки различаются при ротации, но подписать ею ничего
нельзя. Потерянный секрет заменяют новым (`PATCH`), а не восстанавливают. Свой секрет,
уже прошитый у получателя, можно передать при создании.

### Что приходит получателю

`POST` с телом JSON и четырьмя заголовками:

| Заголовок | Что в нём |
|---|---|
| `X-Tracker-Delivery` | идентификатор доставки — по нему получатель распознаёт повтор |
| `X-Tracker-Event` | тип события |
| `X-Tracker-Timestamp` | время отправки, unix-секунды |
| `X-Tracker-Signature` | `sha256=<hex>` — HMAC-SHA256 от строки `<timestamp>.<тело>` |

```json
{"delivery": "f832f424-...",
 "event": {"id": "972a1b70-...", "type": "issue.status_changed",
           "actor": "owner", "occurred_at": "2026-08-29T10:45:16.849934+00:00"},
 "object": {"type": "issue", "key": "TRK-1"},
 "issue": "TRK-1", "queue": "TRK", "projects": [],
 "summary": "TRK-1 status: open -> in_progress",
 "details": {"issue": "TRK-1", "status": "in_progress", "fields": ["status"]}}
```

Снимка задачи целиком в теле нет намеренно: наружу уходит то, по чему получатель
принимает решение и может сходить в API за остальным.

Проверка подписи на стороне получателя (Python):

```python
import hashlib, hmac


def verify(secret: str, timestamp: str, body: bytes, signature: str) -> bool:
    expected = hmac.new(
        secret.encode(), timestamp.encode() + b"." + body, hashlib.sha256
    ).hexdigest()
    return hmac.compare_digest(f"sha256={expected}", signature)
```

Подпись покрывает **и время**, а не одно тело: иначе перехваченный вызов можно было бы
переиграть через сутки, и отличить его от свежего получателю было бы нечем. Отвергайте
доставку, чей `X-Tracker-Timestamp` старше нескольких минут.

### Доставка идёт минимум один раз

Ровно один раз не обещает никто: ответ может потеряться уже после того, как получатель
сделал работу, и повтор в этом случае неизбежен. Поэтому:

- **автоматический повтор** приходит с тем же `delivery` — получатель обязан распознать
  его сам и не делать работу дважды;
- **ручная переотправка** (`POST /webhooks/deliveries/{id}/retry`) приходит с **новым**
  `delivery`, но с тем же `event.id`. Иначе добросовестный получатель отбросил бы её как
  дубль, и переотправка не сделала бы ничего.

Отсюда правило для получателя: дедупликация по `delivery` защищает от автоматических
повторов, дедупликация по `event.id` — от ручной переотправки уже обработанного события.

**Удаление задачи не даёт событий `link.deleted`.** Наружу уходит только `issue.deleted`,
а связи удалённой задачи исчезают каскадом в базе, молча. Получатель, который ведёт свою
копию графа связей, обязан обрабатывать `issue.deleted` как «все связи этой задачи
исчезли», иначе у него останутся висящие рёбра на несуществующую задачу.

### Повторы, журнал и мёртвый адрес

Доставка повторяется с нарастающей паузой (`TRACKER_WEBHOOK_RETRY_DELAY`, удваивается,
потолок `TRACKER_WEBHOOK_MAX_RETRY_DELAY`) до `TRACKER_WEBHOOK_MAX_ATTEMPTS` попыток,
после чего помечается недоставленной. Это **не** те же повторы, что у шины событий:
`TRACKER_OUTBOX_MAX_ATTEMPTS` повторяет событие по упавшим подписчикам, а эти — доставку
по конкретному адресу. Без разделения одно событие уходило бы на живые адреса столько
раз, сколько раз упал мёртвый.

```bash
# журнал доставок целиком
curl -H "Authorization: Bearer $TOKEN" http://localhost:8000/api/v1/webhooks/deliveries

# только неудавшиеся по одной подписке
curl -H "Authorization: Bearer $TOKEN" \
     'http://localhost:8000/api/v1/webhooks/deliveries?subscription=3a4d78fa-...&delivery_status=failed'

# отправить заново
curl -X POST -H "Authorization: Bearer $TOKEN" \
     http://localhost:8000/api/v1/webhooks/deliveries/f832f424-.../retry
```

В записи журнала есть `response_status`, `attempts`, `last_error` и адрес, по которому
вызов уходил **тогда**: адрес подписки могли с тех пор поменять. `response_status: null`
означает, что ответа не было вовсе — таймаут, отказ соединения, неразрешённое имя; «500
от получателя» и «адрес не отвечает» чинятся в разных местах.

После `TRACKER_WEBHOOK_FAILURE_THRESHOLD` неудачных **попыток подряд** подписка
выключается сама: в ней проставляются `disabled_at` и `disabled_reason`, а её ожидающие
доставки гасятся — мёртвый адрес не должен занимать доставщик таймаутами. Любая успешная
доставка обнуляет счётчик: получатель, теряющий каждую вторую доставку, работает.
Включают подписку обратно вручную (`PATCH` с `is_enabled: true`), и включение обнуляет
счётчик — иначе она погасла бы на первой же неудаче после починки.

### Вызов из правила автоматики

Третий способ правила заговорить с миром, кроме комментария и уведомления, и
единственный, который уходит за пределы трекера:

```python
await ctx.webhook("release-bot", "Релиз готов", version="1.2.3")
```

Подписка адресуется **именем**, а не идентификатором: имена настраивают люди. Вызов
**ставится в очередь**, а не уходит по сети из правила: сетевой запрос внутри правила
задержал бы обработку события на таймаут мёртвого адреса. Получателю он приходит с
`event.type = webhook.direct` и пустым `event.id`.

Несуществующее имя — ошибка правила (опечатка в параметрах). Выключенная подписка или её
фильтр типов — пропуск с пометкой в журнале срабатываний (`skipped: subscription_disabled`,
`skipped: event_type_filtered`): чужая настройка не должна ронять правило, но и потеряться
вызов не имеет права. Чтобы адрес получал **только** вызовы правил, заведите ему
`"event_types": ["webhook.direct"]`.

### Доставщик

Отправкой занимается отдельный сервис Compose — `webhooks` (`python -m app.webhooks`).
Подписчик шины кладёт задание в таблицу и на этом заканчивает: HTTP-запрос прямо из
подписчика означал бы, что мёртвый адрес держит всю очередь событий на своём таймауте —
не доходят уведомления, не срабатывает автоматика.

```bash
docker compose logs -f webhooks
docker compose restart webhooks   # после правки кода доставки
```

Строка задания заблокирована всё время HTTP-запроса, включая таймаут, — отсюда короткий
`TRACKER_WEBHOOK_TIMEOUT`. Перенаправления не выполняются: переход увёл бы подписанный
запрос на адрес, которого нет в подписке.


## Живой поток событий (SSE)

Фронтенду не нужно опрашивать сервер: события приходят в открытое соединение
`text/event-stream`.

```bash
curl -N -H "Authorization: Bearer $TOKEN" \
     'http://localhost:8000/api/v1/events/stream?queue=TRK'
```

```
retry: 3000

id: 34bf5e53-6465-4a23-adaa-91e1944adfee
event: issue.created
data: {"event": {"id": "34bf5e53-...", "type": "issue.created", "actor": "owner", ...},
       "object": {"type": "issue", "key": "TRK-2"}, "issue": "TRK-2", "queue": "TRK",
       "summary": "TRK-2 created: Событие в живом потоке", "details": {...}}

: ping
```

Тело кадра — та же форма, что у вебхука, без поля `delivery`: одно событие обязано
читаться одинаково у внешнего подписчика и у фронтенда. Строки, начинающиеся с `:`, —
тики: они не дают прокси закрыть простаивающее соединение.

**Поток читается fetch-клиентом, а не голым `EventSource`.** Браузерный `EventSource` не
умеет слать заголовки, а весь `/api/v1` требует токен в `Authorization`; принимать токен
параметром запроса мы не стали — он уехал бы в журналы прокси, в историю браузера и в
`Referer`. Подойдёт любой fetch-клиент SSE, например `@microsoft/fetch-event-source`.

Сужение — `queue`, `project`, `issue`, `event_types` — складывается по «и»:

```bash
curl -N -H "Authorization: Bearer $TOKEN" \
     'http://localhost:8000/api/v1/events/stream?issue=TRK-1&event_types=comment.created'
```

### Переподключение

При обрыве клиент присылает `Last-Event-ID` с идентификатором последнего полученного
события (fetch-клиенты делают это сами), и поток продолжает ровно с него:

```bash
curl -N -H "Authorization: Bearer $TOKEN" \
     -H 'Last-Event-ID: 34bf5e53-6465-4a23-adaa-91e1944adfee' \
     http://localhost:8000/api/v1/events/stream
```

Окно переподключения — это очередь событий (`outbox_events`), которая не чистится, но
обещание ограничено: клиент, отставший больше чем на `TRACKER_STREAM_REPLAY_LIMIT`
событий, получает `422 invalid_stream_cursor` с `reason: too_far_behind`. Неизвестный
идентификатор даёт ту же ошибку с `reason: unknown_event`. Молчаливый старт «с текущего
момента» был бы хуже отказа: клиент считал бы себя синхронизированным, не будучи им.

Догоняют историю обычным запросом — тем же представлением события, страницами:

```bash
curl -H "Authorization: Bearer $TOKEN" \
     'http://localhost:8000/api/v1/events?queue=TRK&limit=100'
```

Сужение по очереди, проекту и задаче считается по нагрузке события и применяется после
выборки страницы, поэтому страница бывает короче `limit`, а `meta.next_cursor` при этом
верен: листать надо до `has_more: false`, а не до первой неполной страницы.

### Ограничения

Один процесс API держит не больше `TRACKER_STREAM_MAX_CONNECTIONS` открытых потоков;
сверх того клиент получает `429 stream_connection_limit` и повторяет через паузу.
Соединение с базой на время ожидания не удерживается — сессия открывается только на
время выборки.

Поток — **единственное место API без оболочки `{"data": ...}`**: её нет в самом формате
SSE. Форма полезной нагрузки кадра при этом описана в OpenAPI (`StreamEventRead`), а
ошибки приходят обычным JSON-конвертом.


## MCP-сервер для агентов

Второй интерфейс трекера. Агент (Claude Code и подобные) ходит не в REST, а в MCP: те же
сценарии, но инструментами, описания которых читает модель.

```bash
docker compose up -d mcp          # поднимается вместе с контуром
curl http://localhost:8100/health
```

```json
{"status": "ok", "version": "0.1.0", "database": "ok"}
```

Адрес — `http://localhost:8100/mcp`, транспорт — streamable HTTP, авторизация — тем же
токеном актора, что и REST: `Authorization: Bearer trk_...`. Второй схемы представления
нет намеренно — акторы и токены общие на оба интерфейса.

### Подключение к Claude Code

Сервер работает в контейнере, наружу опубликован порт `8100` (`TRACKER_MCP_PORT`).
Токен агенту выпускают через REST — MCP этого не умеет и не будет уметь: выдача доступов
остаётся за человеком.

```bash
# завести агента и выпустить ему токен (секрет виден только в этом ответе)
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"type": "agent", "key": "claude", "display_name": "Claude"}' \
     http://localhost:8000/api/v1/actors
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"name": "claude-code"}' \
     http://localhost:8000/api/v1/actors/claude/tokens

# подключить сервер (scope local — конфигурация только этого проекта, без репозитория)
claude mcp add --scope local --transport http tracker http://localhost:8100/mcp \
      --header "Authorization: Bearer trk_..."

claude mcp list    # tracker: http://localhost:8100/mcp (HTTP) - ✔ Connected
```

Если Claude Code работает не на той машине, где поднят контур, вместо `localhost` идёт
адрес хоста, а порт `8100` должен быть до него доступен. Токен кладите в конфигурацию
клиента, а не в репозиторий: `--scope local` пишет его в личный файл настроек.

### Что умеет агент

| Группа | Инструменты |
|---|---|
| Поиск и чтение | `search_issues`, `get_issue` |
| Работа с задачей | `create_issue`, `update_issue`, `assign_issue`, `list_transitions`, `transition_issue` |
| Обсуждение | `list_comments`, `add_comment`, чеклист (`get_checklist`, `add_checklist_item`, `check_checklist_item`, `move_checklist_item`, ...) |
| Связи | `list_links`, `link_issues`, `unlink_issues`, `get_issue_tree` |
| Очереди | `list_queues`, `get_queue_config` |
| Проекты | `list_projects`, `get_project`, `add_issues_to_project`, `remove_issue_from_project`, портфели |
| Доски | `list_boards`, `get_board`, `list_column_issues`, `move_card_to_column`, `rank_card` |
| Автоматика | `list_automation_rules`, `configure_automation_rule`, `run_macro` |
| Инбокс | `list_notifications`, `mark_notifications_read`, `wait_for_notifications` |
| Настройка процесса | `create_queue`, `update_queue`, `set_queue_issue_types`, `create_status`, `create_issue_type`, `create_resolution`, `create_field`, `update_field`, `create_workflow`, `replace_workflow`, `update_workflow_transition`, `get_workflow` |

Плюс ресурсы: `tracker://queues`, `tracker://statuses`, `tracker://me` и
`tracker://inbox/{actor}`.

**Отдельного инструмента «задачи проекта» нет, и это решение.** Список задач проекта —
это `search_issues` со строкой `project: alpha`, задачи очереди — `queue: TRK`, свои
задачи — `assignee: me()`. Второй способ отбирать задачи разошёлся бы с поиском на
первом же краевом случае.

### Экономия контекста

Каждое поле ответа съедает контекст агента, поэтому умолчания скупые:

- поиск и колонки досок отдают восемь полей на задачу; `fields: ["*"]` — задачу целиком,
  `fields: ["summary", "TRK.severity"]` — только названное;
- `get_issue` отвечает кратко, `detail: "full"` добавляет описание и значения полей,
  `detail: "history"` — журнал изменений и обсуждение;
- длинные тексты обрезаются до `TRACKER_MCP_TEXT_LIMIT` символов, и обрезка **видна**:
  рядом приезжают `description_truncated` и полная длина.

Ошибки инструментов устроены как в REST: стабильный код, английская фраза и
подробности. Испорченный запрос отвечает позицией символа и причиной, незаполненное поле
— своей ссылкой и допустимыми значениями. Это не украшение: агент исправляет вызов по
тексту, а по «invalid query» уходит в перебор.

### Уведомления: три канала, один инбокс

1. **Инбокс** — основной канал: `list_notifications`, `mark_notifications_read` и
   `wait_for_notifications`, который блокируется до появления новых записей (потолок
   ожидания — `TRACKER_NOTIFICATION_WAIT_MAX_TIMEOUT`, пустой ответ по таймауту приходит
   с `timed_out: true`, а не ошибкой).
2. **MCP-нотификации** — сигнал «в инбоксе что-то появилось» по адресу
   `tracker://inbox/{actor}`. Содержимого в нём нет: агент читает ленту теми же
   инструментами, и отметка о прочтении одна на оба канала.
3. **Вебхуки** — наружу, для систем за пределами трекера (раздел «Вебхуки»).

**MCP-нотификации доходят не до всякого клиента.** Они идут подписками
(`subscriptions/listen`) и требуют протокола `2026-07-28`; клиент, договорившийся на
`2025-11-25` — а Claude Code сейчас делает именно так, — их не увидит. Для него
работающий способ узнать о чужом изменении один: `wait_for_notifications`. Поэтому инбокс
и есть обязательный канал, а нотификации — дополнение поверх.

### Настройка процесса и предварительная проверка

Агент умеет не только работать внутри готового процесса, но и собрать его: завести
очередь, свои статусы, типы и резолюции, поля и воркфлоу. Граф процесса создаётся **одним
вызовом** (`create_workflow`, `replace_workflow`) и проверяется целиком: достижимость
статусов, путь в `done`, резолюция на закрывающем переходе, наличие выхода у задач,
которые уже стоят в этих статусах.

У опасных инструментов есть предварительная проверка: `dry_run: true` выполняет операцию
по-настоящему, отдаёт отчёт (`impact`: сколько задач останется без исходящих переходов и
в каких статусах) и откатывает транзакцию. Второй, «облегчённой» проверки в проекте нет —
она разошлась бы с настоящей ровно там, где её и звали.

Порядок сборки процесса со своими статусами не произволен: стартовый статус очереди
обязан входить в граф каждого назначенного типа задачи. Поэтому сначала свои статусы
въезжают в граф **вместе** со старым стартовым, потом `update_queue` переводит умолчание
очереди на свой статус, и только после этого старый статус из графа убирается.


### Миграции

Миграции применяются отдельной командой, а не при старте приложения: несколько реплик,
одновременно накатывающих схему, — это гонка и испорченная база. После правки моделей:

```bash
docker compose run --rm migrate alembic revision --autogenerate -m "что изменилось"
docker compose run --rm migrate
```

Автогенерация видит только те модели, которые импортированы в `app/db/models/__init__.py`.

**Ревизия `remove sprints` (`4a7c9e1b53d8`) — необратимая потеря данных.** Она удаляет
таблицу `sprints` и колонку `issues.sprint_id`: сущность «спринт» из продукта убрана
намеренно (`docs/CONCEPT.md`, раздел «Доски»). На свежей установке накатывать её нечего — там
спринтов и не было. На установке, где спринты уже заводили, состав спринтов и их названия
пропадут безвозвратно: `downgrade` вернёт схему, но не данные — восстанавливать их неоткуда.
Если эти данные ещё нужны, снимите дамп **до** наката:

```bash
docker compose exec db pg_dump -U tracker -t sprints -t issues tracker > sprints-backup.sql
```

### Тесты

`docker compose run --rm test` поднимает БД, создаёт базу `tracker_test`, накатывает на неё
миграции и прогоняет весь набор. Каждый тест идёт внутри транзакции, которая откатывается
после него, поэтому порядок тестов не влияет на результат.

## Конфигурация

Приложение настраивается только переменными окружения — один образ работает в любом

```
  domain/       доменные модели и правила
  services/     сценарии: транзакции, события
  db/           модели SQLAlchemy, репозитории, сессии, миграции
  automation/   движок автоматики и правила
  core/         конфиг, логирование, базовые исключения
  cli.py        командная строка: первичная настройка установки
  worker.py     воркер шины событий: разбирает outbox и раздаёт события подписчикам
  scheduler.py  планировщик автодействий: будит правила по расписанию, в одном экземпляре
  webhooks.py   доставщик вебхуков: разбирает очередь доставок и ходит по сети наружу
docker/         образы для разработки и продакшена
docs/           концепция, соглашения, задания
tests/          тесты и общие фикстуры
```

В каждой папке лежит `AGENTS.md` с картой её содержимого.
