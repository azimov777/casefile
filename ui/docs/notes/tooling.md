# Инструменты и окружение

## pnpm 11 разрешает сборочные скрипты картой `allowBuilds`

**Что:** в pnpm 11 список пакетов, которым можно запускать `postinstall`, задаётся
не полем `onlyBuiltDependencies` в `package.json`, а картой `allowBuilds` в
`pnpm-workspace.yaml`.
**Почему важно:** без разрешения `esbuild` не ставит свой бинарник, и Vite не соберётся;
`pnpm install` при этом завершается предупреждением, а не ошибкой, — легко не заметить.
**Как правильно:** `allowBuilds: { esbuild: true, msw: true }`. Старое поле молча
игнорируется, а `pnpm rebuild` дописывает в файл шаблон-подсказку.
**Где:** `pnpm-workspace.yaml`.

## Node на машине новее, чем в `.nvmrc`

**Что:** `.nvmrc` называет Node 22 LTS (как требуют соглашения), `engines` разрешает
`>=22`, а разработка и Docker-сборка проверены на 24 и 22 соответственно.
**Почему важно:** установка Node 22 ради точного совпадения версий ничего не даёт —
проект не использует ничего, что различалось бы между 22 и 24.
**Как правильно:** ставить 22, если менеджера версий нет; на 24 всё работает.
**Где:** `.nvmrc`, `package.json` (`engines`, `packageManager`).

## Проверка здоровья nginx: только 127.0.0.1

**Что:** `wget http://localhost/` внутри контейнера nginx получает отказ соединения.
**Почему важно:** контейнер бесконечно висит `unhealthy`, `docker compose up --wait`
падает, и причина выглядит как поломка сборки, хотя nginx работает.
**Как правильно:** проверять `http://127.0.0.1/`. Причина: наша конфигурация слушает
только IPv4, а `localhost` в контейнере разрешается сначала в `::1`; штатный скрипт
образа `10-listen-on-ipv6-by-default.sh` дописывает `listen [::]:80` только в
нетронутый конфиг, а наш он не трогает.
**Где:** `docker-compose.yml`, проверка здоровья сервиса `ui`.

## Ключ контура берётся из файла, а не из вывода команды

**Что:** установка выдаёт ключ своему интерфейсу командой `local-token`, и результат
у неё — **файл**, а не строка в выводе: секрет не печатается никогда. Разбирать вывод
не надо вовсе.
**Почему важно:** прежде оснастка ловила секрет регуляркой из вывода `issue-token`,
а до того — из вывода `init`, который молчит на уже настроенной установке. Оба способа
ломались молча и давали пустой токен с непонятной ошибкой. Заодно вывод команды —
последнее место, куда секрету стоит попадать: его читают, показывают и сохраняют
в журналы прогонов.
**Как правильно:** `docker compose run --rm local-token`, потом прочитать файл. Порядок
обязателен: `init` считает установку настроенной по наличию **любого** токена, поэтому
ключ интерфейса, выпущенный первым, оставит владельца без токена набора `main`.
**Где:** `e2e/global-setup.ts`; `e2e/contour.ts`, `TOKEN_FILE`.

## Ключ контура сквозных тестов лежит отдельно от ключа дев-контура

**Что:** сервис `local-token` контура сквозных тестов кладёт ключ в `.secrets/ui-token`
**этого** каталога, хотя дев-контур бэкенда кладёт его в `../.secrets/ui-token`.
**Почему важно:** `local-token` отзывает прежний токен с тем же именем тем же действием.
Прогон тестов, перевыпустивший ключ в общем файле, высадил бы дев-сервер интерфейса,
берущий ключ оттуда: открытая вкладка получила бы отказ, а следующий подъём — чужой ключ
от чужой базы.
**Как правильно:** держать точку монтирования в своём репозитории и `--output`
относительно рабочего каталога образа (`/app`), чтобы команда печатала путь, который
на хосте существует.
**Где:** `docker-compose.yml`, сервис `local-token`; `e2e/contour.ts`, `SECRETS_DIR`.

## Bind-mount на несуществующий путь Docker заводит сам — каталогом

**Что:** если смонтировать файл, которого на хосте нет, Docker не откажет и не пропустит
монтирование: он создаст по этому пути **каталог** (на Linux — от root).
**Почему важно:** ключ установки — законно отсутствующая вещь: установка, где людей
несколько, его не выдаёт. Монтируй контур этот файл, подъём без ключа оставлял бы на
хосте каталог с именем `ui-token` ровно там, куда бэкенд обязан потом записать файл, —
и путь «поднял без ключа» ломал бы путь «выдал ключ» молча и необратимо.
**Как правильно:** не монтировать файл с хоста. Контур сквозных тестов передаёт ключ
переменной `TRACKER_UI_TOKEN`: пустая переменная — законное значение, и следов на хосте
она не оставляет, а читать файл на хосте — дело того, кто зовёт compose
(`e2e/global-setup.ts`). Установка монтирует не файл, а именованный том с ключом
(`TRACKER_UI_TOKEN_FILE`): том существует всегда, и каталога на хосте Docker не заводит.
**Где:** `docker/config-json.sh`; `../docker-compose.prod.yml`, `TRACKER_UI_TOKEN_FILE`.

## Свой шаг старта образа nginx обязан быть исполняемым

**Что:** штатный вход образа nginx выполняет `/docker-entrypoint.d/*.sh` перед запуском
сервера, но **только те, у кого стоит бит исполнения**: остальные он пропускает строкой
`Ignoring /docker-entrypoint.d/…, not executable`.
**Почему важно:** контейнер при этом здоров, страница открывается, и единственный след
поломки — строка в журнале, которую никто не читает. Выглядит это как «приложение
не берёт ключ», хотя ключ до него просто не доехал.
**Как правильно:** `RUN chmod +x` в `Dockerfile` после `COPY` (право на файле в git
до образа не доезжает при части способов сборки). Проверять — по журналу контейнера:
`docker compose logs ui` показывает `Launching /docker-entrypoint.d/40-tracker-config-json.sh`.
Сама развилка видна в образе: `docker run --rm --entrypoint sh nginx:1.27-alpine -c
"grep -n -A2 'not executable' /docker-entrypoint.sh"`.
**Где:** `docker/Dockerfile`; `docker/config-json.sh`.

## nginx не стартует, если адрес бэкенда не резолвится

**Что:** `proxy_pass` с именем хоста разрешается один раз, при старте. Неверный
`TRACKER_API_URL` в прод-контуре означает не «интерфейс без API», а «контейнер
в бесконечном перезапуске»: `host not found in upstream` — фатальная ошибка конфигурации.
**Почему важно:** выглядит как поломка образа, хотя образ в порядке. Проверяется одной
командой: `docker logs <контейнер>` покажет `[emerg] host not found in upstream`.
**Как правильно:** поднимать интерфейс в одной сети с бэкендом и называть сервис так,
как он зовётся в ней: в установке это `TRACKER_API_URL: http://api:8000`. Заодно это
доказывает, что адрес действительно берётся из переменной, а не зашит в образ.
**Где:** `../docker-compose.prod.yml`, `TRACKER_API_URL`; `docker/nginx.conf.template`.

## Один образ, два контура: адрес бэкенда подставляется при старте

**Что:** `docker/nginx.conf.template` разворачивает штатный скрипт образа nginx,
подставляя `TRACKER_API_URL`. Фильтр `NGINX_ENVSUBST_FILTER=TRACKER_` не даёт `envsubst`
съесть переменные самого nginx (`$uri`, `$host`).
**Почему важно:** без фильтра конфигурация разваливается на старте, а причина выглядит
как опечатка в шаблоне: `try_files  /index.html` вместо `try_files $uri $uri/ /index.html`.
**Как правильно:** проверять развёрнутую конфигурацию, не поднимая контур целиком:
`docker run --rm --entrypoint sh tracker-ui:latest -c '/docker-entrypoint.sh nginx -t; grep proxy_pass /etc/nginx/conf.d/default.conf'`.
**Где:** `docker/Dockerfile`, `docker/nginx.conf.template`.

## У двух контуров интерфейса разные умолчания портов, и это решение

**Что:** установка (`../docker-compose.prod.yml`) по умолчанию занимает 8080,
контур сквозных тестов (`docker-compose.yml`) — 8081.
**Почему важно:** пока умолчание было общим, `pnpm e2e` падал в `globalSetup` строкой
`Bind for 0.0.0.0:8080 failed: port is already allocated` — до единого сценария — у
всякого, кто держит интерфейс поднятым. Сообщение говорит про порт, но приходит из
`contour.ts` со стеком `execFileSync`, и его читали как поломку обвязки тестов.
Лечилось это приставкой `UI_PORT=8081 pnpm e2e`, которую надо было помнить, — то есть
знанием, жившим в голове и в заметке, а не в коде.
**Как правильно:** ничего не помнить и не гасить: `pnpm e2e` поднимается на своём порту
сам. Умолчания в `docker-compose.yml` и `playwright.config.ts` обязаны двигаться вместе —
адрес, разошедшийся с публикацией, даст прогон в пустоту. Переменная `UI_PORT`
осталась и по-прежнему перебивает оба, но нужна теперь только третьему контуру.
**Где:** `playwright.config.ts`, `BASE_URL`; `docker-compose.yml`, `${UI_PORT:-8081}`;
`../docker-compose.prod.yml`, `${CASEFILE_PORT:-8080}`.

## Вьюпорт для замеров вёрстки задаёт Playwright, а не окно браузера

**Что:** замеры сценариев вида «сколько строк видно на 1440×900» через окно Chrome с
расширением снять не удалось: `resize_window` отвечает «resized to 1440x900», но
`innerWidth`/`innerHeight` остаются прежними (замерено: окно просили 1440×900, потом
1000×700 — вьюпорт оба раза 900×713).
**Почему важно:** число «видно 7 задач» без известного вьюпорта ничего не значит, а
расхождение молчаливое: инструмент отвечает успехом, и замер выглядит достоверным.
**Как правильно:** для любых замеров геометрии заводить контекст Playwright с явным
`viewport` и `colorScheme` — он же даёт обе темы и оба размера одним прогоном. Браузер
с расширением остаётся для того, ради чего он есть: посмотреть глазами.
**Где:** `e2e/*.spec.ts` — `test.use({ viewport })`; обход UI-10 мерил тем же способом
одноразовым скриптом.

## `shadcn add` кладёт компонент в папку `@/` и дописывает в зависимости чужое

**Что:** `pnpm dlx shadcn@latest add pagination` при наших псевдонимах
(`components` → `@/shared/ui`) создал файлы буквально в папке `@/shared/ui`, а не
в `src/shared/ui`, заодно добавив в `package.json` пакеты `cn` и `radix-ui`, которых
проекту не нужно: свой `cn` у нас лежит в `src/shared/lib`, а от Radix взяты отдельные
пакеты, а не зонтичный.
**Почему важно:** установка выглядит успешной («Created 2 files»), файлы лежат рядом
с настоящими, и `pnpm install` тихо тянет лишнее. Компонент при этом импортирует
`cn` из несуществующего у нас модуля и не собирается.
**Как правильно:** после `add` смотреть `git status`: если появилась папка `@`, снести
её вместе с правкой `package.json` и `pnpm-lock.yaml` (`git checkout package.json
pnpm-lock.yaml`), а исходник компонента взять из неё и переписать под наши токены,
подписи и `cn` — что соглашения и требуют от добавленного компонента.
**Где:** `components.json`, `src/shared/ui/pagination.tsx`.

## Сторож подписей: две настройки `no-literal-string`, без которых он бесполезен

**Что:** `i18next/no-literal-string` из коробки (`mode: 'jsx-only'`) даёт на нашем коде
80 ошибок, и ни одна из них не про подпись: `tone="danger"`, `to="/tasks"`,
`aria-hidden="true"`, строки внутри `onClick`. Лечится это двумя настройками, и обе
неочевидны.
**Почему важно:** правило в таком виде выключают на второй день — а выключенный сторож
никто не включает обратно. Подгонять же под него код запрещено: `tone` и `to` подписями
не являются, и переписывать их ради зелёного линта значит ломать работающее.
**Как правильно:** во-первых, `'jsx-attributes': { include: [...] }` превращает список
атрибутов из чёрного в белый — проверяются только названные, а остальные пропускаются
целиком вместе со своими выражениями (`shouldSkip` в `lib/helper/shouldSkip.js`: не
совпало с непустым `include` — пропускаем). Во-вторых, `callees` **перебивает**
умолчания правила, а не дополняет их: options собираются как `{...defaults, ...options}`,
поэтому свои имена дописываются к переписанному списку умолчаний. Забыть про это стоит
177 ошибок вместо нуля — перестаёт пропускаться сам `t`.
**Где:** `eslint.config.js`, правило `i18next/no-literal-string`.

## Исключение сторожа записывается местом в дереве, а не списком файлов

**Что:** `no-restricted-syntax` принимает отбор esquery, а тот умеет и регулярное
выражение по значению узла, и отрицание с предком: `Literal[value=/[А-Яа-яЁё]/]:not(NewExpression[callee.name=/Error$/] *)`
запрещает русскую строку везде, кроме аргументов `new *Error(...)`.
**Почему важно:** русская строка в коде приложения — это подпись мимо словаря, но
`new Error('Поток журнала закрыт сервером')` и `console.warn` — фраза для журнала
разработчика, которую человеку не показывают. Освободить их файловым списком значит
освободить весь файл целиком и дописывать список при каждом новом отказе.
**Как правильно:** отбор по месту; комментарии узлами дерева не являются и под него
не попадают вовсе, поэтому русский спокойно остаётся языком разработки.
**Где:** `eslint.config.js`, правило `no-restricted-syntax`.

## `MERGE_MSG` переживает выход процесса и отдельный повторный вызов — если в него написать до выхода

**Что:** `git merge --no-commit` с конфликтом сам кладёт своё предложение сообщения
в `$(git rev-parse --git-dir)/MERGE_MSG` и оставляет файл как есть до `git commit` или
`git merge --abort`. Файл — обычный файл в `.git`, а не состояние процесса: он
переживает выход скрипта, разбор конфликта руками и совершенно отдельный запуск
`scripts/merge-task-branch.sh --continue`, у которого от прежнего вызова нет ничего,
кроме этого файла и `MERGE_HEAD`.
**Почему важно:** сообщение, переданное через `-m` при первом вызове, доступно только
в его собственном `$MESSAGE` — при `--continue` это уже новый процесс с пустым
`$MESSAGE`, и если не записать `-m` в `MERGE_MSG` до выхода на конфликте, оно теряется
безвозвратно, а git молча подставляет своё «Merge branch '…'» (UI-96).
**Как правильно:** писать `$MESSAGE` в `MERGE_MSG` (когда он не пуст) сразу в точке,
где скрипт обнаруживает конфликт и вот-вот выйдет — не только перед итоговым
`git commit`. Второго места для сообщения заводить не нужно: `MERGE_MSG` уже переживает
ровно то, что нужно пережить.
**Где:** `scripts/merge-task-branch.sh`, функция `stage_message` и её вызов в ветке
конфликта `git merge --no-ff --no-commit`.

## `git rev-parse --show-toplevel` — корень репозитория, а не каталог интерфейса (UI-108)

**Что:** до монорепозитория (TRK-64) `tracker-ui` был отдельным репозиторием, и его
корень (`git rev-parse --show-toplevel`) совпадал с каталогом интерфейса — там же лежал
`package.json`. После переезда `package.json` — в `ui/`, а корень репозитория — каталог
бэкенда. `scripts/merge-task-branch.sh` брал корень и оставался там: `pnpm check` искал
`package.json` не в том каталоге и падал `ERR_PNPM_NO_IMPORTER_MANIFEST_FOUND`, а
`SCRIPT_PATH="scripts/merge-task-branch.sh"` в паре с этим неверным `cd` считал ревизию
непроверенных слияний от скрипта бэкенда, а не интерфейса.
**Почему важно:** правка искала каталог интерфейса не рядом с файлом самого скрипта
(`$0`) — координатор может вызвать его по абсолютному пути из соседнего дерева, и тогда
`$0` укажет не туда. Нужен каталог интерфейса РЕПОЗИТОРИЯ ТЕКУЩЕГО КАТАЛОГА: `git
rev-parse --show-toplevel` уже берёт его от `cwd`, а не от `$0` — саму эту часть менять
не пришлось, только то, куда скрипт из неё переходит.
**Как правильно:** после `TOPLEVEL="$(git rev-parse --show-toplevel)"` проверить `[ -d
"$TOPLEVEL/ui" ]` и перейти туда; иначе (старая раскладка отдельного репозитория, как в
`testing/merge-script.test.ts`) остаться в `$TOPLEVEL`. Относительный `SCRIPT_PATH` при
этом сам начинает резолвиться от `ui/`, никакой отдельной правки не потребовалось.
**Где:** `scripts/merge-task-branch.sh`, переход в каталог перед разбором аргументов.

## Порт на петле не защищает от страницы в браузере

**Что:** `docker-compose.yml` и `../docker-compose.prod.yml` публикуют nginx только на
`127.0.0.1` — это ограничивает, откуда можно открыть TCP-соединение по сети, а не то,
какой заголовок `Host` в нём придёт. Вкладка чужого домена, перепривязавшего свою
DNS-запись на этот же адрес (DNS rebinding), соединяется с портом так же свободно, как
«своя» страница: браузер сверяет источник с адресной строкой, а не с тем, куда фактически
пришёл сокет, и посылает ровно тот `Host`, на который открыт адрес.
**Почему важно:** решение «порт только на петле — значит безопасно» для веб-сервера,
отдающего секрет статикой (здесь — `/config.json` с ключом установки, UI-107), ложное.
Без проверки самого заголовка внутри сервера чужая вкладка того же браузера читает секрет
как свой источник — сеть тут ни при чём, атакующему не нужно быть даже рядом с этим Wi-Fi.
**Как правильно:** заголовок обязан проверять сам сервер, а не публикация портов. У nginx
единственный `server`-блок сам по себе Host не фильтрует: `server_name` разбирает Host
только когда есть из чего выбирать, то есть при нескольких блоках на одном `listen`, а с
одним блоком нужна явная проверка по `$host`. У дев-сервера Vite такая проверка уже
встроена (`server.allowedHosts`), но действует только на промежуточные обработчики,
поставленные ПОСЛЕ неё в цепочке: прямой вызов `server.middlewares.use` в теле
`configureServer` регистрируется раньше и остаётся без защиты — чинится возвратом функции
из хука, которую Vite вызывает уже после своих внутренних обработчиков.
**Где:** `docker/nginx.conf.template`; `vite.config.ts`, `installConfig`;
`e2e/host-guard.spec.ts`.
