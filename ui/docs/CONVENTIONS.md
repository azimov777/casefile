# Сквозные соглашения проекта

Обязательны к прочтению перед выполнением любой задачи из `tasks/`. Задача описывает
*что* делать, соглашения — *как*.

## Стек

- Node 22 LTS, pnpm. Версии закреплены в `package.json` (`engines`) и `.nvmrc`.
- TypeScript в строгом режиме, React 19, Vite.
- Маршруты: React Router. Серверное состояние: TanStack Query. Клиент API: типы
  из `openapi-typescript`, вызовы через `openapi-fetch`.
- Живой поток: `@microsoft/fetch-event-source` (браузерный `EventSource` не умеет
  заголовок авторизации).
- Markdown: `react-markdown` с `remark-gfm`; HTML из markdown не разрешается.
- Стили: CSS Modules и переменные темы в `shared/styles`. Библиотек компонентов нет:
  интерфейс маленький, а чужая библиотека тянет свою тему и свой словарь.
- Тесты: Vitest и Testing Library для модулей и страниц, MSW для подмены API,
  Playwright для сквозных сценариев против настоящего бэкенда.
- Качество: ESLint, Prettier, проверка типов `tsc --noEmit`, границы слоёв
  через `steiger` (Feature-Sliced Design).

Новые зависимости добавляются только если без них задача не решается разумным объёмом
кода; каждая называется в отчёте о задаче.

## Запуск

Разработка идёт локально: `pnpm dev` поднимает Vite с прокси `/api` на бэкенд
(`VITE_API_URL`, по умолчанию `http://localhost:8000`). Бэкенд поднимается по его README
из соседнего репозитория `../tracker`, с демо-данными.

Сборка и сквозные тесты идут в Docker: `docker/Dockerfile` собирает статику и отдаёт её
через nginx, `docker-compose.yml` поднимает интерфейс вместе с бэкендом из `../tracker`
для Playwright. Задача, после которой что-то работает только «руками на моей машине»,
не считается выполненной.

## Структура кода

Feature-Sliced Design, четыре слоя, без `widgets`:

```
src/
  app/        — точка входа, маршруты, провайдеры, тема, глобальные стили
  pages/      — по странице на экран из CONCEPT.md: login, tasks, task, case, questions
  features/   — действия и интерактив: фильтры списка, форма ответа, живой поток
  entities/   — задача, запись дела, участник, очередь: типы из контракта, запросы,
                представление одной сущности (строка, карточка, запись)
  shared/     — клиент API и сгенерированные типы, словарь ошибок, тема, утилиты, ui-кирпичи
```

Правила импортов: слой импортирует только слои ниже; срезы одного слоя друг друга
не импортируют; наружу срез отдаёт только `index.ts`. Нарушения ловит `steiger`
в `pnpm check`.

## Клиент API

- Типы генерируются из `../tracker/openapi.json` командой `pnpm gen:api`
  в `src/shared/api/openapi.ts`; сгенерированный файл коммитится, чтобы сборка не зависела
  от соседнего репозитория. Тест сверяет его с источником и падает при расхождении.
- Ручных типов ответов нет: всё берётся из сгенерированных. Если типа не хватает,
  чинится контракт бэкенда, а не дописывается тип на клиенте.
- Оболочка ответа (`data`, `meta`, `error`) разбирается в одном месте (`shared/api`);
  страницы получают уже распакованные данные или типизированную ошибку с `code`,
  `message`, `details`.
- Токен хранится в `localStorage` под одним ключом, добавляется в `Authorization: Bearer`
  одним перехватчиком. Ответ `401` сбрасывает токен и ведёт на вход.
- Тексты ошибок для человека берутся из словаря `shared/errors` по `error.code`;
  неизвестный код показывает `message` бэкенда и попадает в отчёт задачи как пункт
  «дополнить словарь».

## Состояние

- Серверное состояние живёт только в TanStack Query: ключи запросов строятся из
  идентификаторов контракта (`['task', key]`, `['tasks', filters]`), инвалидация по кадрам
  живого потока идёт по этим ключам.
- Фильтры, режим отображения, выбранная очередь и курсор живут в адресе страницы.
- Локальное состояние компонентов — `useState`; глобального хранилища нет, пока не
  появится состояние, которое нужно двум страницам сразу и не выражается адресом.

## Интерфейс

- Подписи на русском; идентификаторы контракта (статусы, типы записей, ключи) как есть,
  моноширинным шрифтом.
- Тема светлая и тёмная по `prefers-color-scheme`; цвета, отступы и шрифты только через
  переменные из `shared/styles/tokens.css`.
- Доступность: семантическая разметка, фокус виден, таблицы с заголовками, формы
  с подписями; Playwright гоняет `axe` на каждой странице.
- Пустые и ошибочные состояния у каждого запроса нарисованы явно; спиннер без текста
  не считается состоянием.
- Даты показываются в местном времени и относительно («3 мин назад») с точным временем
  в подсказке.

## Тесты

- Каждая задача завершается тестами: модульные на разбор данных и словари, страничные
  с MSW на состояния (данные, пусто, ошибка, загрузка), сквозные Playwright на главный
  сценарий задачи против бэкенда с демо-данными.
- `pnpm check` = типы, линт, границы слоёв, модульные тесты. `pnpm e2e` = Playwright
  в Docker. Задача выполнена, когда зелёно и то и другое.
- Подгонять тест под поведение, ослаблять проверку или помечать пропущенным ради
  зелёного запрещено.

## Документация

- Каждая папка описывается `AGENTS.md`: что в ней лежит, одним уровнем. Создал
  или переместил файл — обновил карту.
- Соглашения бэкенда не копируются: контракт описан в `../tracker/docs/FRONTEND.md`
  и `openapi.json`.

## Коммиты

Conventional Commits: `<тип>(<область>): описание в повелительном наклонении`.
Типы: `feat`, `fix`, `docs`, `refactor`, `test`, `build`, `chore`, `style`, `perf`.
Области: `app`, `tasks`, `task`, `case`, `questions`, `live`, `api`, `ui`, `docker`.
Один коммит — одно осмысленное изменение; карты `AGENTS.md` и правки заданий идут тем же
коммитом, что и код. В индекс добавляются только свои файлы поимённо. Пуш и ветки
только по явной просьбе.

## Формат задания

Файл в `tasks/` устроен так же, как задача в трекере: пять разделов.

| Раздел | Что в нём |
|---|---|
| **Цель** | Зачем задача нужна и что изменится для системы. |
| **Контекст** | Что уже есть, на что опираться, какие документы и заметки читать. |
| **Ограничения** | Чего не делать, что не входит, какие решения концепции нельзя менять. |
| **Выход** | Что должно существовать по завершении: код, тесты, документация. |
| **Обзорные проверки** | Нумерованный список проверок, каждую можно провалить: что сделать и что должно получиться. |

Дописывая чужую задачу, добавляй пункты в существующие разделы с пометкой источника
`(выявлено в задаче 03)`; чужие пункты не переписываются. Новая задача получает
следующий свободный номер и строку в `ROADMAP.md` и `tasks/AGENTS.md`.

## Протокол выполнения задачи

Обязателен для любого агента, берущего файл из `tasks/`. Шаги идут по порядку.

1. **Подготовка.** Прочитать `CONCEPT.md`, этот файл, свою задачу целиком, заметки
   в `notes/` по своей области, `../tracker/docs/FRONTEND.md`. Проверить по коду,
   что задачи-зависимости выполнены.
2. **Реализация** в границах слоёв и правил выше.
3. **Проверка.** `pnpm check` и `pnpm e2e` зелёные целиком, не только свои тесты.
   Затем живая проверка руками: поднять бэкенд с демо, открыть интерфейс в браузере,
   пройти сценарий задачи, посмотреть консоль браузера и сеть на ошибки и лишние
   запросы.
4. **Зафиксировать находки** в `notes/` по формату ниже.
5. **Обновить карты** `AGENTS.md` затронутых папок.
6. **Закрыть задание.** Выполнено полностью: удалить файл из `tasks/`, строку из
   `tasks/AGENTS.md`, отметить в `ROADMAP.md`. Частично: оставить невыполненное
   с шапкой «Уже реализовано» в три-пять строк.
7. **Закоммитить** самостоятельно, если всё зелёно и живая проверка прошла; иначе
   оставить в рабочем дереве и объяснить в отчёте.
8. **Погасить всё, что запускал**: dev-сервер, контуры Docker, Playwright.
9. **Проверить готовность к передаче.** Следующий агент не знает ничего из твоего
   контекста: всё знание в файлах, все «надо не забыть» стали пунктами задач.
10. **Отчитаться**: что сделано, что не сделано и почему, какие решения приняты
    самостоятельно, что дописано в чужие задачи, что осталось запущенным, вердикт
    «можно закрывать сессию, следующая задача N» или «закрывать рано, потому что».

## Заметки: находки, грабли, особенности

Папка `notes/`, один файл на область: `api.md`, `live.md`, `ui.md`, `testing.md`,
`tooling.md` и подобные. Заметки только копятся. Формат записи:

```markdown
## Краткое название находки

**Что:** факт одной фразой.
**Почему важно:** что сломается или сколько времени потеряет тот, кто этого не знает.
**Как правильно:** конкретное действие или пример.
**Где:** файл или место в коде, если применимо.
```

Что писать: поведение библиотеки, выясненное опытным путём; неочевидное решение
и причину, по которой очевидное не подошло; ограничение окружения; место, которое
выглядит странно, но так задумано. Что не писать: пересказ документации библиотек,
описание собственного кода, историю попыток, планы.
