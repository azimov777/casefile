# tracker-ui

Интерфейс человека для трекера задач, которые ведут агенты. Человек здесь наблюдает
и отвечает на вопросы; задачи создают и двигают агенты через MCP бэкенда.

Бэкенд — корень этого репозитория (`..`): контракт в его `openapi.json`,
коды ошибок в его `docs/ERRORS.md`; карта контракта для интерфейса — здесь,
`docs/FRONTEND.md`.

Что и зачем строим: `docs/CONCEPT.md`. Как строим: `docs/CONVENTIONS.md`. Задания
приходят задачами трекера, проект `UI`.

Стек: React 19 и Vite, маршруты React Router, серверное состояние TanStack Query,
клиент API из `openapi-typescript` и `openapi-fetch`. Оформление — Tailwind CSS 4
с токенами в `@theme` и компоненты shadcn/ui на Radix; шрифты Fira Sans и Fira Code
с запасной системной гарнитурой. Раскладка кода — Feature-Sliced Design.

## Требования

Node 22 или новее и pnpm — для разработки; Docker и Docker Compose — для сборки
и сквозных тестов. pnpm ставить отдельно не нужно, его версию задаёт `packageManager`:

```bash
corepack enable pnpm
pnpm install
```

## Первый запуск

Установка целиком — база, бэкенд, MCP, интерфейс и ключи — поднимается одной командой
из готовых образов. Ни одного секрета человек при этом не вводит и не копирует:

```bash
docker compose -f ../docker-compose.prod.yml up -d   # из клона; без клона — install.sh
```

Интерфейс открывается на `http://127.0.0.1:8080` сразу, без экрана входа. Ключ выпускает
сама установка (команда бэкенда `local-token`) и кладёт в именованный том, который
интерфейс монтирует только на чтение, а тот отдаёт ключ браузеру конфигурацией
`GET /config.json` на своём источнике. Повторный подъём безопасен: действующий ключ
не перевыпускается, открытая вкладка продолжает работать. Устройство установки,
автообновление и её настройки — в `../docker-compose.prod.yml`.

Ключ не покидает машину. Порт публикуется только на петлю (`127.0.0.1`) — с ключом
от установки этот адрес раздаёт полный доступ ко всему трекеру всякому, кто его открыл.
Кому нужен интерфейс для нескольких людей, тому ниже отдельный раздел.

## Разработка

Интерфейс ходит на свой источник и полагается на прокси `/api`, поэтому нужен
поднятый бэкенд. Проще всего — рабочий контур бэкенда из корня репозитория
(`../docs/DEVELOPMENT.md`, «Быстрый старт»): миграции, `init` печатает первый токен,
`demo` наполняет проект `DEMO`.

```bash
pnpm dev                                   # прокси /api на http://localhost:8000
VITE_API_URL=http://localhost:8010 pnpm dev  # или на любой другой бэкенд
```

Откройте адрес, который напечатал Vite, введите токен участника — и попадёте
на `/tasks`. Токен хранится только в `localStorage` и уходит на сервер заголовком
`Authorization`; в адресе страницы его нет никогда.

### Ключ от установки

Источников ключа два. Второй — сама установка: она отдаёт его конфигурацией
`GET /config.json` на своём источнике, и человек ключа не видит вовсе. Так работает
локальный трекер на одного, где человек сам себе владелец; экран входа остаётся
для установки, где людей несколько и ключ у каждого свой.

Дев-сервер отдаёт эту конфигурацию по переменной `TRACKER_UI_TOKEN`. Ключ выпускает
бэкенд, и берётся он из файла, а не из вывода команды:

```bash
(cd .. && docker compose run --rm local-token)
TRACKER_UI_TOKEN=$(cat ../.secrets/ui-token) pnpm dev
```

Без переменной `/config.json` отвечает `404` — это не поломка, а «ключа от установки
нет»: открывается экран входа, как прежде. Переменная нарочно без приставки `VITE_`:
такое значение не попадает в собранный код ни при какой ошибке. В `.env` её класть
можно — этот файл в репозиторий не коммитится.

## Проверки

```bash
pnpm check   # формат, линт, типы, границы слоёв (steiger), модульные и страничные тесты
pnpm e2e     # Playwright против настоящего бэкенда в Docker
pnpm gen:api # перегенерировать клиент из ../openapi.json
```

Новый кирпич интерфейса из shadcn/ui добавляется его же командой — псевдонимы
в `components.json` уже настроены на слои проекта, и файл попадает в `src/shared/ui`:

```bash
pnpm dlx shadcn@latest add dialog   # положит src/shared/ui/dialog.tsx
```

`pnpm check` сверяет закоммиченный `src/shared/api/openapi.ts` с контрактом бэкенда
(`../openapi.json`) и словарь ошибок с его `docs/ERRORS.md`: разошлись — прогон падает
и говорит, что делать. Он же стережёт указатели «Где:» в `docs/notes/`: названный файл
обязан существовать, а названный символ — находиться в нём (`testing/notes.test.ts`).

`pnpm e2e` поднимает свой контур целиком (база, бэкенд, собранный образ интерфейса),
применяет миграции, наполняет демо-данными, просит у установки ключ интерфейса — тем же
путём, каким его получает человек, — и гасит всё за собой.
Первый прогон собирает образы и потому долгий. При падении в отчёте остаются снимок
экрана, видео и трасса: `pnpm exec playwright show-report`.

Сценарии, которые пишут в демо-установку (ответ на вопрос, живой поток, листание),
собраны в отдельный проект `запись`: он идёт после читающих и по одному сценарию за раз,
иначе читающие видели бы уже изменённое демо.

### Слияние ветки задачи

Ветка задачи сливается в `main` не голым `git merge`, а скриптом:

```bash
scripts/merge-task-branch.sh task/UI-93 -m "merge(область): что изменилось (UI-93)"
```

Он сливает без коммита, прогоняет на результате слияния сперва `pnpm check`, затем (если
он зелёный) `pnpm e2e`, и коммитит только на двойном зелёном, оставив в сообщении строку
`Merge-verified:` с исходом обоих наборов. Красный любой — `git merge --abort`: ветка не
слита, `main` прежний. Конфликты скрипт оставляет человеку — разобрать, `git add`, довести
тем же скриптом с `--continue`.

Зачем это отдельный шаг и почему проверок два разной цены — `docs/CONVENTIONS.md`,
раздел «Слияние ветки задачи в main».

## Сборка и контур

Запуск с нуля, на машине, где есть только Docker:

```bash
mkdir -p .secrets                      # каталог под ключ заводит человек, а не Docker
docker compose up -d --wait api        # база и бэкенд из корня репозитория
docker compose run --rm migrate        # миграции
docker compose run --rm init           # владелец установки и его первый токен
docker compose run --rm local-token    # ключ интерфейса — в .secrets/ui-token
docker compose run --rm demo           # демо-данные: проект DEMO, дело, открытый вопрос
TRACKER_UI_TOKEN=$(cat .secrets/ui-token) docker compose up -d --wait --build ui
open http://127.0.0.1:8081             # задачи сразу: входить не нужно
docker compose down -v                 # погасить вместе с данными
```

Порядок тот же, что у первого запуска бэкенда: `init` считает установку настроенной по
наличию **любого** токена и после ключа интерфейса промолчал бы. Права владельца это не
отнимает — ключ интерфейса сам набора `main`, — но своего токена `init` не выпустил бы.

Наружу торчит только интерфейс, и только на петлю: `/api` проксирует nginx внутрь сети
compose. Порты рабочего контура бэкенда (8000, 8100, 5432) этот контур не занимает — их
можно держать поднятыми одновременно.

Ключ этот контур держит у себя (`.secrets/ui-token` в этом репозитории), а не в
`../.secrets/ui-token`, где лежит ключ дев-контура бэкенда: общий файл прогон тестов
перезаписывал бы ключом от своей базы, и дев-сервер интерфейса, берущий ключ оттуда,
получал бы отказ.

Порт у него 8081, а не 8080, и это не произвол: 8080 занимает установка
(`../docker-compose.prod.yml`). Умолчания разведены затем, чтобы `pnpm e2e` работал без
приставки из переменных у всякого, кто держит установку поднятой.

Образ интерфейса один на оба контура: адрес бэкенда (`TRACKER_API_URL`) и ключ
подставляются при старте, а не при сборке. Секрета в слоях образа нет — `config.json`
рождается при старте контейнера (`docker/config-json.sh`), — и это проверяется одной
командой:

```bash
docker run --rm --entrypoint grep tracker-ui:latest -r trk_ /usr/share/nginx/html
```

### Установка в сети: вход по учётным записям

Выдача ключа без входа и открытый в сеть порт вместе недопустимы: с конфигурацией этот
адрес раздаёт рабочий ключ администратора всякому, кто его открыл, — то есть полный доступ
ко всему трекеру. Поэтому установка в сети работает в режиме входа по учётным записям
(`TRK-113`): образ с `TRACKER_UI_LOGIN=password` ключа не отдаёт никому —
`/config.json` отвечает `401 {"login":"password"}`, — и каждый входит своей почтой и
паролем. Ответ входа отдаёт вкладке её собственный токен сеанса, а кука `HttpOnly`
возвращает его после перезагрузки; записи подписаны именем того, кто вошёл. Выход
закрывает сеанс на сервере и только в этом браузере.

Людей заводит администратор на экране «Люди» (`/people`): почта, имя-подпись, флаг
администратора и пароль — вписанный или сгенерированный, показанный один раз. Там же
товарища отключают и сбрасывают ему пароль; свой пароль каждый меняет на экране «Моя
учётная запись» (`/account`). На своей машине этих экранов нет вовсе: вход не
спрашивается, а владелец — единственный человек установки.

Без режима входа образ не поднимается, если порт опубликован не на петле
(`TRACKER_UI_BIND`). Как включить — `../README.md`, «Network mode»; как устроено —
`../docs/DEVELOPMENT.md`, «Учётные записи и вход: установка в сети» и `docs/FRONTEND.md`.

Дев-сервер `pnpm dev` режима входа не знает: его `/config.json` отдаёт ключ из переменной,
как локальная установка. Экран входа по почте проверяется в образе —
`e2e/account-login.spec.ts`, управление людьми — `e2e/people.spec.ts`.

### Установка без ключа: вход токеном

Образ, которому не дали ни ключа, ни режима входа (без тома `ui-key` и переменной
`TRACKER_UI_TOKEN_FILE`), отвечает на `/config.json` `404`, и экран входа спрашивает токен
участника — его выпускают на экране «Доступы» или командой бэкенда `issue-token`. Это
запасной путь, а не способ раздать установку команде: людям нужны учётные записи и режим
входа выше.

## Папки

- `docs/` — концепция, соглашения, дорожная карта, задания для агентов, заметки
- `src/` — исходный код по слоям Feature-Sliced Design
- `testing/` — обвязка модульных и страничных тестов и проверки вне экранов: подмена API, рендер, сторож заметок
- `e2e/` — сквозные сценарии Playwright и подъём контура для них
- `docker/` — образ интерфейса и шаблон конфигурации nginx
- `scripts/` — команда слияния ветки задачи
