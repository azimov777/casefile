# Фронтенду: с чего начать

Документ для разработчика интерфейса. Он отвечает на вопросы, которые иначе пришлось бы
задавать: как устроен ответ, откуда взять токен, что читать на первом экране, чем
отличается перенос карточки от перестановки и почему поток событий не открывается через
`EventSource`.

Полное описание каждого маршрута — в схеме OpenAPI: она поставляемый артефакт, а не
побочный продукт. Здесь только то, чего в схеме нет: связи между маршрутами, смысл
механик и грабли.

- Схема: `http://localhost:8000/openapi.json`, интерактивно — `/docs`.
- Коды ошибок с описанием, когда какой возникает: [`ERRORS.md`](ERRORS.md).
- Доменная модель целиком: [`CONCEPT.md`](CONCEPT.md).

## Поднять бэкенд и получить данные

```bash
docker compose up -d
docker compose run --rm migrate   # схема базы
docker compose run --rm init      # владелец и его первый токен — секрет печатается один раз
docker compose run --rm demo      # осмысленный набор данных: две очереди, проект, доска
```

Разрабатывать на пустой базе не нужно и вредно: половина недоделок интерфейса видна
только на данных. Демо-набор даёт две очереди с **разными** процессами, эпик с
подзадачами, обсуждение, чеклист, проект поперёк очередей внутри портфеля, доску с
колонками и включённое правило автоматики.

Повторный запуск `demo` отказывает: набор — связный граф, доливать его нечем. Начать
заново — `docker compose down -v` и всё сначала.

## Генерация типизированного клиента

```bash
docker compose run --rm schema     # пишет openapi.json и пересобирает docs/ERRORS.md
```

Дальше — любым генератором, например `openapi-typescript`:

```bash
npx openapi-typescript openapi.json -o src/shared/api/openapi.ts
```

Схема к этому пригодна, и это проверяется тестами, а не обещается: у каждого маршрута
есть модель ответа, `operation_id` стабилен и читаем (`read_issue`, а не
`read_issue_api_v1_issues__key__get`), перечисления — строковые enum, объектов
неизвестной формы нет нигде, кроме трёх задокументированных мест (см. «Свободная
форма»).

## Аутентификация

Токен передаётся заголовком, других способов нет:

```
Authorization: Bearer trk_...
```

Токен принадлежит **актору** — человеку или агенту. Ролей в первой версии нет: любой
действующий токен может всё. Первый токен выпускает `docker compose run --rm init`,
остальные — `POST /api/v1/actors/{actor_key}/tokens`; секрет виден **только** в ответе
на выпуск и больше нигде.

Отсутствие или недействительность токена — всегда `401` с кодом `unauthorized`;
причина в `details.reason` (`missing_token`, `unknown_token`, `revoked`,
`actor_inactive`). Токен в параметре запроса не принимается намеренно: он уехал бы в
журналы прокси, в историю браузера и в `Referer`.

## Оболочка ответа

Внешняя структура одинакова у всех эндпоинтов. Клиент разбирает любой ответ одним и тем
же кодом, не зная, какой маршрут его вернул.

Одиночный ресурс:

```json
{"data": {"key": "TRK-123", "summary": "..."}}
```

Коллекция — всегда с курсорной пагинацией:

```json
{"data": [{"key": "TRK-123"}],
 "meta": {"next_cursor": "eyJpZCI6...", "has_more": true}}
```

Ошибка:

```json
{"error": {"code": "issue_not_found", "message": "Issue TRK-123 not found", "details": {}}}
```

Исключений ровно три, и других не будет:

1. действие без результата (удаление) отвечает `204` без тела;
2. `/health` живёт вне `/api/v1` и отдаёт плоский ответ — он для мониторинга;
3. `GET /api/v1/events/stream` отдаёт `text/event-stream`: завернуть кадр SSE во
   что-то ещё нельзя, не перестав быть SSE.

Что важно знать про пагинацию:

- листать надо **до `has_more: false`**, а не до первой неполной страницы. У поиска и
  ленты событий сужение применяется после выборки, поэтому страница бывает короче
  запрошенного размера, а курсор при этом верен;
- `next_cursor` непрозрачен: разбирать его нельзя, он меняется;
- `total` в ответах нет и не будет: курсорная пагинация его не считает, а отдельный
  `COUNT` по фильтру доски дороже всего остального в ответе.

## Ошибки

Решения принимаются по `code`, а не по тексту и не по HTTP-статусу. `message` —
английская техническая фраза для лога и разработчика; текст для пользователя выбирает
интерфейс по коду. `details` — структурированные подробности: какое поле, какое
правило, какие значения допустимы.

Полный список с описанием — [`ERRORS.md`](ERRORS.md). Самые частые в интерфейсе:

| Код | Когда и что делать |
|---|---|
| `version_conflict` | Задачу изменили под вами. Перечитать и показать расхождение, а не перезаписывать |
| `validation_error` | Тело не прошло проверку; разбор — в `details` |
| `field_values_invalid` | Значения кастомных полей не прошли проверку; **все** ошибки сразу лежат в `details.fields` |
| `transition_not_allowed` | Такого ребра нет в процессе. Перечитать доступные переходы |
| `transition_requirements_not_met` | Переходу не хватает полей; их имена — в `details` |
| `issue_resolution_required` | Закрытие требует резолюции — спросить её и повторить одним запросом |
| `link_cycle_detected` | Иерархия замкнулась бы в цикл |
| `invalid_stream_cursor` | Поток событий отстал больше окна переподключения; догонять надо лентой `GET /events` |

## Сущности: что с чем связано

**Очередь** владеет процессом. Не папка, а контейнер конфигурации: свои типы задач,
свой воркфлоу, свои поля, свои правила. Две очереди могут иметь совершенно разные
процессы.

**Статус** обязательно имеет категорию — `new`, `in_progress` или `done`. Доски, прогресс
и автоматика опираются на **категорию**, а не на название: команда может переименовать
статус, ничего не сломав. Интерфейсу следует делать так же.

**Ссылки вместо вложенных объектов.** Задача приезжает с ключом очереди (`TRK`),
ссылками справочника (`open`, `TRK.review`) и ключами акторов (`alice`). Полные записи
отдают `GET /queues/{key}/config` и `GET /actors` — их достаточно закешировать один раз.
Ссылка вида `КЛЮЧ.значение` означает запись, локальную для очереди; без точки —
глобальную.

**Связи** хранятся один раз и показываются с двух сторон: связь, заведённая как
«TRK-2 depends_on TRK-1», приезжает к TRK-1 типом `blocks`. Тип всегда назван со стороны
той задачи, о которой спрашивали.

**Эпик — это тип задачи, а не тип связи.** Задачи входят в эпик обычной иерархической
связью `subtask_of`. У задачи один родитель; у эпика родителя не бывает вовсе.

**Проект** собирает задачи из разных очередей, **портфель** объединяет проекты.
Прогресс считается по задачам в статусах категории `done` и приезжает внутри карточки
проекта.

## Экраны и агрегаты

Три маршрута собраны под реальные экраны, чтобы страница не начиналась с пяти запросов
подряд. Каждый отдаёт ровно то же, что отдали бы отдельные эндпоинты, — это проверяется
тестом, а не обещается.

### Первый экран — `GET /api/v1/bootstrap`

Текущий актор, неархивные очереди, глобальные справочники и поля, счётчик непрочитанных.
Всё, что нужно шапке и навигации, одним запросом. Локальные записи очереди сюда не
входят — они приезжают с её конфигурацией, когда пользователь в неё зашёл.

### Карточка задачи — `GET /api/v1/issues/{issue_key}/card`

Задача, доступные переходы, связи, обсуждение и чеклист. Параметр `limit` задаёт,
сколько комментариев и связей положить сразу; остальное дочитывается их собственными
маршрутами по курсору из `comments_next_cursor` и `links_next_cursor`. Своей пагинации
агрегат не заводит — он передаёт вам курсор того эндпоинта, который эту коллекцию
листает.

Переходы приезжают **вместе с недоступными**: у недоступного заполнено `missing_fields`.
Это позволяет объяснить отказ до нажатия кнопки, а не после.

### Сводка по проекту — `GET /api/v1/projects/{project_key}/summary`

Карточка проекта с прогрессом и первая страница его задач. `query`, `sort` и `fields`
работают ровно как в поиске и могут выдачу сузить, но не могут вывести её за пределы
проекта.

## Задачи: чтение и изменение

Частичное обновление — `PATCH /issues/{issue_key}` с явно переданными полями.
Различайте три состояния:

- поле **не передано** — не меняется;
- поле передано как `null` — очищается (осмысленно у `resolution`, `assignee`,
  `deadline`, `project`);
- поле передано со значением — заменяется.

Схема это различает на уровне типов: там, где `null` смысла не имеет, он просто не
пройдёт валидацию.

**Оптимистичная блокировка.** У задачи есть `version`, растущая с каждым изменением.
Пришлите её обратно в `PATCH`, и потерянное обновление превратится в
`409 version_conflict` вместо тихой перезаписи чужой работы. В `PATCH` это
необязательно, **в переходе — обязательно**: ход в процессе, сделанный вслепую по
устаревшему состоянию, повторять нельзя.

**Смена статуса — только переходом.** `PATCH` статус не меняет: процесс не обходится.

```
GET  /issues/TRK-1/transitions              → что можно и чего не хватает
POST /issues/TRK-1/transitions/{id}         → выполнить, вместе с резолюцией и полями
```

Резолюция, исполнитель и значения полей передаются **тем же запросом**: закрытие не
требует предварительного `PATCH` и всё равно даёт одну версию, одну запись истории и
одно событие.

## Поиск

Два способа описать один и тот же отбор — и оба разбираются в один внутренний фильтр:

```
GET  /search/issues?query=queue: TRK and status: open and assignee: me()
POST /search/issues                                  ← структурный фильтр телом
```

Функции языка: `me()`, `today()`, `empty()`. Ошибка разбора приходит с позицией в
строке — её можно подсветить прямо в поле ввода.

`fields` — повторяющийся параметр (`?fields=key&fields=summary`), не список через
запятую. Он режет ответ: доске обычно хватает ключа, названия и исполнителя, а полная
задача на сто карточек — это мегабайты.

Сохранённые фильтры — именованные запросы: `POST /filters`, затем
`GET /search/issues?saved_filter=<uuid>`. Их же используют доски и автодействия.

## Доска

Собирается покомпонентно, и это осознанно: одна доска может тянуть тысячи задач.

```
GET /boards/{id}                                  → настройки и колонки
GET /boards/{id}/columns/{column_id}/issues       → карточки одной колонки, своим курсором
GET /boards/{id}/issues                           → все задачи доски, ранговым порядком
```

Счётчиков задач в колонке нет намеренно: курсорная пагинация не считает `total`.

**Два движения карточки — два разных запроса, и порядок между ними не важен:**

| Действие | Запрос | Что меняет |
|---|---|---|
| Перенос в другую колонку | `POST /boards/{id}/issues/{key}/column` | Статус задачи — **через процесс**, со всеми проверками. Версия растёт, попадает в историю. Может отказать: `transition_not_allowed`, `issue_resolution_required` |
| Перестановка внутри колонки | `PUT /boards/{id}/issues/{key}/rank` | Только порядок. Статус не трогает, версию не поднимает, в историю не попадает |

Отказ переноса — это работающий процесс, а не недоработка доски.

**Порядок отдаётся только порядком.** Числовых позиций в контракте нет: при
перенумерации доски они все меняются, сохраняя порядок, и клиент, на них опирающийся,
сломается молча. Новое место задаётся соседом:

```json
{"after": "TRK-4"}     // сразу за TRK-4
{"before": "TRK-4"}    // прямо перед ним
{"after": null}        // в начало списка
{"before": null}       // в конец
```

Задача, попадающая в фильтр доски, но стоящая в статусе, не разложенном ни в одну
колонку, **через колонки не видна**. Её показывает `GET /boards/{id}/issues`. Раскладывая
статусы по колонкам, покрывайте все статусы процесса.

## Живой поток событий (SSE)

```
GET /api/v1/events/stream
```

Единственное место без оболочки `data`: кадры `id:`, `event:`, `data:`. Полезная
нагрузка кадра описана схемой `StreamEventRead` — та же, что у ленты `GET /api/v1/events`.

**Открывать надо fetch-клиентом, а не `EventSource`.** Браузерный `EventSource` не умеет
слать заголовки, а поток защищён токеном в `Authorization`. Токен параметром запроса не
принимается (см. «Аутентификация»). Рабочий вариант — `@microsoft/fetch-event-source`:

```ts
import { fetchEventSource } from "@microsoft/fetch-event-source";

await fetchEventSource("/api/v1/events/stream?queue=TRK", {
  headers: { Authorization: `Bearer ${token}` },
  onmessage(frame) {
    const view = JSON.parse(frame.data);   // StreamEventRead
    // frame.id — идентификатор события; его же вернут в Last-Event-ID при обрыве
  },
});
```

**Переподключение.** Клиент присылает `Last-Event-ID` (или параметр `last_event_id`) —
поток продолжается ровно с него. Слишком большое отставание или неизвестный
идентификатор — `422 invalid_stream_cursor`, а не тихий старт с конца: клиент,
пропустивший события и не знающий об этом, разошёлся бы с сервером незаметно. Догонять
пропущенное надо лентой `GET /api/v1/events` — у неё обычная оболочка и обычная
пагинация.

Событие несёт **снимок и идентификаторы**, а не полный объект: получив его, свежее
состояние надо перезапросить. Строки вида `: heartbeat` — это комментарии SSE, их клиент
игнорирует; они нужны, чтобы прокси не закрыл простаивающее соединение.

## Уведомления

Инбокс актора — очередь непрочитанного в базе:

```
GET  /notifications?is_read=false     → что пришло
POST /notifications/read              → отметить прочитанным
GET  /notifications/wait              → длинный опрос: вернётся, как только что-то появится
```

Счётчик непрочитанных для бейджа приезжает в `GET /bootstrap` — отдельного запроса не
нужно. По умолчанию актор получает уведомления о задачах, где он автор, исполнитель или
наблюдатель, и об упоминаниях; настраивается подписками `/notifications/subscriptions`.
Собственные действия по умолчанию не уведомляют.

## Свободная форма: три места, и они задокументированы

Всё остальное в схеме типизировано. Эти три — нет, и каждое по своей причине:

1. **`values` задачи** — значения кастомных полей. Форма каждого значения зависит от типа
   поля и описана в реестре: `GET /fields` и `GET /queues/{key}/config`. По нему же
   стройте редактор.
2. **`details` ошибки** — подробности зависят от кода ошибки.
3. **`params` правила автоматики** — у каждого правила своя схема, и она приезжает рядом
   со значениями (`params_schema`). Форму настройки стройте по ней, а не по догадке.

## Мелочи, на которых спотыкаются

- **Даты** — ISO 8601 с таймзоной, всегда UTC. Значение без таймзоны отвергается.
- **Ключи задач неизменяемы и не переиспользуются.** Удалённый ключ не достанется другой
  задаче.
- **Адресация мягкая:** `/issues/trk-123` находит ту же задачу, что и `TRK-123`,
  `/queues/trk` — ту же очередь. А вот при создании ключ проверяется строго.
- **Удаление комментария мягкое:** реплика остаётся в ленте с `body: null` и
  `is_deleted: true`. Прятать её нельзя — соседние потеряют контекст.
- **Отзыв токена идемпотентен:** повторный `DELETE` снова отвечает `204`.
- **Чеклист не листается** — он приходит целиком: половина чеклиста не ответ.
- **Комментарии автоматики** приезжают в обычной ленте, автор у них — актор `system`.
- **Порядок элементов, созданных одной транзакцией**, определяется не временем создания:
  у них совпадает `created_at`. Полагайтесь на порядок, который отдал сервер.
