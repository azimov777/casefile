# Фронтенду: с чего начать

Документ для разработчика интерфейса человека. Бэкенд переписывается под трекер для
агентов (`CONCEPT.md`); здесь описано, каким будет контракт после задач 20–29
из `ROADMAP.md`. Пока задачи не закрыты, точные пути и схемы берутся из OpenAPI,
который выгружается бэкендом, а не из этого файла.

## Роль человека в интерфейсе

Человек **наблюдает и отвечает**. Он не ведёт задачи руками: задачи создают и двигают
агенты. Отсюда четыре экрана, и только они:

| Экран | Что показывает | Откуда данные |
|---|---|---|
| Список задач | Задачи с фильтрами по очереди, статусу, исполнителю, тегам, приоритету, признаку «заблокирована», открытым вопросам | `GET /api/v1/tasks?query=...` |
| Карточка задачи | Поля, пять разделов, статус, связи, последняя сводка, открытые вопросы, опись дела; тела записей по клику | `GET /api/v1/tasks/{key}`, `GET /api/v1/tasks/{key}/entries` |
| Открытые вопросы | Вопросы без ответа, адресованные текущему участнику или всем, с признаком «блокирующий» | `GET /api/v1/questions` |
| Ответ | Форма ответа на вопрос | `POST /api/v1/tasks/{key}/entries` с типом `answer` |

Всё, что человеку может понадобиться сверх этого, уже возможно через API: прав по роду
участника нет. Интерфейс дорастёт, когда роль человека прояснится.

## Доска без доски

В бэкенде досок нет. Статусы зашиты и одинаковы для всех очередей, поэтому доска это
список задач одной очереди, разложенный по столбцам `backlog`, `open`, `in_progress`,
`review`, `done`, `cancelled`. Один запрос списка с фильтром по очереди даёт всё, что
нужно; ручного порядка карточек и лимитов в работе нет.

## Поднять бэкенд и получить данные

По README: контур разработки в Docker, миграции явным шагом, демо-данные одной командой.
Демо содержит очередь, задачи во всех статусах и дела с записями всех типов, чтобы каждый
экран было чем наполнить.

## Генерация типизированного клиента

Схема OpenAPI это поставляемый артефакт: каждый эндпоинт объявляет модель ответа,
оболочка ответа параметризована, `operation_id` стабильные, перечисления строковые.
Правила в `CONVENTIONS.md`, раздел «Типизация и генерация клиента».

## Аутентификация

Токен участника в заголовке, схема та же, что в текущей версии (README, «Доступ к API»).
У токена набор `task` или `main`; интерфейсу человека хватает `task`, администрирование
очередей и участников требует `main`. Ответ `401` при отсутствии или недействительности
токена, `403` при выходе за набор.

`GET /api/v1/bootstrap` отдаёт первый экран одним запросом: текущий участник, очереди,
число открытых вопросов, адресованных ему.

## Оболочка ответа и ошибки

Одна оболочка на все эндпоинты: `data` для ресурса, `data` плюс `meta` с курсором для
коллекции, `error` с `code`, `message`, `details` для ошибки. Единственное исключение
из оболочки: `GET /api/v1/journal/stream` отдаёт SSE. Полный список кодов ошибок
собирается в `ERRORS.md`.

Ошибки, которые интерфейс увидит чаще всего:

| Код | Когда |
|---|---|
| `validation_error` | Тело запроса не прошло проверку; в `details.fields` все поля сразу |
| `task_not_found`, `queue_not_found`, `participant_not_found` | Нет такого объекта |
| `version_conflict` | Задача изменилась с момента чтения; перечитать и повторить |
| `question_not_found`, `question_already_answered` | Ответ не на тот вопрос |

## Сущности: что с чем связано

- **Очередь** содержит задачи. У очереди ключ, название, описание.
- **Задача**: ключ `TRK-42`, название, описание, пять разделов, статус, исполнитель
  (свободная строка), теги, приоритет, версия. Разделы неизменяемы от `open` и дальше.
- **Дело** задачи: упорядоченные неизменяемые записи с номером внутри задачи. Типы записей
  и их структура в `CONCEPT.md`, 3.4. Опись это список заголовков; тело читается отдельно.
- **Связи**: `parent` / `child`, `blocks` / `blocked_by`, `relates`; показываются с обеих
  сторон под своим именем и со статусом задачи на другой стороне.
- **Участники**: `human` и `agent` с именем и описанием. Автор записи это род и подпись;
  у временных агентов подпись это метка, а не имя из реестра.
- **Вычисляемые признаки** в карточке и в поиске: `blocked`, `open_questions`,
  `open_blocking_questions`, `last_summary_at`.

## Карточка задачи одним запросом

`GET /api/v1/tasks/{key}` отдаёт пакет: карточку, связи, признаки, последнюю сводку
целиком, открытые вопросы целиком, опись дела и список доступных переходов. Этого хватает,
чтобы отрисовать экран без второго запроса; тела остальных записей подгружаются
по номерам через `GET /api/v1/tasks/{key}/entries?nos=3,7,12`.

## Живой поток

`GET /api/v1/journal/stream?after=<seq>` отдаёт SSE с записями дела всех задач по мере
появления; `id:` кадра это сквозной номер `seq`, и по нему поток продолжается после
переподключения. Фильтры по очереди и типу записи те же, что у ленты
`GET /api/v1/journal`. Записи постоянны: срока хранения нет, «догнать» можно с любого номера.

Для экрана списка достаточно по каждому кадру перечитать затронутую задачу или
инвалидировать список; для карточки — дописать запись в опись.

## Что изменилось относительно прошлой версии контракта

Ушли и не вернутся: проекты, доски, спринты, портфели, комментарии, чеклисты, кастомные
поля, настраиваемые статусы и процессы, инбокс и подписки, сохранённые фильтры, вебхуки.
Путь `issues` переименован в `tasks`, `events` в `journal`. Клиент, собранный по старой
схеме, нужно перегенерировать целиком.
