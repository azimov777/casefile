# Концепция: таск-трекер (бэкенд)

## 1. Что мы строим

Собственный таск-трекер — бэкенд-система управления задачами. Яндекс Трекер взят как
источник удачных механик (очереди, локальные поля, связи, проекты и портфели, автоматика),
а не как эталон для копирования. Всё, что не нужно нам, не переносим.

Три потребителя бэкенда:

1. **Фронтенд** (делается отдельным проектом) — REST API + стрим событий.
2. **Агенты** (Claude Code и подобные) — MCP-сервер: работа с задачами и получение уведомлений.
3. **Автоматика** — правила, написанные кодом внутри этого же проекта.

Режим работы первой версии: **один владелец + его агенты**. Ролевой модели и проверок прав нет,
но есть сущность «актор», чтобы задачи было на кого назначать, а уведомления — кому адресовать.

## 2. Опорные принципы

**Очередь владеет процессом.** Очередь — не папка, а контейнер конфигурации: свой набор типов
задач, свой воркфлоу, свои локальные поля, свои правила автоматики. Две очереди могут иметь
совершенно разные процессы и не мешать друг другу.

**Поля — данные, а не колонки.** Системные поля (статус, тип, исполнитель, дедлайн, приоритет)
живут отдельными колонками — по ним идёт основная фильтрация. Всё остальное описывается в
реестре полей и хранится в JSONB. Добавление нового поля не требует миграции.

**История изменений первична.** Каждое изменение задачи фиксируется в журнале: кто, когда, что
и с какого значения на какое. Из журнала растут три вещи сразу: аудит, срабатывание автоматики
(«поле изменилось так, что условие стало истинным») и уведомления. Одно место — три механики.

**Событие существует, только если изменение зафиксировано.** События пишутся в outbox в одной
транзакции с изменением задачи, а обрабатываются отдельным воркером. Никаких «уведомление ушло,
а транзакция откатилась».

**Автоматика — это код.** Правила пишутся на Python в репозитории и регистрируются в реестре.
В базе хранится только их состояние: включено/выключено, к какой очереди привязано, с какими
параметрами. Меняем поведение — правим код; включаем и настраиваем — через API.

## 3. Доменная модель

### 3.1 Акторы

| Сущность | Смысл |
|---|---|
| `Actor` | Человек или агент. Тип, имя, признак активности. |
| `ApiToken` | Токен доступа, привязанный к актору. Через него ходят фронт и агенты. |

Ролевой модели в v1 нет: любой валидный токен может всё. Проверка прав вынесена в единую точку,
чтобы позже её можно было наполнить, не переписывая эндпоинты.

### 3.2 Очередь и её конфигурация

| Сущность | Смысл |
|---|---|
| `Queue` | Ключ (`TRK`), название, описание, владелец, счётчик номеров задач. |
| `IssueType` | Тип задачи (задача, баг, эпик, ...). Глобальный справочник, очередь подключает нужные и назначает тип по умолчанию. |
| `Status` | Статус (открыт, в работе, закрыт, ...). Создаётся пользователем или агентом, обязательно имеет категорию: `new` / `in_progress` / `done`. |
| `Resolution` | Резолюция при закрытии (сделано, отклонено, дубликат, ...). |
| `Workflow` | Именованный процесс: набор разрешённых переходов между статусами для связки «очередь + тип задачи». Собирается пользователем или агентом. |
| `Transition` | Один переход: из статуса в статус, условия, требуемые поля, действия. |

Статусы, типы задач и воркфлоу — редактируемые данные, а не зашитый справочник: собственный
процесс со своими статусами и переходами собирается и через REST, и через MCP.

Категория статуса важнее самого статуса: доски, отчёты и правила автоматики опираются на
`done`/`in_progress`, а не на конкретное название, поэтому команда может переименовать статус,
ничего не сломав.

### 3.3 Задача

Системные поля (колонки): ключ (`TRK-123`), очередь, тип, статус, резолюция, приоритет,
название, описание, автор, исполнитель, наблюдатели, дедлайн, теги, даты создания/обновления,
версия (для оптимистичной блокировки).

Кастомные поля: `values JSONB` + реестр `Field`.

| Сущность | Смысл |
|---|---|
| `Field` | Описание поля: ключ, название, тип значения, множественность, область (глобальное или локальное для очереди), обязательность, значения для перечислений. |
| `Issue` | Задача. |
| `IssueLink` | Связь между задачами. |
| `Comment` | Комментарий. |
| `ChecklistItem` | Пункт чеклиста внутри задачи. |
| `ChangelogEntry` | Запись в истории изменений. |

Локальные поля адресуются с префиксом очереди (`TRK.severity`), глобальные — без.

### 3.4 Связи

Типы связей симметричны: у каждой связи есть прямая и обратная сторона.

| Прямая | Обратная | Смысл |
|---|---|---|
| `relates` | `relates` | Просто связано. |
| `depends_on` | `blocks` | Задача не может начаться, пока не сделана другая. |
| `subtask_of` | `parent_of` | Декомпозиция. |
| `duplicates` | `duplicated_by` | Дубликат. |
| `epic_of` | `in_epic` | Эпик и входящие в него задачи. |

Иерархические связи (`subtask_of`, `epic_of`) не должны образовывать циклы — это проверяется
при создании связи.

### 3.5 Проекты и портфели

Надочередной слой планирования: проект собирает задачи из разных очередей вокруг общего
результата, портфель объединяет проекты и другие портфели.

| Сущность | Смысл |
|---|---|
| `Project` | Название, описание, ответственный, участники, статус, даты начала и окончания, теги, прогресс. |
| `Portfolio` | То же плюс состав: проекты и вложенные портфели. |

Задача может входить в проект; проект может входить в портфель; портфель может входить в
портфель. Прогресс считается по задачам проекта (доля задач в статусах категории `done`).

### 3.6 Доски и спринты

| Сущность | Смысл |
|---|---|
| `Board` | Доска: источник задач (очереди или фильтр), колонки, порядок. |
| `BoardColumn` | Колонка доски и список статусов, которые в неё попадают. |
| `Sprint` | Спринт: название, даты, доска, состояние (планируется / активен / завершён). |
| `IssueRank` | Позиция задачи в бэклоге и на доске. |

Ранжирование задач нужно отдельной сущностью: порядок карточек на доске не выводится ни из
одного бизнес-поля, а перетаскивание карточки не должно переписывать половину таблицы.

## 4. Механики

### 4.1 События и журнал изменений

Любая мутация задачи проходит через единый слой, который:
1. применяет изменение,
2. пишет записи в журнал изменений (по полю: было → стало),
3. кладёт событие в outbox — всё в одной транзакции.

Воркер разгребает outbox и рассылает событие подписчикам: движку автоматики, движку
уведомлений, вебхукам, стриму для фронтенда.

Типы событий: создание задачи, изменение полей, смена статуса, комментарий, изменение связей,
изменение проекта/портфеля, наступление дедлайна.

### 4.2 Автоматика

Три формы, как в Трекере, но настраиваются кодом:

- **Триггер** — реагирует на событие. Пример: «перевели в „в работе“ без исполнителя — назначить автора».
- **Автодействие** — работает по расписанию, отбирает задачи фильтром. Пример: «задачи без движения 7 дней — вернуть в бэклог и уведомить».
- **Макрос** — запускается вручную человеком или агентом. Пример: «оформить как релизную задачу».

Правило — это функция на Python с декоратором, объявляющая: на какие события реагирует, какое
условие проверяет, что делает. Реестр в БД хранит включённость, привязку к очереди и параметры.

Обязательные свойства движка: защита от бесконечных цепочек (правило породило событие, которое
снова вызвало правило), выполнение от имени системного актора, лог каждого срабатывания.

### 4.3 Уведомления

Подписка задаётся правилом: «актор X хочет получать события типа Y по объектам Z» (по очереди,
проекту, конкретной задаче или через «я наблюдатель / я исполнитель»).

Доставка идёт по трём каналам:

1. **Inbox актора** — очередь непрочитанных событий в БД. Агент забирает их инструментом MCP или ждёт появления новых.
2. **MCP-нотификации** — push поверх streamable HTTP для клиентов, которые их поддерживают.
3. **Вебхуки** — исходящие HTTP-вызовы на внешние адреса, с повторами и подписью.

Плюс SSE-стрим для фронтенда, чтобы интерфейс обновлялся без опроса.

### 4.4 Поиск

Два уровня:

- **Структурный фильтр** — параметры запроса: очередь, статус, исполнитель, теги, диапазоны дат, значения кастомных полей, сортировка, курсорная пагинация.
- **Язык запросов** — строка вида `queue: TRK and status: open and assignee: me() and deadline: <= today()`. Разбирается в тот же внутренний фильтр. Для агентов это главный способ искать: одна строка вместо конструктора.

Сохранённые фильтры — именованные запросы, которые можно переиспользовать из фронта, MCP и автодействий.

## 5. Интерфейсы

### 5.1 REST API для фронтенда

Полное покрытие домена: очереди и их конфигурация, задачи, связи, комментарии, чеклисты,
проекты, портфели, доски, спринты, фильтры, автоматика, уведомления, справочники.
Единый формат ошибок, курсорная пагинация, OpenAPI-схема, SSE-стрим событий.

### 5.2 MCP-сервер для агентов

Инструменты покрывают рабочий цикл агента: найти задачи, прочитать задачу с историей и
комментариями, создать, обновить, сменить статус, связать, прокомментировать, запустить макрос,
забрать уведомления, дождаться новых.

Отдельная группа инструментов — настройка процесса: создать очередь, завести собственные статусы
и типы задач, собрать воркфлоу из статусов и переходов одним вызовом, добавить поля, включить и
настроить правило автоматики. Агент должен уметь не только работать внутри готового процесса, но
и конструировать его.

Ключевое требование: инструменты должны быть **экономными по контексту**. Задача с полным
журналом изменений — это килобайты текста, поэтому у чтения есть уровни детализации, а у поиска
— выбор возвращаемых полей.

## 7. Что сознательно не делаем в первой версии

- Учёт времени (оценки, списание, Story Points).
- Вложения файлов.
- Дашборды и отчёты.
- Права доступа, роли, мультиарендность.
- Почтовые уведомления и интеграции с мессенджерами.
- Импорт из внешних трекеров (кандидат на следующую итерацию).

Каждый пункт исключён из объёма, но не из архитектуры: модель не должна делать их невозможными.
