# Сквозные соглашения проекта

Этот файл обязателен к прочтению перед выполнением любой задачи репозитория.
Он описывает правила, единые для всего проекта. Задача описывает *что* делать,
соглашения — *как*.

## Стек

- Python 3.14, FastAPI, Pydantic v2.
- PostgreSQL, SQLAlchemy 2 (async), Alembic.
- pytest + pytest-asyncio + httpx для тестов.
- Docker и Docker Compose — обязательная и единственная поддерживаемая среда запуска.

Новые зависимости добавляются только если без них задача не решается разумным объёмом кода.
Каждая добавленная зависимость упоминается в отчёте о выполнении задачи.

## Запуск: всё работает в Docker

Проект запускается только в контейнерах. Установка Python и зависимостей на хост-машину не
поддерживается и не документируется: сервер, миграции, тесты и линтер выполняются внутри
контейнера. Требование сквозное — задача, после которой что-то запускается только «локально
руками», считается невыполненной.

Ведутся **два отдельных Dockerfile**:

| Файл | Назначение | Что делает |
|---|---|---|
| `docker/Dockerfile.dev` | разработка | Код монтируется томом, автоперезапуск при изменениях, установлены dev-зависимости, подробные логи |
| `docker/Dockerfile.prod` | продакшен | Многостадийная сборка, только рантайм-зависимости, код скопирован внутрь образа, запуск от непривилегированного пользователя, без автоперезапуска |

И два файла Compose: `docker-compose.yml` (разработка, используется по умолчанию) и
`docker-compose.prod.yml` (продакшен). Продакшен-контур — это установка из готовых образов:
прод-образ собирает конвейер из каждого коммита main и публикует в ghcr.io, а исходников и
сборки в самом контуре нет — его же одной строкой ставят пользователи (`install.sh`).

Требования к обоим контурам:

- Один и тот же базовый образ Python и один и тот же набор переменных окружения — расхождение
  сред не должно быть причиной «на дев работает, на проде нет».
- Все процессы приложения — отдельные сервисы Compose из одного образа с разными командами:
  HTTP-сервер и MCP-сервер. Фоновых процессов нет: автоматики в трекере нет, а лента
  читается прямо из таблицы записей.
- Проверка здоровья у сервиса приложения и у БД; приложение стартует после готовности БД.
- Данные БД — в именованном томе, чтобы перезапуск не стирал состояние.
- Прод-образ не содержит инструментов сборки, тестов и dev-зависимостей.
- Миграции применяются явным шагом (отдельная команда или init-контейнер), а не втихую при
  старте нескольких реплик: параллельный запуск миграций из трёх контейнеров даёт гонку.

Каждая задача, добавляющая новый процесс (например, MCP-сервер), обязана добавить
его в оба файла Compose и описать в README.

## Структура кода

Слоистая, границы жёсткие:

```
app/
  api/          — HTTP-слой: роутеры, схемы запросов и ответов, обработка ошибок
  mcp/          — MCP-сервер: инструменты, промпт и инструкции сервера
  domain/       — доменные модели и бизнес-правила, без знания об HTTP и ORM
  services/     — сценарии: оркестрация домена, транзакции, служебные записи дела
  db/           — модели SQLAlchemy, репозитории, миграции
  core/         — конфиг, зависимости, логирование, общие утилиты
```

Правила направления зависимостей:

- `api` и `mcp` зависят от `services`, но не друг от друга.
- `services` зависит от `domain` и `db`.
- `domain` не импортирует ничего из `api`, `db`, `mcp`.
- Любая мутация данных проходит через `services`. Роутер, который сам ходит в БД и меняет
  состояние — ошибка: тогда та же операция из MCP пойдёт мимо служебных записей дела.

Один сценарий — одна функция сервиса, вызываемая и из REST, и из MCP. Это главное требование
проекта: **бизнес-логика не дублируется между интерфейсами.**

## API

### Общие правила

- Префикс `/api/v1`.
- Ресурсы во множественном числе: `/api/v1/tasks`, `/api/v1/queues/{key}`.
- Задачи адресуются ключом (`TRK-123`), не числовым id.
- Имена полей — `snake_case`, латиницей.
- Даты в ISO 8601 с таймзоной, UTC.
- Частичное обновление — `PATCH` с явно переданными полями; отличать «поле не передано» от
  «поле передано как null» обязательно.

### Единая внешняя структура ответа

Внешняя оболочка ответа **одинакова у всех эндпоинтов без исключений**. Меняется только
содержимое `data` — оболочка не меняется никогда. Клиент должен уметь разбирать любой ответ
одним и тем же кодом, не зная заранее, какой эндпоинт его вернул.

Одиночный ресурс:

```json
{"data": {"key": "TRK-123", "summary": "..."}}
```

Коллекция — всегда с курсорной пагинацией:

```json
{"data": [{"key": "TRK-123"}, {"key": "TRK-124"}],
 "meta": {"next_cursor": "eyJpZCI6...", "has_more": true}}
```

Ошибка:

```json
{"error": {"code": "task_not_found",
           "message": "Task TRK-123 not found",
           "details": {}}}
```

Запрещено:

- отдавать ресурс «голым», без оболочки `data`;
- возвращать коллекцию как массив верхнего уровня;
- называть один и тот же по смыслу элемент по-разному в разных эндпоинтах (`items` здесь,
  `results` там, `list` в третьем месте);
- добавлять служебные поля рядом с `data` мимо `meta`;
- отвечать пустым телом там, где по смыслу есть результат: пустая коллекция — это `"data": []`.

Исключения — только эти, и других быть не может:

- действия без результата (удаление) отвечают `204` без тела;
- `/health` живёт вне `/api/v1`, предназначен для Docker и мониторинга и не входит в контракт
  с фронтендом, поэтому отдаёт плоский ответ;
- `GET /api/v1/journal/stream` отдаёт `text/event-stream`: кадры `id:`, `event:`, `data:`.
  Это не выбор, а свойство формата — завернуть кадр в `{"data": ...}` значит перестать быть
  SSE. Контракт при этом не теряется: полезная нагрузка кадра описана схемой
  `EntryRead`, и та же схема у ленты `GET /api/v1/journal`, где оболочка обычная.
  Клиенту, которому нужна оболочка, поток не нужен — ему нужна лента.

Список исключений живёт не только здесь: он объявлен кодом в
`app/api/contract.py` — ответ без тела в `BODYLESS_STATUS_CODES`, остальные маршрутами
в `ENVELOPE_EXEMPT`, — и сплошная проверка оболочки
(`tests/test_api_contract.py`) исключает маршруты по нему, а не по молчаливому пропуску.
Новое исключение поэтому нельзя завести, не назвав причину в коде, — и оно сразу же
разойдётся с этим разделом, что видно на ревизии.

### Ошибки — только на английском

Оболочка ошибки одна на весь проект: `code`, `message`, `details`.

- `code` — стабильный идентификатор в `snake_case`, часть контракта с фронтом. По нему клиент
  принимает решения; менять код существующей ошибки — ломающее изменение.
- `message` — **на английском языке**, одной фразой, без точки в конце. Это техническое
  сообщение для разработчика, агента и лога, а не текст для конечного пользователя: перевод и
  формулировки для интерфейса — задача фронтенда, который выбирает их по `code`.
- `details` — структурированные подробности, тоже на английском: какое поле, какое правило,
  какие значения допустимы. Именно отсюда агент понимает, как исправить запрос.

```json
{"error": {"code": "validation_error",
           "message": "Request validation failed",
           "details": {"fields": [{"field": "priority",
                                   "reason": "not_allowed",
                                   "allowed": ["low", "normal", "high", "critical"]}]}}}
```

Английский обязателен для всего служебного слоя: коды ошибок, сообщения, `details`, имена
полей, ключи очередей, статусы, типы записей, виды связей. Русский остаётся только
в пользовательских данных: названиях и разделах задач, записях дела, описаниях очередей.

### Типизация и генерация клиента

Схема OpenAPI — не побочный продукт, а поставляемый артефакт: фронтенд генерирует из неё
`openapi.ts` и получает типы запросов и ответов. Всё, что не описано типом, приходит на фронт
как `unknown` и убивает смысл генерации. Поэтому:

- **Каждый эндпоинт объявляет модель ответа.** Возврат `dict`, `Any`, `list[dict]` или голого
  `JSONResponse` без модели запрещён. Ошибочные ответы описываются через `responses` — фронт
  должен видеть форму ошибки, а не догадываться о ней.
- **Оболочка ответа — дженерик.** `data` обязан быть параметризован конкретной моделью, иначе в
  схеме окажется объект неизвестной формы, и вся типизация сведётся к `Record<string, unknown>`.
- **Стабильный `operation_id` у каждого маршрута**, в `snake_case`, уникальный. Генераторы
  клиента делают из него имена функций и типов, а автоматический идентификатор FastAPI
  (`read_task_api_v1_tasks__key__get`) даёт нечитаемый клиент и меняется при любой правке
  пути — фронт ломается на ровном месте. Задавать явно или единой функцией генерации на всё
  приложение.
- **Именованные схемы.** Модели объявляются классами с осмысленными именами; никаких inline-схем
  в сигнатуре — они попадают в документацию как `Body_create_task_...` и всплывают такими же
  именами в сгенерированном TypeScript.
- **Перечисления — строковые `Enum`**, а не свободные строки: в TypeScript это превращается в
  union допустимых значений и ловит опечатки на этапе сборки фронта.
- **Все параметры пути и запроса типизированы** через `Annotated`, с описаниями и значениями по
  умолчанию.
- **Различать «поле не передано» и «поле передано как null»** в схемах `PATCH` — на уровне
  типов, а не соглашения в голове.
- **Описания и примеры** у моделей и полей: они попадают и в Swagger, и в сгенерированный
  клиент, и заменяют собой половину переписки с фронтендом.

Свободная форма допускается только там, где типа не может быть в принципе, и каждое такое
место задокументировано в схеме: `details` ошибки и `payload` записи дела, форма которого
зависит от типа записи и описана отдельной моделью на каждый тип. Везде ещё — конкретный
тип, и список исключений стережёт тест `tests/test_openapi.py`, где новое исключение
заводится именем `Модель.поле`, а не именем поля.

Схема выгружается в файл одной командой в Docker и отдаётся фронтенду как есть, вместе
с проверкой, что схема собирается без дублей `operation_id` и без эндпоинтов без модели
ответа.

Базовые коды ошибок и их HTTP-статусы едины для всех эндпоинтов:

| HTTP | `code` | Когда |
|---|---|---|
| 400 | `bad_request` | Запрос синтаксически неверен |
| 401 | `unauthorized` | Нет токена или он недействителен |
| 403 | `permission_denied` | Действие запрещено |
| 404 | `not_found` | Маршрут или объект не найден на уровне транспорта |
| 404 | `<entity>_not_found` | Доменный объект не найден: `task_not_found`, `queue_not_found` |
| 405 | `method_not_allowed` | Метод не поддерживается маршрутом |
| 409 | `conflict` / `version_conflict` | Конфликт состояния или устаревшая версия |
| 422 | `validation_error` | Не прошла валидация тела запроса |
| 429 | `too_many_requests` | Превышен лимит запросов |
| 500 | `internal_error` | Непредвиденная ошибка; подробности только в лог, не в ответ |

Доменные коды (`transition_not_allowed`, `link_cycle_detected`, `summary_required`) строятся по той
же схеме и перечисляются в одном месте, а не заводятся по месту возникновения.

**Отдельно про FastAPI:** стандартные обработчики отдают собственные форматы — `{"detail": ...}`
для `HTTPException` и список ошибок Pydantic для `422`. Это прямое нарушение единой оболочки,
поэтому оба обработчика переопределены. Проверять это надо специально: ошибка
валидации приходит не из кода эндпоинта, а из фреймворка, и легко остаётся незамеченной до
момента, когда фронт получит ответ неизвестной ему формы.

## Работа с БД

- Все таблицы имеют `id` (UUID), `created_at`, `updated_at`.
- Внешние ключи обязательны, каскады выставляются осознанно.
- Индексы под реальные запросы: задачи по очереди и статусу, записи по задаче и номеру,
  сквозной номер записи для ленты, триграммы под подстроку в названии и описании.
- Каждое изменение схемы — миграция Alembic. Правка модели без миграции считается незавершённой работой.
- Границу транзакции держит вход в приложение: `get_session` (HTTP-запрос) и `session_scope`
  (MCP-сервер, скрипт демо-данных) коммитят при успешном завершении и откатывают при исключении.
  Сценарий в `services` коммитит сам только тогда, когда нужна промежуточная фиксация;
  тихо потерять изменения, забыв финальный коммит, при такой схеме невозможно.
- Репозиторий транзакциями не управляет никогда.

## Журнал

Отдельных событий нет: каждый факт в трекере — это запись дела (`CONCEPT.md`, 3.4 и 4.1).
Любое изменение состояния задачи обязано:

1. подшить служебную запись в дело **в той же транзакции**, что и само изменение;
2. не рассылать ничего синхронно из обработчика запроса: лента читается потребителями
   по сквозному номеру `seq`, а долгое ожидание новых записей строится на LISTEN/NOTIFY.

Тип служебной записи выводится из сценария в `services`, а не задаётся вызывающим кодом:
два независимых словаря имён разъехались бы, и новое действие молча осталось бы без записи.
Словарь типов записей живёт в `app/domain` одним перечислением и закрыт: новый тип записи —
это изменение концепции, а не задачи.

Записи неизменяемы на уровне кода и схемы: в репозиториях нет методов правки и удаления
записей, а сквозной номер выдаётся базой монотонно. Совпадение порядка `seq` с порядком
фиксации и чтение фактов перехода под блокировкой обеспечивает очередь изменений
`app/db/locks.py` (`lock_changes`): любой мутирующий сценарий берёт её первым делом.

## Именование

- Ключи очередей — латиница в верхнем регистре: `TRK`, `OPS`.
- Ключи задач — `КЛЮЧ-НОМЕР`, номер уникален внутри очереди и не переиспользуется.
- Статусы, типы записей, виды связей, наборы токена — зашитые идентификаторы snake_case
  латиницей. Отображаемые названия делает интерфейс.

## Тесты

- Каждая задача завершается тестами на свой слой. Без тестов задача не считается выполненной.
- Обязательный минимум: сценарии сервиса (успех и основные ошибки) + smoke-тест эндпоинтов.
- Тесты запускаются в контейнере и идут на реальной PostgreSQL, не на SQLite: проект опирается
  на JSONB и специфичные индексы, и расхождение диалектов сделает тесты бесполезными.
- В README должна быть одна команда, запускающая весь набор тестов в Docker.

## Документация

- Каждая папка описывается файлом `AGENTS.md` — что в ней лежит (файлы и подпапки одним уровнем,
  без раскрытия внутренностей вложенных папок). Создали или переместили файл — обновили `AGENTS.md`.
- Изменения контракта API отражаются в OpenAPI автоматически через схемы Pydantic; ручные описания
  дублировать не нужно.
- **Число, которое считается из кода, в документации не пишется.** «Сейчас исключений три»,
  «восемнадцать типов записей», «шесть признаков» — это факт на один день: следующая задача его
  меняет, а проза продолжает утверждать прежнее. Читатель принимает по числу решение, не ходя в
  код, — оно стоит в тексте как факт и ничем не помечено как протухшее. Вместо числа называется
  правило, по которому читатель посчитает сам: перечисление, словарь, файл, команда. Запрет узкий
  и касается того, что считается `grep`-ом прямо сейчас. Замер с датой и условиями
  (`notes/search.md`, замер на 40 000 задач) числом остаётся: это факт измерения, а не свойство
  кода. Остаётся и число при перечислении, стоящем тут же: оно врёт вместе со списком, который
  читатель видит рядом, а не отдельно от него.
- **Перечень, который отдаёт код, в прозу не переписывается.** Инструменты MCP, коды ошибок, поля
  схемы, типы записей — называется источник (`tools/list`, `ERRORS.md`, схема в `openapi.json`), а
  не копия. Копия отстаёт молча и в обе стороны: таблица инструментов в `README.md` разошлась с
  сервером на `close_task` и `resolve`, и заметила это ревизия, а не прогон. Там, где перечень
  обязан лежать в двух местах, их сводит сплошная проверка, сверяющая **множества**, а не
  «пропускающая известные»: образец — `app/api/contract.py` (`ENVELOPE_EXEMPT`) и
  `tests/test_api_contract.py`.

## Коммиты

Формат сообщения — Conventional Commits:

```
<тип>(<область>): краткое описание в повелительном наклонении

Тело: зачем это сделано и что важно знать читателю. Необязательно для
тривиальных изменений.
```

Типы:

| Тип | Когда |
|---|---|
| `feat` | новая функциональность (любое «добавил возможность») |
| `fix` | исправление ошибки |
| `docs` | документация, ТЗ, README, карты `AGENTS.md` |
| `refactor` | изменение кода без изменения поведения |
| `test` | тесты и тестовая инфраструктура |
| `build` | зависимости, Dockerfile, Compose, сборка |
| `chore` | служебное: конфиги, `.gitignore`, скрипты |
| `perf` | оптимизация производительности |
| `ci` | конвейеры автоматической проверки |

Область — блок или модуль: `tasks`, `queues`, `participants`, `case`, `links`, `search`,
`journal`, `mcp`, `api`, `db`, `docker`. Область необязательна, если изменение сквозное.

Примеры:

```
feat(case): сводка обязательна перед выходом из in_progress
fix(tasks): частичное обновление больше не затирает непереданные поля
build(docker): раздельные образы для разработки и продакшена
docs(tasks): требование запуска в Docker во всех задачах
```

Правила:

- Добавление нового — это `feat`, а не отдельный тип `add`: синонимы размывают историю.
- Один коммит — одно осмысленное изменение. Задача обычно разбивается на несколько
  коммитов, а не сваливается в один.
- Изменённые `AGENTS.md` идут в том же коммите, что и изменения, которые они описывают.
- Описание — о том, что изменилось для системы, а не «правки по задаче 07».
- Коммит делается агентом самостоятельно по завершении работы (шаг 7 протокола), а не по
  отдельной просьбе.

## Слияние ветки задачи в main

Ветку задачи сливает не её исполнитель, а тот, кто ведёт слияния: в соседних деревьях
`git worktree` в это время идут другие задачи, и `main` двигают в одном месте.

**Зелёные родители слияния не означают зелёного результата.** Каждая ветка прогоняла
набор на своём дереве, а базой для следующего агента становится результат. Ветка A
переименовала символ, ветка B в это же время назвала его в заметке или в докстроке — git
сведёт их без конфликта, файлы-то разные, и красным окажется `main`, которого не прогонял
никто. Это не теория: две зелёные ветки этого репозитория дали `2 failed` сразу после
чистого слияния (`TRK-45`).

Поэтому слияние делается одной командой, из того дерева, где лежит `main`:

```bash
scripts/merge-task-branch.sh task/TRK-45 -m "merge(область): что изменилось (TRK-45)"
```

Она сливает без коммита (`--no-ff --no-commit`), прогоняет на результате весь набор в
контейнере и коммитит слияние **только на зелёном**, поставив в сообщение строку
`Merge-verified:` с исходом прогона. Красный набор — `git merge --abort`, и `main`
остаётся прежним: расхождение видно до того, как стало базой. Конфликты скрипт оставляет
человеку: разобрать, добавить в индекс, довести слияние тем же скриптом с `--continue`.

Исход слияния называется в деле задачи, а не подразумевается:

- зелёное — запись `artifact` с ключом коммита слияния и строкой прогона;
- красное — запись `remark` в дело той задачи, чья ветка не сошлась с базой: ветка не
  слита, и разбирается это по правилам замечаний, а не молчаливой правкой `main`.

Слияние руками (`git merge`) не запрещено, но не остаётся незаметным: у такого коммита нет
строки `Merge-verified:`, и следующий запуск скрипта называет его перед тем, как сделать
своё слияние. Вписать строку задним числом нельзя — она означает прогон, а не намерение.

## Протокол выполнения задачи

Обязателен для любого агента, берущего задачу репозитория. Шаги идут по порядку, ни один
не пропускается.

### 1. Подготовка

- Прочитать `CONCEPT.md` и этот файл целиком.
- Прочитать свою задачу целиком, включая разделы «Контекст» и «Ограничения» — там лежат
  ловушки, стоившие времени при проектировании.
- Прочитать заметки в `notes/`, относящиеся к затрагиваемым областям. Это чужой опыт по этому
  же проекту: он экономит часы.
- Проверить, что задачи-зависимости действительно выполнены — посмотреть код, а не поверить
  статусу связи.

### 2. Реализация

Реализовать объём задачи, соблюдая слои и правила из этого файла.

### 3. Тесты и проверка работы

Тесты:

- Написать тесты на свой слой и прогнать **весь** набор тестов в Docker, а не только новые:
  задача считается выполненной, когда зелёный весь проект, а не своя папка.
- Падающий тест — это результат работы, а не помеха. Подгонять тест под текущее поведение,
  ослаблять проверку или помечать тест пропущенным, чтобы «стало зелено», запрещено.
- Если сломался чужой тест — разобраться, чьё поведение неверно, и починить причину.

Живая проверка — обязательна, зелёных тестов недостаточно:

- Поднять дев-контур в Docker с нуля, применить миграции, дождаться готовности сервисов.
- Своими руками выполнить основной сценарий задачи: дёрнуть добавленные эндпоинты, вызвать
  добавленные инструменты MCP, проверить, что фоновый процесс делает то, что должен.
- Посмотреть логи контейнеров: молчаливые ошибки, предупреждения ORM о ленивой загрузке и
  повторяющиеся запросы видны только там.
- Проверить, что контур поднимается **с нуля** (без старого тома с данными): тесты идут на
  готовой схеме и не заметят сломанную миграцию или неверный порядок старта сервисов.

Тесты проверяют логику, живой прогон — что система вообще работает как система. Каждое из двух
регулярно ловит то, чего не видит другое.

### 4. Зафиксировать находки

Всё, что выяснилось дорогой ценой, записывается в `notes/` (формат — раздел ниже). Это
обязательный шаг, а не пожелание: знание, оставшееся только в отчёте, потеряно для следующего
агента.

Сюда же относятся особенности собственной реализации, которые обязаны учитывать другие: см.
раздел «Неявного поведения быть не должно». Локальная особенность объясняется комментарием в
коде, сквозная — заметкой.

### 5. Обновить карты

Обновить `AGENTS.md` всех затронутых папок, создать карты для новых папок.

### 6. Закрыть задачу

Закрытие идёт в трекере и по дисциплине скила, который сервер раздаёт сам: сводка,
вердикт по каждой обзорной проверке, `close_task`. Пересказывать её здесь нечем —
агент получает этот текст вместе с инструментами.

Со стороны репозитория остаётся одно: сделанное не должно жить только в деле. Находки —
в `notes/`, карты — в `AGENTS.md`, а обнаруженная работа, не влезающая в твою задачу, —
отдельной задачей в трекере, а не строкой в отчёте.

### 7. Закоммитить

Если работа доведена до конца и проблем не осталось — **сделать коммит самостоятельно**, не
дожидаясь просьбы. «Проблем не осталось» означает всё сразу:

- весь набор тестов зелёный;
- живая проверка из шага 3 прошла;
- объём задачи закрыт полностью или закрытая часть самодостаточна и ничего не ломает;
- не осталось отладочного мусора, закомментированного кода и временных файлов.

Правила коммита:

- Добавлять в индекс **только явно перечисленные свои файлы**. Запрещены и `git add -A`, и
  `git add <папка>`: в репозитории параллельно работает другой агент, и его недоделанная работа
  уедет в чужой коммит вместе с папкой. Перечислять файлы поимённо.
- Перед коммитом просмотреть `git status` и `git diff --staged`: в индекс не должны попасть
  `.env` с реальными доступами, дампы, файлы IDE и чужие изменения.
- Разбивать работу на осмысленные коммиты по правилам раздела «Коммиты», а не сваливать задачу
  в один. Правки ТЗ, заметки и карты идут вместе с кодом, который они описывают.
- Не пушить и не создавать ветки без явной просьбы.
- Слияние своей ветки в `main` в шаг не входит: это отдельная работа со своей проверкой, раздел «Слияние ветки задачи в main».

Когда коммит делать **нельзя**: тесты падают, живая проверка не прошла, работа брошена
посередине, принято спорное решение, требующее подтверждения человека. В этом случае оставить
изменения в рабочем дереве и объяснить ситуацию в отчёте — незакоммиченное состояние честнее,
чем коммит, маскирующий проблему.

### 8. Погасить всё, что запускал

Работа заканчивается чистой машиной. Перед отчётом остановить всё, что было поднято ради задачи:

- контуры Docker (дев и прод), поднятые для проверки, — вместе с временными томами, если они
  создавались специально под проверку;
- фоновые процессы: серверы, воркеры, планировщики, режимы слежения за файлами, туннели;
- всё, что занимает порты проекта.

Проверить, что не осталось висящего: `docker ps` пуст по контейнерам задачи, фоновых заданий
нет, порты свободны.

Почему это не мелочь: висящий контейнер продолжает держать порт и том с данными. Следующий
агент поднимет свой контур, получит «порт занят» или, хуже, молча подключится к чужой базе со
старой схемой и полдня будет ловить необъяснимые ошибки миграций.

Чего **не** трогать:

- процессы и контейнеры, поднятые не тобой и существовавшие до начала работы: в репозитории
  может параллельно работать другой агент, и `docker compose down` уронит его проверку;
- то, что пользователь явно просил оставить запущенным.

Если что-то оставлено намеренно — сказать об этом в отчёте: что именно работает и как это
погасить.

### 9. Проверить готовность к передаче

После задачи пользователь закрывает сессию с тобой и открывает новую с другим агентом.
**Твой контекст при этом исчезает целиком:** новый агент не знает ни твоих рассуждений, ни
отложенных мелочей, ни того, что «осталось поправить в одном месте». Всё, что не попало в файлы,
потеряно безвозвратно.

Поэтому перед отчётом пройти по списку и убедиться, что передавать можно:

- весь набор тестов зелёный, живая проверка пройдена;
- работа закоммичена; если что-то осталось незакоммиченным — это осознанное решение, а не забытое;
- в рабочем дереве нет твоего мусора: отладочных файлов, черновиков, временных скриптов;
- всё знание вынесено в файлы: находки — в `notes/`, особенности реализации — в комментарии,
  новые требования — в задачи, прогресс — сводкой в деле;
- нет незаписанных «надо не забыть»: любая отложенная мелочь либо сделана, либо стала пунктом
  задачи, либо названа в отчёте;
- запущенные процессы погашены (шаг 8);
- понятно, какую задачу можно брать следующей и не блокирует ли её что-то.

По итогу дать в отчёте **однозначный вердикт**, а не оставлять пользователя гадать:

- «Задача закрыта полностью, сессию можно закрывать. Следующая задача — 06» — либо
- «Закрывать рано: не сделано X, потому что Y» — с конкретным перечнем оставшегося.

Отдельно предупредить, если перед следующей задачей нужно действие человека: выдать доступ,
поднять внешний сервис, принять решение, применить миграцию на своей машине. Новый агент об
этом не догадается, а упрётся в него через полчаса работы.

### 10. Отчитаться пользователю

В финальном сообщении обязательно:

- что сделано;
- **что не реализовано** относительно исходного текста задачи и последующих корректировок — с
  причиной: не успел, оказалось невозможным, противоречит архитектуре, требует решения
  пользователя. Этот пункт не пропускается никогда: молчание о невыполненном читается как
  «сделано полностью» и всплывёт в самый неудобный момент;
- какие решения приняты самостоятельно и почему;
- какие чужие задачи дополнены и какие новые заведены — с причиной;
- что осталось запущенным, если что-то оставлено намеренно;
- что стоит перепроверить человеку;
- вердикт из шага 9: можно ли закрывать сессию и какую задачу брать следующей.

Если по ходу выясняется, что задача противоречит уже написанному коду или концепции — не
изобретать обходной путь молча, а сформулировать проблему и предложить решение.

## Чужие задачи и новые

Агент видит проект глубже, чем тот, кто нарезал задачи заранее. Поэтому он **обязан**
дописывать требования в чужие задачи и заводить новые, когда обнаруживает необходимость:
знание, оставшееся только в голове или в отчёте, до исполнителя не дойдёт. Как это
сделать — дело трекера и скила; здесь только границы, которые трекер не проверяет.

- **Нельзя перекладывать в другую задачу свою работу.** Если пункт входит в твой объём — он
  делается сейчас, а не переносится «туда, где логичнее». Это главный способ испортить механизм.
- Не расширять чужие задачи пожеланиями «хорошо бы ещё»: дописывается то, без чего задача даст
  неверный результат или сломает уже сделанное. Чужой объём не переписывается и не сокращается.
- Перед заведением новой проверить, что такого пункта нет в существующих: дубль хуже пропуска,
  потому что двое сделают одно и то же по-разному.
- `CONCEPT.md` и `CONVENTIONS.md` — правятся иначе: уточнить факт, вытекающий из реализации,
  можно; менять принятое решение — только по согласованию с пользователем, вынеся вопрос в отчёт.
- Все правки чужих задач и новые задачи перечисляются в отчёте: что изменено, что создано, почему.

## Неявного поведения быть не должно

Код читают чаще, чем пишут, и читают его агенты, у которых нет твоего контекста. Поэтому
поведение, о котором нужно догадаться, считается дефектом — наравне с ошибкой. Если при
реализации возникает нюанс, который вызывающая сторона обязана учитывать, действовать надо в
таком порядке.

**1. Убрать неявность.** Лучший вариант — переписать так, чтобы учитывать было нечего:
выразить требование в сигнатуре и типах, бросить исключение вместо тихого значения по
умолчанию, разделить метод с побочным эффектом на два явных. Комментарий — это признание, что
сделать очевидным не получилось, а не первый выбор.

**2. Если убрать нельзя — комментарий рядом с кодом.** Он объясняет **почему** так сделано и
что произойдёт при нарушении, а не пересказывает, что делает строка. Комментарий живёт в том же
файле: особенность, описанная где-то далеко, до читателя не дойдёт.

**3. Если особенность выходит за пределы файла — запись в `notes/`.** Всё, что должны учитывать
авторы других модулей и следующих задач, идёт в заметки по своей области. При необходимости —
дополнить пункт в затронутой задаче по правилам раздела «Правка чужих задач и создание новых».

Что считается неявным поведением и требует одного из трёх действий выше:

- метод меняет что-то помимо заявленного в имени: сохраняет, шлёт событие, чистит кеш;
- порядок вызовов важен, но ниоткуда не следует;
- у вызова есть невыраженное требование: открытая транзакция, предварительная загрузка связей,
  выполненная миграция;
- ошибка проглатывается и подменяется значением по умолчанию — молчаливые сбои запрещены
  отдельно: если что-то пошло не так, это видно в ответе или в логе;
- результат зависит от глобального состояния, времени или порядка выполнения;
- есть неочевидное ограничение: лимит, таймаут, максимальная глубина, потолок размера выборки;
- код выглядит странно, но так и задумано — без пометки следующий агент «починит» его.

Обратная сторона правила: комментарии пишутся там, где есть неочевидность, а не над каждой
строкой. Комментарий, пересказывающий код, устаревает первым и учит не доверять остальным.

## Заметки: находки, грабли, особенности

Папка `notes/`, один файл на область: `docker.md`, `db.md`, `api.md`, `mcp.md`,
`journal.md`, `testing.md`, `python.md` и подобные.

Заметки не чистятся, пока жив код, который они описывают: находка не устаревает от того,
что о ней забыли, и вычёркивать её «за ненадобностью» нельзя. Но при сносе механики её
заметки удаляются **вместе с кодом, той же задачей**. Запись, ведущая в удалённый файл,
хуже отсутствующей: следующий агент читает её как действующую и полдня ищет описанное
поведение в коде, где его нет.

Отсюда три правила на снос:

- Урок, переживший механику, переносится в живую заметку с указателем на живой код, а не
  остаётся сиротой. Перед удалением записи проверить, что её урок есть где-то ещё или что
  для нового кода он смысла не имеет.
- Заметки, оставленные намеренно как материал для возможного возврата, помечаются
  баннером в первых строках файла: механика снесена, задача такая-то, по записям не
  судить о текущем поведении. Такой файл целиком — история, и вперемешку с живыми
  записями он не лежит.
- Указатели «Где:» живых заметок обязаны вести в существующие файлы и символы. Это
  стережёт `tests/test_notes.py`, а не вычитка.

**Запись, опровергнутая позже, заменяется той, что её опровергла.** Это единственное исключение
из «заметки только дополняются», и оно узкое: речь о паре, где младшая запись отменяет вывод
старшей про тот же код — обычно у обеих и указатель «Где:» один. Читатель платит за обе, а правды
в них на одну, и какая действует, он узнаёт, только дочитав вторую. Урок отменённой записи
переезжает в ту, что её заменяет: почему очевидное решение не подошло и чем это кончилось — и
есть находка, и терять её ради короткого файла нельзя. Отменённая запись удаляется той же
правкой, которой урок переехал: пара, оставленная «на потом», остаётся навсегда. Всё остальное
по-прежнему дописывается — запись, которая уточняет или расширяет соседнюю, не опровержение.

Формат записи:

```markdown
## Краткое название находки

**Что:** факт одной фразой.
**Почему важно:** что сломается или сколько времени потеряет тот, кто этого не знает.
**Как правильно:** конкретное действие или пример.
**Где:** файл или место в коде, если применимо.
```

Что писать:

- поведение библиотеки, которое пришлось выяснять опытным путём;
- неочевидное решение и причину, по которой очевидное не подошло;
- ограничение окружения (версии, Docker, PostgreSQL, MCP-клиент);
- место, которое выглядит странно, но так и задумано — чтобы следующий не «починил» его.

Что не писать: пересказ документации библиотек, описание собственного кода (для этого есть код
и карты), историю своих попыток, планы на будущее.
