# Сквозные соглашения проекта

Этот файл обязателен к прочтению перед выполнением любой задачи из `tasks/`.
Он описывает правила, единые для всего проекта. Задача описывает *что* делать,
соглашения — *как*.

## Стек

- Python 3.14, FastAPI, Pydantic v2.
- PostgreSQL, SQLAlchemy 2 (async), Alembic.
- pytest + pytest-asyncio + httpx для тестов.
- Docker и Docker Compose — обязательная и единственная поддерживаемая среда запуска.

Новые зависимости добавляются только если без них задача не решается разумным объёмом кода.
Каждая добавленная зависимость упоминается в отчёте о выполнении задачи.

## Запуск: всё работает в Docker

Проект запускается только в контейнерах. Установка Python и зависимостей на хост-машину не
поддерживается и не документируется: сервер, миграции, тесты и линтер выполняются внутри
контейнера. Требование сквозное — задача, после которой что-то запускается только «локально
руками», считается невыполненной.

Ведутся **два отдельных Dockerfile**:

| Файл | Назначение | Что делает |
|---|---|---|
| `docker/Dockerfile.dev` | разработка | Код монтируется томом, автоперезапуск при изменениях, установлены dev-зависимости, подробные логи |
| `docker/Dockerfile.prod` | продакшен | Многостадийная сборка, только рантайм-зависимости, код скопирован внутрь образа, запуск от непривилегированного пользователя, без автоперезапуска |

И два файла Compose: `docker-compose.yml` (разработка, используется по умолчанию) и
`docker-compose.prod.yml` (продакшен).

Требования к обоим контурам:

- Один и тот же базовый образ Python и один и тот же набор переменных окружения — расхождение
  сред не должно быть причиной «на дев работает, на проде нет».
- Все процессы приложения — отдельные сервисы Compose из одного образа с разными командами:
  HTTP-сервер, воркер событий, планировщик автодействий, MCP-сервер.
- Проверка здоровья у сервиса приложения и у БД; приложение стартует после готовности БД.
- Данные БД — в именованном томе, чтобы перезапуск не стирал состояние.
- Прод-образ не содержит инструментов сборки, тестов и dev-зависимостей.
- Миграции применяются явным шагом (отдельная команда или init-контейнер), а не втихую при
  старте нескольких реплик: параллельный запуск миграций из трёх контейнеров даёт гонку.

Каждая задача, добавляющая новый процесс (воркер, планировщик, MCP-сервер), обязана добавить
его в оба файла Compose и описать в README.

## Структура кода

Слоистая, границы жёсткие:

```
app/
  api/          — HTTP-слой: роутеры, схемы запросов и ответов, обработка ошибок
  mcp/          — MCP-сервер: инструменты, ресурсы, нотификации
  domain/       — доменные модели и бизнес-правила, без знания об HTTP и ORM
  services/     — сценарии: оркестрация домена, транзакции, публикация событий
  db/           — модели SQLAlchemy, репозитории, миграции
  automation/   — движок автоматики и правила
  core/         — конфиг, зависимости, логирование, общие утилиты
```

Правила направления зависимостей:

- `api` и `mcp` зависят от `services`, но не друг от друга.
- `services` зависит от `domain` и `db`.
- `domain` не импортирует ничего из `api`, `db`, `mcp`.
- Любая мутация данных проходит через `services`. Роутер, который сам ходит в БД и меняет
  состояние — ошибка: тогда та же операция из MCP пойдёт мимо событий и автоматики.

Один сценарий — одна функция сервиса, вызываемая и из REST, и из MCP. Это главное требование
проекта: **бизнес-логика не дублируется между интерфейсами.**

## API

- Префикс `/api/v1`.
- Ресурсы во множественном числе: `/api/v1/issues`, `/api/v1/queues/{key}`.
- Задачи адресуются ключом (`TRK-123`), не числовым id.
- Курсорная пагинация: запрос принимает `cursor` и `limit`, ответ возвращает `items` и `next_cursor`.
- Единый формат ошибки:

```json
{"error": {"code": "issue_not_found", "message": "Задача TRK-123 не найдена", "details": {}}}
```

- Коды ошибок — стабильные строковые идентификаторы в snake_case, они часть контракта с фронтом.
- Даты в ISO 8601 с таймзоной, UTC.
- Частичное обновление — `PATCH` с явно переданными полями; отличать «поле не передано» от
  «поле передано как null» обязательно.

## Работа с БД

- Все таблицы имеют `id` (UUID), `created_at`, `updated_at`.
- Внешние ключи обязательны, каскады выставляются осознанно.
- Индексы под реальные запросы: фильтрация задач по очереди, статусу, исполнителю, дедлайну;
  GIN-индекс по `values` для кастомных полей.
- Каждое изменение схемы — миграция Alembic. Правка модели без миграции считается незавершённой работой.
- Транзакция открывается на уровне сценария в `services`, а не внутри репозитория.

## События

Любое изменение состояния, значимое для пользователя, обязано:

1. записаться в журнал изменений,
2. положить событие в outbox **в той же транзакции**,
3. не рассылать ничего синхронно из обработчика запроса.

Событие имеет стабильный тип (`issue.created`, `issue.field_changed`, `issue.status_changed`,
`comment.created`, ...), идентификатор актора-инициатора и полезную нагрузку с «было/стало».

## Именование

- Ключи очередей — латиница в верхнем регистре: `TRK`, `OPS`.
- Ключи задач — `КЛЮЧ-НОМЕР`, номер уникален внутри очереди и не переиспользуется.
- Ключи полей, статусов, типов — snake_case латиницей. Отображаемые названия — отдельное поле,
  на русском.

## Тесты

- Каждая задача завершается тестами на свой слой. Без тестов задача не считается выполненной.
- Обязательный минимум: сценарии сервиса (успех и основные ошибки) + smoke-тест эндпоинтов.
- Тесты запускаются в контейнере и идут на реальной PostgreSQL, не на SQLite: проект опирается
  на JSONB и специфичные индексы, и расхождение диалектов сделает тесты бесполезными.
- В README должна быть одна команда, запускающая весь набор тестов в Docker.

## Документация

- Каждая папка описывается файлом `AGENTS.md` — что в ней лежит (файлы и подпапки одним уровнем,
  без раскрытия внутренностей вложенных папок). Создали или переместили файл — обновили `AGENTS.md`.
- Изменения контракта API отражаются в OpenAPI автоматически через схемы Pydantic; ручные описания
  дублировать не нужно.

## Коммиты

Формат сообщения — Conventional Commits:

```
<тип>(<область>): краткое описание в повелительном наклонении

Тело: зачем это сделано и что важно знать читателю. Необязательно для
тривиальных изменений.
```

Типы:

| Тип | Когда |
|---|---|
| `feat` | новая функциональность (любое «добавил возможность») |
| `fix` | исправление ошибки |
| `docs` | документация, ТЗ, README, карты `AGENTS.md` |
| `refactor` | изменение кода без изменения поведения |
| `test` | тесты и тестовая инфраструктура |
| `build` | зависимости, Dockerfile, Compose, сборка |
| `chore` | служебное: конфиги, `.gitignore`, скрипты |
| `perf` | оптимизация производительности |
| `ci` | конвейеры автоматической проверки |

Область — блок или модуль: `issues`, `queues`, `workflow`, `fields`, `links`, `automation`,
`notifications`, `mcp`, `api`, `db`, `docker`. Область необязательна, если изменение сквозное.

Примеры:

```
feat(workflow): конструирование собственных процессов через API и MCP
fix(issues): частичное обновление больше не затирает непереданные поля
build(docker): раздельные образы для разработки и продакшена
docs(tasks): требование запуска в Docker во всех задачах
```

Правила:

- Добавление нового — это `feat`, а не отдельный тип `add`: синонимы размывают историю.
- Один коммит — одно осмысленное изменение. Задача из `tasks/` обычно разбивается на несколько
  коммитов, а не сваливается в один.
- Изменённые `AGENTS.md` идут в том же коммите, что и изменения, которые они описывают.
- Описание — о том, что изменилось для системы, а не «правки по задаче 07».

## Протокол выполнения задачи

Обязателен для любого агента, берущего файл из `tasks/`. Шаги идут по порядку, ни один не
пропускается.

### 1. Подготовка

- Прочитать `CONCEPT.md` и этот файл целиком.
- Прочитать файл своей задачи, включая раздел «Что учесть» — там лежат ловушки, стоившие
  времени при проектировании.
- Прочитать заметки в `notes/`, относящиеся к затрагиваемым областям. Это чужой опыт по этому
  же проекту: он экономит часы.
- Проверить, что задачи-зависимости действительно выполнены — посмотреть код, а не поверить
  списку в `ROADMAP.md`.

### 2. Реализация

Реализовать объём задачи, соблюдая слои и правила из этого файла.

### 3. Тесты

- Написать тесты на свой слой и прогнать **весь** набор тестов в Docker, а не только новые:
  задача считается выполненной, когда зелёный весь проект, а не своя папка.
- Падающий тест — это результат работы, а не помеха. Подгонять тест под текущее поведение,
  ослаблять проверку или помечать тест пропущенным, чтобы «стало зелено», запрещено.
- Если сломался чужой тест — разобраться, чьё поведение неверно, и починить причину.

### 4. Зафиксировать находки

Всё, что выяснилось дорогой ценой, записывается в `notes/` (формат — раздел ниже). Это
обязательный шаг, а не пожелание: знание, оставшееся только в отчёте, потеряно для следующего
агента.

### 5. Обновить карты

Обновить `AGENTS.md` всех затронутых папок, создать карты для новых папок.

### 6. Закрыть ТЗ

- **Задача выполнена полностью** — удалить её файл из `tasks/`, убрать строку из
  `tasks/AGENTS.md`, отметить задачу выполненной в `ROADMAP.md`.
- **Задача выполнена частично** — удалить из файла реализованные пункты, оставив только
  невыполненное. В начале файла оставить короткую шапку «Уже реализовано» на три-пять строк:
  без неё следующий агент получит огрызок без контекста и заново переделает работающее.
  В `ROADMAP.md` отметить задачу как частично выполненную.
- Изменения ТЗ идут тем же коммитом, что и код, который их закрывает.

Смысл механики: `tasks/` — очередь оставшейся работы, `notes/` — накопленное знание,
`ROADMAP.md` — прогресс. Прочитав их, можно понять состояние проекта, не читая код.

### 7. Отчитаться пользователю

В финальном сообщении обязательно:

- что сделано;
- **что не реализовано** относительно исходного текста задачи и последующих корректировок — с
  причиной: не успел, оказалось невозможным, противоречит архитектуре, требует решения
  пользователя. Этот пункт не пропускается никогда: молчание о невыполненном читается как
  «сделано полностью» и всплывёт в самый неудобный момент;
- какие решения приняты самостоятельно и почему;
- что стоит перепроверить человеку.

Если по ходу выясняется, что задача противоречит уже написанному коду или концепции — не
изобретать обходной путь молча, а сформулировать проблему и предложить решение.

## Заметки: находки, грабли, особенности

Папка `notes/`, один файл на область: `docker.md`, `db.md`, `api.md`, `mcp.md`,
`automation.md`, `testing.md`, `python.md` и подобные. Заметки только копятся и никогда не
чистятся — в отличие от файлов задач.

Формат записи:

```markdown
## Краткое название находки

**Что:** факт одной фразой.
**Почему важно:** что сломается или сколько времени потеряет тот, кто этого не знает.
**Как правильно:** конкретное действие или пример.
**Где:** файл или место в коде, если применимо.
```

Что писать:

- поведение библиотеки, которое пришлось выяснять опытным путём;
- неочевидное решение и причину, по которой очевидное не подошло;
- ограничение окружения (версии, Docker, PostgreSQL, MCP-клиент);
- место, которое выглядит странно, но так и задумано — чтобы следующий не «починил» его.

Что не писать: пересказ документации библиотек, описание собственного кода (для этого есть код
и карты), историю своих попыток, планы на будущее.
