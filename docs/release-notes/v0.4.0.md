# Casefile v0.4.0

Casefile is the task tracker your AI agents keep for each other. AI agents forget
everything between sessions; Casefile gives every task a case file — decisions, failed
attempts, findings, open questions — so the next agent picks up exactly where the last
one stopped. You watch a live board and answer their questions.

This release turns the queue into a **project**: the same grouping of tasks, now with a
short description that travels with every task, reference attributes with a history, a
case file of its own, and an archive instead of deletion. The rename is a clean cut — the
word `queue` is gone from REST, MCP and the query language, with no aliases. Read
**Breaking changes** before you update anything that talks to the tracker besides the
board.

## Install

**macOS / Linux**

```bash
curl -fsSL https://raw.githubusercontent.com/azimov777/casefile/main/install.sh | sh
```

**Windows (PowerShell)**

```powershell
irm https://raw.githubusercontent.com/azimov777/casefile/main/install.ps1 | iex
```

All you need is Docker. The board opens at `http://localhost:8080`, and the installer
prints the one command that connects your agent. An installation on v0.3.x updates itself
to this release within about an hour, or at the next Docker start — see **Upgrade notes**.

## What's new

- **Projects instead of queues.** A project answers "what are these tasks about" — a
  codebase, an area — exactly as a queue did; the name changed because agents read
  `list_queues` as "where to take the next job from", a dispatching meaning the tracker
  rejects. Keys stay: `TRK-42` and `TRK-42#3` point where they pointed before.
- **The project's description rides with every task.** A project description is now at
  most 320 characters, and `get_task` (and `GET /api/v1/tasks/{task_key}`) carries it in
  the task's `project` together with `archived_at` — an agent learns what the project is
  from the same call that hands it the task. Search rows do not carry it. A longer text
  is refused with `422 project_description_too_long`.
- **A project has a case file of its own.** Decisions, findings, artifacts and notes that
  concern the project rather than one task go into the project's case: MCP
  `add_project_entry` and `read_project_entries`, REST
  `POST`/`GET /api/v1/projects/{project_key}/entries` and
  `GET /api/v1/projects/{project_key}/entries/{entry_no}`. Entries are numbered inside the
  project and referenced as `TRK#7`; they are append-only like task entries. The project's
  case also holds the history of its card: `created`, `field_changed` on title and
  description edits, and the attribute and archive entries below. `get_project` returns
  the project's case index. Project entries appear in the journal and in `wait_journal`
  with `project_key` set and `task_key` empty.
- **Project attributes, with a history and a reason.** Reference facts of a project as
  "name → value" — its repository, main branch, the docs to read first. MCP
  `set_attribute` creates or changes one (the tracker files `attribute_created` or
  `attribute_changed`), `remove_attribute` removes one (`attribute_removed` with the last
  value); REST `PUT /api/v1/projects/{project_key}/attributes/{attribute_name}` and
  `POST …/attributes/{attribute_name}/remove`. Changing and removing require a `reason`.
  Names match `^[A-Za-z0-9_-]{1,64}$` and are unique per project regardless of case;
  values are plain text up to 1,000 characters. `get_project` and
  `GET /api/v1/projects/{project_key}` return the current values, and the `attribute`
  parameter of `read_project_entries` / `GET …/entries` returns one attribute's history
  alone. The tracker never filters tasks by attributes or acts on them. Any `task` token
  reads projects and writes project entries and attributes.
- **Archive instead of delete.** `archive_project` and `restore_project` (REST
  `POST /api/v1/projects/{project_key}/archive` and `…/restore`, `main` token) take a
  required `reason` and file `archived` / `restored` in the project's case. An archived
  project is frozen as it is: no new tasks, no entries in its case or its tasks' cases, no
  transitions, card or attribute edits, no new links touching its tasks — all refused
  with `409 project_archived`. The one write that still goes through is `unlink`, so a
  task in a live project can drop a blocker or a child left in the archive. Reading works
  as usual by direct address. An archived project is hidden by default: from
  `list_projects` and `GET /api/v1/projects` and from `bootstrap` (ask with
  `include_archived`), from `search_tasks` unless the filter names the project, the task
  key or the parent, and from the questions and remarks inbox and its counter. After
  `restore` the tasks continue from where they stopped.
- **The board follows.** A project screen shows the card, the attributes with their
  history and the project's case, live; from it a person with a `main` token creates a
  project, edits its title and description (with the characters left out of 320),
  sets and removes attributes with a reason, adds notes, archives and restores.
  "Archived projects" in the panel brings archived ones back into view; a task of an
  archived project shows no actions. Addresses use `?project=`. The **Connect an agent**
  screen no longer offers a command to install the skill. The Access and People dialogs
  and the Composer's discard confirmation return focus to the button that opened them,
  and the project picker on the questions page no longer pushes the page sideways on a
  narrow screen.
- **MCP speaks for itself, in English.** The server's `instructions` (under 2,048
  characters) and every tool's description and argument descriptions are now in English
  and describe what the call does, including its side effects: `create_task` with a
  parent files `link_added` in the parent's case and returns that entry's number as
  `parent_entry`; `transition` and `close_task` say when they clear `blocked` on other
  tasks. The rules the old skill held now arrive with the connection and with each tool.
- **Migration archives from v0.3 still import.** An archive taken from a v0.3
  installation (`docs/moving.md`) is accepted by a v0.4.0 installation: its queues come
  in as projects under the same rules as the upgrade migration below.

## Breaking changes

These change the REST and MCP contracts. The board already follows them; anything else
that reads or writes the tracker needs the changes below. Task keys (`TRK-42`) and entry
references (`TRK-42#3`) are unchanged.

1. **REST: `/api/v1/queues` became `/api/v1/projects`.**
   `GET`/`POST /api/v1/queues` → `GET`/`POST /api/v1/projects`;
   `GET`/`PATCH /api/v1/queues/{queue_key}` → `GET`/`PATCH /api/v1/projects/{project_key}`.
   The `queue` query parameter of `GET /api/v1/tasks`, `/questions`, `/remarks`,
   `/journal` and `/journal/stream` is now `project`; the `queue` field of a task
   (create body, card, search row) is now `project`; `bootstrap.queues` is now
   `bootstrap.projects`. The old paths answer `404`, the old parameter
   `422 validation_error`. `GET /api/v1/projects` and `/bootstrap` now leave archived
   projects out unless `include_archived=true`; `GET /api/v1/projects/{project_key}`
   returns the project with its `attributes` and `archived_at`. New paths:
   `/api/v1/projects/{project_key}/entries` (and `/{entry_no}`),
   `/attributes/{attribute_name}` (and `/remove`), `/archive`, `/restore`.
2. **MCP tools renamed, added and removed.** Renamed: `list_queues` → `list_projects`,
   `get_queue` → `get_project`, `create_queue` → `create_project`, `update_queue` →
   `update_project`; the `queue` argument of `create_task`, `search_tasks` and
   `wait_journal` is now `project`. New: `read_project_entries`, `add_project_entry`,
   `set_attribute`, `remove_attribute`, `archive_project`, `restore_project` — 29 tools
   in all. Removed: the `tracker-discipline` prompt (`prompts/list` is now empty) and the
   `tracker-agent` skill the server used to serve (`TRK-146`).
3. **Query language: `queue:` became `project:`.** `project: TRK and status: open`;
   `queue:` now answers `422 search_field_unknown`. In `fields`, ask for `project`.
   Tasks of an archived project are found only when the query names the project
   (`project:`), the task (`key:`) or the parent (`parent:`).
4. **Error codes.** `queue_not_found` → `project_not_found` (404), `queue_key_taken` →
   `project_key_taken` (409), `invalid_queue_key` → `invalid_project_key` (422); the
   `reason` in `details` of `invalid_task_key` is `project_key_mismatch` instead of
   `queue_key_mismatch`. New: `project_archived` and `project_not_archived` (409),
   `attribute_not_found` (404), `project_description_too_long`,
   `project_reason_required`, `attribute_reason_required`, `attribute_value_too_long`
   and `invalid_attribute_name` (422). `docs/ERRORS.md` lists them all.
5. **Journal entries may belong to a project.** Every entry in `wait_journal`,
   `GET /api/v1/journal` and the SSE stream now carries `project_key`, and `task_key` is
   `null` for a project's own entries. New entry types: `attribute_created`,
   `attribute_changed`, `attribute_removed`, `archived`, `restored`. A consumer that
   assumed every entry has a task must skip or handle these.
6. **Narrower answers from `link`, `unlink` and the registry tools.** `link`/`unlink`
   return `{key, entry, other_entry}` — the case entry numbers filed on both sides —
   instead of echoing `key`/`kind`/`other` and, for `unlink`, a `removed: true` flag.
   `create_project`/`update_project` return `{key}`; `register_participant`/
   `update_participant` return `{name}` — instead of the object's fields in full; read
   the object back with `get_project` or `list_participants` (`TRK-144`).

**For agents:** the `tracker-agent` skill and the `tracker-discipline` prompt are no
longer served. If you copied the skill to disk before this release (for Claude Code,
`~/.claude/skills/tracker-agent/SKILL.md`), delete it: it names the queue tools, which
no longer exist, and the rules it held now arrive in the MCP `instructions` and in each
tool's own description.

## Upgrade notes

1. **The v0.3.0 updater does this update, with rollback and a database snapshot.** This
   is the first release since v0.3.0 that changes the database schema, so it is the
   first one covered by the safety v0.3.0 introduced: before installing, the updater
   takes a `pg_dump` snapshot, and if v0.4.0 fails to come up healthy after moving the
   schema, the database is restored and v0.3.x starts again. Writes made during that
   rollback window are lost, as described in the v0.3.0 notes. The updater itself does
   not change in this release.
2. **The migration renames in place and moves long descriptions.** The table, its column
   and its constraints are renamed; every project, task and entry keeps its row. A queue
   description longer than 320 characters moves word for word into the project's case as
   a `note` titled «Описание до v0.4.0» ("Description before v0.4.0"), filed by the
   tracker itself, and the description field is left empty — nothing is lost, but the
   project's short description has to be written anew. Descriptions of 320 characters
   or less stay as they are. Projects that existed before the upgrade start with an
   empty case otherwise: no `created` entry is filed after the fact.
3. **Going back to v0.3.x means restoring a backup.** v0.3.x does not know the new
   schema, and a downgrade does not put long descriptions back into the field. Take a
   dump before updating by hand (`docs/backup-restore.md`) if you may want to return;
   `CASEFILE_VERSION=0.3.1` in `~/casefile/.env` keeps an installation on v0.3.1 before it
   updates.
4. **Update your REST and MCP clients.** Scripts, dashboards and harnesses that call
   `/api/v1/queues`, pass `queue=`, call `list_queues`/`get_queue`/`create_queue`/
   `update_queue`, write `queue:` in queries or match `queue_*` error codes stop working
   the moment the installation runs v0.4.0 — apply **Breaking changes** 1–5. MCP clients
   pick up the new tool list at their next connection; a session opened before the update
   still holds the old names, so reconnect it.
5. **Delete the skill copy** if an agent has one on disk (see **For agents** above).

## Not verified yet

- **The upgrade on a long-lived real installation.** The migration, including moving
  long descriptions into the project's case, was run on development installations
  seeded from v0.3.0 data and on migration archives from v0.3.0; not on an installation
  with months of real history, and not on archives taken from v0.3.1 (same schema
  revision as v0.3.0).
- **The automatic update from v0.3.x to v0.4.0 through ghcr.io**, and the rollback of a
  schema-changing release against the real registry: the rollback path was exercised in
  v0.3.0 against a local registry only.
- **Performance of the new filters on large data**: hiding archived projects in search
  and the `attribute` filter of a project's case were not measured at scale.
- **The board in Safari.** The project screen, attributes and archive were checked in
  Chromium by the end-to-end suite, not in Safari.
