# Casefile v0.2.0

Casefile is the task tracker your AI agents keep for each other: every task carries a
case file — decisions, failed attempts, findings, open questions — so the next agent,
with a fresh context and zero memory, picks up exactly where the last one stopped. You
watch it all on a live board.

## Install

**macOS / Linux**

```bash
curl -fsSL https://raw.githubusercontent.com/azimov777/casefile/main/install.sh | sh
```

**Windows (PowerShell)**

```powershell
irm https://raw.githubusercontent.com/azimov777/casefile/main/install.ps1 | iex
```

All you need is Docker. The board opens at `http://localhost:8080`, and the installer
prints the one command that connects your agent. Casefile updates itself to each new
release: it checks once an hour and whenever Docker starts
(`CASEFILE_AUTO_UPDATE=false` in `~/casefile/.env` turns that off).

## What's new

- **Board and task page.** Filtering tasks is now a real tool — quick filters for
  priority, assignee and flags, or the query language for anyone who wants it, instead
  of one plain text box. The task header reads in clear groups: where the task lives
  (queue, parent), what it is (key, title), its state (status, priority, assignee,
  flags) and when. The Links panel groups a task's links by kind — blocks, blocked by,
  parent/children, related — with each link's own status, instead of one truncated
  line. Empty states (summary, questions, remarks, links) collapse to a compact row
  instead of an empty box, so the first screen shows what's actually there. The board
  and the task page also hold up on a phone: the task list and the case both switch to
  cards, and the top bar stays one line — no sideways scroll. Plus many layout fixes:
  the Card/Case toggle no longer jumps between the two pages, task keys and inline code
  never break mid-word, dropdown carets sit on the text baseline everywhere, the board
  column's scrollbar is quieter and starts below the column header, the edge mark at the
  bottom of a column is a soft fade instead of a hard line,
  links list rows keep one shape at any title length, a remark or an answer draft can
  be cancelled with confirmation, every tap target on a phone is at least 24×24 px, expanding a case entry no longer jumps the scroll position, and
  buttons and toggles share one size scale.
- **Case feed.** A case entry now carries the action (the single call) it was filed by,
  so a multi-field edit shows in the case index and in the journal as one event you
  expand — not seven separate lines burying the decisions and findings next to them.
  Filtering case entries got the same toolbar and Filter panel as the task list.
- **Questions inbox with history.** The Questions screen still opens on the questions
  waiting for you, and now has a second view, History: every past question together
  with its answer, newest first, addressed to you by default with an option to lift that
  filter, and a jump to the answer's entry in the case. Answering from history is not
  possible — only open questions take an answer.
- **Accounts and network mode.** Casefile now has one authentication path instead of an
  install-wide password. A local installation still asks for nothing: an administrator
  account is created for you and the board signs into it by itself. A network
  installation (`CASEFILE_LOGIN=password`) signs each person in with their own email
  and password, and every case entry they file is signed with their name instead of a
  shared owner. The administrator flag is the only role, and all it opens is managing
  people — adding a teammate no longer needs the server console, the board does it.
- **Moving an installation.** An administrator can take an entire installation — every
  task, case entry, person and agent token — to another machine or their own server
  with two HTTP requests and no shell: export an archive, then import it into a fresh,
  empty installation (`docs/moving.md`). The board does the same in two clicks:
  download the archive on the old installation, choose the file on the new one, and see
  what happened to access afterward.
- **Per-agent tokens.** Issuing and managing agent tokens is no longer
  administrator-only: anyone signed in issues a named token to their own agent, sees
  their own tokens with when each was last used, and revokes them — without touching
  anyone else's and without asking an administrator. An administrator still sees every
  token on the installation, with an All/Mine toggle, and login sessions are listed
  apart from agent tokens. The **Connect an agent** and **Access** screens were also
  rebuilt to be readable end to end: a first-time visitor understands what to do within
  a minute and copies the right snippet for their client.
- **Auto-update channel.** v0.2.0 is the first release on the `stable` channel:
  installations made with `install.sh` / `install.ps1` check for a new release once an
  hour, at a slightly random minute, and again whenever Docker starts, reaching a
  tagged release within about an hour and ten minutes with nothing to restart by hand.
  `CASEFILE_AUTO_UPDATE=false` turns it off, `CASEFILE_UPDATE_INTERVAL` changes how
  often it checks, and `CASEFILE_VERSION` pins a specific release — all in
  `~/casefile/.env`.
- **MCP over stdio, as an alternative.** Streamable HTTP stays the main way in; a client
  that can only launch a command and talk over stdin/stdout now gets the same server via
  `python -m app.mcp --stdio` in a short-lived container of your installation — same
  tools, same token (passed in `TRACKER_MCP_TOKEN`), same case. See **Connect your
  agent** in the README.
- **README tools list.** The README now has a `## Tools` section listing every MCP tool
  a `task` or `main` token opens, grouped by area (Tasks, Case, Links, Queues &
  participants, Journal), with one-line descriptions kept in sync with the code, plus a
  ready-made `mcpServers` JSON snippet — so MCP directories that read the README show
  what Casefile's server can do on its card.

## Upgrade notes

1. **Installations now follow the `stable` release channel, checked hourly.** v0.2.0 is
   the first release on that channel — before it there was nothing to update to. An
   installation from before v0.2.0 (effectively pinned to `latest`) moves to `stable` by
   itself the next time Docker starts: a one-time helper service swaps in the new
   updater, which then checks once an hour on its own. If you set
   `CASEFILE_VERSION=latest` in `.env` yourself, remove that line to keep following
   releases. `CASEFILE_UPDATE_INTERVAL` sets how often to check (hours, or e.g. `30m`;
   `0` means only at Docker start), and `CASEFILE_AUTO_UPDATE=false` turns updating off
   entirely. The compose file itself now ships inside each release's image instead of
   being fetched from `main`, so it only ever changes together with a tagged release,
   in step with the images; the `CASEFILE_COMPOSE_URL` and `CASEFILE_SOURCE` variables
   are gone and do nothing if still set. An update recreates the Casefile containers
   and keeps your data in its volumes; an agent mid-MCP-call when that happens gets a
   dropped connection and has to retry.
2. **Breaking for agents: a task enters `in_progress` only for its assignee.** A task
   without an assignee refuses entry into `in_progress` with `assignee_required`; a
   task assigned to someone else refuses with `assignee_mismatch`, naming both the
   assignee and the requester. There is no administrator exception, and this holds the
   same way over REST and MCP. An agent must set itself as assignee first
   (`update_task(key, {"assignee": ...})`) before transitioning a task into
   `in_progress`. The tracker-agent skill and the MCP tool descriptions already tell
   agents this.
3. **Accounts replace the install password on network installations.** An installation
   locked with `TRACKER_PASSWORD_HASH` before accounts existed keeps working after the
   upgrade with no action needed: sign-in turns on by itself, and the old password
   becomes the password of the administrator account `owner@localhost` — sign in with
   that email and the same password. The hash in `.env` is carried over only once; a
   password set later is never overwritten by it. Local, un-networked installations are
   unaffected — still zero input, still signed in automatically. Separately, token
   management is no longer administrator-only: every signed-in person now issues
   tokens to their own agents from the **Access** screen, sees only their own tokens
   (an administrator sees all, with an All/Mine toggle), and revokes them without
   asking the administrator.
