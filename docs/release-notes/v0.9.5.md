# Casefile v0.9.5

A release around trust and wording. The installer now asks before it changes files that
belong to other programs, the updater keeps a copy of your database from before a schema
update, the installers and the README say plainly that Casefile updates itself and how to
turn that off, and Casefile describes itself as one case file per task. The service code
and the board are unchanged.

## Install

**macOS / Linux**

```bash
curl -fsSL https://raw.githubusercontent.com/azimov777/casefile/main/install.sh | sh
```

**Windows (PowerShell)**

```powershell
irm https://raw.githubusercontent.com/azimov777/casefile/main/install.ps1 | iex
```

An installation on v0.9.4 updates its service to this release by itself within about an
hour, or at the next Docker start. The service has no migrations and no new settings.
The plugin and the installer's new behavior reach you the next time you run the install
line (see "Upgrade notes").

## What's changed

- **The installer asks before it touches another program's files.** The plugin step edits
  files that are not Casefile's: Claude Code's `~/.claude/settings.json`, Codex's
  `~/.codex/config.toml`, the manual MCP entries `casefile` and `tracker` that point at
  this installation, and `~/.agents/skills`. The installer prints that list and asks
  `[y/N]` on your terminal, also under `curl … | sh` (it reads the answer from
  `/dev/tty`; `install.ps1` asks with `Read-Host`). `N` skips the whole plugin step and
  installs the service as usual, and the output says how to add the plugin later. Without
  a terminal (an agent, CI) nothing is asked and the step runs as before;
  `CASEFILE_SKILL=0` skips it and `CASEFILE_SKILL=1` answers "yes" in advance (TRK-546).
- **Copies and a one-line edit.** Before the first change to a file the installer saves a
  copy next to it: `settings.json.casefile-bak`, `config.toml.casefile-bak`, and a copy of
  `.claude.json` before it removes a manual entry. The copy is made once and never
  overwritten, and it keeps the file's permissions. `settings.json` is no longer rebuilt:
  the installer inserts one line, `"autoUpdate": true`, inside
  `extraKnownMarketplaces.casefile`, and the rest of the file stays byte for byte as it
  was (TRK-546).
- **`CASEFILE_PLUGIN_AUTOUPDATE=0`.** Installs the Claude Code plugin without `autoUpdate`,
  so the plugin only changes when you run `claude plugin update casefile@casefile`
  yourself. The output says so (TRK-546).
- **A copy of the database from before a schema update is kept.** When a release changes
  the database schema, the updater takes a `pg_dump -Fc` snapshot first. It used to sit in
  the updater container's `/tmp` and was deleted after the update, so it did not survive.
  It now goes into the named volume `updater-snapshot` (for the standard install,
  `casefile_updater-snapshot`, file `before-update.dump`), and a good update and a rollback
  both leave it there. There is one copy: the next schema update replaces it, and a
  snapshot that fails never replaces the earlier one. The updater's log names the volume
  and the release the copy belongs to. Restoring from it is described in
  [`docs/backup-restore.md`](../backup-restore.md#restoring-from-the-updaters-snapshot).
  The automatic rollback of a release that fails to start works as before (TRK-547).
- **The installers and the README say that Casefile updates itself.** Before it installs,
  the installer now prints that the `updater` service installs new releases once an hour,
  that it holds the Docker socket (`/var/run/docker.sock`, which is root access to the
  machine) to do so, and how to turn it off: `CASEFILE_AUTO_UPDATE=false` in
  `~/casefile/.env`, then `docker compose up -d --no-deps updater`. The same is repeated at
  the end. If auto-update is already off, the installer says so and how to update by hand.
  The README has the same text in its "Updates" section. With auto-update off the board
  still tells you when a release is out: a note at the bottom of the side panel links to
  the release notes (that note was already there and is unchanged;
  `TRACKER_RELEASE_CHECK=false` turns it off) (TRK-548).
- **New wording: one case file per task.** The README, the public site, the Claude Code,
  Codex, Cursor and Gemini CLI manifests and the MCP registry card describe Casefile as a
  case file for every task, shared by every session, agent and person, instead of "a task
  tracker your agents keep for each other". Only the wording changed; Casefile does what it
  did before (TRK-540).
- **The installer follows Claude Code 2.1.289.** To move an installation from the old
  `stable` source to the `plugin` branch the installer recognises the refusal of
  `claude plugin marketplace add`. Claude Code 2.1.289 words that refusal differently
  ("its source doesn't match its extraKnownMarketplaces entry"), and the installer stopped
  recognising it: the old source stayed and the Claude Code step ended with "failed -
  repeat by hand". Both wordings are recognised now, in `install.sh` and `install.ps1`;
  any other `add` error still does not remove the declared source (TRK-550).

## Upgrade notes

- No migrations. The service code (API, MCP server, board) is unchanged; the images differ from
  v0.9.4 by the version number and by the `docker-compose.prod.yml` they carry.
- **The updater container is replaced once.** `docker-compose.prod.yml` changed the
  `updater` service (it gained the snapshot volume), so its revision label moved and
  `updater-renew` recreates the updater on the first start on this release. It is the normal
  path; do not be surprised to see the container restart, or a new volume
  `updater-snapshot` in `docker volume ls`.
- **The snapshot volume works from the next release on.** The update to this release is
  done by the updater you run today. This release changes no schema, so it needs no
  snapshot. A later release that changes the schema will be installed by the new updater and
  will leave its snapshot in the volume. An update done by an older updater still keeps its
  snapshot in the container's `/tmp` only, and it goes away with the container.
- **The installer's new behavior and the new plugin text come with the install line.** The
  hourly self-update changes the service only and never runs the installer. Run the
  install line again to get the plugin and its manifest text for v0.9.5 (to touch only the
  plugin, add `CASEFILE_SKILL_ONLY=1`); a Claude Code plugin with `autoUpdate` on normally
  updates itself.
- **The `.casefile-bak` copies hold what the files held.** If the installer removes a
  manual MCP entry that carries a token, the token stays in the copy. Delete the copy when
  you no longer need it.
- **`CASEFILE_VERSION=0.9.4`** in `.env`, if you pin a release, is the line to change to move
  to this one by hand.

## Not verified yet

- **`install.ps1` was never run end to end** on Windows or in Windows PowerShell 5.1. In
  PowerShell 7.4 on Linux the parser, the consent step with stand-in prompts, the
  `settings.json` scanner and the terminal check were run; how `Read-Host` behaves in 5.1, in
  ISE and in Windows Terminal, and the permissions of the copies on Windows, are not measured.
  The change of the `add` refusal matching in `install.ps1` is by parity with `install.sh`.
- **The `curl | sh` question was not run in a real terminal.** The path is reproduced with a
  pty driver (`cat install.sh | sh` with a controlling terminal, in a Linux container and on
  macOS). An agent started in a shell that gives it a real terminal looks like a person to
  the installer and will wait for an answer unless `CASEFILE_SKILL` is set.
- **A `settings.json` with comments, or one edited by another program during the install,**
  is refused with a line to edit by hand; it was not tried on real files. A marketplace
  declared in managed settings (written by an administrator) is not removed by the
  installer.
- **The Claude Code move from `stable` to `plugin` was measured only on 2.1.289** with the
  real `claude` and `codex`; the old wording is covered by a stand-in in the tests. The next
  rewording of that refusal will break the move silently until a live check on that
  version is run.
- **The whole updater was not run on a real Docker with the snapshot volume.** The snapshot
  and restore functions were run live in a container with their own volume, and the update
  cycle with a stand-in `docker`. That a real `docker compose up` creates `updater-snapshot`
  and mounts it, including through the updater replacement, rests on reading the file and on
  a test that parses it. The restore commands are written for a POSIX shell and were not
  tried in PowerShell.
- **The "release available" note with auto-update off** was checked on a development image
  with a substituted version and a production environment, not on the production image
  behind the installation's web server.
- **The new wording** has not been read by real people or taken by the directories yet: the
  MCP registry card changes only when this release is published, and the descriptions on
  external directory sites were not edited. The public page `site/index.html` was not
  opened in a browser. A few older phrases remain: the first-run text of the board ("AI
  agents forget everything between sessions"), `docs/agent-install.md` ("a local task
  tracker") and `CONTRIBUTING.md`.
- The items of v0.9.0's to v0.9.4's "Not verified yet" are still open.
