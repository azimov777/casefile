# Casefile v0.8.0

The release that gives your agents the Casefile skill. Connecting an agent gave it the
tools; the skill teaches it how to use them: how to connect to an installation, how to set
up the journal watcher, what to do on a `401`, and how to install and update the skill
itself. The skill reaches agents three ways: the installer puts it into every agent
harness it finds, a plugin marketplace serves it from the `stable` channel, and the MCP
server hands it out by the SEP-2640 convention. The release also adds a "new release"
notice to the interface and rewrites a few texts so they no longer assume the work is
software development. It adds and changes nothing you depend on, hence a minor version.

## Install

**macOS / Linux**

```bash
curl -fsSL https://raw.githubusercontent.com/azimov777/casefile/main/install.sh | sh
```

**Windows (PowerShell)**

```powershell
irm https://raw.githubusercontent.com/azimov777/casefile/main/install.ps1 | iex
```

All you need is Docker. The board opens at `http://localhost:8080`, and the installer
prints the commands that connect your agent and install the skill, followed by two short
phrases to say to it. An installation on v0.7.0 updates itself to this release within about
an hour, or at the next Docker start.

## What's new

- **The Casefile skill.** `skills/casefile/SKILL.md` covers what MCP does not deliver:
  connecting to an installation (including a shared one on a server), the journal watcher,
  the `401` case, and installing and updating the skill. The rules of the contract stay in
  the MCP `instructions` and tool descriptions; the skill does not repeat them.
- **The installer installs the skill.** `install.sh` and `install.ps1` install the skill
  into every harness they find on the machine (Claude Code, Codex, Hermes, and other agents
  through `npx skills` when `npx` is present) and print one line per harness: installed,
  not found, or failed with the command to repeat by hand. A failed skill step does not
  fail the installation of the service. Running the installer line again installs the skill
  into a harness that appeared later.
  - For Claude Code the installer also writes `"autoUpdate": true` for the `casefile`
    marketplace into `~/.claude/settings.json`, so the skill updates itself. This is the
    only file of a harness the installer edits; it never writes your token into any of them.
  - `CASEFILE_SKILL_ONLY=1` installs only the skill: no Docker, no installation directory,
    no token. It is meant for a machine that only connects to a Casefile running on a
    server.
  - `CASEFILE_SKILL=0` skips the skill step.
  - A full installation prints the `CASEFILE_SKILL_ONLY=1` line for other machines that
    will connect to it.
- **A plugin marketplace with a `stable` channel.** The repository is a marketplace named
  `casefile` with one plugin, `casefile`, that carries only the skill. Claude Code and
  Codex install it from the `stable` branch, which moves to the release commit after the
  release images are published, so the skill never reaches agents before the server. The
  plugin version equals the release version. The installer and the agent guide print the
  exact commands per harness.
- **The server serves the skill by SEP-2640.** The MCP server declares the
  `io.modelcontextprotocol/skills` extension and answers `skills/list` and `skills/get`;
  the skill is also a plain resource, `skill://casefile/SKILL.md`. A client that supports
  the convention gets the skill from the server, so it is updated together with the server.
- **A "new release" notice.** The bottom of the side panel shows "Casefile vX.Y.Z is
  available" with a link to the release page when your installation is behind the latest
  release. The API reads the latest release from GitHub about once an hour and on the first
  request after a start; it is the only call the API makes to the outside world. A network
  failure shows no notice and no error. Set `TRACKER_RELEASE_CHECK=false` in `.env` to
  never ask. A development setup does not ask. There is no "update" button: the updater
  does that, as before. The data comes from `GET /api/v1/installation/release`.
- **Screens that show the skill.** "Connect an agent" and "Access" show installing the
  skill as the second step, next to the connection command, and it is copied the same way.
- **"Start" and the project explanation no longer assume development.** Their examples are
  gone; the texts describe the work of an agent in general and say that without a case the
  decisions made in a conversation are lost. "Start" has a section, "When you need it":
  any conversation that ends in a result or a decision, and work that moves between
  sessions and agents. The "Start" item in the side panel is highlighted until you finish
  the introduction.
- **Smaller interface fixes.** "Leave a remark" is a button in the "Remarks" block of a task
  card instead of a line in the navigation row. The "?" next to "show archive" opens a panel
  over the page instead of pushing the board. Applying or resetting a filter no longer moves
  the search row and the board.

## For agents

- **MCP `instructions`** gained two sentences: a conversation that ends in a result or a
  decision becomes a task even if one session holds all of it, and the resource
  `skill://casefile/SKILL.md` covers setup, journal watching and skill installation. To make
  room, some sentences were shortened without dropping a rule. This pointer is the one path
  by which the skill reaches an installation that only the updater has updated: the updater
  installs nothing on the machine of the agent.
- **The phrase about the task file** in the installers' output, `README.md`,
  `docs/agent-install.md` and the "Start" screen now says the same thing: each task names
  where the work lives and how to check it is done (it used to say how to run its checks).
- Tool contracts, error codes and `openapi.json` paths are otherwise unchanged; the only
  API addition is `GET /api/v1/installation/release`.

## Upgrade notes

**What happens to your installation**

- **No database migration.** Your data and accounts are left as they are.
- **The skill does not arrive by the update alone.** The updater replaces Casefile's images
  and installs nothing into an agent harness on your machine. To get the skill, run the
  installer line again (it installs the skill into every harness it finds),
  or use the per-harness commands from `docs/agent-install.md`. Agents of an
  updated installation are also pointed at the skill by the MCP `instructions`.
- **`~/.claude/settings.json` gains one key** when you run the installer with Claude Code
  present: `extraKnownMarketplaces.casefile` with `autoUpdate: true`. Nothing else in your
  harness files is touched, and `CASEFILE_SKILL=0` avoids even that.
- **The API now makes one outgoing request** to `api.github.com` about once an hour (the
  release check). If your installation must not reach out, set `TRACKER_RELEASE_CHECK=false`
  in `.env`.
- **A new dependency**, `pyyaml`, is part of the server image; nothing to do.
- **`CASEFILE_VERSION`** in `.env`, if you pin a release, is the only thing to change to
  move to this one by hand.

## Not verified yet

- **No model was run on the skill.** That a model in a live session reads the skill, follows
  it to connect and to install the plugin, or reads the resource from the `instructions`
  pointer was not measured. Support for MCP resources in Codex was not checked.
- **The marketplace and the `stable` branch were tried locally, not on GitHub.** The forms
  `azimov777/casefile#stable` and `--ref stable` and the `channel` job that moves `stable`
  were checked on a local git server and a bare repository; the branch does not exist until
  this release is published, and the job's permission to push it is proven only by the first
  release.
- **`install.ps1` was never executed by PowerShell**; it was checked by a parser and by
  text tests. Its skill step is the likeliest place for a defect.
- **Hermes was checked with a stand-in**, not a real `hermes`. The Codex desktop app was not
  tried with the plugin or with `http_headers`.
- **`autoUpdate` was checked as a key in `settings.json`**, not as an update happening in a
  running Claude Code session.
- **SEP-2640 was checked with the MCP Inspector, the conformance suite and a server test**,
  not with a real client (Claude Code, Codex) that asks for the skill.
- **The notice was never shown for a real newer release**: "newer" was simulated in tests.
  Its look was checked in headless Chromium only, not in Safari, on wide screens and on a
  phone.
- **The update from v0.7.0** was checked from a local registry, not from ghcr.io (see the
  check recorded in the task).
