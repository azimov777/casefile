# Casefile v0.3.0

Casefile is the task tracker your AI agents keep for each other. AI agents forget
everything between sessions; Casefile gives every task a case file — decisions, failed
attempts, findings, open questions — so the next agent picks up exactly where the last
one stopped. You watch a live board and answer their questions.

## Install

**macOS / Linux**

```bash
curl -fsSL https://raw.githubusercontent.com/azimov777/casefile/main/install.sh | sh
```

**Windows (PowerShell)**

```powershell
irm https://raw.githubusercontent.com/azimov777/casefile/main/install.ps1 | iex
```

All you need is Docker. The board opens at `http://localhost:8080`, and the installer
prints the one command that connects your agent. An installation made from v0.2.0 on
updates itself to this release within about an hour, or at the next Docker start.

## What's new

- **One parent per task, and the card says who is who.** A task now has at most one
  parent and any number of children. The task card shows them as their own fields —
  `parent` (key, title, status, or `null`) and `children` (a list) — instead of mixing
  them into `links`, where `{"kind": "parent", "other": "TRK-56"}` read as "my parent
  is TRK-56" while it meant the opposite. A second parent is refused with
  `409 task_has_parent`, naming the current parent in `details.parent`. The board
  follows: the Links panel labels the parent and the children from the open task's point
  of view, a child's row in the task list carries a "parent KEY" chip that opens a panel
  on tap, and linking a second parent shows a plain-language refusal. See **Breaking
  changes** below.
- **Updates that fail roll back by themselves.** If a new release does not come up
  healthy, the updater puts back the release the installation ran before and does not
  try the failed one again; the next release installs as usual. A release that changes
  the database schema is covered too: before installing it the updater takes a
  `pg_dump` snapshot of the database, and if that release then fails after moving the
  schema, the database is restored from the snapshot before the previous release starts
  again — so a manual `docker compose up -d` afterwards works as usual. The price of
  that safety is in **Upgrade notes**. The updater and the installer also no longer run
  `docker compose up` over each other: running the install line while the updater is
  mid-check waits for it instead of racing it, and the updater never calls `up` when it
  cannot read the compose file or another `up` is already in progress.
- **Listed in the official MCP Registry on every release.** Each release tag now
  publishes Casefile's `server.json` to `registry.modelcontextprotocol.io` under the
  release's version, signed in with GitHub OIDC — no long-lived secret. The repository
  also carries a `glama.json` naming its maintainer, and the README shows the Glama
  score badge. The README's first screen now says who Casefile is for, and a new
  **How it's different** section sets it apart from a notes file, a memory server, an
  issue tracker with MCP added and an orchestrator; the registry entry got a shorter
  description to match.
- **MCP tools describe themselves better.** Every tool now carries the protocol's
  `readOnlyHint`, `destructiveHint` and `idempotentHint` annotations, set by what the call
  actually does (reads, appends to the case, or overwrites a queue or participant
  description), so a client can tell a safe read from a write before calling. Tool
  descriptions now open with the action they perform and, where two tools sit at the same
  fork (`get_queue` and `list_queues`, `get_task` and `search_tasks`, `read_entries` and
  `wait_journal`, `add_summary` and `close_task`, `add_entry` and the tools for
  questions, verdicts and resolutions), say when to take which.
- **Nothing hides behind a mouse hover.** Everything that used to appear only on hover
  opens on a tap too or is shown in full, so it can be read on a phone: exact times
  open on a tap, long queue and parent names wrap instead of being cut off, the archive
  checkbox has a "?" that explains it, and the meaning of flag icons, the live-stream
  indicator and the token-scope chip opens on a tap. Tap targets in the filter chips (the remove cross, the chip
  text, **Reset**) are at least 24×24 px.
- **Copy a link to a case entry.** Every case entry has a "copy link" action: the address
  opens the task scrolled to that entry (`?entry=N`), ready to paste into a chat or
  another case.
- **Language, end to end.** A board set to Russian no longer shows English service text,
  and a board set to English no longer shows Russian: everything the board displayed
  outside its dictionaries was audited, and the expanded case index, author kinds,
  changed-field values and the archive file picker now follow the board's language. Form fields that the server rejects now show
  the reason in the board's language next to the field, instead of a raw code.
- **Smaller fixes.** A transition reason that contains a `KEY#N` link stays on one line;
  a task key in the Links panel never breaks at its hyphen; stopping the MCP server no
  longer logs a false "Journal listener lost its connection" warning; the demo seeding
  script closes tasks with the required `unmeasured` part; the dev image builds on
  `uv` 0.12.18.

## Breaking changes

These change the REST and MCP contract. The board, the MCP tool descriptions and the
tracker-agent skill served by the server already follow them; anything else that reads
the tracker needs the changes below.

1. **`parents` became `parent` in search results.** `GET /api/v1/tasks` (search) and the MCP
   `search_tasks` return `parent` — one object `{key, title}` or `null` — instead of the
   `parents` list. In `fields`, ask for `parent`; `parents` now answers
   `422 search_field_unknown`. The `parent:` filter in the query language and the
   `parent` search parameter are unchanged.
2. **Parent and child are no longer in the card's `links`.** `get_task` and
   `GET /api/v1/tasks/{task_key}` carry them as `parent` (`{key, title, status}` or `null`) and
   `children` (a list of the same, in link order). `links` now holds only `blocks`,
   `blocked_by` and `relates`. A client that looked for `kind: "parent"` or
   `kind: "child"` in `links` finds nothing there and must read the two new fields.
   Creating and removing the relationship is unchanged: `link`/`unlink` with
   `kind: "parent"`/`"child"`, or `create_task(parent=...)`; case entries about links
   keep their payload.
3. **A second parent is refused.** `link` (REST and MCP) and `create_task(parent=...)`
   answer `409 task_has_parent` when the child already has a parent. To move a task
   under another parent, `unlink` the old one first.

**For agents:** an agent that copied the tracker-agent skill to disk before this release
(for Claude Code, `~/.claude/skills/tracker-agent/SKILL.md`) still reads "`get_task(parent)`"
and may look for the parent in `links`. Replace the file with the current
[`skill/tracker-agent/SKILL.md`](https://github.com/azimov777/casefile/blob/main/skill/tracker-agent/SKILL.md),
or let the agent read the skill the server serves over MCP.

**Data made before this release:** earlier versions allowed a second parent. If a task
in your installation already has two, nothing is deleted, but the card and the search
row show only the earliest parent; `unlink` the extra one to make it explicit.

## Upgrade notes

1. **This update is done by the v0.2.0 updater; the new one arrives right after it.**
   The updater of v0.2.0 installs v0.3.0 the way it always has — without rollback and
   without a database snapshot. As part of that update, the one-time `updater-renew`
   service waits for it to finish and then replaces it with the v0.3.0 updater (revision
   `332195ccf849`, was `1285abd038bf`). Rollback and the snapshot therefore protect
   updates **from the release after v0.3.0 on**, not the step to v0.3.0 itself.
   v0.3.0 adds no database migration, so this step leaves the schema as it is. If
   `docker compose logs updater-renew` says it cannot tell where the installation lives,
   run the install line again to get the new updater.
2. **The price of automatic rollback: writes in the rollback window are lost.** When a
   release that changed the schema fails and the database is restored from the
   snapshot, anything written between the snapshot and the restore is gone — task
   changes, case entries, answers. The window is the failed start: about a minute in our
   tests, up to a few minutes. For the first seconds the previous release keeps
   answering, and whatever it accepts then is lost too. The snapshot is kept inside the
   updater container (`/tmp/casefile-before-update.dump`) and takes about as much space
   as a manual backup; it is deleted once the update succeeds or the restore completes.
   If the snapshot cannot be taken, that release is not installed this time; if it
   cannot be restored, the previous release runs on the new schema, the snapshot is kept,
   and `docker compose logs updater` says how to copy it out — copy it before anything
   recreates the updater container.
3. **A failed release is skipped until the next one.** After a rollback the installation
   stays on the previous release and does not retry the failed one; its image stays on
   disk under the `failed` tag until the next release replaces it. `CASEFILE_VERSION`
   pinning, `CASEFILE_AUTO_UPDATE=false` and `CASEFILE_UPDATE_INTERVAL` work as in
   v0.2.0.

## Not verified yet

- **Publishing to the MCP Registry from GitHub Actions.** The workflow is new with this
  release and runs for the first time on this very tag; the registry entry for v0.3.0 is
  expected but has not been seen yet.
- **Rollback against the real registry.** Rollback, the snapshot and the restore were
  exercised end to end on macOS against a local `registry:2` with a one-minute interval
  — not against ghcr.io with the hourly schedule, and not on large databases (dumps of
  hundreds of megabytes). The "database restore itself fails" path and the "api is up but
  mcp or ui never become healthy" path are covered by tests only.

`install.ps1` also changed in this release: like `install.sh`, it now waits for the
updater instead of racing it. A full run on a real Windows machine is tracked separately.
