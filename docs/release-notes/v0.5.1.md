# Casefile v0.5.1

A small release: a batch `move_task` and an installer fix. The contract only grows —
nothing from v0.5.0 is removed or changed shape — and the database is unchanged.

## Install

**macOS / Linux**

```bash
curl -fsSL https://raw.githubusercontent.com/azimov777/casefile/main/install.sh | sh
```

**Windows (PowerShell)**

```powershell
irm https://raw.githubusercontent.com/azimov777/casefile/main/install.ps1 | iex
```

All you need is Docker. The board opens at `http://localhost:8080`, and the installer
prints the one command that connects your agent. An installation on v0.5.0 updates itself
to this release within about an hour, or at the next Docker start.

## What's new

- **`move_task` moves a list of tasks in one call.** Its `key` argument now takes a
  string or a list of 1 to 100 keys (`MAX_MOVE_KEYS`); REST gets a matching
  `POST /api/v1/tasks/move` with `{keys, project, reason}` — one reason and one target
  project for the whole list. Tasks move one by one in list order, so new numbers follow
  that order too, and each gets its own `moved` case entry with the shared reason. The
  answer is one outcome per listed key, repeats included: `moved` (key before and after,
  the entry number), `already` (the task is in that project already,
  `task_already_in_project`) or `error` with the code, message and details a single move
  of that task would give — `task_not_found`, `project_archived` of the task's own
  project, and the like. A refusal of one task leaves the rest moved: this is not
  all-or-nothing. Calling `move_task` with a single string key still answers exactly as
  before, field for field — the single-key contract does not change. Failures common to
  the whole call refuse it before any move: a missing `main` scope
  (`403 permission_denied`), a blank reason (`422 task_move_reason_required`), an unknown
  target project (`404 project_not_found`), an archived target
  (`409 project_archived`), or a list that is empty or longer than the ceiling
  (`422 task_move_batch_size_invalid`, new in this release).
- **The installer prints the board's real port.** `install.sh` and `install.ps1` now read
  `CASEFILE_PORT` from the environment before falling back to the installation's `.env`,
  then the `8080` default — the same order Docker Compose itself uses
  (`${CASEFILE_PORT:-8080}`) for the real port publication. Before this fix, a
  `CASEFILE_PORT` set for the installer moved where the board actually published but not
  the address the installer printed, so the printed line could name a port the board
  wasn't listening on.

## Upgrade notes

No migration and no configuration change: this release adds a REST route, an MCP
argument shape and one error code, and fixes what one line of the installer prints. No
existing REST path, MCP tool, error code or database shape from v0.5.0 changes.
`git diff v0.5.0 main -- openapi.json` shows additions only — no removed or altered
operation, schema or field.

## Not verified yet

- **A batch at the full ceiling.** The 100-key limit itself is covered — one over it is
  refused, one at it is accepted — but no automated test moves 100 real tasks in one
  call. One manual run on a development stack moved 100 tasks in 0.34 s; how long a full
  batch holds the change queue for other writes under real concurrent load
  (`docs/CONCEPT.md`, 4.1) was not measured.
- **`install.ps1`'s port-order fix is guarded by text, not run.** Like the rest of that
  file (`docs/notes/docker.md`), there is no PowerShell in this image to execute it
  against, and no real Windows machine in this loop; the test checks that the same
  `$env:CASEFILE_PORT`-first line is in the script, not that running it prints the right
  port.
