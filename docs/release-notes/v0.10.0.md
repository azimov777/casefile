# Casefile v0.10.0

A release about what a case says it is waiting for, and about checks that did not pass.
**It breaks one contract: the `waiting` task status is gone.** Waiting is now something
the case holds, not a status you set. A check that could not be fully run no longer has
to be reported as `passed` or `failed`. Project decisions can replace each other, search
can select a whole subtree, and an outdated question can be closed. The plugin also
gains a second skill that helps connect Casefile when its tools are missing.

## Install

**macOS / Linux**

```bash
curl -fsSL https://raw.githubusercontent.com/azimov777/casefile/main/install.sh | sh
```

**Windows (PowerShell)**

```powershell
irm https://raw.githubusercontent.com/azimov777/casefile/main/install.ps1 | iex
```

An installation on v0.9.5 updates its service to this release by itself within about an
hour, or at the next Docker start. This release has two migrations (see "Upgrade notes");
the updater takes its database snapshot before them.

## What's changed

- **Breaking: the `waiting` status is gone.** Waiting is no longer a stored status but
  something the case holds: an open question with `blocking` (waiting on a person, or on an
  outside event that whoever learns of it answers) or a `blocked_by` link (waiting on
  another task). Statuses are now `backlog`, `open`, `in_progress`, `done`, `cancelled`;
  `waiting` is refused everywhere, with no alias: `transition` (REST `422 validation_error`,
  MCP argument validation), the query language and `status` filters (`search_value_invalid`).
  Instead of moving a task to `waiting`, an agent whose next move is someone else's asks a
  `blocking` question (or links `blocked_by`), files a summary and moves the task to `open`
  with a reason. The answer to the last blocking question, or the blocker closing, makes the
  task a candidate again (`status: open and blocked: false and open_blocking_questions: 0`)
  with no transition by anyone. New refusal: entering `in_progress` while a `blocking`
  question is unanswered is `409 task_has_open_blocking_questions`, with the question numbers
  in `details.questions`; a question no longer needed is closed by an answer with the
  `withdrawn` outcome. The migration moves every task still in `waiting` to `open` with a
  `status_changed` entry signed by the tracker, whose reason names TRK-573, bumps the task
  version and drops `waiting` from the status constraint; a downgrade restores only the
  constraint. The board keeps its "Waiting for an answer" column, now computed from open
  blocking questions (TRK-573, TRK-571). The concept and the skill say the same (TRK-569,
  TRK-572).
- **Checks that did not fully pass: `partial` and `unverifiable`.** A verdict now has four
  outcomes: `passed`, `failed`, `partial` and `unverifiable`, and the last two need evidence.
  Closing a task with an incomplete check files a `warning` entry. A person (or another
  agent, never the one who closed the task) reacts to it with `acceptance` or a `remark`;
  `acceptance_by_closer` and `warning_not_open` refuse the wrong reactions. Tasks carry an
  `open_warnings` feature that can be filtered on, and the board has a "Needs attention"
  section in the inbox, a notice on the task page with "Accept" and "Send back" buttons, and
  words for the new outcomes in the case. The `tools/list` text grew by about 3.7k characters
  (TRK-561).
- **Project decisions can replace each other.** A `decision` in the project case can
  replace an earlier one with `supersedes`; a task links to the decisions in force, and a
  `decision:` selection returns the history (TRK-554).
- **`under` selects a subtree.** The search field `under` selects everything below a task,
  and the card of a child shows the goal of its parent (TRK-468).
- **An outdated question can be closed.** A question that is no longer needed is closed with
  the outcome "withdrawn" or "replaced by question #N"; an answered question cannot be
  withdrawn (TRK-552).
- **An answer filed before outcomes existed reads as answered.** Over both MCP and REST,
  such an answer is no longer shown as an open question (TRK-563).
- **A second skill, `casefile-setup`.** It helps connect Casefile and triggers when an
  agent has no Casefile tools. The plugin descriptions in the four manifests now say plainly
  that Casefile needs a server you run yourself ("Needs a Casefile server you run")
  (TRK-566).

## Upgrade notes

- **Update the clients.** Open Claude Code sessions keep the old tool schemas (`transition`
  still lists `waiting`): run `/mcp` and reconnect, or start a new session. Agents and
  scripts that call `transition` with `waiting`, or filter by `status: waiting`, must switch
  to a `blocking` question or a `blocked_by` link.
- **Tasks in `waiting` become `open`.** The migration (revision `a9cb1ec147c4`) does it with a
  `status_changed` entry written by the tracker; nothing is lost from their cases, and the
  open `blocking` questions keep them out of the candidate list. There is also a migration
  for the new entry types (`warning`, `acceptance`). The updater's snapshot
  (`updater-snapshot` volume) is taken before them.
- **New error code:** `task_has_open_blocking_questions` (see `docs/ERRORS.md`); the REST
  schema in `openapi.json` changed (status enum, outcomes, new fields).
- **The plugin text comes with the install line.** The hourly self-update changes the
  service only; run the install line again (or `CASEFILE_SKILL_ONLY=1` for the plugin alone)
  to get the new skills and manifest text.
- **`CASEFILE_VERSION=0.9.5`** in `.env`, if you pin a release, is the line to change to move
  to this one by hand.

## Not verified yet

- **The migration was not run on a real long-lived installation.** It was tried on a
  synthetic database and a live development setup with one task in `waiting`; an archive from
  an older version holding `waiting` tasks was not restored through it.
- **Agent behavior with the new wording** of the instructions and tool descriptions was
  tested as text (length, wording, no `waiting`), not with live agents.
- **The interface was run in Chromium only**, not in Safari; the board and the new
  "Needs attention" section were not compared to screenshots on a phone.
- **The table filter lost its "status: waiting" switch**; a replacement is TRK-577. The
  "Start" screen counts started work as `in_progress, done` and does not see a task that was
  taken and sent back to wait in `open`.
- The items of v0.9.0's to v0.9.5's "Not verified yet" are still open.
