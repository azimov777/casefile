# Casefile v0.5.0

A task can now move from one project to another. This is the mechanic behind merging the
`UI` project into `TRK` later in this release cycle (`TRK-170`) — every task keeps working
under the key it used to have, wherever that key is read, written or searched for. The
contract only grows: nothing from v0.4.0 is removed or renamed.

## Install

**macOS / Linux**

```bash
curl -fsSL https://raw.githubusercontent.com/azimov777/casefile/main/install.sh | sh
```

**Windows (PowerShell)**

```powershell
irm https://raw.githubusercontent.com/azimov777/casefile/main/install.ps1 | iex
```

All you need is Docker. The board opens at `http://localhost:8080`, and the installer
prints the one command that connects your agent. An installation on v0.4.x updates itself
to this release within about an hour, or at the next Docker start.

## What's new

- **A task can move to another project.** `POST /api/v1/tasks/{task_key}/move` and MCP
  `move_task` (`main` token set) move a task — any status, closed tasks included — into
  another project. It gets that project's next number, or, if it already carried a key
  there from an earlier move, that same key back. Parent, children, links and the rest of
  the case stay as they are; the task's own case gets a `moved` entry naming both
  projects, both keys and the reason. A reason is required
  (`422 task_move_reason_required`); moving into the project the task is already in fails
  with `409 task_already_in_project` rather than succeeding silently; moving into or out
  of an archived project fails with `409 project_archived`, same as any other change
  there. Concurrent moves of one task serialize like any other change to it.
- **A previous key works everywhere the current key does.** The task card carries
  `previous_keys` — every key the task used to have, oldest first, empty until it is
  moved. Reading a task (`GET /api/v1/tasks/{key}`, `get_task`), its children
  (`parent:`), a reference in another case's text (`UI-124#12`), search (`key:`,
  `parent:`) and the questions/remarks inbox all resolve a previous key to the task —
  none of them answers "not found" for a task that exists under a new key. Search rows
  and the task card itself always show the current key.
- **The board follows a previous key and then corrects the address.** Opening
  `/tasks/UI-124` (with or without `?entry=N`) loads the task and replaces the browser
  address with its current key, keeping the same entry number; the task header gets a
  "Previous keys" row, shown only on a moved task, each key a link to the same task.
  There is no "move" button for a person — moving is an agent's action with a reason,
  like creating or closing a task.
- **The installation-move archive carries the move.** An archive taken for moving a whole
  installation (`docs/moving.md`) now includes each task's `previous_keys` and the
  `moved` entry type; an archive from an older revision imports with an empty list, as
  before.
- New error codes: `task_move_reason_required` (422) and `task_already_in_project` (409).
  `docs/ERRORS.md` lists them with the rest.

## Upgrade notes

1. **Migration `6d2e9b41c7f3` adds `tasks.previous_keys`** (a JSONB column, empty for
   every task that existed before this release) with a GIN index, and the `moved` case
   entry type. No other data changes.
2. **Nothing from v0.4.0 is removed, renamed or changed shape.** REST paths, MCP tools,
   error codes and query fields from the previous release keep working exactly as they
   did; this is an additive release.
3. **Going back to v0.4.x means restoring a backup** taken before the update
   (`docs/backup-restore.md`) if a task was moved in the meantime — v0.4.x does not know
   `previous_keys` or `moved`. `CASEFILE_VERSION=0.4.0` in `~/casefile/.env` keeps an
   installation on v0.4.0 before it updates.

## Not verified yet

- **The GIN index under load.** Resolving a previous key runs `key = K OR
  previous_keys @> [K]`; this was not profiled past a handful of moved tasks, and no
  `EXPLAIN` was taken against a table with hundreds of moved rows.
- **Key uniqueness is held by the number counter and the return rule, not a database
  constraint.** A hand-assembled installation archive with a foreign previous key, or a
  direct edit of the database, could in theory produce two tasks answering to the same
  key. Considered a theoretical risk.
- **The board's move outcome was checked in Chromium and Playwright's WebKit**, not in
  Safari itself.
- **Concurrent moves were exercised with two sessions on one machine**, not with a larger
  number of simultaneous callers.
