# Casefile v0.6.0

The first-entry release. A person who installs Casefile for the first time now lands on a
screen that says what it is, what to tell their agent and what to do themselves, and finds
a small training project waiting on the board. One small change breaks agents that wrote
free-form strings into `refs` (see "Breaking for agents"); everything else only adds.

## Install

**macOS / Linux**

```bash
curl -fsSL https://raw.githubusercontent.com/azimov777/casefile/main/install.sh | sh
```

**Windows (PowerShell)**

```powershell
irm https://raw.githubusercontent.com/azimov777/casefile/main/install.ps1 | iex
```

All you need is Docker. The board opens at `http://localhost:8080`, and the installer
prints the one command that connects your agent, followed by three short phrases to say
to it. An installation on v0.5.1 updates itself to this release within about an hour, or
at the next Docker start.

## What's new

- **A "Start" screen (`/start`).** It answers four questions in order: why Casefile
  exists, where tasks come from (agents create and run them; there is deliberately no
  "create task" button for a person), what to say to the agent (three phrases with a copy
  button, and a note that the agent should be a fresh session), and what you do yourself
  (watch, answer questions, leave remarks, run projects). While your introduction is
  pending the app opens on it; afterwards it opens on the task list, and "Start" stays in
  the side panel. Three steps at the top tick off from what the server already knows:
  agent connected, tasks exist, questions answered.
- **A training project, `START`.** On the first start of an installation that has no
  project at all (archived ones count), Casefile creates the project `START` with one task,
  `START-1`, written for your agent: the agent takes it and walks you through a live cycle
  (a question to you, your answer, a remark, closing). It is created once, by the
  installation itself, as the author `tracker`; nothing recreates it on a timer or an
  event. The board address inside the task uses your `CASEFILE_PORT`. Its language follows
  `CASEFILE_LANGUAGE`: the installers write it into a fresh `.env` from your shell locale
  (`LC_ALL`/`LC_MESSAGES`/`LANG`, or the system culture on Windows), `en` otherwise, and a
  value you set yourself is kept as is. The three phrases for the agent are the same in the
  installers' output, in `README.md`, in `docs/agent-install.md`, on the "Start" screen and
  on the "Connect an agent" screen.
- **Explanations on each screen, and a walk-through.** The first time you open the
  task list, board, task card, case, project, "Connect an agent", "Access" and the inbox,
  a short explanation sits at the top. You close one, or all at once; "Show explanations
  again" on the "Start" screen brings them back. "Walk through the screens" on "Start"
  goes through the same explanations screen by screen (Back / Next / Finish), with no
  second set of texts. Archived projects and tasks show none.
- **Your introduction state lives on the server, with your account**, so it is the same in
  every browser: `status` (`pending`, `completed`, `skipped`), all explanations hidden or
  not, and which ones are hidden one by one. It is read with `bootstrap` (`account.onboarding`)
  and changed only by the account's own owner through
  `PATCH /api/v1/accounts/{account_id}/onboarding`. It is account data, not case history,
  so it is not written to the journal.
- **Empty lists say why.** An empty project with the archive shown reads "no tasks yet"
  with a link to "Start", rather than suggesting a filter reset; the sidebar scrolls on
  its own, so a long project list no longer stretches the page.
- **The application version is read from `pyproject.toml`**, one source for the API, the
  log and `openapi.json`. Earlier builds reported `0.1.0` in the schema.
- **A small installer fix.** `install.ps1` writes its second sentence with an explicit
  em-dash code point, so code lines stay ASCII.

## Breaking for agents

- **`refs` accepts only tracker references and URLs with a scheme.** A case entry's `refs`
  used to take any string. Now a string that is neither a tracker reference nor a URL with
  a scheme is refused with `entry_fields_invalid`, detail `not_a_reference`. Strings such
  as `7`, `docs/x.md` or `commit abc` used to be stored and are now rejected. An agent that
  wrote them must put a tracker reference (a task key or an entry of a case) or a full URL
  there, and keep prose in the entry body. Entries already stored are not touched. REST and
  MCP go through the same check.

## Upgrade notes

**What happens to your installation**

- **A database migration runs.** It adds three columns to `accounts` for the introduction
  state. Accounts that existed before the update get `skipped` with all explanations
  hidden: those people already use the product, so nothing new pops up in front of them.
  New accounts start as `pending` with everything shown. The migration is one-way for
  data written afterwards: rolling back drops the columns.
- **The training project does not appear on an installation that already has projects.**
  The step that creates it runs on every start but only acts when no project exists, so
  an updated installation is not given one. The "Start" screen opens from the side panel
  for everyone. If you want the training project anyway, run the command yourself:
  `docker compose run --rm --entrypoint python api -m app.cli tutorial --force`.
- **The updater container is replaced once.** `docker-compose.prod.yml` changed the
  `updater` service (its list of one-off steps now includes `tutorial`), and its revision
  label moved. `updater-renew` replaces the updater when the running container's label
  differs from the release file, so each installation recreates the updater container on
  the first start on v0.6.0. This is the normal path; nothing to do, but do not be
  surprised to see the container restart.
- **Moving an installation.** An archive is still accepted only by an installation with no
  projects of yours; the training project `START` (author `tracker`) is not counted, so a
  fresh installation still takes an archive.
- **Configuration.** New optional settings: `CASEFILE_LANGUAGE` (language of the training
  project, `en` or `ru`, default `en`) and `TRACKER_UI_PUBLIC_URL` (board address printed in
  the training task, defaults to `http://localhost:` plus `CASEFILE_PORT`). Nothing is
  required.
- **API.** `openapi.json` gains `PATCH /api/v1/accounts/{account_id}/onboarding` and the
  `onboarding` field on the account. The only behaviour change to an existing operation is
  the `refs` check above.

## Not verified yet

- **Nothing here was looked at in Safari.** Screens were checked in headless Chromium and
  by page tests; how the explanations, the walk-through bar and the "Start" screen look in
  Safari, in dark theme and at phone width beyond "no sideways scroll" has not been seen.
- **The training text has no full measurement.** A trial with a weak model closed the
  cycle in some runs and stumbled in others; the final text was not measured over a full
  series of blind runs (that is a separate task). The English version passed fewer trial
  runs than the Russian one.
- **`install.ps1` was never executed by PowerShell** (no PowerShell in the build
  environment); its language detection and the new phrases are checked by reading and by
  text tests.
- **The step-one tick is approximate.** "Agent connected" reads the author kind of a token,
  so a token issued to a named agent by a person from the "Access" screen may not tick it.
- **The "Connect an agent" screen always shows the training-project phrase**, even on an
  installation where `START` was archived or never created.
- **The full chain of `CASEFILE_LANGUAGE` from `.env` through a real production start to a
  Russian `START-1`** was checked link by link, not as one run.
- **A live MCP `add_entry` call with a rejected `refs` value was not run**; REST and the
  domain are tested, and MCP uses the same check.
