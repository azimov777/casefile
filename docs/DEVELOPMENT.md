# Tracker

Бэкенд трекера задач, в котором задачи ведут агенты. Человек смотрит задачи и отвечает
на вопросы. Два интерфейса поверх одного слоя сценариев: **REST API** для интерфейса
человека и назначателя и **MCP-сервер** для агентов; бизнес-логика между ними не
дублируется.

Что и зачем строим — `docs/CONCEPT.md`, правила разработки — `docs/CONVENTIONS.md`,
разработчику интерфейса — `ui/docs/FRONTEND.md`, коды ошибок — `docs/ERRORS.md`.

## Требования

Docker и Docker Compose. Больше ничего: Python, зависимости, миграции, тесты и линтер
живут в контейнерах. Установка Python на хост-машину не поддерживается и не нужна.

## Быстрый старт

С нуля, на машине, где есть только Docker:

```bash
cp .env.example .env          # необязательно: у дев-контура есть значения по умолчанию
docker compose up -d          # поднимает постоянные сервисы (какие — раздел «Структура»)
docker compose run --rm migrate   # применяет миграции
docker compose run --rm init      # заводит владельца и печатает его первый токен
docker compose run --rm local-token   # кладёт ключ интерфейса в .secrets/ui-token
docker compose run --rm demo      # наполняет установку демонстрационными данными
curl http://localhost:8000/health
```

Ответ здорового сервиса:

```json
{"status": "ok", "version": "0.1.0", "environment": "local", "database": "ok"}
```

Дальше — первый экран с токеном, который напечатал `init`: раздел «Первый экран».

Документация API — http://localhost:8000/docs, схема — http://localhost:8000/openapi.json
и в корне репозитория.

Останавливается контур предсказуемо и без убийства: `docker compose stop` укладывается в
секунды даже при открытом потоке ленты и подключённом агенте. Открытые чтения закрываются
сами по сигналу, а запрос и вызов инструмента, которые пишут в базу, дописываются —
сроки объявлены в самих файлах Compose рядом с сервисами.

### Демо-данные

```bash
docker compose run --rm demo
```

Заводит очередь `DEMO` и задачи на каждый статус: дела с записями всех типов,
связи всех видов, один открытый блокирующий вопрос владельцу,
человек и постоянный агент в реестре и одна запись, подписанная меткой временного
агента. Этого хватает, чтобы наполнить каждый экран интерфейса и увидеть цикл
назначателя на живых данных:

```bash
# кандидаты: в демо такой ровно один — остальные заблокированы или ждут ответа
curl -H "Authorization: Bearer $TOKEN" --get --data-urlencode \
     'query=queue: DEMO and status: open and blocked: false and open_blocking_questions: 0' \
     http://localhost:8000/api/v1/tasks
```

Команда идемпотентна: повторный запуск видит очередь `DEMO` и ничего не делает. Начать
заново — снести том с данными: `docker compose down -v`. В прод-контуре сервиса `demo`
нет намеренно — демо-данные в рабочей установке мусор.

## Поставляемые артефакты контракта

```bash
docker compose run --rm schema
```

Пишет два файла: `openapi.json` — схему для генерации типизированного клиента, и
`docs/ERRORS.md` — справочник кодов ошибок. Базы команде не нужно: и то и другое —
свойства кода, а не работающей установки.

Схема пригодна к генерации клиента, и это проверяется тестом, а не обещается: у каждого
маршрута есть модель ответа, `operation_id` читаем и стабилен, перечисления — строковые
enum, объектов неизвестной формы нет нигде, кроме задокументированных мест.

```bash
npx openapi-typescript openapi.json -o src/shared/api/openapi.ts
```

Оба файла **коммитятся**: интерфейс (`ui/`) берёт схему из git, не поднимая Docker, а
справочник ошибок читают прямо здесь. Отставание копии от кода снято не обещанием, а
тестами: `tests/test_artifacts.py` сравнивает закоммиченный `openapi.json` с выгруженным,
`tests/test_api_contract.py` — `docs/ERRORS.md`. Забыли пересобрать — падает прогон, а не
фронтенд. Выгружает их только дев-контур: установке из готовых образов схема не нужна.

## Доступ к API

Все маршруты `/api/v1` требуют токена — исключений нет. Вне защиты остался только `/health`:
он для Docker и мониторинга и в контракт с фронтендом не входит.

```bash
curl -H "Authorization: Bearer trk_..." http://localhost:8000/api/v1/participants
```

### Первый экран

`GET /api/v1/bootstrap` отдаёт всё, чем интерфейс рисует первый кадр, одним запросом:
участника за токеном, сам токен (`token`: его `id` и набор `scope`), очереди установки и
число открытых вопросов, адресованных участнику.

```bash
curl -H "Authorization: Bearer $TOKEN" http://localhost:8000/api/v1/bootstrap
```

Ровно это и ничего сверх: списки задач и вопросов приходят своими запросами, уже с
фильтрами, которые выбрал человек. У общего агентского токена участника нет — тогда
`participant` приходит `null`, а `open_questions` равен нулю, потому что временного
агента нельзя адресовать вопросом.

Токен стоит в первом кадре потому, что «кто я» в трекере — это участник и его право, а
право одно: набор токена. По набору интерфейс с первого кадра решает, открыта ли запись;
по `id` — тому же, что в `GET /api/v1/tokens`, — узнаёт свой ключ в списке токенов. Токен
есть у любого запроса, в том числе с общим агентским токеном, где `participant` пуст.
Секрета и хеша в ответе нет.

### Сведения установки: адрес MCP

`GET /api/v1/installation` отдаёт то, что одинаково для любого токена и меняется только с
настройкой установки: `mcp_url` — адрес, по которому клиент агента подключается к MCP. Из
него интерфейс собирает готовую конфигурацию клиента на экранах «Подключить агента»
(`/connect`) и «Доступы» (`/access`). В первый кадр адрес не входит: он нужен этим двум
экранам и больше никому.

```bash
curl -H "Authorization: Bearer $TOKEN" http://localhost:8000/api/v1/installation
# {"data": {"mcp_url": "http://localhost:8100/mcp"}}
```

Адрес задаёт `TRACKER_MCP_PUBLIC_URL` целиком — со схемой, хостом, портом и путём. Пусто —
`http://localhost:<TRACKER_MCP_PORT><TRACKER_MCP_PATH>`: это верно для клиента на машине
установки и двигается вместе с портом MCP. Задавать адрес нужно, когда клиент видит MCP
иначе: через прокси с TLS или с другой машины. По заголовкам запроса (`Host`,
`X-Forwarded-*`) он не угадывается намеренно: запрос пришёл на адрес интерфейса, а не MCP,
и заголовки пишет клиент. Адрес не HTTP или с паролем (`user:password@`) не пройдёт
проверку настроек, и процессы `api` и `mcp` не поднимутся: адрес видит всякий держатель
любого ключа. Решение и отвергнутые варианты — `docs/CONCEPT.md`, 5.1, и дело `TRK-65`.

### Первичная инициализация

Первый токен взять неоткуда, кроме командной строки: выпустить его через API нельзя, потому
что API уже требует токен. Это и делает `docker compose run --rm init` — заводит
участника-человека `owner` и печатает его токен набора `main`.

Команда срабатывает **только на пустой установке**: если в базе есть хотя бы один токен, она
ничего не создаёт и говорит об этом. Так её можно держать рядом с миграциями, не боясь, что
случайный повторный запуск наплодит действующие доступы. Потеряли секрет — выпускайте новый
явно:

```bash
docker compose run --rm --entrypoint python api -m app.cli issue-token \
       --participant owner --scope main
```

Токен показывается **один раз**: в базе лежит только его хеш, восстановить секрет нельзя.

### Ключ для локального интерфейса

Три команды выдают доступ, и берутся они в разных случаях:

| Команда | Кому доступ | Набор | Куда попадает секрет | Повтор |
|---|---|---|---|---|
| `init` | человеку, один раз на пустой установке | `main` | в вывод команды | ничего не делает |
| `issue-token` | кому назвали, когда доступ нужен ещё раз | любой | в вывод команды | выпускает ещё один |
| `local-token` | интерфейсу этой машины | `main` | **только в файл**, права `0600` | ничего не делает, ключ другого набора заменяет |

`local-token` существует потому, что на локальной установке человек у трекера один, и он же
её владелец: ключ добывает сама установка, а человек его не видит и не хранит. Права у ключа
владельческие — набор `main`, почему — ниже.

```bash
docker compose run --rm local-token     # пишет .secrets/ui-token
```

Секрет в вывод не попадает **никогда**: команда стоит в журнале подъёма контура, а секрет
в журнале — это тот же секрет на виду. Проверить выданный ключ, не печатая его:

```bash
curl -H "Authorization: Bearer $(cat .secrets/ui-token)" \
     http://localhost:8000/api/v1/bootstrap
```

Идемпотентность здесь держится на файле, а не на базе, и иначе быть не может: в базе лежит
хеш, и секрет выпущенного токена не восстановить. Отсюда пять исходов:

1. в файле действующий секрет набора `main` — не делается **ничего**, файл не
   переписывается;
2. установка пуста — заводится владелец и выпускается его первый токен набора `main`;
3. файла нет или секрет в нём негоден — выпускается новый, а прежний токен с тем же именем
   отзывается тем же действием: действующих секретов, которых никто не знает, не остаётся;
4. в файле действующий секрет другого набора — выпускается ключ набора `main`, а прежний
   отзывается тем же действием, какое бы имя он ни носил;
5. названного участника нет, а установка не пуста — отказ `participant_not_found` с кодом
   возврата 1. Второго участника опечатка в имени не заведёт.

При любом исходе, кроме отказа, у человека за ключом есть учётная запись администратора:
её команда заводит, если её нет (`<имя>@localhost`, без пароля), и кладёт в неё прежний
`TRACKER_PASSWORD_HASH`, если пароля у неё ещё нет (раздел «Учётные записи и вход:
установка в сети»). Вывод называет почту и то, задан ли пароль.

Набор — `main`, и это решение владельца от 11 сентября 2026 (дело `UI-104`, запись 7), а
не умолчание: на локальной установке человек и есть её владелец, и выпускать и отзывать
доступы агентов он должен мочь в интерфейсе, а не в терминале. Без этого после установки
одной строкой он не выпустил бы токена вовсе: прод-контур `init` не запускает, а `main`
установщик выдаёт только агенту (`agent-token`).

Прежде набор был `task` (`TRK-46`): ключ уезжает в браузер, и открывать им выпуск токенов
казалось нельзя. Риск за этим доводом настоящий, но закрывает его не набор. Порт интерфейса
опубликован только на петле, и от сети этого хватает, а от страницы в том же браузере —
нет: чужой домен, перепривязавший свою запись DNS на `127.0.0.1` (DNS rebinding), читает
`/config.json` как свой источник и ходит полученным ключом в `/api/`. С ключом `task` это
давало чужой странице задачи, с `main` дало бы и выпуск доступов. Поэтому ключ отдаётся
только своим адресам: nginx интерфейса отвечает на `localhost`, `127.0.0.1` и `[::1]`, а
чужой `Host` получает `421` без ключа и без прокси в API (`UI-107`,
`ui/docker/nginx.conf.template`); дев-сервер интерфейса проверяет `Host` сам. Где такой
границы нет, граница другая: у установки, выставленной в сеть, общего ключа нет вовсе —
каждый получает свой токен входом по почте и паролю (раздел «Учётные записи и вход:
установка в сети»).

Ключ другого набора в файле заменяется при следующем запуске команды — так работающие
установки, получившие `task` до этого решения, переходят на `main` сами. Прод-контур зовёт
`local-token` на каждом подъёме, дев-контур — только руками: там сервис за профилем `tools`.
Сверяется один набор, имя участника и имя токена — нет: файл это собственная копия
установки, и лишние условия дали бы перевыпуск на ровном месте. Имя токена (`local-ui`)
постоянное — по нему же находится предшественник под отзыв.

Файл содержит **только секрет**, без перевода строки в конце, и лежит в `.secrets/` —
каталоге, невидимом ни репозиторию (`.gitignore`), ни сборке образа (`.dockerignore`).
Своё место задаётся ключом `--output`, участник и имя токена — `--participant` и `--name`:

```bash
docker compose run --rm --entrypoint python api -m app.cli local-token \
       --output /куда/нибудь/ещё --participant owner --name local-ui
```

**Порядок команд при первом запуске решает одно — будет ли у человека секрет в руках.**
`init` считает установку настроенной, если в базе есть хотя бы один токен — любой. Поэтому
`local-token` на пустой установке закрывает дверь `init`: права владельца это не отнимает —
ключ интерфейса сам набора `main`, — но секрета, который `init` печатает для `curl` и
терминала, человек не получит, и выпускать его придётся явно через `issue-token`. Хотите и
то и другое — зовите `init` раньше:

```bash
docker compose run --rm migrate
docker compose run --rm init          # секрет человеку в руки, набор main
docker compose run --rm local-token   # ключ интерфейсу в файл, набор main
```

Сервис есть в обоих контурах, но ключ из них выходит по-разному. В разработке файл
ложится в `.secrets/ui-token` смонтированного репозитория, откуда его берёт дев-сервер
интерфейса (`ui/README.md`). В проде ключ живёт в именованном томе, который интерфейс
монтирует только на чтение, и на хост не выходит вовсе — раздел «Продакшен-контур».

Владельца файла дев-контур возвращает хозяину, и `cat` из подсказки выше работает
благодаря этому. Дев-контур пишет от root — непривилегированного пользователя дев-образ не
заводит, — и на Linux файл с правами `0600` достался бы хозяину машины чужим: ни прочитать,
ни удалить. Поэтому команда сервиса заканчивается возвратом владельца: root узнаёт хозяина
у самого смонтированного каталога и отдаёт файл ему. Готовить и настраивать для этого
нечего: контур по-прежнему поднимается одной командой. Разбор — `docs/notes/docker.md`.

Токен агенту выпускается тем же способом — `docker compose run --rm agent-token`: действующий
токен набора `main` участника `agent` в `.secrets/agent-token`, секрет не печатается.

### Наборы токена

Прав в трекере ровно одно — набор токена. Ролей, владельцев и разрешений по роду участника
нет: любую запись и любой переход может сделать кто угодно. Единственное условие «кто» —
вход в `in_progress` только исполнителю задачи; это проверка перехода в домене
(`check_taken_by_assignee`), а не право набора.

| Набор | Что открывает |
|---|---|
| `task` | Рабочий цикл агента: задачи, дело, связи, поиск, лента, чтение реестров. |
| `main` | То же плюс запись участников, токенов и очередей. |

### Участники, токены и очереди

Человеку за этим в терминал ходить не нужно: участники и токены живут на экране «Доступы»
(`/access`) — завести агенту участника, выпустить ему токен, увидеть, чем на установку
ходят и когда ходили в последний раз, отозвать лишнее. На локальной установке экран открыт
сразу, потому что ключ самого интерфейса набора `main` (раздел «Ключ для локального
интерфейса»); список токенов виден и с ключом `task`, а запись — нет. Очереди в интерфейс
не входят намеренно (`ui/docs/CONCEPT.md`, 7) и заводятся отсюда.

Ниже — тот же контракт напрямую: он нужен скриптам, установке, где ключа в браузере нет,
и разбору отказов.

```bash
# завести постоянного агента (нужен набор main)
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"kind": "agent", "name": "release_bot", "description": "Релизный бот"}' \
     http://localhost:8000/api/v1/participants

# выпустить ему токен рабочего цикла (секрет виден только в этом ответе)
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"name": "ci", "scope": "task", "participant": "release_bot"}' \
     http://localhost:8000/api/v1/tokens

# завести очередь
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"key": "TRK", "title": "Трекер", "description": "Где лежит код, куда смотреть"}' \
     http://localhost:8000/api/v1/queues

# отозвать токен
curl -X DELETE -H "Authorization: Bearer $TOKEN" http://localhost:8000/api/v1/tokens/$TOKEN_ID
```

Имена участников уникальны без учёта регистра и хранятся в нижнем; ключи очередей — в
верхнем. Переименования нет ни у тех, ни у других: имя стоит подписью в записях дела, ключ
вшит в ключ каждой задачи очереди. Удаления тоже нет — доступ снимается отзывом токена.

### Задачи и дело

Задача рождается в `backlog` и живёт по зашитой таблице переходов: `backlog → open →
in_progress → done`, из любого незакрытого статуса — в `cancelled`. Шаг назад и
отмена требуют `reason`; перед `open` четыре раздела и `checks` должны быть заполнены.
Название, описание и разделы правятся только в `backlog`; исполнитель и приоритет
— в любом незакрытом статусе. Каждое действие подшивает служебную запись в дело.

```bash
# завести задачу (набора task достаточно)
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"queue": "TRK", "title": "Починить выдачу ключей", "description": "Ключ сгорает",
          "goal": "...", "context": "...", "constraints": "...", "output": "...",
          "checks": ["Пустое название не тратит номер"]}' \
     http://localhost:8000/api/v1/tasks

# пакет преемника: карточка, признаки, последняя сводка, открытые вопросы, опись дела
curl -H "Authorization: Bearer $TOKEN" http://localhost:8000/api/v1/tasks/TRK-1

# поправить раздел (только в backlog) с проверкой версии
curl -X PATCH -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"goal": "Ключи не сгорают", "version": 1}' http://localhost:8000/api/v1/tasks/TRK-1

# перевести статус; шаг назад — с причиной
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"to": "open"}' http://localhost:8000/api/v1/tasks/TRK-1/transition

# записи дела с телами и нагрузкой; фильтры nos, types, after_no
curl -H "Authorization: Bearer $TOKEN" \
     'http://localhost:8000/api/v1/tasks/TRK-1/entries?types=summary&after_no=3'

# одна запись по её номеру в задаче — адрес из ссылки TRK-1#5
curl -H "Authorization: Bearer $TOKEN" http://localhost:8000/api/v1/tasks/TRK-1/entries/5
```

#### Список и поиск задач

`GET /api/v1/tasks` — единственный способ отобрать задачи, и он принимает два входа
сразу: строку на языке запросов (`query`) и структурные параметры по каждому полю. На
одинаковых условиях они дают одинаковый результат — это один и тот же код, а не две
похожие реализации. Условия из обоих источников складываются по `and`.

Поля отбора: `queue`, `parent` (прямые дети названной задачи; `empty()` — верхний
уровень очереди), `status`, `assignee`, `priority`, `text` (подстрока в названии
и описании) и вычисляемые признаки — `blocked`, `open_questions` и соседи. Признаки не
хранятся колонками, а считаются из связей и дела прямо в запросе, поэтому они всегда
согласованы с карточкой. Полный список полей отбора трекер называет сам: отказ на
неизвестное поле несёт его в `details.allowed`.

Они же приезжают **в каждой строке выдачи** объектом `features` — тем самым, что лежит в
пакете преемника, и тем же составом: он описан схемой `TaskFeaturesRead` в `openapi.json`.
Назначателю не нужен второй запрос на задачу, чтобы понять, можно ли её брать. Стоят они
дёшево: подзапросы считаются только для строк страницы, замеры на 40 000 задач — в
`docs/notes/search.md`.

Рядом с ними в строке лежит `parent` — родитель задачи, ключ и название (схема
`TaskParentRead`); у задачи верхнего уровня `null`. По нему видно, к какой программе
относится задача, без чтения её карточки. Выбирается поле тоже именем
(`fields=key,parent`), и тем же именем по родителю отбирают: `parent: TRK-7`. В карточке
(`GET /api/v1/tasks/{key}`) родитель и дети — поля `parent` и `children`, а не виды в
`links`.

```bash
# кандидаты назначателя одной строкой: что можно брать в работу прямо сейчас
curl -H "Authorization: Bearer $TOKEN" --get --data-urlencode \
     'query=queue: TRK and status: open and blocked: false and open_blocking_questions: 0' \
     http://localhost:8000/api/v1/tasks

# то же самое структурными параметрами — тот же список в том же порядке
curl -H "Authorization: Bearer $TOKEN" \
     'http://localhost:8000/api/v1/tasks?queue=TRK&status=open&blocked=false&open_blocking_questions=0'

# только нужные поля: полная задача с пятью разделами съедает контекст агента
curl -H "Authorization: Bearer $TOKEN" \
     'http://localhost:8000/api/v1/tasks?fields=title,status,assignee&limit=100'

# признаки выбираются целиком именем features; отдельный признак в fields не поле ответа
curl -H "Authorization: Bearer $TOKEN" \
     'http://localhost:8000/api/v1/tasks?fields=title,features&limit=100'

# дети программы и её имя в каждой строке: parent и отбирает, и приезжает в ответе
curl -H "Authorization: Bearer $TOKEN" --get --data-urlencode 'query=parent: TRK-7' \
     --data-urlencode 'fields=title,parent' http://localhost:8000/api/v1/tasks

# порядок и страницы: sort принимает key, updated_at и priority, минус — по убыванию
curl -H "Authorization: Bearer $TOKEN" \
     'http://localhost:8000/api/v1/tasks?sort=-updated_at&limit=20'
```

Операторы языка: `=`, `!=`, `>`, `>=`, `<`, `<=`, `~` (вхождение подстроки), `!~`, `in`,
`not in`; значения перечисляются через запятую (`status: open, in_progress`), условия
связываются `and`, `or` и скобками. `empty()` находит задачи без значения:
`assignee: empty()`. Значение с пробелом или похожее на вызов функции пишется в кавычках.

Функций дат, `me()` и сохранённых фильтров нет намеренно. Ошибка разбора приходит с
позицией символа и причиной (`invalid_search_query`), незнакомое имя поля — со списком
допустимых (`search_field_unknown`): запрос чинится за одну попытку, а не подбором.

Курсор устойчив к вставкам: граница страницы задана значением ключа сортировки, а не
смещением, поэтому задача, заведённая между запросами, не сдвигает выдачу и не вытесняет
из неё соседа. Порядок по умолчанию — по ключу задачи: `TRK-10` идёт после `TRK-2`.

#### Записи агента

Дело пополняется одним маршрутом `POST /tasks/{key}/entries`. Тело — размеченное по
`type` объединение: у каждого типа своя форма `payload`, и клиент, сгенерированный из
OpenAPI, знает её точно.

```bash
# сводка: четыре части, все непустые. Заголовок не принимается — им становится
# первая строка done. Здесь подшивают промежуточную; закрывающая едет в
# POST /tasks/{key}/close и несёт пятую часть — unmeasured
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"type": "summary", "payload": {"done": "Разобрался", "remaining": "Дописать",
          "blockers": "нет", "next_step": "Перенести вызов в конец create_task"}}' \
     http://localhost:8000/api/v1/tasks/TRK-1/entries

# вопрос участнику реестра; blocking обязателен и значения по умолчанию не имеет
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"type": "question", "title": "Какой ключ канонический?",
          "payload": {"addressees": ["owner"], "blocking": true}}' \
     http://localhost:8000/api/v1/tasks/TRK-1/entries

# вердикт по обзорной проверке; тело записи — доказательство
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"type": "verdict", "body": "Прогон зелёный",
          "payload": {"check_no": 1, "outcome": "passed"}}' \
     http://localhost:8000/api/v1/tasks/TRK-1/entries

# решение, попытка, находка, артефакт, заметка — без нагрузки, но с заголовком
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"type": "finding", "title": "Номер выдаётся до валидации",
          "refs": ["TRK-1#3", "https://example.com/pr/12"]}' \
     http://localhost:8000/api/v1/tasks/TRK-1/entries
```

Заголовок принимается только там, где его нечем вывести. У `summary` он равен первой
строке `done`, у `answer` и `verdict` собирается из нагрузки. Служебные типы
(`status_changed`, `created`, ...) подшивает сам трекер, и в запросе они не принимаются.
`refs` со ссылками на задачи (`TRK-7`) и записи (`TRK-42#12`) проверяются на
существование; адреса — нет.

Две валидации перехода живут именно здесь, и обе считаются **после последнего входа
в `in_progress`**: выход из работы требует сводки, подшитой после этой границы
(`409 summary_required`), а `in_progress → done` — чтобы последний вердикт каждой
проверки, подшитый после неё же, был `passed` (`409 checks_not_passed`; незасчитанные
проверки — в `details.checks` парами `check_no` и `reason`: `no_verdict` или `failed`).
Обзорные проверки прогоняет исполнитель, не выходя из работы; вердикты прошлых заходов
остаются в деле историей, но не засчитываются.

Записи дела неизменяемы: маршрутов правки и удаления нет, а триггер в базе отклоняет
`UPDATE` и `DELETE`. Ошибочная запись исправляется следующей. В закрытую задачу записи
подшивать можно — меняться нельзя полям, а не делу.

#### Вопросы

Вопрос — не отдельная сущность, а представление над делом: он открыт, пока в той же
задаче нет записи `answer` с его номером.

```bash
# входящая: по умолчанию открытые вопросы участника, чьим токеном сделан запрос
curl -H "Authorization: Bearer $TOKEN" \
     'http://localhost:8000/api/v1/questions?blocking=true&queue=TRK'

# ответить — записью в дело той задачи, где вопрос задан
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"type": "answer", "body": "Верхний регистр", "payload": {"question_no": 4}}' \
     http://localhost:8000/api/v1/tasks/TRK-1/entries
```

### Лента журнала

Отдельной таблицы событий в трекере нет: журнал всех записей дела **и есть** лента для
внешнего мира (`docs/CONCEPT.md`, 4.1). У каждой записи свой сквозной номер `seq`, он же
курсор ленты. Записи постоянны — срока хранения нет, догнать можно с любого номера.

Отсюда правило, о которое легко споткнуться: **изменение, не оставившее записи, до
ленты не доходит**. Поэтому записи оставляет каждое изменение задачи, включая правку
приоритета — она подшивается типом `field_changed`. Раньше обвязка была исключением,
и открытый экран молча показывал устаревшее значение.

```bash
# хвост: всё, что случилось после записи 1024
curl -H "Authorization: Bearer $TOKEN" \
     'http://localhost:8000/api/v1/journal?after=1024'

# фильтры складываются по «и»: задача, очередь, типы записей
curl -H "Authorization: Bearer $TOKEN" \
     'http://localhost:8000/api/v1/journal?queue=TRK&types=answer&types=status_changed'

# долгое ожидание: ответ приходит, как только появилась первая подходящая запись,
# и не позже чем через 30 секунд. Потолок — 60, выше отвечает 422
curl -H "Authorization: Bearer $TOKEN" \
     'http://localhost:8000/api/v1/journal?after=1024&wait=30'
```

Ожидание построено на `LISTEN/NOTIFY` PostgreSQL, а не на опросе базы, и на время сна
отпускает соединение из пула. Пустой список по истечении ожидания означает «ничего не
случилось» — это не ошибка. Оповещение уходит из транзакции подшивки и доставляется при её
фиксации, поэтому разбуженный читатель всегда видит строку, из-за которой проснулся.
Оборванный запрос ожидание не досиживает: сервер замечает ушедшего клиента не позже
следующего контрольного опроса (`TRACKER_JOURNAL_WAIT_POLL_INTERVAL`) и отпускает вызов.

Отсюда строится цикл назначателя: прочитать хвост с курсора, пересчитать кандидатов,
запустить харнесс. Различать записи для этого не нужно — пересчёт дёшев:

```bash
AFTER=0
while :; do
  BATCH=$(curl -sH "Authorization: Bearer $TOKEN" \
               "http://localhost:8000/api/v1/journal?after=$AFTER&wait=60")
  LAST=$(jq -r '.data[-1].seq // empty' <<<"$BATCH")
  [ -n "$LAST" ] || continue
  AFTER=$LAST
  # пересчитать кандидатов и запустить харнесс для новых
  curl -sH "Authorization: Bearer $TOKEN" \
       'http://localhost:8000/api/v1/tasks?query=status:%20open%20and%20blocked:%20false%20and%20open_blocking_questions:%200'
done
```

#### Поток тех же записей (SSE)

Тот же хвост, но потоком — для браузера и всего, что не хочет опрашивать:

```bash
curl -N -H "Authorization: Bearer $TOKEN" -H 'Last-Event-ID: 1024' \
     'http://localhost:8000/api/v1/journal/stream?queue=TRK'
```

```
id: 1025
event: answer
data: {"id":"...","seq":1025,"no":4,"task_key":"TRK-1","type":"answer", ...}
```

Фильтры те же, что у ленты. `id:` кадра — это `seq`; он же возвращается в `Last-Event-ID`
при переподключении, и поток продолжает ровно со следующей записи, без пропусков и
повторов. Без курсора поток начинает с конца журнала: «что будет дальше». Слишком старого
курсора не бывает — отказ здесь один, `Last-Event-ID`, который не разбирается как
неотрицательное целое.

Это **единственный** ответ API без оболочки `data`: завернуть кадр во что-то ещё значит
перестать быть SSE. Полезная нагрузка кадра описана той же схемой, что и элемент ленты.
Браузерный `EventSource` заголовков не шлёт, а токен в адресе уехал бы в журналы прокси и
в историю браузера — поэтому фронтенд открывает поток `fetch`-клиентом (например,
`@microsoft/fetch-event-source`), а для клиентов, которые не умеют и этого, есть параметр
`last_event_id`.

Число одновременно открытых потоков на процесс ограничено
`TRACKER_JOURNAL_STREAM_MAX_CONNECTIONS`; сверх него приходит `429`, который повторяют
через паузу.

### Временные агенты и `X-Actor-Label`

Токен, выпущенный **без** `participant`, — общий агентский. Он не называет автора сам, и
каждый запрос с ним обязан нести метку временного агента:

```bash
curl -X POST -H "Authorization: Bearer $SHARED_TOKEN" -H "X-Actor-Label: nightly_agent" \
     -H 'Content-Type: application/json' -d '{"key": "OPS", "title": "Эксплуатация"}' \
     http://localhost:8000/api/v1/queues
```

Без заголовка запрос отклоняется с кодом `actor_label_required`: приписать действие некому.
Именной токен метку игнорирует — его подпись всегда имя своего участника, и подделать её
заголовком нельзя. Временного агента нельзя адресовать вопросом: для этого участника надо
завести в реестре.

### Повтор создающего вызова и `Idempotency-Key`

Агент падает и повторяет запрос, не зная, прошёл ли предыдущий. Любой создающий вызов —
задача, запись дела, связь, очередь, участник, токен — принимает заголовок с ключом,
который клиент придумывает сам (обычно UUID):

```bash
curl -X POST -H "Authorization: Bearer $TOKEN" -H "Idempotency-Key: $(uuidgen)" \
     -H 'Content-Type: application/json' \
     -d '{"queue": "TRK", "title": "Починить выдачу ключей", "description": "..."}' \
     http://localhost:8000/api/v1/tasks
```

- **Повтор с тем же ключом и тем же запросом** отвечает первым ответом целиком, а второй
  объект не заводится. Одновременные повторы тоже: они расходятся на уникальности в базе,
  а не на проверке в коде, поэтому десять параллельных попыток дают одну задачу.
- **Тот же ключ с другим запросом** — `409 idempotency_key_reused`: ключ обещает «это тот
  же самый вызов», и обещание проверяется отпечатком тела и адреса.
- **Ключ живёт в паре с токеном.** Одинаковые ключи разных агентов независимы.
- **Ключ помнят сутки**, потом он забывается вместе с сохранённым ответом и может быть
  использован заново. Устаревшие ключи снимаются попутно, при записи следующего.
- **Без заголовка поведение обычное**: два одинаковых запроса заведут два объекта.

Отдельно про выпуск токена: повтор с тем же ключом возвращает **тот же секрет** — иначе
запрос, оборвавшийся по сети, оставлял бы действующий токен, которого никто не видел.
Ровно поэтому ответ хранится целиком и живёт не дольше суток.

## MCP-сервер для агентов

Второй интерфейс трекера. Агент (Claude Code и подобные) ходит не в REST, а в MCP: те же
сценарии, но инструментами, описания которых читает модель. Через MCP проходит **весь**
цикл задачи — взять, вести дело, спросить, декомпозировать, проверить, закрыть.

```bash
docker compose up -d mcp          # поднимается вместе с контуром
curl http://localhost:8100/health
```

```json
{"status": "ok", "version": "0.1.0", "database": "ok"}
```

Второй контур рядом с рабочим — так прогоняют живые проверки, не трогая установку с
открытыми соединениями агентов, — поднимается своим именем проекта и своими портами:

```bash
POSTGRES_PORT=5433 TRACKER_PORT=8001 TRACKER_MCP_PORT=8101 \
    docker compose -p tracker-check up -d db api mcp
docker compose -p tracker-check down -v   # погасить вместе с томом
```

`TRACKER_MCP_PORT` compose подставляет и в проброс, и в окружение контейнера, поэтому
процесс слушает ровно тот порт, который опубликован.

Адрес — `http://localhost:8100/mcp`, транспорт — streamable HTTP, авторизация — тем же
токеном, что и REST: `Authorization: Bearer trk_...` плюс `X-Actor-Label`, если токен общий
агентский. Второй схемы представления нет намеренно — участники и токены общие на оба
интерфейса.

Альтернатива HTTP — stdio, для клиентов, которые умеют только запустить команду: `docker
compose run --rm --no-deps -T -e TRACKER_MCP_TOKEN mcp python -m app.mcp --stdio`, токен в
`TRACKER_MCP_TOKEN` окружения. Тот же сервер и тот же разбор токена; без токена процесс не
стартует (`app/mcp/__main__.py`, `docs/notes/mcp.md`).

Этот же адрес установка сообщает интерфейсу (`GET /api/v1/installation`). Если клиент видит
MCP по другому адресу — через прокси или с другой машины, — его задаёт
`TRACKER_MCP_PUBLIC_URL` (раздел «Сведения установки: адрес MCP»).

### Инструменты по наборам токена

`tools/list` отдаёт только то, что открывает токен: набор `task` — рабочий цикл, набор
`main` — то же плюс очереди и участники. Это не безопасность (вызов недоступного
инструмента всё равно отвечает `permission_denied`), а экономия контекста: описание
инструмента, которым нельзя воспользоваться, модель читает зря.

Списка инструментов здесь нет: его отдаёт сам сервер, вместе с описанием каждого
вызова. Выпуска токенов через MCP нет и не будет — выдача доступов остаётся за
человеком.

Пакет преемника из `get_task` совпадает с ответом `GET /api/v1/tasks/{key}` поле в поле:
агент и человек видят одну и ту же задачу.

### Дисциплина: промпт и инструкции

Сервер раздаёт текст скила сам, двумя способами:

- промпт `tracker-discipline` — весь файл `skill/tracker-agent/SKILL.md`;
- поле `instructions` при подключении — его раздел «Кратко».

Показывает ли клиент их модели, решает клиент. Надёжный путь — установить скил в харнесс:
`skill/tracker-agent/` копируется в каталог скилов агента как есть.

Дисциплина живёт там и только там. Описание инструмента — контракт **одного вызова**: что
делает, что меняется во внешнем мире, что вернёт, при каких условиях откажет; ходов агента
и порядка вызовов в нём нет. Скил — последовательность из нескольких ходов и выбор между
ними. Результат — только данные. Границу держит `tests/test_mcp_skill.py`, а не вычитка:
описание, заговорившее с агентом в повелительном наклонении, роняет набор.

### Подключение к Claude Code

Сервер работает в контейнере, наружу опубликован порт `8100` (`TRACKER_MCP_PORT`).

Готовую команду с адресом этой установки и подставленным секретом выдаёт интерфейс. Экран
«Доступы» (`/access`) показывает её в тот единственный раз, когда виден секрет
выпущенного токена, — там же секция `~/.codex/config.toml` для Codex и JSON `mcpServers`
для прочих клиентов. Экран «Подключить агента» (`/connect`) показывает те же фрагменты без
секрета, с подстановкой на его месте, и работает любым ключом. Скопировать и вставить —
собирать команду руками не нужно.

В терминале то же самое делается так: токен агенту выпускают через REST.

```bash
# завести агента и выпустить ему токен рабочего цикла (секрет виден только в этом ответе)
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"kind": "agent", "name": "claude", "description": "Claude Code"}' \
     http://localhost:8000/api/v1/participants
curl -X POST -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"name": "claude-code", "scope": "task", "participant": "claude"}' \
     http://localhost:8000/api/v1/tokens

# подключить сервер (scope local — конфигурация только этого проекта, без репозитория)
claude mcp add --scope local --transport http tracker http://localhost:8100/mcp \
      --header "Authorization: Bearer trk_..."

claude mcp list    # tracker: http://localhost:8100/mcp (HTTP) - ✔ Connected
```

Дальше агент работает инструментами: `create_queue` токеном набора `task` отвечает
`permission_denied` с нужным набором в подробностях.

Если Claude Code работает не на той машине, где поднят контур, вместо `localhost` идёт
адрес хоста, а порт `8100` должен быть до него доступен. Токен кладите в конфигурацию
клиента, а не в репозиторий: `--scope local` пишет его в личный файл настроек.

### Ожидание ответа без опроса

`wait_journal(after, task, types, timeout)` возвращается, как только появилась первая
подходящая запись, и не позже, чем через `timeout` секунд (потолок — 60). Механика та же,
что у `GET /api/v1/journal?wait=` (раздел «Лента журнала»), с одной оговоркой процесса:
слушателя оповещений поднимает сам процесс MCP, и в логе это видно строкой
`Journal listener connected to channel tracker_journal`. Если её нет, ожидание работает
контрольным опросом и отвечает с задержкой до `TRACKER_JOURNAL_WAIT_POLL_INTERVAL`
секунд.

### Экономия контекста агента

Две настройки, обе про то, сколько токенов стоит один ответ:

| Переменная | Что делает |
|---|---|
| `TRACKER_MCP_PAGE_SIZE` | размер страницы у `read_entries`, `search_tasks`, `wait_journal`, `list_queues`, `list_participants`; по умолчанию 25 — меньше, чем у REST |
| `TRACKER_MCP_TEXT_LIMIT` | потолок длинного текста в выдаче `search_tasks`; обрезка объявлена полями `<поле>_truncated` и `<поле>_length`, а задача целиком — один `get_task` |

`search_tasks` по умолчанию просит узкий набор полей (`key`, `title`, `status`,
`assignee`, `priority`, `features`, `parent`): полная задача с пятью разделами съедает
контекст ровно там, где агент выбирает, что брать. Признаки в набор входят — по ним
решают, можно ли брать задачу, и без них пришлось бы звать `get_task` на каждую строку.
Родитель входит по той же причине: без него не видно, к какой программе относится задача.
Задаче верхнего уровня он стоит `"parent":null`. Пустой список `fields` возвращает задачу
целиком.

Службы `db`, `api` и `mcp` подняты с `restart: unless-stopped` и возвращаются сами после
перезагрузки машины: контур разработки и есть работающая установка трекера, а агенты
ходят в MCP из любой папки, не только когда открыт этот репозиторий. Ручную остановку
политика уважает — после `docker compose stop` или `down` контур остаётся выключенным до
следующего `up`. Разовые сервисы профиля `tools` из этого исключены (`restart: "no"`):
упавшая миграция или красные тесты не должны крутиться в цикле перезапусков. Автоподъём
работает, пока сам Docker запускается при входе в систему — в Docker Desktop это
«Start Docker Desktop when you sign in to your computer».

Правка исходника подхватывается автоматически: код смонтирован в контейнер, uvicorn
перезапускается сам. Пересборка образа нужна только после изменения `uv.lock` — раздел
«Зависимости» ниже; `up -d` следом переводит на новый образ поднятые службы:

```bash
docker compose build api
docker compose up -d
```

### Миграции

Миграции применяются отдельной командой, а не при старте приложения: несколько реплик,
одновременно накатывающих схему, — это гонка и испорченная база. После правки моделей:

```bash
docker compose run --rm migrate alembic revision --autogenerate -m "что изменилось"
docker compose run --rm migrate
```

Автогенерация видит только те модели, которые импортированы в `app/db/models/__init__.py`.

Цепочка ревизий начата заново задачей 20 и состоит из семи шагов: акторы и токены;
участники, токены с наборами и очереди; задачи и записи дела; выборки по делу; связи;
индексы поиска; ключи идемпотентности. Прежняя схема живёт в git по коммиту `49e2e49`.

`alembic check` на сошедшейся схеме штатно сообщает о снятии `CHECK` у каждой колонки-
перечисления — это ложное срабатывание, объяснённое в `docs/notes/db.md`. Если в выводе
**только** такие строки, модели и схема совпадают.

### Тесты

`docker compose run --rm test` поднимает БД, создаёт базу `tracker_test`, накатывает на неё
миграции и прогоняет весь набор. Каждый тест идёт внутри транзакции, которая откатывается
после него, поэтому порядок тестов не влияет на результат.

### Зависимости

Версии зависимостей бэкенда закрепляет `uv.lock` в корне репозитория. В `pyproject.toml`
стоят только нижние границы — с какой версии проект работает, — а оба образа и конвейер
ставят ровно записанное в lock-файле (`uv sync --locked`, `docker/Dockerfile.dev` и
`docker/Dockerfile.prod`). Сборка без кэша на любой машине получает те же версии, пока их
не обновили намеренно. Lock-файл, разошедшийся с `pyproject.toml`, валит сборку образа:

```
error: The lockfile at `uv.lock` needs to be updated, but `--locked` was provided.

hint: To update the lockfile, run `uv lock`.
```

uv на хосте не нужен: команда из подсказки — это сервис `lock`, и всё, что написано после
имени сервиса, уходит аргументами в `uv lock`. Базы он не поднимает.

Добавить или поменять зависимость — правка `pyproject.toml` нижней границей и lock-файл
тем же коммитом:

```bash
docker compose run --rm lock      # свести uv.lock с правкой pyproject.toml
docker compose build api          # образ с новым набором
docker compose run --rm test
```

Обновить зависимости — отдельный шаг с прогоном набора, отдельным коммитом
`build(deps): …`. Меняется только `uv.lock`:

```bash
docker compose run --rm lock --upgrade                   # все до свежих версий
docker compose run --rm lock --upgrade-package fastapi   # или одну
docker compose build api
docker compose run --rm lint && docker compose run --rm test
```

Красный набор после обновления — это находка, а не помеха: либо код догоняет библиотеку,
либо lock-файл возвращается (`git checkout uv.lock`) и причина становится задачей.

Регулярно то же самое делает бот обновлений на GitHub (`.github/dependabot.yml`). Раз в
неделю он открывает PR с новыми версиями: мелкие и исправляющие выпуски одним PR,
мажорные — каждый своим, транзитивные зависимости наравне с прямыми. Конвейер прогоняет на
PR линтер и весь набор. Бот, как и ручная команда, правит только `uv.lock`. Отдельным PR
он же двигает версию uv в образах (стадия `uv` в `docker/Dockerfile.*`).

Автослияния нет: зелёный PR сливает человек, потому что слитый коммит main уйдёт во все
установки со следующим выпуском (тег `vX.Y.Z`), а под `latest` — сразу. Чтобы и красный нельзя было слить по ошибке,
один раз после публикации в настройках репозитория включается защита `main` с обязательной
проверкой «Backend — ruff and pytest in Docker». Слитое на GitHub доезжает до локального
`main` через `git pull`, а до контура — через `docker compose build api` и `docker compose up -d`.

### Слияние ветки задачи

Ветка задачи сливается в `main` не голым `git merge`, а скриптом:

```bash
scripts/merge-task-branch.sh task/TRK-45 -m "merge(область): что изменилось (TRK-45)"
```

Он сливает без коммита, пересобирает образ из смёрженного дерева (`docker compose
build`) и прогоняет на этом результате тот же набор, что `checks` из
`.github/workflows/ci.yml`, кроме сквозных e2e (TRK-117): `docker compose run --rm lint`
(ruff check + ruff format --check) — всегда, `docker compose run --rm test` (весь
pytest) — всегда, `pnpm check` в `ui/` — только если сама ветка трогает `ui/`
(`git diff --name-only HEAD...MERGE_HEAD -- ui/`, не диффа смёрженного дерева, где `ui/`
есть всегда). Коммитит только зелёное во всех запущенных проверках, оставив в сообщении
строку `Merge-verified:` с исходом каждой. Пересборка — не жёстко названным тегом, а тем
же `docker compose`, что и прогон, — иначе ветка, меняющая `uv.lock` или
`docker/Dockerfile.dev`, проверялась бы зависимостями, поставленными в образ до слияния.
Красная любая проверка или неудачная пересборка — `git merge --abort`: ветка не слита,
`main` прежний. Конфликты скрипт оставляет человеку — разобрать, `git add`, довести тем
же скриптом с `--continue`.

Ветки очереди `TRK`, трогающие `ui/`, сливаются этим же корневым скриптом: `pnpm check`
запускается на хосте (нужен Node рядом с Docker-контуром бэкенда), из каталога `ui/`.
Сквозной `pnpm e2e` в этот скрипт не входит — им сливают только ветки очереди `UI`,
своим `ui/scripts/merge-task-branch.sh`.

Зачем это отдельный шаг: у слияния два зелёных родителя не означают зелёного результата.
Каждая ветка прогоняла набор у себя, а базой для следующей задачи становится результат, и
проверить его больше некому: конвейер GitHub видит только запушенное, а база агентам —
локальный main. Правило целиком
и что делать с исходом — `docs/CONVENTIONS.md`, раздел «Слияние ветки задачи в main».

### Выпуск

Выпуск — это тег `vX.Y.Z` в `origin` (`vX.Y.Z-rc.N` — пре-релиз). На него порознь реагируют
два конвейера, не дожидаясь друг друга:

- `.github/workflows/images.yml` — публикует образы `ghcr.io/<владелец>/casefile` и
  `casefile-ui` под номером версии и (кроме пре-релиза) двигает канал выпусков `stable`,
  который автообновятели установок сверяют раз в час.
- `.github/workflows/mcp-registry.yml` — публикует `server.json` в официальный реестр MCP
  (`registry.modelcontextprotocol.io`) под тем же номером версии. Вход — GitHub OIDC
  (`mcp-publisher login github-oidc`), без долгоживущего секрета: доступ подтверждает сама
  сборка, запущенная в этом репозитории с правом `id-token: write` (TRK-133). Версия в
  закоммиченном `server.json` — памятка о последнем выпуске, а не источник истины: workflow
  подставляет её из тега прямо перед публикацией и не коммитит правку обратно, поэтому
  файл руками перед выпуском не правят.

Тег пушится раньше `main` — иначе автообновятель прежней установки успел бы забрать файл
compose, который зовёт канал `stable` до того, как тот на него укажет (комментарий в
`images.yml`, `TRK-119`):

```bash
git tag vX.Y.Z
git push origin vX.Y.Z
# дождаться зелёных Actions на оба workflow, затем:
git push origin main
```

Живая проверка публикации в реестр — после самого выпуска, не раньше:

```bash
curl https://registry.modelcontextprotocol.io/v0.1/servers?search=io.github.azimov777/casefile
```

Ответ называет версию только что вышедшего тега с `isLatest: true`.

Затем идут площадки. GitHub Release руками создают из заметок к выпуску:
`gh release create vX.Y.Z --verify-tag --title "Casefile vX.Y.Z" --notes-file docs/release-notes/vX.Y.Z.md --latest`.
От него сама обновляется версия в Glama (Auto-Release). Что на каких площадках (GitHub,
Glama, mcp.so, списки awesome, каталоги поверх реестра) обновляется само, а что руками и где, —
таблица в деле `TRK-138#12`.

## Продакшен-контур

Продакшен-контур — это установка Casefile целиком (база, API, MCP, интерфейс) из готовых
образов, которые конвейер собирает из каждого коммита main и публикует в ghcr.io
(`.github/workflows/images.yml`). Исходников и сборки в нём нет, поэтому поднимается он
одной командой — из клона:

```bash
docker compose -f docker-compose.prod.yml up -d
```

— или без клона, установщиком одной строкой (`install.sh`, `install.ps1`): он кладёт
этот же файл в `~/casefile`, поднимает контур и печатает команду подключения агента.

Разовые шаги идут сами на каждом подъёме, в порядке зависимостей: миграции, ключ
интерфейса (`local-token`), токен агента (`agent-token`). Все идемпотентны. Ключи живут в
именованных томах `ui-key` и `agent-key` и на хост не выходят: интерфейс монтирует свой том
только на чтение, а токен агента читается разовым контейнером:

```bash
docker compose -f docker-compose.prod.yml run --rm --no-deps -T agent-token cat .secrets/agent-token
```

Доступ набора `main` человек получает ключом интерфейса — тем, которым браузер ходит в API
(раздел «Ключ для локального интерфейса»). Секрета в руки — для `curl` или скрипта —
установка сама не выпускает: `init` печатал бы его в журнал контейнера. Нужен — выпускается
явно, секрет печатается в этот терминал:

```bash
docker compose -f docker-compose.prod.yml run --rm --no-deps api \
  python -m app.cli issue-token --participant owner --scope main
```

Автообновление — служба `updater`: на старте Docker и дальше раз в час она сверяет канал
выпусков `stable` (его двигает только тег `vX.Y.Z`, `.github/workflows/images.yml`) и,
если вышел новый выпуск, берёт из его образа compose-файл и пересоздаёт службы; без сети
остаётся на прежних. Выпуск, который не поднялся (службы не стали здоровыми), откатывается
на прежний и больше не пробуется — до следующего выпуска. Коммит main без тега уходит под `latest` и до установок на
умолчаниях не доходит. Выключается `CASEFILE_AUTO_UPDATE=false`, закрепляется
`CASEFILE_VERSION=X.Y.Z`; остальные настройки установки (`CASEFILE_*`) — в
`.env.example`, устройство — в комментариях `docker-compose.prod.yml`. Живая проверка
цикла на своём реестре — `scripts/check-auto-update.sh`.

Отличия от контура разработки:

| | Разработка | Продакшен |
|---|---|---|
| Образ | собирается из `docker/Dockerfile.dev` | готовый из ghcr.io, `docker/Dockerfile.prod`, многостадийный |
| Код | смонтирован томом | в образе |
| Обновление кода | `--reload` при правке | новый выпуск в течение часа |
| Зависимости | рантайм + dev, из `uv.lock` | только рантайм, из того же `uv.lock` |
| Пользователь | root | непривилегированный `tracker` |
| Ключи интерфейса и агента | файлы в `.secrets/`, владелец возвращается хозяину | именованные тома |
| Разовые шаги | руками, `docker compose run --rm …` | сами, на каждом подъёме |
| Порты наружу | API, MCP, база | интерфейс и MCP, на `CASEFILE_BIND` (по умолчанию петля) |

Настройки самой установки — пул соединений, потолки ленты, страница выдачи MCP —
правятся в `.env` рядом с compose-файлом, тем же способом, что и в разработке: раздел
«Конфигурация» ниже. В образ файл не копируется, доступы остаются на машине владельца.

Прод-образ примерно вдвое легче дев-образа: компиляторы остаются в стадии сборки.

### Учётные записи и вход: установка в сети

Человек входит учётной записью — почтой и паролем; флаг администратора открывает
управление людьми (`docs/CONCEPT.md`, 3.1 и 5.4; решения — дело `TRK-113`, записи 9 и 10).
Пользовательская инструкция по-английски — `README.md`, «Network mode»; здесь — как это
устроено.

Путь аутентификации один — токен. Различается только то, как токен человека доезжает до
вкладки:

| Где | Своя машина (`TRACKER_UI_LOGIN` пуст) | Сервер (`TRACKER_UI_LOGIN=password`) |
|---|---|---|
| Кто вошёл | администратор `owner@localhost`, заведённый шагом `local-token` | каждый своей учётной записью |
| `/config.json` | ключ `local-ui` администратора любому своему адресу петли | никому: `401 {"login":"password"}`, файла нет |
| Токен вкладки | ключ из `/config.json` | токен сеанса: `POST /api/v1/session` отдаёт его в `data.token`, после перезагрузки — `GET /api/v1/session` по куке |
| Проверка `Host` в nginx | только адреса петли, чужой — `421` | нет: общего ключа, который она берегла, здесь не отдают |
| Порты на `CASEFILE_BIND` не на петле | интерфейс не поднимается, `docker compose logs ui` говорит почему | можно |
| REST и MCP | токен на каждом запросе | то же самое |

Режим включает владелец установки (`CASEFILE_LOGIN=password` в `.env`); у установки,
закрытой прежним паролем, он включается сам — `TRACKER_UI_LOGIN:
${CASEFILE_LOGIN:-${TRACKER_PASSWORD_HASH:+password}}` у службы `ui`. Из адреса публикации
режим не выводится намеренно: установку за прокси на той же машине публикуют на петле, и
такой вывод раздал бы ключ администратора всему, что проходит через прокси. Шаг старта
образа `ui/docker/access-mode.sh` пишет правило `Host` и условие выдачи `/config.json`,
шаблон их подключает.

Учётную запись администратора заводит шаг `local-token` (и `init` в дев-контуре,
`app/services/setup.py`): почта `<имя>@localhost`, без пароля. Тот же шаг переносит
прежний `TRACKER_PASSWORD_HASH` паролем в эту учётную запись, если пароля у неё ещё нет —
формат хеша тот же (`app/domain/passwords.py`), поэтому прежний пароль пускает как был.
Испорченный хеш роняет шаг, а за ним и подъём интерфейса.

Людей заводит администратор — REST `/api/v1/accounts` или командой на сервере (сценарии
общие, `app/services/accounts.py`):

```bash
docker compose run --rm api python -m app.cli account-create --email alice@example.com --name alice [--admin] [--set-password]
docker compose run --rm api python -m app.cli account-list
docker compose run --rm api python -m app.cli account-update --email alice@example.com [--new-email ...] [--admin|--no-admin] [--disable|--enable]
docker compose run --rm api python -m app.cli account-password --email alice@example.com [--set-password]
```

Без `--set-password` пароль генерируется и печатается один раз; с ним — спрашивается
дважды без эха (из трубы — первой строкой). Команда действует от имени самого трекера:
флага у запустившего её не спрашивают — у него и так доступ к базе.

Вход — `POST /api/v1/session` с телом `{"email": "...", "password": "..."}`: выпускает
участнику учётной записи токен набора `main` со сроком (`TRACKER_SESSION_HOURS`, колонка
`tokens.expires_at`) и ставит его секрет в куку `casefile_session` (`HttpOnly`,
`SameSite=Strict`, `Path=/`, `Secure` — когда прокси прислал `X-Forwarded-Proto: https`).
Сеанс — строка `tokens`, а не память процесса: перезапуск API его не гасит, выход
(`DELETE`) отзывает токен, смена и сброс пароля отзывают сеансы учётной записи,
отключение — все свои токены человека, и выпущенные им агентам тоже (`TRK-114`), а
токен отключённого человека отвечает `401` с `details.reason: account_disabled`;
просроченный токен отвечает `401` с `details.reason: token_expired`. Токена эти маршруты не требуют: они объявлены в `TOKEN_EXEMPT`
(`app/api/contract.py`), и сплошная проверка контракта сверяет список с кодом.

Перебор ограничен окнами за 60 секунд (решения — дело `TRK-98`, записи 6–8, и `TRK-113`,
запись 10): неудачи на адрес клиента (`ATTEMPT_LIMIT_PER_ADDRESS`), на почту — заведённую
или нет (`ATTEMPT_LIMIT_PER_ACCOUNT`) — и общий потолок установки (`ATTEMPT_LIMIT_TOTAL`,
`app/services/login.py`), который защищает процессор от scrypt, а не служит окном входа.
Сверх любого — `429 password_attempts_exceeded` с `Retry-After` и `details.scope`
(`address`, `account` или `installation`), и пароль в этот момент не проверяется вовсе,
даже верный. Незаведённая почта проверяется против пустышки той же цены: по времени ответа
не прочитать, кто заведён. Отказ места не занимает: перебирающий адрес держит только себя.
Окна живут в памяти процесса API — отсюда требование к службе `api`: процесс один,
`--workers` у неё нет. Кто клиент, решают два звена, и у каждого сосед назван явно:

| Звено | Клиент | Кому верит заголовок с адресом | Чем задаётся |
|---|---|---|---|
| nginx интерфейса | `$remote_addr` | `X-Forwarded-For` — только от прокси из списка (`realip`, самый правый не доверенный адрес) | `CASEFILE_TRUSTED_PROXIES` → `TRACKER_UI_TRUSTED_PROXIES`, пусто по умолчанию; файл пишет `ui/docker/access-mode.sh` |
| API | собеседник TCP | `X-Real-IP` — только от собеседника из списка; nginx этот заголовок перезаписывает | `TRACKER_REAL_IP_FROM`: прод-контур и контур сквозных тестов — `ui`, дев-контур — пусто |

Имя из `TRACKER_REAL_IP_FROM` API разрешает при попытке входа и помнит несколько секунд
(`app/api/client_address.py`): служба `ui` поднимается позже API и при пересоздании
получает новый адрес. Какой адрес видит nginx за прокси владельца и почему доверенного
прокси по умолчанию нет — замер в деле `TRK-98`, запись 5; инструкция владельцу — `README.md`,
«Network mode».

Проверить руками, не печатая пароль в историю:

```bash
curl -s -o /dev/null -w '%{http_code}\n' http://<сервер>:8080/config.json    # 401
read -rs PW && curl -s -c /tmp/jar -H 'Content-Type: application/json' \
  -d "{\"email\": \"owner@localhost\", \"password\": \"$PW\"}" \
  http://<сервер>:8080/api/v1/session       # {"data": {"token": "trk_...", "expires_at": ..., "account": ...}}
curl -s -b /tmp/jar http://<сервер>:8080/api/v1/session    # тот же токен по куке
```

TLS ядро не даёт: дальше доверенной сети — обратный прокси с TLS перед обоими портами и
`CASEFILE_BIND=127.0.0.1`, чтобы до портов доходил только он (`README.md`, «Network mode»).

### Установка и разработка на одной машине

Рабочий трекер владельца — установка, а дев-контур рядом нужен для разработки. Оба хотят
одних и тех же портов, и по умолчанию берут их: установка — 8080 (интерфейс) и 8100 (MCP),
контур разработки — 8000 (API), 8100 (MCP), 5432 (база). Поэтому порты **контура
разработки** сдвигаются в его `.env`, а установка остаётся на умолчаниях: её адреса
напечатаны в выводе установщика, стоят в конфигурации MCP-клиентов и в закладках браузера,
и двигать их дороже.

```dotenv
# .env репозитория: дев-контур рядом с установкой Casefile
POSTGRES_PORT=5442
TRACKER_PORT=8001
TRACKER_MCP_PORT=8101
```

После правки `docker compose up -d` поднимает контур разработки рядом с установкой, а
`docker compose run --rm test` в нём идёт как обычно. Агенты и интерфейс продолжают
ходить в **установку** (`localhost:8100/mcp`, `localhost:8080`): менять их подключение
не нужно.

Что важно помнить при такой раскладке:

- две базы с похожими данными живут одновременно. Команда без `-p` в каталоге репозитория
  всегда попадает в контур разработки, установка — это `~/casefile` (проект `casefile`);
- дев-контур монтирует рабочее дерево, поэтому слияние ветки меняет код **разработки**, а
  не рабочего трекера: установка обновляется только выпусками — образами ghcr.io и службой `updater`;
- `docker compose run --rm local-token` в контуре разработки перевыпускает ключ **его**
  интерфейса, а не ключ установки, и наоборот — путать каталоги нельзя.

## Конфигурация

Приложение настраивается только переменными окружения — один образ работает в любом
контуре без пересборки. Полный список с комментариями — в `.env.example`, разбор и
валидация — в `app/core/config.py`. Все переменные приложения начинаются с `TRACKER_`.

Настройки установки живут в `.env` рядом с compose-файлами, и оба контура читают файл
одинаково: `env_file:` у сервисов приложения передаёт его контейнеру. Внутрь образа
файл не копируется (`.dockerignore`), поэтому доступы остаются на машине владельца
установки; без файла контур поднимается на значениях по умолчанию.

Переменные из таблицы ниже контур задаёт сервису сам (блок `x-app-environment` в
compose-файле), и они приоритетнее файла — в Compose `environment` побеждает `env_file`:

| Переменная | Откуда берётся | Чем менять |
|---|---|---|
| `TRACKER_ENVIRONMENT` | свойство контура: `local` или `production` | правкой compose-файла |
| `TRACKER_DEBUG` | свойство контура: `true` или `false` | правкой compose-файла |
| `TRACKER_DATABASE_URL` | собирается из `POSTGRES_*`, чтобы адрес не разошёлся с поднятой базой | правкой `POSTGRES_*` в `.env` |
| `TRACKER_CORS_ORIGINS` | подставляется контуром из `.env` | правкой `.env` |
| `TRACKER_MCP_PORT` | подставляется контуром из `.env` той же строкой, что стоит в пробросе порта | правкой `.env` |
| `TRACKER_MCP_PUBLIC_URL` | подставляется контуром из `.env`; пусто — адрес выводится из `TRACKER_MCP_PORT` | правкой `.env` |

Всё остальное — пул соединений, потолки ленты и потока SSE, страница и обрезка выдачи
MCP — правится прямо в `.env`, и в проде тоже. Что в итоге доедет до приложения, видно
до запуска: команда печатает окружение каждого сервиса целиком.

```bash
docker compose config                                # разработка
docker compose -f docker-compose.prod.yml config     # продакшен
```

## Структура

```
app/
  api/          HTTP-слой: роутеры, схемы, обработка ошибок, контракт
  mcp/          MCP-сервер для агентов: инструменты, промпт дисциплины (`python -m app.mcp`)
  domain/       доменные модели и правила
  services/     сценарии: транзакции, служебные записи
  db/           модели SQLAlchemy, репозитории, сессии, миграции
  core/         конфиг, логирование, базовые исключения
  cli.py        командная строка: инициализация, ключ интерфейса, демо-данные, выгрузка артефактов
docker/         образы для разработки и продакшена
docs/           концепция, соглашения, задания, заметки
skill/          скил дисциплины работы с трекером, раздаётся агентам через MCP
tests/          тесты и общие фикстуры
scripts/        команды, которым нужен хост: слияние ветки задачи с прогоном набора
```

Фоновых процессов нет: автоматики в трекере нет, а лента читается прямо из таблицы
записей. Постоянно работают три сервиса Compose — БД, HTTP-сервер и MCP-сервер;
остальные (`migrate`, `init`, `local-token`, `agent-token`, `demo`, `schema`, `test`,
`lint`, `lock`) спрятаны
за профилем `tools`, запускаются точечно через `run --rm` и завершаются.

В каждой папке лежит `AGENTS.md` с картой её содержимого.
