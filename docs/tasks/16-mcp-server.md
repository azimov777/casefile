# 16. MCP-сервер для агентов

- **Блок:** MCP
- **Зависимости:** 05, 07, 08, 09, 12, 13, 14
- **Результат:** агент полноценно работает с трекером и получает уведомления

## Зачем

Основной интерфейс для агентов. От его качества зависит, сможет ли агент вести работу в трекере
сам: находить свои задачи, отчитываться, двигать статусы и реагировать на события.

## Объём

**Инструменты (минимальный полный набор рабочего цикла):**

- Поиск задач строкой запроса с выбором возвращаемых полей.
- Чтение задачи с уровнями детализации (кратко / полностью / с историей и комментариями).
- Создание задачи, частичное обновление, назначение исполнителя.
- Получение доступных переходов и выполнение перехода.
- Комментирование, чтение обсуждения.
- Работа со связями и деревом подзадач.
- Работа с чеклистом. Перемещение пункта задаётся соседом (`after`), а не индексом и не
  позицией: позиции наружу не отдаются, это внутреннее число разреженной шкалы
  (выявлено в задаче 09).
- Запуск макроса.
- Список очередей и конфигурация очереди (типы, статусы, поля) — чтобы агент знал, что вообще
  можно заполнять.
- Проекты и портфели (задача 10): список и карточка с прогрессом, добавление и удаление задач
  проекта, список задач проекта. Без них агент не может отчитаться о результате, ради которого
  работает: очередь показывает процесс, а «сколько сделано по проекту» живёт только здесь.
  Список задач проекта — тот же инструмент поиска со строкой `project: <ключ>`, а не отдельный;
  заводить второй способ отбирать задачи нельзя (выявлено в задаче 10).
- Инбокс: получить непрочитанные, отметить прочитанными.
- Ожидание новых уведомлений с таймаутом.

**Инструменты настройки процесса** (отдельное требование заказчика — агент должен уметь
конструировать процесс, а не только работать внутри готового):

- Создать очередь.
- Создать собственные статусы, типы задач, резолюции.
- Создать воркфлоу целиком одним вызовом: граф из статусов и переходов, с назначением на тип
  задачи в очереди; изменить отдельный переход; получить текущий граф процесса.
- Создать и изменить поле задачи (глобальное или локальное для очереди).
- Включить, выключить и настроить правило автоматики (сами правила пишутся кодом, но их
  привязка и параметры доступны агенту).

**Уведомления по трём каналам:** инбокс (инструменты выше), MCP-нотификации поверх streamable
HTTP для клиентов с их поддержкой, вебхуки (задача 15).

**Прочее:** аутентификация по тому же токену актора, что и REST; ресурсы MCP для справочной
информации (список очередей, словарь статусов); запуск отдельным сервисом Compose в дев- и
прод-контуре; инструкция по подключению к Claude Code в README — с учётом того, что сервер
работает в контейнере (проброс порта, адрес, токен).
- Инструмент поиска принимает **строку на языке запросов** и параметр `fields`, а не набор
  аргументов под каждое поле: ради этого язык и делался — одна строка вместо конструктора, и её
  же агент может сохранить фильтром. Сценарий уже готов (`search_issues` в
  `app/services/search.py`), собственного отбора заводить нельзя (выявлено в задаче 12).
- Ошибка разбора запроса несёт позицию символа и причину в `details`. Инструмент обязан
  доносить их до агента целиком: по ним запрос исправляется за одну попытку, а «invalid query»
  отправляет агента в слепой перебор (выявлено в задаче 12).

- **Инструменты инбокса вызывают готовые сценарии, своей логики не заводят.**
  `list_notifications`, `mark_read` и `wait_for_notifications` в `app/services/notifications.py`
  — те же, что зовёт REST. У ожидания уже есть всё, что просит эта задача: таймаут ограничен
  сверху настройкой (`TRACKER_NOTIFICATION_WAIT_MAX_TIMEOUT`), запрос сверх потолка
  отвергается кодом `invalid_wait_timeout`, а исход по таймауту — не ошибка, а результат с
  полями `waited` и `timed_out`. Инструмент обязан донести оба поля до агента: по коду
  ответа «ничего не пришло» от сбоя не отличить (выявлено в задаче 14).
- **Ожидание отпускает соединение с базой на время сна**, поэтому длинный вызов инструмента
  не занимает пул. Если MCP-сервер обернёт сценарий в собственную транзакцию и будет держать
  её открытой, это свойство пропадёт — и несколько ждущих агентов исчерпают пул
  (выявлено в задаче 14).
- **MCP-нотификации не второй канал, а показ того же инбокса.** Записи те же самые, и
  отметка о прочтении одна на оба способа: агент, разобравший ленту инструментом, не должен
  получить её повторно нотификацией (выявлено в задаче 14).

## Что учесть

- **Инструменты автоматики строятся на готовых сценариях `app/services/automation.py`, а
  своей проверки параметров не заводят.** Схема параметров у каждого правила своя и
  объявлена в его модуле (`params_schema` в ответе API); проверяет их `update_rule` той же
  моделью, которой правило пользуется при выполнении. Вторая проверка «попроще» в MCP
  разошлась бы с настоящей, и правило запускалось бы с параметрами, которых не приняло
  сохранение. Ошибка внутри макроса при этом **не** исключение, а запись журнала со
  статусом `failed`: инструмент должен отдать её агенту как результат, а не как сбой вызова
  (выявлено в задаче 13).

- **Экономия контекста — главное требование.** Каждый ответ инструмента съедает контекст агента.
  Поэтому: у чтения — уровни детализации, у поиска — выбор полей и разумный лимит по умолчанию,
  у длинных текстов — усечение с пометкой. Инструмент, возвращающий задачу с полной историей по
  умолчанию, сделает MCP-сервер непригодным на реальных объёмах.
- Описания инструментов и параметров — это промпт, который читает модель. Писать их так, чтобы
  из описания было ясно, когда инструмент применять и что он вернёт. Отдельно описать синтаксис
  языка запросов в описании инструмента поиска: агент не будет искать документацию.
- Ошибки должны быть обучающими и на английском, как и в REST: не `400 Bad Request`, а
  `field TRK.severity is required for issue type "bug"; allowed values: minor, major, critical`.
  Агент исправится по такому тексту с первого раза, а по коду статуса — нет.
- Инструменты вызывают те же сервисы, что и REST. Дублирование логики в MCP — прямой путь к
  расхождению поведения между интерфейсами.
- Ожидание уведомлений: таймаут ограничен сверху (клиент MCP разорвёт слишком долгий вызов),
  ответ по таймауту — не ошибка, а пустой результат. Инструмент должен явно сообщать, сколько
  ждал и что ничего не пришло.
- MCP-нотификации поддержаны не всеми клиентами. Инбокс — обязательный основной канал,
  нотификации — дополнение поверх, а не замена. Проверить фактическое поведение в Claude Code.
- Мутирующие инструменты именовать так, чтобы было очевидно, что они меняют данные, и не
  прятать за одним инструментом несколько разнородных действий.
- Инструменты настройки процесса опасны по последствиям: изменение воркфлоу задевает все задачи
  очереди. Поэтому у них должны быть предварительная проверка («что сломается, если применить»)
  и отчёт о последствиях в ответе, а ошибки — объяснять, какое именно правило целостности
  нарушено. Агент не видит интерфейса и узнаёт о последствиях только из текста ответа.
- Создание процесса целиком одним вызовом важнее, чем набор мелких операций: собирать граф из
  пятнадцати последовательных вызовов агент будет долго и с ошибками в середине.

- **Инструменты доски не заводят своего отбора.** Колонка, бэклог и состав спринта —
  это поиск с приклеенным условием (`app/services/boards.py`), и инструмент MCP обязан
  звать те же сценарии, а не собирать условия сам. Порядок карточек при этом задаёт ранг
  доски, и параметра сортировки у колонки нет намеренно (выявлено в задаче 11).
- **Перемещение карточки между колонками — переход воркфлоу и может отказать.** Инструмент
  обязан отдавать агенту причину отказа как есть (`transition_not_allowed`,
  `issue_resolution_required`), а не пытаться дожать смену статуса другим путём: доска
  специально не умеет писать статус напрямую (выявлено в задаче 11).
- **`sprint: current` — готовый ответ на «чем команда занята сейчас».** Отдельного
  инструмента «текущий спринт» заводить не нужно, хватает фильтра (выявлено в задаче 11).

## Готово, когда

- Агент проходит полный цикл: нашёл задачу → прочитал → прокомментировал → сменил статус →
  получил уведомление о чужом изменении.
- Агент создаёт с нуля очередь со своими статусами, воркфлоу и полями и заводит в ней задачу.
- Поиск и чтение не возвращают избыточных данных по умолчанию.
- Ожидание уведомлений работает и корректно завершается по таймауту.
- Сервер подключается к Claude Code по инструкции из README.
- Тесты на инструменты и сценарий полного цикла.

## Не входит

Собственный клиент MCP, управление акторами и токенами через MCP (выпуск доступов остаётся за
человеком через REST).
