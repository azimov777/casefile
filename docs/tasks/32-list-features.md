# 32. Вычисляемые признаки в строках списка задач

## Цель

Экран списка показывает «заблокирована» и открытые вопросы прямо в строках, а назначатель
получает признаки без второго запроса на каждую задачу. Сейчас признаки доступны только
как условия отбора и в карточке; `fields=blocked` отвечает `search_field_unknown`
с причиной `not_selectable`.

## Контекст

- `CONCEPT.md`, 4.3 и 4.4; `FRONTEND.md`, экран «Список задач».
- Поиск уже считает признаки коррелированными подзапросами для фильтра (`app/services`
  и репозиторий поиска, `notes/search.md`); карточка считает их тем же кодом, и тест
  сверяет обе стороны.
- Ревизия 2026-09-04: добавить признаки в выдачу дёшево по SQL, но это правка контракта:
  схема строки списка и тест на совпадение полей `TaskSearchRead` и `TaskRead`.

## Ограничения

- Признаки считаются тем же кодом, что для фильтра и карточки; третьей реализации нет.
- Признаки в строке списка отдаются вложенным объектом `features` с теми же полями,
  что в пакете преемника; в `fields` он выбирается целиком именем `features`.
- Без `fields` признаки входят в строку по умолчанию; стоимость подзапросов на страницу
  измерить и записать в заметку.

## Выход

- `GET /api/v1/tasks` и `search_tasks` отдают `features` в каждой строке; `fields=features`
  допустим; `openapi.json`, `FRONTEND.md` и README обновлены.
- Тест на совпадение признаков строки списка и карточки для каждой задачи демо.

## Обзорные проверки

1. `GET /api/v1/tasks?query=queue: DEMO` отдаёт в каждой строке `features` с четырьмя полями, и для каждой задачи они равны `features` из `GET /api/v1/tasks/{key}`.
2. `fields=title,features` отдаёт `key`, `title`, `features` и ничего больше; `fields=blocked` по-прежнему отвечает `search_field_unknown`.
3. `search_tasks` по MCP отдаёт те же строки, что REST, поле в поле.
4. Полный набор тестов зелёный; `openapi.json` в репозитории равен выгруженному; `docker ps` чист после работы.
