# 17. Сборка публичного API и сквозные сценарии

- **Блок:** API
- **Зависимости:** все предыдущие
- **Результат:** фронтенд может быть написан по документации, ничего не спрашивая

## Зачем

К этому моменту эндпоинты написаны разными агентами в разное время. Их нужно привести к одному
контракту, закрыть дыры и проверить работу системы целиком, а не по частям.

## Объём

- Ревизия всех эндпоинтов на соответствие соглашениям: именование, пагинация, формат дат.
- **Сплошная проверка единой оболочки**: каждый эндпоинт отдаёт `data` (плюс `meta` для
  коллекций), каждая ошибка — `error` с `code`, `message` и `details`, все сообщения и коды на
  английском. Отклонения править в исходных модулях.
- Автоматический тест единообразия: пройти по всем маршрутам из OpenAPI и проверить форму
  ответов, а не полагаться на ручной просмотр — при нескольких десятках эндпоинтов глазами
  расхождение не отлавливается.
- Агрегирующие эндпоинты под реальные экраны фронта, чтобы не заставлять его делать по
  пять запросов на страницу:
  - карточка задачи целиком (задача + доступные переходы + связи + комментарии + чеклист);
  - стартовые данные (очереди, справочники, текущий актор, счётчик непрочитанных);
  - сводка по проекту (проект + прогресс + задачи).
- Полная OpenAPI-схема с описаниями и примерами.
- Выгрузка схемы в файл одной командой в Docker — фронтенд генерирует из неё `openapi.ts`.
- Тест на пригодность схемы к генерации клиента: у каждого маршрута есть модель ответа и
  стабильный `operation_id`, идентификаторы уникальны, в схемах нет объектов неизвестной формы
  кроме двух задокументированных исключений.
- Единый справочник кодов ошибок с описанием, когда какой возникает; коды собраны в одном месте,
  а не разбросаны по модулям.
- Сквозные тесты основных сценариев:
  - создать очередь → настроить воркфлоу и поля → создать задачу → провести по статусам → закрыть;
  - создать проект → добавить задачи из двух очередей → проверить прогресс;
  - декомпозировать задачу на подзадачи и проверить дерево;
  - сработавшее правило автоматики → уведомление → получение его агентом через MCP;
  - работа доски: перемещение карточки и ранжирование.
- Наполнение демо-данными (команда, создающая осмысленный набор очередей, задач, проекта, доски)
  — чтобы фронтенд разрабатывался не на пустой базе. Запускается в Docker одной командой.
- Проверка прод-контура: сборка прод-образов, запуск `docker-compose.prod.yml`, прогон сквозных
  сценариев против него — дев-контур не является доказательством работоспособности продакшена.
- Документ для фронтенд-разработчика: сущности, основные потоки, аутентификация, подписка на
  SSE, примеры запросов.

## Что учесть

- **Живой поток событий — третье исключение из единой оболочки, и его надо узаконить или
  переделать.** `GET /api/v1/events/stream` отдаёт `text/event-stream`: кадры `id:`, `event:`,
  `data:`, без `{"data": ...}`. Обернуть их нельзя, не перестав быть SSE, поэтому в
  `CONVENTIONS.md` сейчас перечислены два исключения, а фактически их три. При сплошной
  проверке оболочки этот маршрут обязан быть **явно** исключён из проверки с указанием
  причины, а не молча пропущен, — и решение об исправлении соглашений принимает человек
  (выявлено в задаче 15).
- **`response_class` у маршрута задаёт тип содержимого всем ответам операции, включая
  ошибки.** Из-за этого `401` у потока описывался в схеме как `text/event-stream`, хотя
  ошибка приходит обычным JSON-конвертом. Ревизия контракта обязана проверять это по всем
  маршрутам с нестандартным типом ответа, а не только у потока: тест
  `test_errors_are_described_with_the_common_envelope` ловит именно такой случай
  (выявлено в задаче 15).
- **Таблица доставок вебхуков растёт вместе с журналом срабатываний и тоже не чистится.**
  `webhook_deliveries` хранит по строке на каждую доставку каждого события каждому адресу —
  при трёх подписках это троекратный объём потока событий. Решение о сроке хранения принимать
  вместе с решением по журналу автоматики и по `outbox_events`, а не по отдельности: окно
  переподключения SSE (`TRACKER_STREAM_REPLAY_LIMIT`) обещано по `outbox_events`, и чистка,
  назначенная независимо, молча сузит это обещание (выявлено в задаче 15).
- **У доски нет маршрута «все её задачи»: задачи в статусах вне колонок через её API не
  видны.** Маршрут бэклога ушёл вместе со спринтами, и это осознанно, но при ревизии контракта
  надо решить, достаточно ли этого фронтенду: сейчас такую задачу находит только общий поиск по
  сохранённому фильтру доски. Если недостаточно — завести `GET /boards/{id}/issues` с ранговым
  порядком, а не возвращать бэклог под прежним именем (выявлено в задаче 14a).
- **Журнал срабатываний автоматики растёт быстрее любой другой таблицы и не чистится.**
  Запись пишется на каждое **рассмотренное** срабатывание, включая пропуски: включённое
  правило на активной очереди даёт строку на почти каждое изменение задачи. То же верно и
  для `outbox_events`, которые тоже никогда не удаляются. Нужна команда или фоновая чистка
  с настраиваемым сроком хранения — и решение, что делать с журналом правила, которое
  удалили из кода: его строка состояния специально не удаляется, чтобы каскад не унёс
  историю (выявлено в задаче 13).
- **В демо-данных должно быть включённое правило автоматики.** Иначе сквозной сценарий
  «сработавшее правило → уведомление → получение агентом через MCP» не на чем прогнать:
  все поставочные правила приезжают выключенными, и без явного включения демо-контур
  показывает трекер без единственной механики, ради которой он во многом и строится
  (выявлено в задаче 13).

- Агрегирующие эндпоинты не должны становиться вторым слоем логики: они собирают ответы уже
  существующих сценариев, а не реализуют свои правила.
- Расхождения, найденные при ревизии, править в исходных модулях, а не заглушать адаптерами
  в API-слое.
- Демо-данные должны создаваться через сервисы (с событиями и историей), а не прямыми вставками
  в БД: иначе на них не проверить ни автоматику, ни уведомления.
- Если сквозной тест выявит противоречие в архитектуре — фиксировать его как проблему с
  предложением решения, а не обходить в тесте.

- **Ревизия контракта обязана касаться и MCP.** Представления инструментов
  (`app/mcp/views.py`) повторяют имена полей REST намеренно и **без общего кода**: `api` и
  `mcp` друг от друга не зависят. Поэтому переименование поля в схеме REST не долетает до
  MCP автоматически, и интерфейсы разъезжаются молча — агент продолжает получать старое
  имя. Проверять оба слоя вместе, желательно тестом на совпадение набора имён у задачи
  (выявлено в задаче 16).
- **Сквозной сценарий «уведомление дошло до агента» проверяется инбоксом, а не
  MCP-нотификацией.** Нотификации идут подписками `subscriptions/listen` и требуют
  протокола `2026-07-28`; Claude Code сейчас договаривается на `2025-11-25` и их не
  получает. Тест, написанный на нотификациях, проверял бы канал, которого у реального
  клиента нет (выявлено в задаче 16).
- **Проверка прод-контура включает сервис `mcp`.** Он опубликован отдельным портом и имеет
  собственную проверку здоровья средствами Python (в прод-образе нет `curl`). Прогон
  сквозных сценариев против прод-контура без него оставил бы непроверенным целый
  интерфейс (выявлено в задаче 16).

- **Сборка доски — самый нагруженный сценарий контракта, и он собран покомпонентно.**
  Карточка доски отдаёт настройки и колонки, задачи каждой колонки — свой маршрут со своим
  курсором и своим `fields`. Счётчиков задач в колонке нет намеренно: курсорная пагинация не
  считает `total`, а отдельный `COUNT` по фильтру доски дороже всего остального в ответе.
  Ревизия контракта не должна «дособрать» доску в один ответ, не измерив цену
  (выявлено в задаче 11).
- **Порядок карточек наружу отдаётся только порядком.** Позиции разреженной шкалы в контракт
  не входят: при перенумерации доски все они меняются, сохраняя порядок, и клиент, на них
  опирающийся, сломается молча (выявлено в задаче 11).

## Готово, когда

- Все эндпоинты соответствуют соглашениям, оболочка ответа единообразна и подтверждена
  автоматическим тестом, OpenAPI полон и читаем.
- Исключения из единой оболочки перечислены в одном месте и совпадают с фактическими:
  `204`, `/health` и поток событий (выявлено в задаче 15).
- Схема выгружается командой и пригодна для генерации типизированного клиента.
- Сквозные сценарии проходят, включая сценарий агента через MCP на демо-данных
  (выявлено в задаче 16).
- Демо-данные разворачиваются одной командой.
- Документ для фронтенда написан и достаточен, чтобы начать разработку интерфейса.

## Не входит

Оптимизация производительности под нагрузку, кеширование.
