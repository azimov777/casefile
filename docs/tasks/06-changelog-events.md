# 06. Журнал изменений и шина событий

- **Блок:** События
- **Зависимости:** 05
- **Результат:** каждое изменение зафиксировано в истории и породило событие

## Зачем

Это фундамент трёх механик сразу: аудита (кто и что менял), автоматики (правило срабатывает на
изменение) и уведомлений (кому сообщить). Если построить их по отдельности, получится три
источника правды, которые начнут расходиться.

## Объём

- Модель `ChangelogEntry`: задача, актор, время, тип действия, список изменений поле-за-полем
  (было → стало).
- Модель `OutboxEvent`: тип события, объект, актор, полезная нагрузка, время создания, статус
  обработки, счётчик попыток.
- Подключение к точке применения изменений из задачи 05: запись в журнал и событие в outbox
  происходят в **той же транзакции**, что и само изменение.
- Диспетчер событий: воркер, который выбирает необработанные события и раздаёт их подписчикам.
- Реестр подписчиков: механизм, позволяющий следующим задачам (автоматика, уведомления,
  вебхуки, SSE) подписаться на типы событий, не трогая ядро.
- Словарь типов событий: `issue.created`, `issue.updated`, `issue.status_changed`,
  `issue.assigned`, `issue.deleted` и место для расширения.
- Эндпоинт истории изменений задачи с пагинацией.

## Что учесть

- Outbox нужен именно ради атомарности: событие обязано появиться тогда и только тогда, когда
  изменение зафиксировано. Прямая рассылка из обработчика запроса даст рассинхрон при откате
  транзакции — это не гипотетическая проблема, а первое, что сломается.
- Воркер должен переживать перезапуск: событие считается обработанным только после успешной
  доставки всем подписчикам; при падении подписчика — повтор с ограничением попыток и пометкой
  «не доставлено».
- Один обработчик не должен блокировать остальные: падение вебхука не должно останавливать
  автоматику.
- Полезная нагрузка события должна быть самодостаточной (содержать «было» и «стало»), чтобы
  подписчику не приходилось лезть в БД за контекстом — иначе он прочитает уже изменённое дальше
  состояние.
- Воркер запускается **отдельным сервисом Compose** из того же образа, а не потоком внутри
  веб-процесса: при нескольких репликах API фоновый поток размножится вместе с ними и события
  начнут обрабатываться дважды. Добавить сервис в оба файла Compose (дев и прод) и описать в README.
- Воркер должен корректно завершаться по сигналу остановки контейнера: дообработать текущее
  событие и выйти, а не бросить его в середине.

## Готово, когда

- Изменение задачи создаёт запись в журнале и событие в outbox в одной транзакции.
- Откат транзакции не оставляет ни записи, ни события.
- Воркер доставляет события подписчикам, повторяет неудачные, не теряет их при перезапуске.
- Тесты: атомарность, доставка, повтор при ошибке подписчика.

## Не входит

Конкретные подписчики: автоматика (13), уведомления (14), вебхуки (15).
