# 34. Прод-контур не читает `.env`

## Цель

Сделать так, чтобы установка настраивалась одним и тем же способом в обоих контурах.
Сейчас владелец прод-установки правит `.env` по инструкции README и не получает
ничего: приложение в проде этого файла не видит, и все настройки, кроме четырёх,
остаются на значениях из кода.

## Контекст

Выявлено в задаче 33 при сверке `Settings` с `.env.example`.

- Дев-контур читает `.env` случайно, а не намеренно: репозиторий смонтирован томом
  целиком (`docker-compose.yml`, `volumes: ./:/app`), и pydantic-settings находит файл
  как `/app/.env`. Объявленного `env_file:` у сервисов нет ни в одном контуре.
- Прод-образ `.env` не содержит: файл исключён `.dockerignore`, тома с исходниками нет.
  До приложения доходит только `x-app-environment` из `docker-compose.prod.yml` —
  `TRACKER_ENVIRONMENT`, `TRACKER_DEBUG`, `TRACKER_DATABASE_URL`, `TRACKER_CORS_ORIGINS`.
  Проверяется без сборки: `docker compose -f docker-compose.prod.yml config`.
- Остальные поля `Settings` — пул соединений, потолки ленты и потока SSE, страница и
  обрезка MCP — в проде неизменяемы, хотя их описания в `.env.example` и в README прямо
  предлагают крутить их под своё железо.
- Соглашения требуют от контуров «один и тот же набор переменных окружения»
  (`CONVENTIONS.md`, раздел «Запуск»), и это требование сейчас нарушено.
- Подробности и способ проверки — `docs/notes/docker.md`, запись «`.env` действует в
  дев-контуре и почти не действует в прод-контуре».

## Ограничения

- Секреты в образ не класть: `.env` остаётся в `.dockerignore`, файл подключается
  контейнеру снаружи, а не копируется внутрь.
- Отсутствие `.env` не должно ронять запуск: сейчас `docker compose up` без файла
  работает на значениях по умолчанию, и это поведение сохраняется (`env_file` с
  `required: false` либо другой способ с тем же результатом).
- Переменные, которые compose задаёт сам (`x-app-environment`), по-прежнему побеждают
  файл — менять приоритет нельзя: адрес БД в проде собирается из обязательных
  `POSTGRES_*` и не должен подменяться строкой из чужого `.env`.
- `TRACKER_PORT` остаётся переменной самого compose и в `Settings` не возвращается.

## Выход

- Оба контура читают `.env` объявленным способом, одинаково; дев больше не зависит от
  того, что репозиторий смонтирован томом.
- Тест: набор переменных, доходящих до приложения, одинаков в обоих контурах — сверка
  идёт по `docker-compose.yml` и `docker-compose.prod.yml`, а не по списку в коде теста.
- README и `.env.example` описывают, что и где правится в проде; предупреждение из шапки
  `.env.example` снимается или переписывается по факту.
- Заметка в `docs/notes/docker.md` дополнена итогом (правило «заметки только копятся»:
  дописать новую запись, старую не править).

## Обзорные проверки

1. `docker compose -f docker-compose.prod.yml config` показывает у сервисов `api` и `mcp`
   тот же набор переменных приложения, что и дев-контур.
2. Прод-контур поднимается с нуля без `.env` в рабочем дереве: сборка, миграции,
   `/health` отвечает, в логах нет жалоб на отсутствующий файл.
3. Прод-контур с `.env`, где `TRACKER_MCP_PAGE_SIZE=7`, отдаёт страницу инструмента
   MCP в семь строк — значение из файла доехало до приложения.
4. Полный набор тестов зелёный; `docker ps` чист после работы.
