# 08. Связи между задачами

- **Блок:** Связи
- **Зависимости:** 05, 06
- **Результат:** задачи связываются, иерархия не зацикливается

## Зачем

Реальная работа декомпозируется и зависит сама от себя: подзадачи, блокировки, эпики.
Без связей трекер остаётся плоским списком.

## Объём

- Модель `IssueLink`: исходная задача, целевая задача, тип связи, автор, время.
- Типы связей и их обратные стороны:
  `relates` ↔ `relates`, `depends_on` ↔ `blocks`, `subtask_of` ↔ `parent_of`,
  `duplicates` ↔ `duplicated_by`, `epic_of` ↔ `in_epic`.
- Сценарии: создать связь, удалить связь, получить связи задачи, получить дерево подзадач.
- Проверки: нет дубликатов связей, нет связи задачи с самой собой, нет циклов в иерархических
  связях (`subtask_of`, `epic_of`), у задачи не более одного родителя.
- События изменения связей.
- Эндпоинты связей и дерева подзадач.

## Что учесть

- Связь хранится один раз, а показывается с двух сторон. Хранить обе строки — значит рано или
  поздно получить рассогласование, когда одна сторона удалилась, а вторая осталась.
- Проверка циклов должна работать на произвольной глубине, а не только на прямом
  «А родитель Б, Б родитель А».
- `epic_of` разрешён только когда исходная задача имеет тип «эпик».
- Дерево подзадач нужно фронту для отображения и агенту для понимания контекста — ограничить
  глубину выдачи параметром, иначе один запрос вытащит половину базы.
- Каскад при закрытии родителя (закрывать ли детей) — **не решать самостоятельно**: это правило
  процесса, ему место в автоматике (задача 13). Здесь только хранение и целостность связей.

## Готово, когда

- Связь создаётся и видна с обеих сторон в корректных направлениях.
- Попытка создать цикл в иерархии отклоняется.
- Дерево подзадач строится с ограничением глубины.
- Тесты на каждый тип связи, на циклы, на дубликаты.

## Не входит

Правила поведения при закрытии связанных задач.
