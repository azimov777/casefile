# 26. Лента журнала: хвост с курсором, ожидание, SSE

## Цель

Открыть журнал наружу: назначатель и живой харнесс читают записи после сквозного номера
с фильтрами и долгим ожиданием, браузер получает тот же хвост потоком. После задачи
внешний назначатель может построить свой цикл «прочитать хвост, пересчитать кандидатов,
запустить харнесс» без опроса всех задач.

## Контекст

- `CONCEPT.md`, разделы 4.1 и 4.6.
- В старом коде (git `49e2e49`) есть ожидание на LISTEN/NOTIFY (`notes/notifications.md`)
  и поток SSE с переподключением по `Last-Event-ID` (`notes/webhooks.md`, окно
  переподключения). Переносить механику, источник другой: таблица записей.
- Исключение из оболочки для SSE уже объявлено в `CONVENTIONS.md` и в `ENVELOPE_EXEMPT`.

## Ограничения

- Источник ленты только таблица записей: никаких отдельных таблиц событий, outbox,
  воркера и срока хранения. Записи постоянны, догнать можно с любого номера.
- Долгое ожидание ограничено потолком (например, 60 секунд), потолок задокументирован
  в схеме параметра. Ожидание строится на LISTEN/NOTIFY, а не на опросе базы в цикле.
- Уведомление NOTIFY отправляется после фиксации транзакции, чтобы читатель не увидел
  сигнал раньше строки.
- Фильтры ленты и потока одинаковые: задача, очередь, типы записей.

## Выход

- `GET /api/v1/journal` с параметрами `after`, `task`, `queue`, `types`, `limit`, `wait`.
- `GET /api/v1/journal/stream` с теми же фильтрами, `id:` кадра равен `seq`,
  продолжение по `Last-Event-ID`.
- Сервис ожидания, который переиспользует задача 28 для `wait_journal`.
- Тесты, включая проверку гонки «сигнал раньше строки», заметки о неочевидном.

## Обзорные проверки

1. `after=N` отдаёт только записи с `seq > N` по возрастанию; `limit` соблюдается, `meta.has_more` верен.
2. `wait=3` при отсутствии новых записей отвечает пустым списком примерно через три секунды; если запись добавлена через секунду, ответ приходит примерно через секунду и содержит её.
3. `wait=600` отвечает `422` с потолком в `details`.
4. Фильтр `types=answer&task=TRK-1` пропускает ответы других задач и записи других типов.
5. Поток SSE, разорванный после кадра с `id: 17` и переоткрытый с `Last-Event-ID: 17`, продолжает с `seq = 18` без пропусков и повторов; проверяется тестом.
6. Тест на гонку: сто записей из параллельных транзакций, читатель с ожиданием ни разу не получает сигнал без соответствующей строки в ответе.
7. `curl -N` на поток вживую показывает записи по мере действий через REST.
8. Полный набор тестов зелёный; `docker ps` чист после работы.
