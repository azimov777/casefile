# 23. Дело: записи агента, сводка, вопросы, вердикты, пакет преемника

## Цель

Сделать дело рабочим: агент подшивает типизированные записи, трекер требует сводку перед
выходом из `in_progress` и вердикты перед `done`, вопросы адресуются участникам, а чтение
задачи отдаёт пакет преемника одним вызовом. После задачи цикл «вход, работа, выход,
проверка» проходится через REST целиком.

## Контекст

- `CONCEPT.md`: 3.4 (типы записей и `payload`), 3.6 (вопросы), 4.2 (пакет преемника),
  4.3 (вычисляемые признаки), валидации в 3.3.
- Таблица записей, служебные типы и точки подключения проверок перехода сделаны
  в задаче 22.
- Форма ошибок с полным списком полей: `CONVENTIONS.md`, раздел «Ошибки».

## Ограничения

- `payload` типизирован на каждый тип отдельной моделью; в OpenAPI это размеченное
  объединение по `type`, а не свободный объект.
- `summary`: четыре части непустые; `title` строится из первой строки `next_step`.
- `question`: адресаты только из реестра участников, хотя бы один; `blocking` обязателен.
  `answer`: `question_no` указывает на запись `question` той же задачи; ответов может быть
  несколько, открытым вопрос перестаёт быть после первого.
- `verdict`: `check_no` в пределах списка `checks`, `outcome` из двух значений.
- `refs`: ссылки на записи `КЛЮЧ-N#M` и задачи `КЛЮЧ-N` проверяются на существование;
  адреса не проверяются.
- Валидации переходов подключаются к точкам из задачи 22: выход из `in_progress`
  требует сводки, добавленной после последнего входа в `in_progress`; `review → done`
  требует, чтобы последний по времени вердикт каждой проверки был `passed`.
- Записи в закрытую задачу подшивать можно.
- Никаких подсказок в ответах: только данные и ошибки.

## Выход

- `POST /api/v1/tasks/{key}/entries` для всех типов записей агента с валидацией по типу.
- `GET /api/v1/tasks/{key}/entries` с фильтрами `nos`, `types`, `after_no`, `limit`;
  `GET /api/v1/tasks/{key}/entries/{no}`.
- `GET /api/v1/tasks/{key}` как пакет преемника: карточка, вычисляемые признаки
  `open_questions`, `open_blocking_questions`, `last_summary_at` (признак `blocked`
  добавит задача 24), последняя сводка целиком, открытые вопросы целиком, опись дела,
  доступные переходы.
- `GET /api/v1/questions` с фильтрами по адресату, очереди, признаку `blocking`
  и открытости; по умолчанию открытые вопросы текущего участника.
- Тесты сервисов и маршрутов, заметки о неочевидном.

## Обзорные проверки

1. `summary` с пустым `next_step` отвечает `422`; с четырьмя частями подшивается, и в описи её заголовок равен первой строке `next_step`.
2. `in_progress → review` без сводки отвечает `409` с кодом про обязательную сводку; после `summary` проходит.
3. Задача вышла из `in_progress` в `open` и снова взята: переход в `review` без новой сводки отвечает `409`, старая сводка не считается.
4. `question` с адресатом, которого нет в реестре, отвечает `422` с именем адресата в `details`.
5. `answer` с `question_no`, указывающим на запись другой задачи или не на вопрос, отвечает `422`.
6. `verdict` с `check_no = 5` у задачи с тремя проверками отвечает `422` с допустимым диапазоном.
7. `review → done` при последнем вердикте `failed` по одной из проверок отвечает `409`, в `details` перечислены проверки без положительного вердикта; после `passed` по ней переход проходит.
8. Пакет преемника содержит последнюю сводку целиком, все открытые вопросы целиком и опись со всеми записями (только `no`, `type`, `author`, `created_at`, `title`); тел остальных записей в нём нет.
9. `GET /api/v1/questions?blocking=true` отдаёт только открытые блокирующие вопросы, адресованные текущему участнику; после ответа вопрос из выдачи исчезает.
10. Запись с `refs: ["TRK-1#99"]` при отсутствии такой записи отвечает `422`; с существующей проходит.
11. Запись `note` в задачу в `done` подшивается.
12. Полный набор тестов зелёный; контур поднимается с нуля; `docker ps` чист после работы.
