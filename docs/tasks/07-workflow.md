# 07. Воркфлоу: статусы и переходы

- **Блок:** Воркфлоу
- **Зависимости:** 03, 05, 06
- **Результат:** пользователь и агент собирают собственный процесс, статус меняется только по разрешённым переходам

## Зачем

Процесс команды выражается через допустимые переходы. Без них статус — просто произвольное
поле, и любой агент может перевести задачу из «закрыто» в «в работе» мимо всякого смысла.

## Объём

- Модель `Workflow`: собственное имя, привязка к связке «очередь + тип задачи».
- Модель `Transition`: исходный статус (или «любой»), целевой статус, название действия,
  требуемые поля, требуемая резолюция.
- Движок: проверить допустимость перехода, получить список доступных переходов для задачи,
  выполнить переход.
- Правило резолюции: при переходе в статус категории `done` резолюция обязательна;
  при выходе из `done` — сбрасывается.
- Наполнение точки-заглушки из задачи 05 реальной проверкой: `ensure_transition_allowed` в
  `app/services/workflow.py`. Сигнатура уже даёт всё, что нужно проверке (задача, целевой
  статус, инициатор), и менять её не придётся — только тело. Вызов стоит внутри
  `apply_issue_changes` и срабатывает только при фактической смене статуса
  (выявлено в задаче 05).
- **Правило резолюции наполнить там же.** Сейчас резолюция ставится и снимается напрямую
  через `PATCH`, без связи со статусом: задача 05 намеренно не трогала это правило, чтобы не
  делить его между двумя задачами. Требование «в статусе категории `done` резолюция
  обязательна, при выходе из `done` сбрасывается» реализуется в единой точке изменений, а не
  в эндпоинте (выявлено в задаче 05).
- **Полноценное редактирование воркфлоу** (это требование заказчика, а не опция): создать
  воркфлоу, добавить и убрать статус, добавить, изменить и удалить переход, назначить воркфлоу
  типу задачи в очереди, клонировать существующий воркфлоу, получить воркфлоу целиком в виде
  графа (статусы + переходы) для отрисовки на фронте.
- Валидация целостности воркфлоу: есть начальный статус, каждый статус достижим, нет переходов
  в несуществующие статусы, есть хотя бы один путь в статус категории `done`.
- Эндпоинты: доступные переходы задачи, выполнение перехода, полный набор операций
  редактирования воркфлоу.
- Воркфлоу по умолчанию для новых очередей плюс пара готовых шаблонов процессов
  (простой и с ревью), от которых удобно отталкиваться.
- Заменить заглушку воркфлоу в конфигурации очереди настоящим графом: эндпоинт
  `GET /api/v1/queues/{key}/config` уже отдаёт ключ `workflows` с пустым списком и схемой
  `QueueWorkflowStub` (`app/api/schemas/queues.py`) (выявлено в задаче 03).
- Привязка «очередь + тип задачи» уже существует отдельной таблицей `queue_issue_types`
  (модель `QueueIssueType`) — воркфлоу вешается на неё, а не заводится третья таблица связи
  (выявлено в задаче 03).

## Что учесть

- Список доступных переходов для конкретной задачи — то, чем будет пользоваться и фронт (кнопки
  на карточке), и агент (какие действия вообще возможны). Он должен считаться быстро и отдавать
  причину недоступности, если переход заблокирован незаполненными полями.
- Требование «при переходе заполнить поле» — самая частая настройка реальных процессов
  (например, при закрытии указать резолюцию и комментарий). Заложить это как данные перехода,
  а не как хардкод.
- Переход должен порождать событие `issue.status_changed` через общий механизм из задачи 06,
  а не собственный.
- Не путать статус и резолюцию: статус говорит «где задача», резолюция — «чем кончилось».
  Закрытая с резолюцией «отклонено» и закрытая с «сделано» — разные исходы одного статуса.
- **Редактирование живого воркфлоу — главная опасность этой задачи.** Задачи уже стоят в
  статусах, и удаление статуса или перехода делает часть из них недостижимыми. Обязательно:
  запрет удаления статуса, в котором есть задачи (с подсказкой, сколько их и как перенести);
  проверка целостности графа перед сохранением; отчёт «после этого изменения N задач останутся
  без исходящих переходов».
- Изменение воркфлоу не должно задним числом ломать историю: журнал изменений хранит имена
  статусов на момент события, а не ссылку, которая может исчезнуть.
- Граф воркфлоу должен отдаваться одним запросом в виде, пригодном и для отрисовки схемы во
  фронте, и для понимания агентом. Это же представление принимается на вход при массовом
  сохранении процесса — так агенту проще создать процесс целиком, чем собирать по одному переходу.
- Запрет удаления статуса с задачами и сценарий переноса задач не пишутся заново: они
  сделаны в задаче 03 — `catalogs_service.delete_entry` (код ошибки `status_in_use`) и
  `POST /api/v1/statuses/{ref}/move-issues`. Задача 07 добавляет к ним проверку целостности
  графа и отчёт «после этого изменения N задач останутся без исходящих переходов»
  (выявлено в задаче 03).

## Готово, когда

- Собственный воркфлоу создаётся целиком (статусы + переходы) одним вызовом и правится точечно.
- Некорректный граф (недостижимый статус, тупик, отсутствие пути в `done`) отклоняется с
  указанием проблемы.
- Удаление статуса с задачами отклоняется, перенос задач работает.
- Запрещённый переход отклоняется с внятной ошибкой.
- Переход с незаполненным обязательным полем отклоняется с указанием поля.
- Закрытие требует резолюции, переоткрытие её снимает.
- Тесты на движок и эндпоинты.

## Не входит

Действия автоматики при переходе (задача 13). Визуальный редактор схемы — это фронтенд.
