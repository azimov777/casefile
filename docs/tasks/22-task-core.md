# 22. Задача: поля, статусы, переходы и хранилище дела

## Цель

Завести задачу с фиксированными полями и пятью разделами, зашитую таблицу переходов
с валидациями, которые не зависят от ещё не построенных частей, и таблицу записей дела,
в которую трекер подшивает служебные записи. После задачи задачу можно создать, править
в `backlog`, переводить по статусам, и каждое действие оставляет след в деле.

## Контекст

- `CONCEPT.md`, разделы 3.3 (поля, статусы, таблица переходов, валидации) и 3.4 (форма
  записи и служебные типы). Словарь идентификаторов в разделе 7.
- Из старого кода задач (git `49e2e49`) стоит перенести: единую точку мутаций,
  возвращающую фактические изменения; оптимистичную блокировку по версии; различение
  «не передано» и `null` через `unset_field` из `app/core/sentinels.py`.
- Валидации переходов, зависящие от следующих задач: сводка перед выходом из `in_progress`
  (23), вердикты для `done` (23), блокеры для `in_progress` (24), дети для `done` (24).
  Их точки подключения проектируются здесь: одно место в `domain`, где переход
  проверяется списком независимых проверок, и каждая следующая задача добавляет свою,
  не трогая таблицу.

## Ограничения

- Статусы, порядок цепочки и таблица переходов зашиты перечислениями; в базе нет
  справочника статусов.
- Новая задача рождается только в `backlog`; статус при создании не принимается.
- Название, описание и пять разделов меняются только в `backlog`. Исполнитель, теги
  и приоритет меняются в любом незакрытом статусе. В `done` и `cancelled` не меняется ничего.
- Записи дела неизменяемы: у репозитория нет методов правки и удаления, у API нет таких
  маршрутов. Сквозной номер `seq` выдаёт база монотонно; номер в задаче `no` начинается с 1.
- Здесь подшиваются только служебные записи: `created`, `status_changed`, `section_changed`,
  `assignee_changed`. Записи агента добавляет задача 23, записи о связях задача 24.
- Проверки `checks` хранятся упорядоченным списком строк; нумерация с 1 по позиции.

## Выход

- Таблицы `tasks` и `entries` с индексами по концепции и `CONVENTIONS.md`.
- Домен: перечисления статусов, типов записей, приоритетов; таблица переходов; список
  проверок перехода с точками подключения; правило «шаг назад».
- Сервисы: создать, частично обновить, перевести статус; подшить служебную запись
  в той же транзакции.
- REST: `POST /api/v1/tasks`, `GET /api/v1/tasks/{key}` (карточка, доступные переходы
  и опись дела; полный пакет достраивает задача 23), `PATCH /api/v1/tasks/{key}`,
  `POST /api/v1/tasks/{key}/transition`, `GET /api/v1/tasks/{key}/entries`.
- Миграция, тесты сервисов и smoke-тесты маршрутов, заметки о неочевидном.

## Обзорные проверки

1. Создание задачи отвечает статусом `backlog`, и в деле одна запись `created` с `no = 1` и автором из токена.
2. `backlog → open` у задачи без `checks` отвечает `422`, в `details.fields` перечислены все незаполненные разделы сразу.
3. `open → done` отвечает `409 transition_not_allowed`, в `details` перечислены допустимые переходы.
4. `in_progress → open` без `reason` отвечает `422` с кодом, названным в `ERRORS.md`; с `reason` проходит, и в `status_changed` лежат `from`, `to`, `reason`.
5. `PATCH` поля `goal` у задачи в `open` отвечает `409` с кодом про запрет правки; тот же запрос в `backlog` проходит и подшивает `section_changed` с «было / стало».
6. Смена исполнителя в `review` проходит и подшивает `assignee_changed`; та же смена в `done` отвечает `409`.
7. `PATCH` с устаревшей `version` отвечает `409 version_conflict`.
8. Две задачи в разных очередях, записи в них чередуются: `seq` растёт строго монотонно по всему трекеру, `no` в каждой задаче идёт с 1 без пропусков.
9. В OpenAPI нет маршрутов `PATCH` или `DELETE` для записей; тест проверяет это по схеме.
10. Полный набор тестов зелёный; контур поднимается с нуля; `docker ps` чист после работы.
