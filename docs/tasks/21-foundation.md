# 21. Фундамент: участники, токены с наборами, очереди

## Цель

Построить три сущности, на которые опирается всё остальное: реестр участников, токены
с двумя наборами и очереди с описанием и счётчиком номеров. После задачи можно
зарегистрировать человека и постоянного агента, выпустить им токены, завести очередь
и подписывать действия временного агента меткой.

## Контекст

- `CONCEPT.md`, разделы 3.1 и 3.2; словарь идентификаторов в разделе 7.
- Старые акторы, токены и аутентификация остались после задачи 20: хеширование, отзыв,
  отметка последнего использования, единая точка проверки прав. Схема авторизации
  описана в `notes/api.md`. Счётчик номеров очереди без гонок был в старом коде очередей:
  git `49e2e49`, заметки `notes/db.md`.
- Автор любого действия описывается одной структурой: род (`agent`, `human`, `tracker`)
  и подпись (имя участника или метка). Её будут использовать все последующие задачи
  для служебных записей и авторства.

## Ограничения

- Прав нет, кроме набора токена: `task` или `main`. Единая точка проверки прав проверяет
  только набор и ничего больше; роли, владельцы и разрешения по роду не заводятся.
- Участника и очередь нельзя удалить. Ключ очереди неизменяем.
- Секрет токена показывается один раз при выпуске; в базе только хеш.
- Общий агентский токен (без участника) принимается только с заголовком `X-Actor-Label`;
  без него запрос отклоняется. Токен участника метку игнорирует: подпись это имя участника.
- Фильтрация инструментов MCP по набору делается в задаче 28; здесь набор должен быть
  в модели токена и в структуре автора, доступной сервисам.
- Имена участников и ключи очередей: латиница, `snake_case` для имён, верхний регистр для
  ключей; уникальны без учёта регистра.

## Выход

- Таблицы `participants` (род, имя, описание), `tokens` (участник или null, набор, хеш,
  отзыв, последнее использование), `queues` (ключ, название, описание, счётчик).
- Сервисы: регистрация и правка участника, список; выпуск, список и отзыв токенов;
  создание, правка, чтение и список очередей; выдача следующего номера задачи без гонок.
- REST: `participants` (`POST`, `GET`, `GET /{name}`, `PATCH /{name}`), `tokens`
  (`POST`, `GET`, `DELETE /{id}`), `queues` (`POST`, `GET`, `GET /{key}`, `PATCH /{key}`).
  Запись участников, токенов и очередей требует набора `main`; чтение доступно обоим.
- Зависимость аутентификации, отдающая сервисам структуру автора с набором.
- Команда первичной инициализации в Docker: создаёт участника-человека и печатает его
  токен набора `main`, если в базе ещё нет ни одного токена.
- Миграция, тесты сервисов и smoke-тесты маршрутов, README: раздел о доступе и первичной
  инициализации, заметки о неочевидном.

## Обзорные проверки

1. Регистрация участника с именем, отличающимся от существующего только регистром, отвечает `409`.
2. Токен набора `task` на `POST /api/v1/queues` получает `403 permission_denied`; тот же запрос с `main` создаёт очередь.
3. Общий агентский токен без `X-Actor-Label` получает ошибку с кодом, названным в `ERRORS.md`; с заголовком запрос проходит, и в ответе на любой создающий вызов автор имеет род `agent` и подпись из заголовка.
4. `PATCH /api/v1/queues/{key}` с полем `key` в теле отвечает `422`, а с `description` меняет описание.
5. Тест на гонку: 50 параллельных запросов следующего номера одной очереди дают 50 разных последовательных номеров.
6. Команда инициализации на пустой базе печатает токен; повторный запуск ничего не создаёт и говорит об этом.
7. Ответ на выпуск токена содержит секрет, `GET /api/v1/tokens` его не содержит.
8. Полный набор тестов зелёный; контур поднимается с нуля; `docker ps` чист после работы.
