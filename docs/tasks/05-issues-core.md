# 05. Задачи: ядро

- **Блок:** Задачи
- **Зависимости:** 01, 02, 03, 04
- **Результат:** задачу можно создать, прочитать и изменить

## Зачем

Центральная сущность системы. От того, как устроен слой мутаций задачи, зависят история
изменений, автоматика и уведомления — они все подключаются к одной точке.

## Объём

- Модель `Issue`: ключ (`TRK-123`), очередь, тип, статус, резолюция, приоритет, название,
  описание, автор, исполнитель, наблюдатели, дедлайн, теги, `values JSONB`, версия, даты.
- Генерация ключа при создании через счётчик очереди.
- Сценарии: создать задачу, получить задачу, обновить поля, назначить исполнителя,
  добавить и убрать наблюдателя, удалить задачу.
- Валидация значений кастомных полей через валидатор из задачи 04.
- Оптимистичная блокировка: клиент передаёт версию, при расхождении — ошибка конфликта.
- Эндпоинты задач.
- Простое перечисление задач очереди с пагинацией (полноценный поиск — задача 12).
- **Наполнить `app/services/issue_usage.py` настоящими запросами.** Модуль отвечает на
  вопрос «сколько задач ссылается на справочник» и сейчас состоит из заглушек: таблицы задач
  не было. На нём держится защита справочников — запрет удаления статуса с задачами, запрет
  смены категории, запрет удаления непустой очереди, перенос задач между статусами. Заглушки
  падают с `NotImplementedError`, как только модель `Issue` появится в
  `app/db/models/__init__.py`, поэтому пропустить пункт не выйдет — но и оставлять его
  напоследок не стоит (выявлено в задаче 03).

## Что учесть

- **Ключевое требование задачи.** Все изменения задачи должны проходить через одну функцию
  применения изменений, которая принимает «что меняем» и «кто меняет» и возвращает список
  фактических изменений (поле, было, стало). В следующей задаче к этой точке подключатся журнал
  и события. Если мутации будут размазаны по десяти местам, задача 06 превратится в
  переписывание задачи 05.
- **Общий механизм «не передано» против «передано как null» строит эта задача** (выявлено в
  задаче 02). Сейчас его нет: у актора нет поля с осмысленным `null`, поэтому `ActorUpdate`
  просто отвергает явный `null` как ошибку схемы. У задачи так нельзя — `assignee`, `deadline`
  и `resolution` очищаются именно передачей `null`, и отличать её от отсутствия ключа
  обязательно, иначе PATCH либо не даст очистить поле, либо затрёт его. Сделать признак
  «не передано» (сентинел `UNSET` или разбор `model_fields_set`) один на проект, в
  `app/api/schemas/common.py`, и перевести на него `ActorUpdate`: две разные механики
  частичного обновления в одном API — ровно то, ради чего заведён этот пункт.
- Смена статуса в этой задаче делается напрямую, без проверки переходов: правила появятся в
  задаче 07. Заложить вызов проверки в виде функции-заглушки, чтобы потом просто наполнить её.
- Ключ задачи не меняется никогда, в том числе при переносе задачи в другую очередь (перенос в
  v1 не делаем, но модель не должна ему противоречить).
- Индексы: по очереди и статусу, по исполнителю, по дедлайну, GIN по `values`. Добавить
  составной под пагинацию: она идёт по паре `(created_at, id)`, и на таблице задач это уже не
  мелочь (выявлено в задаче 02).
- Взять курсорную пагинацию из `app/db/pagination.py`, а не писать вторую: `paginate` принимает
  готовый `select` с любыми фильтрами. Своя реализация разойдётся с первой по формату курсора,
  и клиент, обходящий разные коллекции одним кодом, сломается (выявлено в задаче 02).
- Автор и исполнитель — внешние ключи на `actors`. Инициатора мутации принимать параметром
  `initiator: Actor` (в HTTP-слое это `CurrentActorDep`), а не брать из глобального состояния:
  ту же функцию вызовут MCP, воркер и автоматика, у которой инициатор — системный актор с
  фиксированным идентификатором `SYSTEM_ACTOR_ID` (выявлено в задаче 02).
- Начинать каждый сценарий с `ensure_allowed(initiator, "issue.<действие>")` из
  `app/services/permissions.py`. В v1 она разрешает всё; смысл в том, чтобы при появлении
  ролей наполнять один файл, а не искать пропущенные проверки по эндпоинтам (выявлено в
  задаче 02).
- **Проверить, что падение коммита доходит до клиента правильным ответом.** Транзакцию
  фиксирует `session_scope` (см. `app/db/session.py`) уже после того, как обработчик вернул
  результат. Пока в схеме не было таблиц, воспроизвести падение самого коммита было нечем — с
  появлением `Issue` с уникальным ключом это становится возможным: две параллельные вставки
  одного ключа или отложенное ограничение (`DEFERRABLE INITIALLY DEFERRED`) роняют не запрос, а
  коммит. Нужен тест: клиент получает единую оболочку ошибки с кодом `conflict`, а не пустой
  ответ и не голый пятисотый от Starlette. Если окажется, что ответ к этому моменту уже ушёл и
  обработчик ошибок не срабатывает, — фиксировать транзакцию придётся до формирования ответа, и
  это изменение `session_scope`, а не эндпоинта.
- Ключ задачи выдаётся через `queues_service.allocate_issue_key`, а не собственным
  счётчиком: выдача сделана одним `UPDATE ... RETURNING` и уже проверена тестом на
  конкурентность. Там же стоит запрет на архивную очередь. Вторая реализация нумерации
  разойдётся с первой и даст дубли ключей (выявлено в задаче 03).
- Статус, тип и резолюция задачи проверяются на доступность в очереди через
  `catalogs_service.ensure_available_in_queue`: локальная запись чужой очереди и отключённая
  запись в задачу попасть не должны (выявлено в задаче 03).

## Готово, когда

- Задача создаётся с валидацией обязательных полей, ключ выдаётся корректно.
- Частичное обновление меняет только переданные поля.
- Переданный `null` очищает поле, отсутствующий ключ — не трогает; признак «не передано» —
  общий для проекта, и `ActorUpdate` переведён на него (выявлено в задаче 02).
- Конфликт версий возвращает ошибку конфликта, а не молча перезаписывает.
- Тесты на создание, чтение, частичное обновление, конфликт версий, валидацию полей.
- Падение коммита на границе запроса (дубликат ключа задачи) отдаёт ошибку в единой
  оболочке — есть тест.
