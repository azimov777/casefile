# 05. Задачи: ядро

- **Блок:** Задачи
- **Зависимости:** 01, 02, 03, 04
- **Результат:** задачу можно создать, прочитать и изменить

## Зачем

Центральная сущность системы. От того, как устроен слой мутаций задачи, зависят история
изменений, автоматика и уведомления — они все подключаются к одной точке.

## Объём

- Модель `Issue`: ключ (`TRK-123`), очередь, тип, статус, резолюция, приоритет, название,
  описание, автор, исполнитель, наблюдатели, дедлайн, теги, `values JSONB`, версия, даты.
- Генерация ключа при создании через счётчик очереди.
- Сценарии: создать задачу, получить задачу, обновить поля, назначить исполнителя,
  добавить и убрать наблюдателя, удалить задачу.
- Валидация значений кастомных полей через валидатор из задачи 04.
- Оптимистичная блокировка: клиент передаёт версию, при расхождении — ошибка конфликта.
- Эндпоинты задач.
- Простое перечисление задач очереди с пагинацией (полноценный поиск — задача 12).

## Что учесть

- **Ключевое требование задачи.** Все изменения задачи должны проходить через одну функцию
  применения изменений, которая принимает «что меняем» и «кто меняет» и возвращает список
  фактических изменений (поле, было, стало). В следующей задаче к этой точке подключатся журнал
  и события. Если мутации будут размазаны по десяти местам, задача 06 превратится в
  переписывание задачи 05.
- Отличать «поле не передано» от «поле передано как null» — иначе частичное обновление будет
  затирать данные.
- Смена статуса в этой задаче делается напрямую, без проверки переходов: правила появятся в
  задаче 07. Заложить вызов проверки в виде функции-заглушки, чтобы потом просто наполнить её.
- Ключ задачи не меняется никогда, в том числе при переносе задачи в другую очередь (перенос в
  v1 не делаем, но модель не должна ему противоречить).
- Индексы: по очереди и статусу, по исполнителю, по дедлайну, GIN по `values`.
- **Проверить, что падение коммита доходит до клиента правильным ответом.** Транзакцию
  фиксирует `session_scope` (см. `app/db/session.py`) уже после того, как обработчик вернул
  результат. Пока в схеме не было таблиц, воспроизвести падение самого коммита было нечем — с
  появлением `Issue` с уникальным ключом это становится возможным: две параллельные вставки
  одного ключа или отложенное ограничение (`DEFERRABLE INITIALLY DEFERRED`) роняют не запрос, а
  коммит. Нужен тест: клиент получает единую оболочку ошибки с кодом `conflict`, а не пустой
  ответ и не голый пятисотый от Starlette. Если окажется, что ответ к этому моменту уже ушёл и
  обработчик ошибок не срабатывает, — фиксировать транзакцию придётся до формирования ответа, и
  это изменение `session_scope`, а не эндпоинта.

## Готово, когда

- Задача создаётся с валидацией обязательных полей, ключ выдаётся корректно.
- Частичное обновление меняет только переданные поля.
- Конфликт версий возвращает ошибку конфликта, а не молча перезаписывает.
- Тесты на создание, чтение, частичное обновление, конфликт версий, валидацию полей.
- Падение коммита на границе запроса (дубликат ключа задачи) отдаёт ошибку в единой
  оболочке — есть тест.

## Не входит

Журнал изменений и события (задача 06), связи (задача 08), комментарии (задача 09).
