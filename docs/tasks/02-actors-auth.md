# 02. Акторы и аутентификация

- **Блок:** Акторы
- **Зависимости:** 01
- **Результат:** у каждого запроса есть инициатор — человек или агент

## Зачем

Задачу нужно на кого-то назначать, изменение — кому-то приписывать, уведомление — кому-то
адресовать. Даже в однопользовательском режиме без понятия «актор» не работают ни история
изменений, ни автоматика, ни уведомления агентам.

## Объём

- Модель `Actor`: тип (`human` / `agent` / `system`), ключ, отображаемое имя, активность.
- Модель `ApiToken`: привязка к актору, хеш токена, название, дата создания, дата последнего
  использования, возможность отзыва.
- Аутентификация по токену в заголовке; зависимость `current_actor` для роутеров и MCP.
- Системный актор — от его имени будут действовать автоматика и фоновые процессы.
- Сценарии: создать актора, выпустить токен, отозвать токен, список акторов.
- Эндпоинты управления акторами и токенами.
- Начальные данные: владелец-человек и системный актор создаются миграцией или командой инициализации.
- Единая точка проверки прав — функция, которая в v1 всегда разрешает, но вызывается везде,
  где позже появится ограничение.

## Что учесть

- Токен хранится только в виде хеша; полное значение показывается один раз при выпуске.
- Токен агента и токен человека — один механизм, разница только в типе актора. Не делать две
  параллельные схемы аутентификации для REST и MCP: MCP-сервер будет использовать ту же самую.
- Единая точка проверки прав — это не преждевременное усложнение, а маркер: когда роли появятся,
  их надо будет наполнить в одном файле, а не искать по всем эндпоинтам.
- Не строить сессии, пароли, OAuth — в v1 их нет.

## Готово, когда

- Запрос без валидного токена получает ошибку с кодом из соглашений.
- Запрос с валидным токеном имеет доступ к своему актору.
- Тесты: выпуск токена, доступ по токену, отзыв токена, доступ отозванным токеном.

## Не входит

Роли, группы, разграничение доступа к очередям.
