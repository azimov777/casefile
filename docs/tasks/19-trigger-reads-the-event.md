# 19. Триггер обязан реагировать на изменение, а не на состояние

- **Блок:** Автоматика
- **Зависимости:** 13
- **Результат:** правило срабатывает столько раз, сколько раз произошло то, на что оно подписано

## Зачем

Найдено сквозным прогоном против прод-контура (задача 17).

`ctx.target` — живая строка задачи из базы, а не снимок из события. Правило, чьё условие
написано по ней, проверяет состояние на момент **обработки** события воркером, а не то,
которое событие описывает. Пока воркер разбирает очередь по одному событию сразу, разницы
не видно. Стоит событиям накопиться — и каждое из них проходит условие, истинное для
последнего.

Воспроизведение (прод-контур, воркер стартует раньше миграций и разбирает очередь пачкой):

```
эпик TRK-1: open → in_progress → review → closed        три события issue.status_changed
→ три успешных срабатывания close_children_with_parent
→ три одинаковых комментария «подзадачи ещё открыты»
→ три уведомления наблюдателю
```

Ожидалось одно. Условие правила —
`if parent.status.category is not StatusCategory.DONE: ctx.skip(...)`, и к моменту
обработки первых двух событий задача **уже** была закрыта.

Дефект не в самом правиле: так написано бы любое правило, потому что `ctx.target` —
самое очевидное, что даёт контекст, а нагрузка события выглядит вспомогательной. Значит,
чинить надо контракт движка, а не одно правило.

## Объём

- Сформулировать и закрепить правило: **условие** триггера проверяется по нагрузке
  события, **действие** выполняется над актуальной строкой. Записать это в описание
  `RuleContext` и в раздел README про добавление своего правила.
- Дать условию удобную опору. Сейчас есть `ctx.change_of(field)` и `ctx.changed_fields()`,
  но категория статуса из них не выводится: в нагрузке лежит ссылка (`TRK.closed`), а
  категория — свойство справочника. Нужен способ спросить «событие перевело задачу в
  категорию `done`» одним вызовом, иначе каждое правило будет доставать её само и
  по-разному.
- Починить поставочные правила, которые читают состояние вместо события. Начать с
  `close_children_with_parent`; проверить `nudge_stale_issues` и `prepare_release`.
- Тест на **накопленную** очередь: несколько событий кладутся в outbox и разбираются
  **после** того, как задача достигла конечного состояния. Именно такой тест ловит
  дефект; тест, где события обрабатываются по одному сразу, зелёный и на сломанном коде.
- Ревизия остальных мест, где нагрузка события подменяется чтением базы: подписчик
  уведомлений (`audience_of` уже читает нагрузку — проверить, что везде так) и подписчик
  вебхуков.

## Что учесть

- **Дев-контур дефект не показывает.** Воркер там разбирает очередь по мере поступления,
  и каждое событие обрабатывается до следующего изменения. Проверять надо на очереди,
  накопленной заранее, — или на прод-контуре, где воркер стартует раньше миграций и
  первые секунды не работает (выявлено в задаче 17).
- **Защита от зацикливания здесь ни при чём.** Ограничение глубины цепочки (задача 13)
  считает события, порождённые правилом, а тут все три события породил человек. Ни один
  из трёх запусков не выглядел аномальным ни для одной существующей защиты.
- **Идемпотентность действия — не замена исправлению условия.** Соблазн «не
  комментировать, если такой комментарий уже есть» решает симптом одного правила и
  оставляет причину: следующее правило напишет условие так же и сработает трижды.
- Журнал срабатываний уже показывает проблему целиком: три записи `success` с тремя
  разными `event`, все с действием `comment`. Диагностика есть, механики нет.

## Готово, когда

- Контракт «условие — по событию, действие — по строке» записан рядом с `RuleContext` и
  в README.
- У условия есть удобный способ спросить о категории целевого статуса события.
- Поставочные правила ему следуют.
- Тест на накопленной очереди событий проходит и падает на прежнем коде.

## Не входит

Изменение порядка обработки событий, дедупликация событий в outbox, отказ от
`ctx.target`.
