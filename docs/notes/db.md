# База данных

## gen_random_uuid() встроен в PostgreSQL 13+

**Что:** для `server_default` первичного ключа расширение `pgcrypto` не нужно — функция
доступна из коробки.
**Почему важно:** миграция с `CREATE EXTENSION pgcrypto` требует прав суперпользователя и
ломается в управляемых базах, где их нет.
**Где:** `app/db/base.py`, `UUIDPrimaryKeyMixin`.

## Идентификатор считается в Python, а не в базе

**Что:** у `id` заданы оба значения по умолчанию: `default=uuid.uuid4` (Python) и
`server_default=text("gen_random_uuid()")` (PostgreSQL).
**Почему важно:** сценарию нужен id объекта до `flush` — чтобы в той же транзакции сослаться
на него из записи журнала изменений и события outbox. Если полагаться только на базу,
придётся делать лишний round-trip ради значения, которое можно знать заранее.
**Где:** `app/db/base.py`, `UUIDPrimaryKeyMixin`.

## Имена ограничений заданы соглашением, а не Alembic

**Что:** `MetaData(naming_convention=...)` фиксирует шаблоны имён для индексов, внешних
ключей и проверок.
**Почему важно:** без соглашения Alembic придумывает имена сам и по-разному для одинаковых по
смыслу ограничений. Откатить такую миграцию вслепую нельзя: имя, которое нужно удалить,
придётся искать в базе.
**Где:** `app/db/base.py`, `NAMING_CONVENTION`.

## Автогенерация видит только импортированные модели

**Что:** `alembic revision --autogenerate` строит diff по `Base.metadata`, а метаданные
наполняются в момент импорта модуля с моделью.
**Почему важно:** модель, не импортированная в `app/db/models/__init__.py`, для автогенерации
не существует — миграция выйдет пустой, и это заметят через несколько задач.
**Как правильно:** каждая новая модель добавляется в `app/db/models/__init__.py`.
**Где:** `app/db/models/__init__.py`, `app/db/migrations/env.py`.

## Коммит делает граница запроса, а не сценарий

**Что:** транзакция фиксируется в `session_scope`: ветка `else` после `yield` коммитит,
`except` откатывает. `get_session` — тонкая обёртка (`async with session_scope() as session:
yield session`), собственной логики транзакции у неё нет.
**Почему важно:** `finally` здесь был бы ошибкой — он коммитил бы и после исключения. FastAPI
закрывает `yield`-зависимость через `__anext__` при успехе и через `athrow` при ошибке, поэтому
ветки `else` и `except` попадают ровно куда нужно.
**Как правильно:** менять поведение транзакции только в `session_scope`. Заводить вторую
реализацию границы (в зависимости, в репозитории, в декораторе сценария) нельзя: две копии
неизбежно разъедутся, и один и тот же сценарий начнёт вести себя из REST иначе, чем из воркера.
Явный `commit()` внутри сценария остаётся допустимым, когда нужна промежуточная фиксация.
**Где:** `app/db/session.py`, тесты — `tests/test_transactions.py`.

## Enum без `create_constraint=True` — это просто VARCHAR

**Что:** `sa.Enum(MyEnum, native_enum=False)` не создаёт никакой проверки значений: с версии
SQLAlchemy 1.4 параметр `create_constraint` по умолчанию `False`.
**Почему важно:** ошибка молчаливая. Миграция проходит, `\d table` показывает колонку
`character varying(16)`, всё выглядит правильно — а записать в неё можно любую строку.
Обнаруживается это тогда, когда в колонке `type` уже лежит мусор.
**Как правильно:** заводить перечисления только через `string_enum` из `app/db/base.py` — там
флаг выставлен. После миграции проверять глазами: `\d actors` должен показать блок
`Check constraints` с именем вида `ck_actors_actor_type`.
**Где:** `app/db/base.py`, `string_enum`.

## Перечисления хранятся как VARCHAR, а не как тип PostgreSQL

**Что:** проект нигде не использует native enum PostgreSQL.
**Почему важно:** выглядит как упущение, поэтому: это решение, а не недосмотр. Native enum
расширяется через `ALTER TYPE ... ADD VALUE`, и добавленное значение нельзя использовать в той
же транзакции — миграция, которая заводит значение и тут же им пользуется, падает. Плюс каждый
такой тип надо создавать и удалять в миграции руками, иначе `downgrade` оставляет мусор.
**Как правильно:** `string_enum(MyEnum, name="my_enum")`. Расширение набора значений — замена
одного ограничения CHECK.
**Где:** `app/db/base.py`, `string_enum`.

## `updated_at` после UPDATE требует `eager_defaults`

**Что:** обращение к `obj.updated_at` сразу после изменения объекта падает с
`MissingGreenlet: greenlet_spawn has not been called`.
**Почему важно:** значение вычисляет база (`onupdate=func.now()`), поэтому после flush
SQLAlchemy помечает атрибут протухшим и при первом же обращении лезет за ним в базу — уже вне
async-контекста. Ловушка коварна вдвойне: на INSERT всё работает (там RETURNING включён по
умолчанию), тесты сервиса объект целиком не сериализуют, и падает только живой PATCH-запрос
при сборке ответа Pydantic. Поймала это живая проверка, а не тесты.
**Как правильно:** `__mapper_args__ = {"eager_defaults": True}` — уже стоит в `BaseModel`,
поэтому новые модели наследуют его сами. Снимать нельзя.
**Где:** `app/db/base.py`, `BaseModel`.

## Курсорная пагинация сортирует по паре `(created_at, id)`

**Что:** второй элемент ключа — не украшение. Без него записи с одинаковым временем создания
проваливаются между страницами или дублируются.
**Почему важно:** `created_at` не уникален: массовая вставка в одной транзакции даёт всем
строкам одно `now()`. Курсор, хранящий только время, на такой границе теряет данные.
**Как правильно:** брать `paginate` из `app/db/pagination.py`, не писать свою пагинацию.
Запрашивается `limit + 1` запись — лишняя и есть признак следующей страницы, `COUNT(*)` не нужен.
**Где:** `app/db/pagination.py`.

## Время в именах ревизий закреплено за UTC

**Что:** в `alembic.ini` стоит `timezone = UTC`. Без этой строки Alembic берёт локальное время
той машины, где выполнялась команда.
**Почему важно:** контейнер живёт в UTC, разработчик — в своём поясе. Ревизия, сделанная мимо
контейнера, получает имя со сдвигом на часы, и файлы перестают сортироваться в порядке
применения: свежая миграция оказывается выше старой. Порядок наката от этого не страдает (его
задаёт `down_revision`), но читать каталог версий становится нельзя.
**Как правильно:** ничего не делать — конфиг уже закрывает вопрос, ревизии всегда получают имя
и заголовок `Create Date` в UTC с явным смещением `+00:00`. Проверить, что заголовок новой
ревизии оканчивается на `+00:00`: если смещения нет, команду запускали старой конфигурацией.
**Где:** `alembic.ini`, ключ `timezone`.

## Переименовать ревизию можно, переписать — нет

**Что:** Alembic находит ревизию по полю `revision` внутри файла, а не по имени файла. Строка
в таблице `alembic_version` ссылается на этот идентификатор.
**Почему важно:** запрет «не править применённую ревизию» относится к её содержимому —
изменённый `upgrade()` разведёт базы, где ревизия уже накатана, с теми, где ещё нет.
Переименование файла на это не влияет и базу не трогает: так была исправлена первая ревизия,
названная в чужом часовом поясе.
**Как правильно:** переименовывать — `git mv`, потом сверить `alembic history` и
`alembic current`. Менять `upgrade`/`downgrade` применённой ревизии — по-прежнему нельзя.
**Где:** `app/db/migrations/versions/`.

## Автогенерация Alembic сама дописывает удаление CHECK у перечислений

**Что:** `alembic revision --autogenerate` в каждой новой ревизии добавляет строку
`op.drop_constraint(op.f("ck_actors_actor_type"), "actors", type_="check")` — и так для
любой уже существующей колонки-перечисления, к самой ревизии отношения не имеющей.
**Почему важно:** оставить строку — молча снять с колонки проверку допустимых значений.
Схема после этого выглядит правильной, а записать в колонку можно любую строку. Ошибка
всплывёт через несколько задач, когда в `type` окажется мусор.
**Как правильно:** удалять эту строку из сгенерированной ревизии руками и проверять глазами:
`\d actors` должен показывать блок `Check constraints`. Причина в сравнении по имени:
ограничение, созданное `string_enum`, получает имя из соглашения об именах только при
компиляции DDL, и до этого момента для сравнения оно «безымянное», то есть отсутствующее.
**Где:** `app/db/migrations/versions/20260827_1927_queues_and_catalogs.py`, шапка файла.

## Кольцо внешних ключей требует `use_alter=True` и явного `create_foreign_key`

**Что:** очередь ссылается на статус по умолчанию, локальный статус — на свою очередь.
Без пометок SQLAlchemy не может отсортировать таблицы (`SAWarning: unresolvable cycles`)
и **выбрасывает внешние ключи из сортировки**, а автогенерация выдаёт неприменимую ревизию.
**Почему важно:** `use_alter=True` кольцо разрывает, но у этого флага есть вторая половина,
о которой легко не знать: `CREATE TABLE` такие ключи **не создаёт вовсе**. `op.create_table`
проходит без ошибок, миграция накатывается, а внешних ключей в базе нет — снова молча.
**Как правильно:** пометить ключ `use_alter=True` в модели и в миграции добавить его
отдельным `op.create_foreign_key` после обеих таблиц, а в `downgrade` снять его первым.
Проверять глазами: `\d queues` должен показать оба ключа в блоке `Foreign-key constraints`.
**Где:** `app/db/models/queue.py`, `default_status_id`; миграция `queues and catalogs`.

## `NO ACTION` и `RESTRICT` — не синонимы, когда есть каскад

**Что:** внешние ключи очереди на справочники по умолчанию объявлены без `ondelete`,
то есть с `NO ACTION`. С `RESTRICT` удаление самой очереди падало бы.
**Почему важно:** выглядит как недосмотр («почему не RESTRICT, раз удалять нельзя?»).
Разница в моменте проверки: `RESTRICT` проверяется сразу, `NO ACTION` — в конце оператора.
Удаление очереди каскадом уносит её локальные статусы, и к концу оператора ссылки на них
из удаляемой очереди уже нет — `NO ACTION` это пропускает, `RESTRICT` нет.
**Где:** `app/db/models/queue.py`, `Queue`.

## Уникальность в двух областях сразу — это `NULLS NOT DISTINCT`

**Что:** ключ записи справочника уникален глобально либо внутри очереди. Одно ограничение
на пару `(queue_id, key)` этого не даёт: PostgreSQL по умолчанию считает NULL-ы различными,
и глобальных статусов `open` можно было бы завести сколько угодно.
**Почему важно:** дефект молчаливый — ограничение есть, выглядит правильным, не работает.
**Как правильно:** `UniqueConstraint("queue_id", "key", postgresql_nulls_not_distinct=True)`.
Требует PostgreSQL 15+ (проект на 17 в обоих контурах). Проверять глазами: `\d statuses`
должен показать `UNIQUE CONSTRAINT, btree (queue_id, key) NULLS NOT DISTINCT`.
**Где:** `app/db/models/catalog.py`, `CatalogEntryMixin.__table_args__`.

## Номера задач выдаёт `UPDATE ... RETURNING`, а не последовательность

**Что:** `UPDATE queues SET last_issue_number = last_issue_number + 1 RETURNING` — один
запрос, инкремент считает база поверх текущего значения строки.
**Почему важно:** наивное «прочитать и записать +1» выдаёт двум параллельным запросам один
номер. `SEQUENCE` не блокирует, но оставляет дыры при любом откате и параллельной работе,
а ключи задач без дыр — требование задачи 03.
**Как правильно:** брать `QueueRepository.allocate_issue_number`, не писать свою выдачу.
Помнить про две особенности, обе намеренные: выдача сериализует создание задач в одной
очереди до конца транзакции, и откатившаяся транзакция свой номер теряет — дыра всё-таки
возможна, убрать её нельзя, не отказавшись от транзакционности.
**Где:** `app/db/repositories/queues.py`; тесты — `tests/test_queue_numbering.py`.

## Массовая вставка даёт всем строкам одинаковый `created_at`

**Что:** `now()` — время начала транзакции, поэтому `op.bulk_insert` проставляет всем
записям начального набора одну отметку, и сортировка по `(created_at, id)` вырождается в
сортировку по случайным UUID.
**Почему важно:** справочник в конфигурации очереди каждый раз выглядит иначе, а порядок
«открыт → в работе → закрыт» превращается в произвольный. Тем же свойством `now()`
объясняется, почему у пары записей, созданных одной транзакцией, порядок тоже произволен.
**Как правильно:** в миграции разводить отметки явно (`created_at + timedelta(microseconds=i)`)
и проставлять `updated_at` тем же значением, иначе у нетронутой записи время изменения
окажется раньше времени создания.
**Где:** `_ordered` в миграции `queues and catalogs`.

## Каскад на таблице ограничений умеет молча расширять правило

**Что:** у `field_issue_types.issue_type_id` стоит `ON DELETE CASCADE`, но удаление типа задачи
отклоняет сценарий (`catalogs.delete_entry`), а не база.
**Почему важно:** ограничение «поле применимо только к багам» выражено строками. Каскад,
удалив их вместе с типом `bug`, превратил бы поле в применимое ко всем типам — молча,
необратимо и в момент, далёкий от места, где это заметят. При этом убрать каскад нельзя:
удаление очереди уносит её локальные типы, и без каскада эта операция падала бы.
**Как правильно:** каскад держать как страховку для удаления очереди, а осмысленный случай
запрещать в сценарии. Так же поступать с любой таблицей, где строка означает «сужение»:
её исчезновение — это расширение правила, а не его удаление.
**Где:** `app/db/models/field.py` (`FieldIssueType`), `app/services/catalogs.py`
(`_ensure_not_field_restriction`).

## JSONB-колонку нельзя менять на месте

**Что:** `field.options.append(...)` не приводит к UPDATE: SQLAlchemy не отслеживает мутации
внутри значения JSONB и считает атрибут неизменённым.
**Почему важно:** сбой полностью молчаливый — код отработал, ошибки нет, изменения нет.
Проявится это при следующем чтении, уже в другом месте.
**Как правильно:** всегда присваивать колонке новый объект целиком
(`field.options = [...]`). Альтернатива — `MutableList.as_mutable(JSONB)`, но она добавляет
слежение за каждым элементом и в проекте не используется.
**Где:** `app/services/fields.py`, `update_field`.

## `alembic check` штатно ругается на CHECK каждого перечисления

**Что:** `alembic check` на актуальной схеме сообщает `remove_constraint` для
`ck_actors_actor_type`, `ck_statuses_status_category`, `ck_fields_field_value_type` и
`ck_issues_issue_priority` — по одной строке на каждое перечисление в схеме, и список
растёт вместе с ними.
**Почему важно:** выглядит как расхождение моделей и схемы, а на деле это то же ложное
срабатывание, что и при автогенерации: имя ограничения от `string_enum` вычисляется соглашением
об именах только при компиляции DDL. Не зная этого, легко «починить» схему, сняв проверки.
**Как правильно:** проверять командой и читать список: если в нём **только** снятие
CHECK у колонок-перечислений — модели и схема сошлись. Любая другая операция —
настоящее расхождение.
**Где:** `docker compose run --rm --entrypoint alembic api check`.

## Колонка `values` — зарезервированное слово, и это видно в метаданных

**Что:** SQLAlchemy и PostgreSQL сами закавычивают имя (`gin ("values")`), поэтому в
SQL и в ORM (`Issue.values`) ловушки нет. Она есть в метаданных: `table.c.values`
вернёт **метод** коллекции колонок, а не колонку.
**Почему важно:** сбой молчаливый и странный — код получает `<bound method>` вместо
выражения и падает далеко от места ошибки, либо строит бессмысленное условие.
**Как правильно:** обращаться `table.c["values"]`. В миграциях и запросах через ORM
ничего делать не нужно.
**Где:** `app/db/models/issue.py`, `Issue.values`.

## У задачи все связи грузятся стратегией `selectin`, и это решение

**Что:** очередь, тип, статус, резолюция, автор, исполнитель и наблюдатели объявлены
`lazy="selectin"`, хотя у очереди и справочников часть связей — `joined`.
**Почему важно:** выглядит как непоследовательность. Причина в количестве: у задачи семь
связанных объектов, и `joined` собрал бы страницу из пятидесяти задач одним запросом с
двумя десятками соединений — очередь тянет владельца и свои значения по умолчанию, а те
свои очереди. `selectin` даёт семь коротких запросов на страницу любого размера и
переиспользует уже загруженные справочники.
**Как правильно:** для новых связей задачи брать `selectin`. Менять на `joined` — только
с замером, а не по аналогии с очередью.
**Где:** `app/db/models/issue.py`.

## Массовый перенос задач между статусами поднимает версию тем же запросом

**Что:** `IssueRepository.move_to_status` пишет `version = version + 1` и `updated_at`
вместе со сменой статуса.
**Почему важно:** без этого клиент, прочитавший задачу до переноса, прошёл бы проверку
оптимистичной блокировки и записал бы поверх нового статуса, ничего не заметив.
**Как правильно:** любой массовый `UPDATE` по задачам обязан поднимать версию.
Помнить и о втором свойстве: `synchronize_session=False` означает, что уже загруженные
объекты сессии держат старый статус — сценарий переноса поэтому отдаёт число, а не
объекты. Журнала и событий такой `UPDATE` не пишет: это осознанно (сотня одинаковых
записей истории бесполезна), но задача 06 обязана решить вопрос явно.
**Где:** `app/db/repositories/issues.py`, `move_to_status`.

## Ключ задачи выдаётся последним, после всех проверок

**Что:** `create_issue` сначала проверяет название, описание, дедлайн, теги, справочники
и значения кастомных полей и только потом зовёт `allocate_issue_key`.
**Почему важно:** номер выдаётся атомарным `UPDATE ... RETURNING` и при откате
транзакции теряется — дыра в нумерации остаётся навсегда. Порядок «сначала номер, потом
проверки» означал бы дыру на каждом неудачном запросе, а неудачные запросы у агентов
обычное дело.
**Как правильно:** новую проверку в создании задачи ставить **до** выдачи ключа. Тест
`test_a_failed_creation_does_not_burn_a_number` стережёт это.
**Где:** `app/services/issues.py`, `create_issue`.

## Записи одной транзакции сортируются по случайным UUID, если время ставит `now()`

**Что:** у `changelog_entries` и `outbox_events` отметка `created_at` ставится
`clock_timestamp()`, а не `func.now()` из `TimestampsMixin`. Это единственное место в
проекте, где общая примесь переопределяется.
**Почему важно:** `now()` — время **начала транзакции**, одно на все её строки. Курсорная
пагинация идёт по паре `(created_at, id)`, и при совпадении времени порядок задаёт
случайный UUID: история задачи, изменённой дважды в одной транзакции, показывалась бы
задом наперёд примерно в половине случаев, а события уходили бы подписчику не в том
порядке, в каком происходили. Для справочников это была косметика (см. заметку про
`bulk_insert`), здесь — уже нет. `clock_timestamp()` идёт вперёд внутри транзакции.
**Как правильно:** новой таблице, куда одна транзакция кладёт больше одной строки и где
порядок значим, задавать `server_default=func.clock_timestamp()`. Где порядок не значим —
оставлять как есть, `now()` дешевле и одинаков для всей транзакции.
**Где:** `app/db/models/event.py`.

## `alembic check` ругается ещё и на CHECK статуса outbox

**Что:** к известному списку ложных срабатываний (`ck_actors_actor_type`,
`ck_statuses_status_category`, `ck_fields_field_value_type`, `ck_issues_issue_priority`)
добавился `ck_outbox_events_outbox_status`, с задачей 08 — `ck_issue_links_issue_link_type`,
а с задачей 10 — `ck_projects_project_status` и `ck_portfolios_project_status` (одно
перечисление на две таблицы даёт два ограничения).
**Почему важно:** список растёт с каждым новым перечислением, и это по-прежнему не
расхождение схемы. Правило проверки неизменно: если в выводе **только** снятие CHECK у
колонок-перечислений — модели и схема сошлись.
**Где:** `docker compose run --rm --entrypoint alembic api check`.

## Массовый `UPDATE` отдаёт ключи через `RETURNING`, и это не бесплатно

**Что:** `IssueRepository.move_to_status` возвращает не `rowcount`, а список пар
`(id, key)` — иначе перенос не смог бы написать запись в историю каждой задачи.
**Почему важно:** ограничение неочевидное и названо прямо: перенос ста тысяч задач
вернёт сто тысяч строк в память процесса. Перенос делается ради удаления статуса, и
такие объёмы в нём реальны.
**Где:** `app/db/repositories/issues.py`, `move_to_status`.

## Второй вид курсора живёт в том же модуле пагинации

**Что:** `encode_text_cursor` / `decode_text_cursor` в `app/db/pagination.py` — курсор для
страницы, упорядоченной по одному текстовому ключу. Нужен словарю тегов: он собирается
агрегатом (`GROUP BY`), у его строк нет ни `created_at`, ни `id`, и общий `paginate` к ним
неприменим.
**Почему важно:** соблазн написать разбор курсора по месту велик — он тривиален. Но второй
разбор однажды истолкует испорченное значение иначе: отдаст пятисотку вместо `invalid_cursor`
или молча начнёт страницу с начала. Правило «одна реализация пагинации» относится к разбору
курсора, а не только к функции `paginate`.
**Как правильно:** новой странице с нестандартным порядком брать готовые `encode_text_cursor`
и `decode_text_cursor`, а если ключ другого типа — заводить пару рядом с ними, в том же файле.
**Где:** `app/db/pagination.py`; применение — `app/db/repositories/issues.py`, `list_tags_page`.

## Функция в `FROM` и `LATERAL`: писать явно

**Что:** `jsonb_array_elements_text(issues.tags)` подключается как
`.table_valued("value").lateral()`, и `LATERAL` указан явно.
**Почему важно:** для функции в списке `FROM` PostgreSQL подразумевает `LATERAL` сам, поэтому
кажется, что слово лишнее. Но правая часть `JOIN` без него не имеет права ссылаться на левую,
и SQLAlchemy строит именно `JOIN ... ON true`. Ошибка при этом приходит от базы и звучит как
проблема с колонкой, а не с формой запроса.
**Где:** `app/db/repositories/issues.py`, `list_tags_page`.

## `%` и `_` в пользовательском поиске экранируются вручную

**Что:** подстрока для `ILIKE` собирается с заменой `\`, `%` и `_` и с параметром
`escape="\\"`.
**Почему важно:** без этого тег `100_percent` находился бы по запросу `100x` — подчёркивание в
`LIKE` означает «любой символ». Сбой молчаливый: подсказка отдаёт лишние совпадения, и
заметить это можно только на редком значении.
**Где:** `app/db/repositories/issues.py`, `list_tags_page`; тест —
`tests/test_tags_api.py::test_a_wildcard_in_the_query_is_not_a_wildcard`.

## `None` в колонке JSONB — это значение `null`, а не SQL NULL

**Что:** `mapped_column(JSONB)` при питоновском `None` пишет в колонку **значение** JSON
`null`. Колонка перестаёт быть пустой: `IS NULL` её не найдёт, а `num_nonnulls` посчитает
заполненной.
**Почему важно:** сбой молчаливый ровно до первой проверки, которая на пустоту опирается.
Поймал его CHECK «ровно один источник» у сохранённого фильтра: строка с заполненным
`query` и «пустым» `structured_filter` не проходила, потому что для базы заполненными
были обе. Без такого ограничения ошибка дожила бы до первого `WHERE ... IS NULL` в другом
модуле и выглядела бы как потеря данных.
**Как правильно:** `JSONB(none_as_null=True)` у любой nullable-колонки JSONB. Колонке, где
`null` — законное значение (а не «значения нет»), флаг не нужен, но такой случай надо
называть комментарием: по типу его не отличить.
**Где:** `app/db/models/saved_filter.py`, `structured_filter`.

## `pg_trgm` заводится миграцией, `pgcrypto` — нет

**Что:** `CREATE EXTENSION IF NOT EXISTS pg_trgm` стоит в миграции, хотя проект
сознательно избегал `CREATE EXTENSION pgcrypto`.
**Почему важно:** выглядит как нарушение собственного правила. Разница в том, что с
PostgreSQL 13 часть расширений помечена доверенными (`trusted`), и создавать их может
владелец базы, а не только суперпользователь. `pg_trgm` в этом списке, `pgcrypto` — нет.
**Как правильно:** перед тем как завести расширение миграцией, проверить
`SELECT name, trusted FROM pg_available_extensions`. Недоверенное по-прежнему ставится
руками и описывается в README, а не прячется в ревизию.
**Где:** миграция `saved filters and search indexes`.

## Индекс объявляется в модели вместе с классом операторов

**Что:** триграммные индексы описаны в `__table_args__` через
`postgresql_using="gin", postgresql_ops={"summary": "gin_trgm_ops"}`, а не только в
миграции.
**Почему важно:** `alembic check` сравнивает схему с метаданными. Индекс, созданный
миграцией и не объявленный в модели, попадает в вывод как «лишний» и тонет среди
известных ложных срабатываний по CHECK перечислений — а вместе с ним утонет и настоящее
расхождение.
**Как правильно:** любой индекс объявлять в модели; миграция повторяет объявление. После
ревизии прогнать `alembic check` и убедиться, что в выводе **только** снятие CHECK у
колонок-перечислений.
**Где:** `app/db/models/issue.py`, `app/db/models/comment.py`.

## Имя составного `UNIQUE` в миграции задаётся полностью

**Что:** соглашение об именах даёт `uq_%(table_name)s_%(column_0_N_name)s`, то есть
`uq_saved_filters_owner_id_name` для пары колонок, а не `uq_saved_filters_owner_id`.
**Почему важно:** `op.f()` объявляет имя окончательным, поэтому короткое имя молча
доедет до базы, и `alembic check` покажет разом «удалить старое ограничение, добавить
новое» — расхождение, которое легко принять за ложное срабатывание.
**Где:** миграция `saved filters and search indexes`; шаблоны — `app/db/base.py`,
`NAMING_CONVENTION`.

## `selectin` не работает у самоссылочной связи «многие к одному»

**Что:** `Portfolio.parent` (`parent_id` → `portfolios.id`) с `lazy="selectin"` **не
загружается**: атрибут остаётся ленивым, и первое обращение к нему падает
`MissingGreenlet` — уже вне async-контекста, при сборке ответа Pydantic.
**Почему важно:** сбой полностью молчаливый на загрузке — ни ошибки, ни
предупреждения ORM, объект выглядит нормальным. Проявляется только у строки, **у
которой родитель есть**: корневой портфель (`parent_id IS NULL`) отвечает исправно, и
тесты, читавшие только корень, были зелёными. Поймала это живая проверка.
**Как правильно:** `lazy="joined"` **вместе с** `join_depth`. Без `join_depth`
joined-загрузка к самоссылке не применяется вовсе — SQLAlchemy нечем ограничить
рекурсию, и она молча оставляет связь ленивой, то есть возвращает ту же ошибку.
`join_depth=1` грузит один уровень: `parent.key` безопасен, `parent.parent` — снова
ленивая загрузка. Подниматься по цепочке — запросом (`has_ancestor`), а не обходом
связей.
**Где:** `app/db/models/project.py`, `Portfolio.parent`; регрессия —
`tests/test_portfolios_api.py::test_a_nested_portfolio_reads_its_parent`.

## Имя новой ревизии надо сверять с именем предыдущей

**Что:** ревизия `20260828_1310_saved_filters_and_search_indexes` названа временем,
опережающим реальные часы примерно на сорок минут, поэтому следующая ревизия,
созданная честно, получила имя `20260828_1226_...` и встала в каталоге **выше** своей
предшественницы.
**Почему важно:** порядок наката от этого не страдает — его задаёт `down_revision`, — а
вот каталог версий перестаёт читаться сверху вниз, и следующий агент видит новую
ревизию раньше старой.
**Как правильно:** после `alembic revision --autogenerate` посмотреть `ls versions/` и,
если имя оказалось раньше предыдущей ревизии, переименовать файл (`git mv`), поставив
время на минуту позже неё. Переименование безопасно: Alembic находит ревизию по полю
`revision` внутри файла, а не по имени. Причину переименования писать в шапку ревизии.
**Где:** `app/db/migrations/versions/20260828_1311_projects_and_portfolios.py`, шапка.

## Двусторонняя связь добавляет объект в коллекцию сама

**Что:** `BoardColumn(board=board)` уже попадает в `board.columns` — `back_populates`
синхронизирует обе стороны в момент присваивания. Явный `board.columns.append(...)` после
этого даёт **вторую** ссылку на тот же объект.
**Почему важно:** проявляется не как дубль в списке, а как ложное срабатывание проверки,
которая по этому списку ходит: у колонок «разъехались» имена, у статусов — принадлежность
колонке. Искать причину приходится далеко от места ошибки.
**Как правильно:** создавать дочерние объекты **без** ссылки на родителя и присваивать
коллекцию целиком (`board.columns = [...]`) либо создавать со ссылкой и не добавлять руками.
Смешивать оба способа нельзя.
**Где:** `app/services/boards.py`, `_column_from_draft` и `create_board`.

## `INSERT ... SELECT` берёт питоновский `default` одним значением на всю вставку

**Что:** `postgresql.insert(Model).from_select([...])` подставляет `default=uuid.uuid4` как
**параметр** запроса — один и тот же UUID для всех вставляемых строк, и со второй строки
вставка падает нарушением первичного ключа.
**Почему важно:** у обычной вставки одного объекта того же дефекта нет, поэтому дефект
выглядит как «почему-то не работает именно массовая операция». Тестами ловится сразу,
глазами по коду — нет: в самом выражении `id` не упоминается вовсе.
**Как правильно:** перечислять `id` в списке колонок явно и считать его в SQL
(`func.gen_random_uuid()`), а не полагаться на питоновский дефолт. То же относится к любой
колонке с `default=` на стороне Python.
**Где:** `app/db/repositories/boards.py`, `BoardIssueRepository.rebalance`.

## Составной внешний ключ несовместим со вторым ключом по той же колонке

**Что:** у `board_column_statuses` колонка `board_id` входит в составной ключ на
`board_columns(id, board_id)` и **не** имеет отдельного ключа на `boards.id`.
**Почему важно:** второй ключ выглядел бы страховкой, но дал бы два пути к одному значению:
связь `BoardColumn.status_links` синхронизирует обе колонки составного ключа сама, и добавить
третий источник для `board_id` значило бы получить конфликт присваиваний. Целостность при
этом не страдает — `board_columns.board_id` сам ссылается на доску, а каскад приходит по
цепочке `boards → board_columns → board_column_statuses`.
**Как правильно:** у новой таблицы с составным ключом-границей не заводить второй ключ по
колонке области. Проверять глазами: `\d board_column_statuses` должен показать ровно два
внешних ключа.
**Где:** `app/db/models/board.py`, `BoardColumnStatus`.

## Связь у только что созданной строки задаётся объектом, а не внешним ключом

**Что:** `WebhookDelivery(subscription=subscription, ...)` вместо
`WebhookDelivery(subscription_id=subscription.id, ...)`.
**Почему важно:** с голым внешним ключом обращение к `delivery.subscription` у ещё не
перечитанной строки уходит в ленивую загрузку, а она вне greenlet падает
`MissingGreenlet`. `lazy="selectin"` от этого не спасает: он работает при загрузке
запросом, а не после `add()`.
**Как правильно:** если код (или тест) читает связь у только что созданного объекта —
задавать её объектом, SQLAlchemy заполнит и ключ, и связь. Правило общее, а не про одну
таблицу: та же ловушка ждёт любую новую модель со ссылкой.
**Где:** `app/services/webhooks.py`, `dispatch_event`.
