# База данных

## gen_random_uuid() встроен в PostgreSQL 13+

**Что:** для `server_default` первичного ключа расширение `pgcrypto` не нужно — функция
доступна из коробки.
**Почему важно:** миграция с `CREATE EXTENSION pgcrypto` требует прав суперпользователя и
ломается в управляемых базах, где их нет.
**Как правильно:** `server_default=text("gen_random_uuid()")` и никаких `CREATE EXTENSION`
в миграциях. Расширение вообще заводится только под явную нужду и с пониманием, что
установка, где прав нет, миграцию не накатит.
**Где:** `app/db/base.py`, `UUIDPrimaryKeyMixin`.

## Идентификатор считается в Python, а не в базе

**Что:** у `id` заданы оба значения по умолчанию: `default=uuid.uuid4` (Python) и
`server_default=text("gen_random_uuid()")` (PostgreSQL).
**Почему важно:** сценарию нужен id объекта до `flush` — чтобы в той же транзакции сослаться
на него из записи журнала изменений и события outbox. Если полагаться только на базу,
придётся делать лишний round-trip ради значения, которое можно знать заранее.
**Как правильно:** новая модель наследует `UUIDPrimaryKeyMixin` и получает оба умолчания
разом. Сценарию, которому нужен `id` до записи, достаточно создать объект — `flush` ради
идентификатора не нужен. Серверное умолчание при этом не лишнее: оно закрывает вставки
мимо ORM (миграции, ручной `INSERT`).
**Где:** `app/db/base.py`, `UUIDPrimaryKeyMixin`.

## Имена ограничений заданы соглашением, а не Alembic

**Что:** `MetaData(naming_convention=...)` фиксирует шаблоны имён для индексов, внешних
ключей и проверок.
**Почему важно:** без соглашения Alembic придумывает имена сам и по-разному для одинаковых по
смыслу ограничений. Откатить такую миграцию вслепую нельзя: имя, которое нужно удалить,
придётся искать в базе.
**Как правильно:** имя ограничения в миграции пишется через `op.f("...")` по шаблону из
`NAMING_CONVENTION`, а не придумывается. Проверить себя дёшево: `alembic check` после
правки покажет пару «удалить — добавить», если имя разошлось с соглашением.
**Где:** `app/db/base.py`, `NAMING_CONVENTION`.

## Автогенерация видит только импортированные модели

**Что:** `alembic revision --autogenerate` строит diff по `Base.metadata`, а метаданные
наполняются в момент импорта модуля с моделью.
**Почему важно:** модель, не импортированная в `app/db/models/__init__.py`, для автогенерации
не существует — миграция выйдет пустой, и это заметят через несколько задач.
**Как правильно:** каждая новая модель добавляется в `app/db/models/__init__.py`.
**Где:** `app/db/models/__init__.py`, `app/db/migrations/env.py`.

## Коммит делает граница запроса, а не сценарий

**Что:** транзакция фиксируется в `session_scope`: ветка `else` после `yield` коммитит,
`except` откатывает. `get_session` — тонкая обёртка (`async with session_scope() as session:
yield session`), собственной логики транзакции у неё нет.
**Почему важно:** `finally` здесь был бы ошибкой — он коммитил бы и после исключения. FastAPI
закрывает `yield`-зависимость через `__anext__` при успехе и через `athrow` при ошибке, поэтому
ветки `else` и `except` попадают ровно куда нужно.
**Как правильно:** менять поведение транзакции только в `session_scope`. Заводить вторую
реализацию границы (в зависимости, в репозитории, в декораторе сценария) нельзя: две копии
неизбежно разъедутся, и один и тот же сценарий начнёт вести себя из REST иначе, чем из воркера.
Явный `commit()` внутри сценария остаётся допустимым, когда нужна промежуточная фиксация.
**Где:** `app/db/session.py`, тесты — `tests/test_transactions.py`.

## Enum без `create_constraint=True` — это просто VARCHAR

**Что:** `sa.Enum(AuthorKind, native_enum=False)` не создаёт никакой проверки значений: с версии
SQLAlchemy 1.4 параметр `create_constraint` по умолчанию `False`.
**Почему важно:** ошибка молчаливая. Миграция проходит, `\d table` показывает колонку
`character varying(16)`, всё выглядит правильно — а записать в неё можно любую строку.
Обнаруживается это тогда, когда в колонке `type` уже лежит мусор.
**Как правильно:** заводить перечисления только через `string_enum` из `app/db/base.py` — там
флаг выставлен. После миграции проверять глазами: `\d participants` должен показать блок
`Check constraints` с именем вида `ck_participants_author_kind`.
**Где:** `app/db/base.py`, `string_enum`.

## Перечисления хранятся как VARCHAR, а не как тип PostgreSQL

**Что:** проект нигде не использует native enum PostgreSQL.
**Почему важно:** выглядит как упущение, поэтому: это решение, а не недосмотр. Native enum
расширяется через `ALTER TYPE ... ADD VALUE`, и добавленное значение нельзя использовать в той
же транзакции — миграция, которая заводит значение и тут же им пользуется, падает. Плюс каждый
такой тип надо создавать и удалять в миграции руками, иначе `downgrade` оставляет мусор.
**Как правильно:** `string_enum(AuthorKind, name="author_kind")`. Расширение набора значений — замена
одного ограничения CHECK.
**Где:** `app/db/base.py`, `string_enum`.

## `updated_at` после UPDATE требует `eager_defaults`

**Что:** обращение к `obj.updated_at` сразу после изменения объекта падает с
`MissingGreenlet: greenlet_spawn has not been called`.
**Почему важно:** значение вычисляет база (`onupdate=func.now()`), поэтому после flush
SQLAlchemy помечает атрибут протухшим и при первом же обращении лезет за ним в базу — уже вне
async-контекста. Ловушка коварна вдвойне: на INSERT всё работает (там RETURNING включён по
умолчанию), тесты сервиса объект целиком не сериализуют, и падает только живой PATCH-запрос
при сборке ответа Pydantic. Поймала это живая проверка, а не тесты.
**Как правильно:** `__mapper_args__ = {"eager_defaults": True}` — уже стоит в `BaseModel`,
поэтому новые модели наследуют его сами. Снимать нельзя.
**Где:** `app/db/base.py`, `BaseModel`.

## Курсорная пагинация сортирует по паре `(created_at, id)`

**Что:** второй элемент ключа — не украшение. Без него записи с одинаковым временем создания
проваливаются между страницами или дублируются.
**Почему важно:** `created_at` не уникален: массовая вставка в одной транзакции даёт всем
строкам одно `now()`. Курсор, хранящий только время, на такой границе теряет данные.
**Как правильно:** брать `paginate` из `app/db/pagination.py`, не писать свою пагинацию.
Запрашивается `limit + 1` запись — лишняя и есть признак следующей страницы, `COUNT(*)` не нужен.
**Где:** `app/db/pagination.py`.

## Время в именах ревизий закреплено за UTC

**Что:** в `alembic.ini` стоит `timezone = UTC`. Без этой строки Alembic берёт локальное время
той машины, где выполнялась команда.
**Почему важно:** контейнер живёт в UTC, разработчик — в своём поясе. Ревизия, сделанная мимо
контейнера, получает имя со сдвигом на часы, и файлы перестают сортироваться в порядке
применения: свежая миграция оказывается выше старой. Порядок наката от этого не страдает (его
задаёт `down_revision`), но читать каталог версий становится нельзя.
**Как правильно:** ничего не делать — конфиг уже закрывает вопрос, ревизии всегда получают имя
и заголовок `Create Date` в UTC с явным смещением `+00:00`. Проверить, что заголовок новой
ревизии оканчивается на `+00:00`: если смещения нет, команду запускали старой конфигурацией.
**Где:** `alembic.ini`, ключ `timezone`.

## Переименовать ревизию можно, переписать — нет

**Что:** Alembic находит ревизию по полю `revision` внутри файла, а не по имени файла. Строка
в таблице `alembic_version` ссылается на этот идентификатор.
**Почему важно:** запрет «не править применённую ревизию» относится к её содержимому —
изменённый `upgrade()` разведёт базы, где ревизия уже накатана, с теми, где ещё нет.
Переименование файла на это не влияет и базу не трогает: так была исправлена первая ревизия,
названная в чужом часовом поясе.
**Как правильно:** переименовывать — `git mv`, потом сверить `alembic history` и
`alembic current`. Менять `upgrade`/`downgrade` применённой ревизии — по-прежнему нельзя.
Тем же приёмом чинится и порядок в каталоге: если `--autogenerate` дал имя со временем
раньше предыдущей ревизии, файл переименовывают на минуту позже неё — накат от этого не
зависит (его задаёт `down_revision`), а каталог снова читается сверху вниз.
**Где:** `app/db/migrations/versions/`; шаблон имени — `alembic.ini`, `file_template`.

## Автогенерация Alembic сама дописывает удаление CHECK у перечислений

**Что:** `alembic revision --autogenerate` в каждой новой ревизии добавляет строку вида
`op.drop_constraint(op.f("ck_tasks_task_status"), "tasks", type_="check")` — и так для
любой уже существующей колонки-перечисления, к самой ревизии отношения не имеющей.
**Почему важно:** оставить строку — молча снять с колонки проверку допустимых значений.
Схема после этого выглядит правильной, а записать в колонку можно любую строку. Ошибка
всплывёт через несколько задач, когда в `status` окажется мусор.
**Как правильно:** удалять эту строку из сгенерированной ревизии руками и проверять глазами:
`\d tasks` должен показывать блок `Check constraints`. Причина в сравнении по имени:
ограничение, созданное `string_enum`, получает имя из соглашения об именах только при
компиляции DDL, и до этого момента для сравнения оно «безымянное», то есть отсутствующее.
**Где:** `app/db/migrations/versions/20260903_2100_participants_tokens_and_queues.py`, шапка файла.

## Номера задач выдаёт `UPDATE ... RETURNING`, а не последовательность

**Что:** `UPDATE projects SET last_task_number = last_task_number + 1 RETURNING` — один
запрос, инкремент считает база поверх текущего значения строки.
**Почему важно:** наивное «прочитать и записать +1» выдаёт двум параллельным запросам один
номер. `SEQUENCE` не блокирует, но оставляет дыры при любом откате и параллельной работе,
а ключи задач без дыр — требование задачи 03.
**Как правильно:** брать `ProjectRepository.allocate_task_number`, не писать свою выдачу.
Помнить про две особенности, обе намеренные: выдача сериализует создание задач в одном
проекте до конца транзакции, и откатившаяся транзакция свой номер теряет — дыра всё-таки
возможна, убрать её нельзя, не отказавшись от транзакционности.
**Где:** `app/db/repositories/projects.py`; тесты — `tests/test_project_numbering.py`.

## JSONB-колонку нельзя менять на месте

**Что:** `field.options.append(...)` не приводит к UPDATE: SQLAlchemy не отслеживает мутации
внутри значения JSONB и считает атрибут неизменённым.
**Почему важно:** сбой полностью молчаливый — код отработал, ошибки нет, изменения нет.
Проявится это при следующем чтении, уже в другом месте.
**Как правильно:** всегда присваивать колонке новый объект целиком
(`field.options = [...]`). Альтернатива — `MutableList.as_mutable(JSONB)`, но она добавляет
слежение за каждым элементом и в проекте не используется.
**Где:** `app/db/base.py`, `type_annotation_map`; колонки JSONB —
`app/db/models/entry.py`, `payload`.

## Ключ задачи выдаётся последним, после всех проверок

**Что:** `create_task` сначала проверяет поля задачи (`normalize_fields`) и только потом
берёт номер — `next_task_number`.
**Почему важно:** номер выдаётся атомарным `UPDATE ... RETURNING` и при откате
транзакции теряется — дыра в нумерации остаётся навсегда. Порядок «сначала номер, потом
проверки» означал бы дыру на каждом неудачном запросе, а неудачные запросы у агентов
обычное дело.
**Как правильно:** новую проверку в создании задачи ставить **до** выдачи ключа. Тест
`test_a_rejected_creation_does_not_burn_a_number` стережёт это.
**Где:** `app/services/tasks.py`, `create_task`; тест —
`tests/test_tasks_service.py`, `test_a_rejected_creation_does_not_burn_a_number`.

## `%` и `_` в пользовательском поиске экранируются вручную

**Что:** подстрока для `ILIKE` собирается с заменой `\`, `%` и `_` и с параметром
`escape="\\"`.
**Почему важно:** без этого исполнитель `100_percent` находился бы по запросу `100x` —
подчёркивание в `LIKE` означает «любой символ». Сбой молчаливый: подсказка отдаёт лишние совпадения, и
заметить это можно только на редком значении.
**Как правильно:** подстрока для `ILIKE` собирается одной функцией, которая экранирует
`\`, `%` и `_` и передаёт `escape="\\"`; сырое пользовательское значение в шаблон не
подставляется никогда. Проверяется тестом на значение со спецсимволом — на обычных словах
ошибка не видна.
**Где:** `app/db/sql.py`, `like_pattern` и `ilike_contains`; применение —
`app/db/repositories/search.py`.

## `None` в колонке JSONB — это значение `null`, а не SQL NULL

**Что:** `mapped_column(JSONB)` при питоновском `None` пишет в колонку **значение** JSON
`null`. Колонка перестаёт быть пустой: `IS NULL` её не найдёт, а `num_nonnulls` посчитает
заполненной.
**Почему важно:** сбой молчаливый ровно до первой проверки, которая на пустоту опирается.
Поймал его CHECK «ровно один источник» у сохранённого фильтра: строка с заполненным
`query` и «пустым» `structured_filter` не проходила, потому что для базы заполненными
были обе. Без такого ограничения ошибка дожила бы до первого `WHERE ... IS NULL` в другом
модуле и выглядела бы как потеря данных.
**Как правильно:** `JSONB(none_as_null=True)` у любой nullable-колонки JSONB. Колонке, где
`null` — законное значение (а не «значения нет»), флаг не нужен, но такой случай надо
называть комментарием: по типу его не отличить.
**Где:** `app/db/models/idempotency.py`, `response`.

## `pg_trgm` заводится миграцией, `pgcrypto` — нет

**Что:** `CREATE EXTENSION IF NOT EXISTS pg_trgm` стоит в миграции, хотя проект
сознательно избегал `CREATE EXTENSION pgcrypto`.
**Почему важно:** выглядит как нарушение собственного правила. Разница в том, что с
PostgreSQL 13 часть расширений помечена доверенными (`trusted`), и создавать их может
владелец базы, а не только суперпользователь. `pg_trgm` в этом списке, `pgcrypto` — нет.
**Как правильно:** перед тем как завести расширение миграцией, проверить
`SELECT name, trusted FROM pg_available_extensions`. Недоверенное по-прежнему ставится
руками и описывается в README, а не прячется в ревизию.
**Где:** `app/db/migrations/versions/20260904_0300_search_indexes.py`.

## Индекс объявляется в модели вместе с классом операторов

**Что:** триграммные индексы описаны в `__table_args__` через
`postgresql_using="gin", postgresql_ops={"summary": "gin_trgm_ops"}`, а не только в
миграции.
**Почему важно:** `alembic check` сравнивает схему с метаданными. Индекс, созданный
миграцией и не объявленный в модели, попадает в вывод как «лишний» и тонет среди
известных ложных срабатываний по CHECK перечислений — а вместе с ним утонет и настоящее
расхождение.
**Как правильно:** любой индекс объявлять в модели; миграция повторяет объявление. После
ревизии прогнать `alembic check` и убедиться, что в выводе **только** снятие CHECK у
колонок-перечислений.
**Где:** `app/db/models/task.py`, `ix_tasks_title_trgm`.

## Имя составного `UNIQUE` в миграции задаётся полностью

**Что:** соглашение об именах даёт `uq_%(table_name)s_%(column_0_N_name)s`, то есть
`uq_idempotency_keys_token_id_key` для пары колонок, а не `uq_idempotency_keys_token_id`.
**Почему важно:** `op.f()` объявляет имя окончательным, поэтому короткое имя молча
доедет до базы, и `alembic check` покажет разом «удалить старое ограничение, добавить
новое» — расхождение, которое легко принять за ложное срабатывание.
**Как правильно:** имя составного ограничения собирается по шаблону из всех колонок
(`uq_<таблица>_<колонка1>_<колонка2>`), а не по первой. Разошедшееся имя выглядит в
`alembic check` как пара «удалить — добавить» одного и того же ограничения: увидев такую
пару, сверять имя со шаблоном, а не списывать на шум.
**Где:** `app/db/models/idempotency.py`, `uq_idempotency_keys_token_id_key`;
шаблоны — `app/db/base.py`, `NAMING_CONVENTION`.

## Связь у только что созданной строки задаётся объектом, а не внешним ключом

**Что:** `Token(participant=participant, ...)` вместо
`Token(participant_id=participant.id, ...)`.
**Почему важно:** с голым внешним ключом обращение к `token.participant` у ещё не
перечитанной строки уходит в ленивую загрузку, а она вне greenlet падает
`MissingGreenlet`. `lazy="selectin"` от этого не спасает: он работает при загрузке
запросом, а не после `add()`.
**Как правильно:** если код (или тест) читает связь у только что созданного объекта —
задавать её объектом, SQLAlchemy заполнит и ключ, и связь. Правило общее, а не про одну
таблицу: та же ловушка ждёт любую новую модель со ссылкой.
**Где:** `app/services/tokens.py`, `issue_token` (комментарий у вызова);
`app/services/links.py`.

## Массовый `UPDATE` не обновляет загруженный объект, и правит это `set_committed_value`

**Что:** после `UPDATE projects SET last_task_number = last_task_number + 1 RETURNING` объект
`Project`, уже загруженный в сессию, держит **старое** значение: `synchronize_session=False`
ничего не синхронизирует, а `"fetch"` добавил бы лишний `SELECT`.
**Почему важно:** ответ, собранный из этого объекта в том же запросе, показал бы счётчик до
выдачи — молча. Обычное присваивание `project.last_task_number = number` чинит вид, но помечает
атрибут изменённым и добавляет второй `UPDATE` той же строки.
**Как правильно:** `sqlalchemy.orm.attributes.set_committed_value(project, "last_task_number",
number)` — правит именно загруженное состояние, не создавая грязного атрибута. Делать это в
репозитории, а не у вызывающего: забытая синхронизация не видна ни в одном тесте сценария.
**Где:** `app/db/repositories/projects.py`, `allocate_task_number`.

## Автор строки хранится двумя колонками, а не JSONB и не ссылкой

**Что:** у `participants`, `projects` и `tokens` есть пара `created_by_kind` /
`created_by_signature`, собранная примесью `CreatedByMixin`.
**Почему важно:** ссылка на участника здесь невозможна — у временного агента строки в реестре
нет, и внешний ключ обнулился бы ровно там, где подпись нужна больше всего. JSONB потребовал
бы своего индекса и своего синтаксиса ради двух строковых значений, по которым ищут («что
делал этот агент»).
**Как правильно:** новой таблице с автором брать `CreatedByMixin` и заполнять её через
`created_by_columns(actor.author)`, а не раскладывать структуру руками: разложенная по месту,
она однажды разложится наполовину, и запись окажется анонимной. Единственный законный `NULL`
в паре — подпись автора рода `tracker`, и инвариант держит конструктор `Author`.
**Где:** `app/db/models/author.py`.

## `alembic check` штатно ругается на CHECK каждого перечисления

**Что:** `alembic check` на сошедшейся схеме печатает `remove_constraint` по строке на
каждую колонку-перечисление: `ck_tasks_task_status`, `ck_tokens_token_scope`,
`ck_<таблица>_author_kind` и так далее. Это шум, а не расхождение.
**Почему важно:** список растёт с каждым новым перечислением и с каждой таблицей, где
перечисление используется, — перечислять его где-либо бессмысленно, он устареет к
следующей миграции. Правило проверки неизменно: если в выводе **только** снятие CHECK
у колонок-перечислений — модели и схема сошлись.
**Как правильно:** новое перечисление и каждая новая таблица с ним добавляют в вывод
ещё одну строку — дописывать её сюда не нужно, список ложных срабатываний определяется
правилом, а не перечислением. Смотреть на имя: `ck_<таблица>_<перечисление>` — шум.
Прогонять `alembic check` после каждой правки моделей, а не перед коммитом задачи: там,
где кроме снятия CHECK у перечислений пусто, расхождение видно в одну строку, а после
десятка правок разом — уже нет.
**Где:** `docker compose run --rm --entrypoint alembic api check`.

## Записи дела неизменяемы триггером, и уборка в тестах его выключает

**Что:** триггер `entries_immutable` отклоняет `UPDATE` и `DELETE` на `entries`
исключением базы (`P0001`, то есть пятисотка, а не `conflict`: это ошибка кода, а не
состояния). `TRUNCATE` он не ловит.
**Почему важно:** у репозитория нет методов правки, но «исправляющий» скрипт напишут
именно мимо репозитория. Побочное следствие — тест на закоммиченных строках не может
убрать за собой обычным `DELETE`.
**Как правильно:** в уборке такого теста — `ALTER TABLE entries DISABLE TRIGGER
entries_immutable`, удаление, `ENABLE TRIGGER`. Это единственное законное место, где
триггер выключается; в коде приложения его выключать нельзя.
**Где:** `app/db/migrations/versions/20260903_2300_tasks_and_entries.py`;
`tests/test_entry_numbering.py`.

## Номер записи в задаче выдаётся под блокировкой строки задачи, а не счётчиком

**Что:** `EntryRepository.allocate_no` делает `SELECT ... FOR UPDATE` по строке задачи и
считает `max(no) + 1`.
**Почему важно:** счётчик на задаче (как `last_task_number` у проекта) терял бы номер на
откате и оставлял дыру, а на номера записей ссылаются (`TRK-42#12`). Блокировка
сериализует записи в одну задачу до конца транзакции — для дела это и есть нужное
свойство. Цена: два запроса на запись.
**Как правильно:** `allocate_no` и `add` — два вызова, а не один с побочным эффектом.
Гонку стережёт `tests/test_entry_numbering.py`; проверять, что он умеет падать, — убрав
`with_for_update()`.
**Где:** `app/db/repositories/entries.py`.

## Записи одной транзакции упорядочены по `no`, а не по `created_at`

**Что:** `entries.created_at` ставит `now()` из общей примеси, и у записей одной
транзакции (правка двух разделов одним `PATCH`) оно совпадает.
**Почему важно:** старый журнал изменений переопределял примесь на `clock_timestamp()`
ради порядка. Здесь это не нужно: у записи есть `no` внутри задачи и `seq` по трекеру, и
все выборки сортируют по ним. Переопределять примесь — значит получить `updated_at`
раньше `created_at` у неизменяемой строки.
**Как правильно:** любая выборка записей сортируется по `no` (внутри задачи) или по
`seq` (по трекеру); `created_at` — для показа человеку, а не для порядка. Примесь со
временем не переопределяется: `clock_timestamp()` ради сортировки чинит одно и ломает
инвариант `created_at <= updated_at`.
**Где:** `app/db/models/entry.py`; `app/db/repositories/entries.py`, `list_page`.

## Версию задачи ведёт `version_id_col`, а не сценарий

**Что:** у `Task` в `__mapper_args__` стоит `version_id_col`: SQLAlchemy сам добавляет
`WHERE version = :seen` в каждый `UPDATE` и поднимает версию на единицу; расхождение —
`StaleDataError`, который сценарий переводит в `version_conflict`.
**Почему важно:** сравнение `expected_version` в Python ловит устаревший запрос клиента,
но не гонку между чтением объекта и записью. Присваивать `task.version += 1` руками
теперь нельзя: получится двойной инкремент.
**Как правильно:** массовые `UPDATE` по задачам мимо ORM обязаны поднимать версию сами и
знать, что оптимистичную блокировку они обходят.
**Где:** `app/db/models/task.py`; `app/services/tasks.py`, `_flush_checking_version`.

## Индекс по выражению объявляется в модели тем же текстом, что в миграции

**Что:** порядок задач по ключу опирается на `split_part(key, '-', 2)::bigint`, и индекс
под него объявлен и в `__table_args__` модели (`Index(..., text("(split_part(key, '-', 2)::bigint)"))`),
и в ревизии — одинаковым текстом.
**Почему важно:** `alembic check` сравнивает схему с метаданными. Индекс, созданный
миграцией и не объявленный в модели, попадает в вывод как «лишний» и тонет среди
известных ложных срабатываний по CHECK перечислений — а вместе с ним утонет и настоящее
расхождение. Расхождение текстов даёт то же самое.
**Как правильно:** выражение под индексом обязано быть `IMMUTABLE`; `split_part` и
приведение к `bigint` таковы, `now()` и приведение к `timestamptz` — нет, и на них
`CREATE INDEX` откажет.
**Где:** `app/db/models/task.py`; `app/db/migrations/versions/20260904_0300_search_indexes.py`.

## `now()` одинаков для всей транзакции, и это ломает тесты порядка по времени

**Что:** `updated_at` ставит база через `func.now()`, то есть время **начала транзакции**.
Весь тест идёт в одной транзакции, поэтому две задачи, изменённые «по очереди», получают
одинаковое `updated_at`.
**Почему важно:** тест сортировки по времени обновления при этом проходит через раз:
порядок решает тайбрейкер по случайному `id`. Выглядит как плавающий баг сортировки, а
не как свойство фикстуры.
**Как правильно:** в тесте, которому нужны различающиеся отметки, править `updated_at`
запросом (`update(...).values(updated_at=text("now() + interval '1 hour'"))`), а не
настоящей правкой задачи. `statement_timestamp()` в проекте не используется намеренно:
время создания и правки обязано быть одинаковым у всего, что случилось в одной транзакции.
**Где:** `app/db/base.py`, `TimestampsMixin`; `tests/test_search_service.py`.

## Уникальный индекс — это механизм идемпотентности, а не проверка на всякий случай

**Что:** ограничение `uq_idempotency_keys_token_id_key` служит не защитой от «лишних
строк», а самим способом развести одновременные повторы: второй `INSERT` **ждёт** на
индексе конца первой транзакции и дальше либо падает нарушением (первая
зафиксировалась — ответ уже есть), либо вставляется сам (первая откатилась — работу надо
сделать).
**Почему важно:** очевидная альтернатива — «поискать ключ и вставить, если не нашли» —
зелёная в тестах на общей сессии и дырявая в бою: десять параллельных запросов проходят
такую проверку одновременно, создают десять объектов, и девять из них получают `409` на
коммите.
**Как правильно:** вставку заворачивать в `session.begin_nested()` и разбирать
`IntegrityError` как рабочий исход. Без точки сохранения упавший `flush` делает
непригодной всю транзакцию, и перечитать занятую строку в ней уже нечем.
**Где:** `app/services/idempotency.py`, `run_once`;
`app/db/migrations/versions/20260904_0500_idempotency_keys.py`.

## Ключ идемпотентности и созданный объект обязаны жить в одной транзакции

**Что:** строка ключа вставляется до работы, ответ дописывается в неё после, коммит —
общий с созданным объектом.
**Почему важно:** отсюда сразу два нужных свойства. Чужой запрос никогда не видит
занятый ключ без ответа: до коммита строки не существует ни для кого. И откат
освобождает ключ вместе с объектом: неудачный вызов не оставляет ключ, повтор по
которому отвечал бы несуществующим результатом. Промежуточный коммит внутри сценария
ломает оба свойства разом — поэтому у `run_once` это записанное требование к `build`.
**Как правильно:** `build`, передаваемый в `run_once`, не коммитит и не открывает свою
транзакцию — он только собирает объект в текущей сессии. Понадобился коммит внутри —
значит, сценарий не идемпотентен, и чинится это разбиением сценария, а не вторым
коммитом.
**Где:** `app/services/idempotency.py`.

## Попутная уборка вместо фонового процесса стоит индекса по `created_at`

**Что:** устаревшие ключи снимает `DELETE ... WHERE created_at < ...`, который выполняется
при записи каждого нового ключа.
**Почему важно:** фоновых процессов в трекере нет по решению концепции, а ключ, который
никто не удалит, хранил бы секрет выпущенного токена вечно. Без индекса по `created_at`
эта уборка превратилась бы в полный проход по таблице на каждом создающем запросе.
**Как правильно:** уборка идёт внутри той же точки сохранения, что и вставка ключа:
при занятом ключе откатывается всё вместе, и уборка не пропадает — её сделает следующая
запись.
**Где:** `app/db/repositories/idempotency.py`, `delete_expired`.

## Очередь изменений: одна блокировка на весь мутирующий сценарий

**Что:** консультативная блокировка `pg_advisory_xact_lock` (`app/db/locks.py`,
`lock_changes`) берётся **первым делом** в каждом сценарии, меняющем состояние: переход,
правка, создание задачи, постановка и снятие связи, подшивка записи. Раньше её брала
только подшивка — то есть конец сценария.
**Почему важно:** проверки перехода читают чужие строки (блокеры, дети, вердикты), а
`version` переводимой задачи их появление не двигает. Без общей очереди чередование
«A прочитала факты — B зафиксировала связь — A зафиксировала переход» проходит целиком,
и получается закрытый родитель с открытым ребёнком или `in_progress` поверх открытого
блокера. Обе транзакции при этом по отдельности правы, и разобрать это по данным нечем.
**Как правильно:** новый мутирующий сценарий начинается с `lock_changes`. Порядок
захвата единый и обязательный: сначала очередь, потом строки (`allocate_no`,
`allocate_task_number`); обратный даёт взаимную блокировку. Блокировок это не добавляет —
сценарий и так держал очередь до конца транзакции, менялся только момент захвата. Цена
прежняя: изменения по установке идут по одному.
**Где:** `app/db/locks.py`; `app/services/tasks.py`, `app/services/links.py`,
`app/services/case.py` (`_append`).

## Блокировка не помогает объекту, прочитанному до неё

**Что:** `lock_changes` перечитывает переданные ей задачи (`session.refresh`) — потому
что роутер и инструмент MCP читают их **до** вызова сценария, разрешая ключи в объекты.
**Почему важно:** карта объектов сессии отдаёт такой объект как есть, и проверка «связи
закрытой задачи не меняются» решала бы по статусу, прочитанному до очереди: блокировка
взята, а решение принято по устаревшему снимку. Читаемые запросом факты этим не болеют —
`READ COMMITTED` даёт каждому новому `SELECT` свежие данные.
**Как правильно:** перечитывать только в начале сценария, до собственных правок: `refresh`
молча снимает с объекта незаписанные изменения. Признак, посчитанный из объекта (статус,
версия), под очередью надо перечитать; признак, посчитанный запросом, — нет.
**Где:** `app/db/locks.py`, `lock_changes`.

## Перевод `IntegrityError` живёт на границе транзакции, а не в обработчике HTTP

**Что:** `transaction` (`app/db/session.py`) переводит нарушение целостности в
`conflict` и на исключении тела, и на коммите. Обработчик `handle_integrity_error` в
`app/api/errors.py` остался страховкой на то, что случилось мимо этой границы.
**Почему важно:** интерфейсов три. Пока перевод стоял в обработчике HTTP, MCP отдавал
агенту безличное «Error executing tool» без причины, а команда `app.cli` — трассировку
SQLAlchemy: у них своего обработчика нет и не будет. Создающие сценарии при этом опираются
на уникальность в базе как на **механизм** развязки гонки, а не на перестраховку, — то
есть этот отказ штатный, а не авария.
**Как правильно:** тестовая подмена сессии обязана брать ту же `transaction`, а не
повторять её у себя: копия зелёная всегда, в том числе на сломанном переводе.
**Где:** `app/db/session.py`, `transaction`; `tests/test_integrity_conflicts.py`.

## Из JSONB берут ключи выражением, а не выбирают колонку целиком

**Что:** `payload` записи `section_changed` держит прежнее и новое значение раздела
целиком — до `MAX_TEXT_LENGTH` символов каждое. Выбрать колонку и отбросить лишнее в
Python значит прочитать из базы всё то же самое: экономия видна в ответе, но не в
запросе.
**Почему важно:** опись дела входит в каждый пакет задачи. Задача с пятью правлеными
разделами превратила бы дешёвое чтение в мегабайты, и заметно это стало бы не в тестах,
а на живой установке через месяц работы.
**Как правильно:** резать в SQL. Набор ключей зависит от типа записи, поэтому
`CASE ... WHEN type = ... THEN jsonb_build_object('field', payload->'field')`: одно
выражение, один запрос, читаются только короткие значения. Ключи `before`/`after` есть
и у длинных, и у коротких записей — брать их безусловно нельзя, только внутри ветви
своего типа.
**Где:** `app/db/repositories/entries.py`, `_facts_json`.

## Миграции во временной схеме: `search_path` впереди и таблица версии названа схемой

**Что:** приём архива установки строит схему ревизии архива миграциями Alembic во
временной схеме `casefile_import` внутри своей транзакции: `SET LOCAL search_path TO
casefile_import, public` и `version_table_schema=casefile_import`, соединение — готовое,
через `config.attributes["connection"]` (`env.py`).
**Почему важно:** миграции пишут неквалифицированные имена, и первым в пути должна стоять
временная схема — иначе `CREATE TABLE` и `DROP INDEX` уйдут в `public` установки. Убрать
`public` из пути нельзя: там живёт `pg_trgm` с `gin_trgm_ops`, без него индекс поиска не
создаётся. А без явной схемы таблицы версии Alembic находит по пути
`public.alembic_version`, решает, что временная схема уже на head, и не делает ничего —
молча. Опасное следствие того же пути: `DROP ... IF EXISTS` объекта, которого во
временной схеме нет, найдёт одноимённый в `public`. Миграции идут от нуля по порядку,
поэтому всё, что они сносят, во временной схеме к этому моменту есть, — но миграция,
сносящая «на всякий случай», в этом месте стала бы разрушительной.
**Как правильно:** новая миграция сносит только то, что создала цепочка до неё, и не
квалифицирует имена схемой `public`. Конфиг Alembic в процессе — без `alembic.ini`
(`Config()`): ini настраивает логирование и переписал бы его работающему API.
**Где:** `app/db/archive.py` (`build_scratch`, `_upgrade`); `app/db/migrations/env.py`.

## Строки архива: `col::text` на выгрузке и текстовый `COPY` на приёме

**Что:** значения архива — текст, который даёт `col::text` (в UTC: `SET LOCAL TimeZone`),
а принимает их `COPY ... FROM STDIN` в текстовом формате через asyncpg
(`copy_to_table`). Пара вывод/ввод одного типа возвращает значение без потерь, и
приложению не нужно знать типы колонок ни на одной ревизии.
**Почему важно:** три места, где это ломается молча или громко. `copy_to_table` с
`source=bytes` принимает байты за **путь к файлу** (`OSError: File name too long`) —
нужен `io.BytesIO`. `COPY` пишет присланные значения в колонку идентичности `seq` мимо
счётчика: без `setval` следующая запись дела получает уже занятый номер — во временной
схеме это строка, которую подшивает миграция (`drop review status`), в `public` — первая
запись после приёма. И `INSERT ... SELECT` в `public` из временной схемы требует
`OVERRIDING SYSTEM VALUE` из-за той же `GENERATED ALWAYS`.
**Как правильно:** после `COPY` — `restart_identities` для схемы; экранировать в строке
`COPY` ровно `\`, табуляцию, перевод строки и возврат каретки (`copy_text`).
**Где:** `app/db/archive.py` (`copy_rows`, `restart_identities`,
`replace_public_from_scratch`); `app/domain/archive.py` (`copy_text`).

## Приём архива заменяет строки `public`, а не пересоздаёт таблицы

**Что:** строки временной схемы, доведённой до head, переносятся в `public` через
`TRUNCATE` всех таблиц данных и `INSERT ... SELECT`; таблицы не удаляются и не
создаются заново, сессия приёма после замены выбрасывает свои объекты (`expunge_all`).
**Почему важно:** соседний процесс (`mcp`) держит подготовленные запросы asyncpg,
привязанные к OID таблиц; пересозданная таблица дала бы ему протухший кеш на первом же
запросе. `TRUNCATE` не задевает триггер неизменяемости записей дела: он на `UPDATE`
и `DELETE` строк. Отметка использования токена запроса, не сброшенная до замены,
упала бы на коммите `StaleDataError`.
**Как правильно:** `flush` сессии до замены и `expunge_all` после неё; новые таблицы
принимаются без правки кода — их набор берётся из каталога базы, а не из списка.
**Где:** `app/db/archive.py`, `replace_public_from_scratch`; `app/services/archive.py`,
`import_installation`.

## Признак одного действия у записи — Python-значение, а не `pg_current_xact_id()`

**Что:** `entries.action_id` (TRK-118) ставит `uuid.uuid4()`, сгенерированный в
Python на входе вызова (`app/services/case.py`, `_append`), а не настоящий номер
транзакции PostgreSQL.
**Почему важно:** соблазн очевиден — все записи одного вызова и правда лежат в одной
транзакции, и `pg_current_xact_id()`/`txid_current()` дались бы бесплатно, без единой
правки сигнатур. Но тесты сервисного слоя (`tests/test_tasks_service.py` и соседние)
ведут вызовы на одной и той же сессии внутри одной внешней транзакции теста, открытой
`SAVEPOINT`ами (`join_transaction_mode="create_savepoint"`, см. заметку «`now()`
одинаков для всей транзакции» выше): два подряд идущих `update_task` в таком тесте
делят один настоящий номер транзакции PostgreSQL, хотя это два разных действия.
Признак, основанный на `pg_current_xact_id()`, был бы неотличим у них — то самое
смешение «одна транзакция БД = одно действие», от которого и уходит задача (вывод
UI-133#5 о том, что совпадение `created_at` — деталь реализации, а не контракт).
**Как правильно:** генерировать значение в Python и передавать явно вниз по цепочке
вызовов пакетных сценариев (`apply_task_changes`, `close_task`, `_record_on_both_sides`
в `app/services/links.py`), а не спрашивать его у базы или у сессии. Значение не
зависит от того, сколько вызовов делят одну сессию или одну реальную транзакцию —
только от того, сколько раз вызывающий код решил сгенерировать новое.
**Где:** `app/db/models/entry.py`, раздел «`action_id`»; `app/services/case.py`,
`_append`.

## Переименование таблицы — ревизией без схемы в именах, иначе архив старой версии не доедет

**Что:** ревизия `3b8e6d2f9a41` (TRK-152) переименовывает `queues` в `projects`, колонку
`tasks.queue_id` в `project_id` и шесть выведенных из них имён ограничений и индексов
(`pk_`, `uq_`, `ck_…_author_kind`, `fk_`, два `ix_`) — `ALTER … RENAME` без имени схемы.
**Почему важно:** приём архива переноса (`app/services/archive.py`) строит временную
схему на ревизии архива и доводит её до head обычными миграциями, поставив её первой в
`search_path`. Архив v0.3 несёт `queues`, и до `projects` его строки доводит именно эта
ревизия. Имя `public.queues` в миграции переименовало бы не ту схему, и приём упал бы на
сверке `public == scratch`. Отдельного сопоставления «старое имя → новое» в сервисе
приёма поэтому нет: формат различает поле `schema_revision`.
**Как правильно:** следующее переименование таблицы или колонки — тоже ревизией с
неквалифицированными именами. Имена, которые соглашение `NAMING_CONVENTION`
выводит из таблицы и колонки, переименовываются вместе с ними: иначе `alembic check`
и сверка схем в приёме увидят расхождение с моделями. Архив каждой прошлой версии
проверяется тестом, который собирает архив её ревизии с её именами
(`tests/test_archive.py`, `archive_at`).
**Где:** `app/db/migrations/versions/20260924_2100_queues_become_projects.py`;
`tests/test_migrations.py`, `tests/test_archive.py`.

## Дело проекта живёт в той же таблице записей: владелец — `task_id` или `project_id`

**Что:** у записи ровно один владелец — задача или проект; `entries.task_id` допускает
`NULL`, рядом `entries.project_id`, а «ровно один» держит `ck_entries_one_owner`
(`num_nonnulls(task_id, project_id) = 1`). Номер `no` уникален внутри владельца: две
уникальности `(task_id, no)` и `(project_id, no)`; `NULL` в них различны, и записи одного
владельца чужую не задевают (TRK-156).
**Почему важно:** отдельная таблица записей проекта дала бы вторую `IDENTITY` и второй `seq` —
второй журнал, который концепция запрещает (`CONCEPT.md`, 4.1), и правило слияния двух хвостов
в один курсор ленты. Общая таблица отдаёт делу проекта ленту, оповещение, триггер
`entries_immutable`, проверку типов и перенос архивом бесплатно. Обратная сторона: всё, что
читает `entries` с `JOIN tasks`, теперь теряет записи проекта молча — внутренним соединением
их не видно.
**Как правильно:** выборка поперёк записей, где владелец может быть проектом (лента), —
внешние соединения с `tasks` и `projects` (`EntryRepository.journal_page`). Выборки по
вопросам, замечаниям и признакам задач остаются внутренними: таких записей у проекта нет.
Номер записи проекта выдаёт `allocate_project_no` под блокировкой строки проекта, после
очереди изменений — тот же порядок захвата. Откат ревизии `5c1d8e7a2b90` отказывает на
`SET NOT NULL`, пока в деле какого-то проекта есть записи: удалить их нельзя, записи
неизменяемы. Уборка тестов, удаляющих проект, заведённый сценарием, сначала снимает его
записи (у заведённого проекта есть `created`), иначе держит внешний ключ.
**Где:** `app/db/models/entry.py`; `app/db/migrations/versions/20260924_2300_project_case.py`;
`app/db/repositories/entries.py`, `allocate_project_no`, `journal_page`;
`tests/test_migrations.py`, `test_the_project_case_rollback_refuses_while_project_entries_exist`.

## Заведение проекта берёт очередь изменений подшивкой `created`, а не первым делом

**Что:** `create_project` не зовёт `lock_changes` в начале: очередь берёт `_append`, когда
подшивает `created`, то есть уже после вставки строки проекта. Остальные мутирующие сценарии
берут её первым делом (заметка «Очередь изменений: одна блокировка на весь мутирующий
сценарий»).
**Почему важно:** фактов, которые надо читать под очередью, у заведения нет — занятость ключа
решает уникальный индекс. Очередь, взятая первой, сериализовала бы две одновременные попытки до
проверки `get_by_key`: гонка, которую стережёт `tests/test_integrity_conflicts.py` (барьер после
чтения ключа, проигравший получает `conflict` через перевод `IntegrityError`), зависала бы
навсегда — один ждёт барьер под очередью, второй ждёт очередь. Так и случилось на первом прогоне
TRK-156.
**Как правильно:** сценарию без фактов под блокировкой очередь нужна только для порядка `seq`,
и её обеспечивает подшивка. `update_project` читает «было» для `field_changed` и поэтому
берёт очередь первым делом и перечитывает проект под ней.
**Где:** `app/services/projects.py`, `create_project`, `update_project`;
`tests/test_integrity_conflicts.py`, `test_two_parallel_create_project_calls_leave_mcp_a_domain_error`.
