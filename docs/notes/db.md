# База данных

## gen_random_uuid() встроен в PostgreSQL 13+

**Что:** для `server_default` первичного ключа расширение `pgcrypto` не нужно — функция
доступна из коробки.
**Почему важно:** миграция с `CREATE EXTENSION pgcrypto` требует прав суперпользователя и
ломается в управляемых базах, где их нет.
**Где:** `app/db/base.py`, `UUIDPrimaryKeyMixin`.

## Идентификатор считается в Python, а не в базе

**Что:** у `id` заданы оба значения по умолчанию: `default=uuid.uuid4` (Python) и
`server_default=text("gen_random_uuid()")` (PostgreSQL).
**Почему важно:** сценарию нужен id объекта до `flush` — чтобы в той же транзакции сослаться
на него из записи журнала изменений и события outbox. Если полагаться только на базу,
придётся делать лишний round-trip ради значения, которое можно знать заранее.
**Где:** `app/db/base.py`, `UUIDPrimaryKeyMixin`.

## Имена ограничений заданы соглашением, а не Alembic

**Что:** `MetaData(naming_convention=...)` фиксирует шаблоны имён для индексов, внешних
ключей и проверок.
**Почему важно:** без соглашения Alembic придумывает имена сам и по-разному для одинаковых по
смыслу ограничений. Откатить такую миграцию вслепую нельзя: имя, которое нужно удалить,
придётся искать в базе.
**Где:** `app/db/base.py`, `NAMING_CONVENTION`.

## Автогенерация видит только импортированные модели

**Что:** `alembic revision --autogenerate` строит diff по `Base.metadata`, а метаданные
наполняются в момент импорта модуля с моделью.
**Почему важно:** модель, не импортированная в `app/db/models/__init__.py`, для автогенерации
не существует — миграция выйдет пустой, и это заметят через несколько задач.
**Как правильно:** каждая новая модель добавляется в `app/db/models/__init__.py`.
**Где:** `app/db/models/__init__.py`, `app/db/migrations/env.py`.

## Коммит делает граница запроса, а не сценарий

**Что:** транзакция фиксируется в `session_scope`: ветка `else` после `yield` коммитит,
`except` откатывает. `get_session` — тонкая обёртка (`async with session_scope() as session:
yield session`), собственной логики транзакции у неё нет.
**Почему важно:** `finally` здесь был бы ошибкой — он коммитил бы и после исключения. FastAPI
закрывает `yield`-зависимость через `__anext__` при успехе и через `athrow` при ошибке, поэтому
ветки `else` и `except` попадают ровно куда нужно.
**Как правильно:** менять поведение транзакции только в `session_scope`. Заводить вторую
реализацию границы (в зависимости, в репозитории, в декораторе сценария) нельзя: две копии
неизбежно разъедутся, и один и тот же сценарий начнёт вести себя из REST иначе, чем из воркера.
Явный `commit()` внутри сценария остаётся допустимым, когда нужна промежуточная фиксация.
**Где:** `app/db/session.py`, тесты — `tests/test_transactions.py`.

## Enum без `create_constraint=True` — это просто VARCHAR

**Что:** `sa.Enum(MyEnum, native_enum=False)` не создаёт никакой проверки значений: с версии
SQLAlchemy 1.4 параметр `create_constraint` по умолчанию `False`.
**Почему важно:** ошибка молчаливая. Миграция проходит, `\d table` показывает колонку
`character varying(16)`, всё выглядит правильно — а записать в неё можно любую строку.
Обнаруживается это тогда, когда в колонке `type` уже лежит мусор.
**Как правильно:** заводить перечисления только через `string_enum` из `app/db/base.py` — там
флаг выставлен. После миграции проверять глазами: `\d actors` должен показать блок
`Check constraints` с именем вида `ck_actors_actor_type`.
**Где:** `app/db/base.py`, `string_enum`.

## Перечисления хранятся как VARCHAR, а не как тип PostgreSQL

**Что:** проект нигде не использует native enum PostgreSQL.
**Почему важно:** выглядит как упущение, поэтому: это решение, а не недосмотр. Native enum
расширяется через `ALTER TYPE ... ADD VALUE`, и добавленное значение нельзя использовать в той
же транзакции — миграция, которая заводит значение и тут же им пользуется, падает. Плюс каждый
такой тип надо создавать и удалять в миграции руками, иначе `downgrade` оставляет мусор.
**Как правильно:** `string_enum(MyEnum, name="my_enum")`. Расширение набора значений — замена
одного ограничения CHECK.
**Где:** `app/db/base.py`, `string_enum`.

## `updated_at` после UPDATE требует `eager_defaults`

**Что:** обращение к `obj.updated_at` сразу после изменения объекта падает с
`MissingGreenlet: greenlet_spawn has not been called`.
**Почему важно:** значение вычисляет база (`onupdate=func.now()`), поэтому после flush
SQLAlchemy помечает атрибут протухшим и при первом же обращении лезет за ним в базу — уже вне
async-контекста. Ловушка коварна вдвойне: на INSERT всё работает (там RETURNING включён по
умолчанию), тесты сервиса объект целиком не сериализуют, и падает только живой PATCH-запрос
при сборке ответа Pydantic. Поймала это живая проверка, а не тесты.
**Как правильно:** `__mapper_args__ = {"eager_defaults": True}` — уже стоит в `BaseModel`,
поэтому новые модели наследуют его сами. Снимать нельзя.
**Где:** `app/db/base.py`, `BaseModel`.

## Курсорная пагинация сортирует по паре `(created_at, id)`

**Что:** второй элемент ключа — не украшение. Без него записи с одинаковым временем создания
проваливаются между страницами или дублируются.
**Почему важно:** `created_at` не уникален: массовая вставка в одной транзакции даёт всем
строкам одно `now()`. Курсор, хранящий только время, на такой границе теряет данные.
**Как правильно:** брать `paginate` из `app/db/pagination.py`, не писать свою пагинацию.
Запрашивается `limit + 1` запись — лишняя и есть признак следующей страницы, `COUNT(*)` не нужен.
**Где:** `app/db/pagination.py`.
