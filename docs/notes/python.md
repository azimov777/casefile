# Python и библиотеки

## pydantic-settings разбирает списки как JSON до валидаторов

**Что:** поле `list[str]`, заданное переменной окружения через запятую, роняет запуск:
`SettingsError: error parsing value for field "cors_origins"`. Валидатор с `mode="before"`
не спасает — источник настроек пытается разобрать значение как JSON раньше него.
**Почему важно:** симптом выглядит как ошибка валидации, хотя валидация даже не началась.
**Как правильно:** пометить поле `Annotated[list[str], NoDecode]` и разбирать строку самому
в `field_validator(mode="before")`. Либо всегда писать в окружении JSON-массив.
**Где:** `app/core/config.py`, поле `cors_origins`.

## RUF001 работает сторожем языка сообщений

**Что:** `RUF001` ругается на кириллицу в строковых литералах, `RUF002` — в докстрингах,
`RUF003` — в комментариях. В проекте отключены только два последних.
**Почему важно:** сообщения об ошибках, описания схем и логи обязаны быть английскими, а
докстринги и комментарии — русские. `RUF001` разделяет эти два мира автоматически: русский
текст, случайно попавший в сообщение об ошибке, не пройдёт линтер.
**Как правильно:** не добавлять `RUF001` в `ignore`, чтобы обойти находку, — переводить строку.
Остальную группу `RUF` тоже не отключать: `RUF012` ловит реальные ошибки.
**Где:** `pyproject.toml`, `[tool.ruff.lint]`.

## Атрибуты SQLAlchemy объявляются через ClassVar

**Что:** `type_annotation_map = {...}` в наследнике `DeclarativeBase` даёт `RUF012`.
**Почему важно:** очевидное «решение» — навесить `noqa`; правильное — аннотация
`ClassVar[dict[Any, Any]]`, которую декларативный слой SQLAlchemy пропускает при разборе
модели и не пытается превратить в колонку.
**Как правильно:** служебный атрибут в наследнике `DeclarativeBase` объявляется как
`ClassVar[...]`. `noqa` здесь не просто хуже стилистически: без `ClassVar` декларативный
слой разбирает аннотацию как объявление колонки, и ошибка приходит из SQLAlchemy, а не от
линтера.
**Где:** `app/db/base.py`, класс `Base`.

## RUF001 срабатывает на односложных кириллических словах

**Что:** `"В работе"` и `"На ревью"` не проходят линтер: `В` неотличима от латинской `B`,
`На` — от `Ha`. Слова из одной-двух букв не дают правилу контекста, по которому определяется
алфавит; `"Открыт"` и `"Задача"` проходят свободно.
**Почему важно:** правило стережёт английский в служебных строках и отключать его нельзя, но
пользовательские названия статусов и типов по соглашениям пишутся по-русски — и упираются
ровно в этот случай.
**Как правильно:** точечный `# noqa: RUF001` на конкретной строке с объяснением, почему
перевод здесь неуместен. В тестах проще подобрать название без односложных слов.
**Где:** `pyproject.toml`, `[tool.ruff.lint.per-file-ignores]`: русский пользовательский
текст живёт в `app/services/demo.py`, и правило снято на весь файл целиком.

## RUF001 срабатывает на `\n` перед кириллическим словом

**Что:** литерал `"Первая строка\nвторая строка"` не проходит линтер, хотя обе половины
целиком кириллические.
**Почему важно:** находка выглядит бессмысленной, и первый порыв — навесить `noqa` на
ровном месте. Правило читает исходник, а не значение строки: символ `n` из escape-
последовательности приклеивается к следующему слову, получается `nвторая` — смесь
латиницы с кириллицей, ровно то, что правило и ловит.
**Как правильно:** собрать строку из частей (`"\n".join([...])`) либо поставить после
`\n` пробел. `noqa` здесь не нужен — неоднозначности в самих данных нет.
**Где:** `tests/test_domain_case.py`, `"Первая строка\nи вторая"`.

## `except A, B:` без скобок — это не опечатка, а синтаксис Python 3.14

**Что:** `ruff format` приводит `except (ValueError, TypeError):` к `except ValueError,
TypeError:` — без скобок.
**Почему важно:** выглядит как синтаксис Python 2 и как ошибка форматтера, и первый порыв —
вернуть скобки руками. Следующий прогон форматтера снимет их снова, а на Python до 3.14 такой
файл действительно не разбирается.
**Как правильно:** так и оставлять. PEP 758 разрешил перечисление исключений без скобок в
3.14, а `target-version = "py314"` в `pyproject.toml` включает эту нормализацию. Проверять
подозрительное место `python -c "import ast; ast.parse(open(path).read())"`, а не глазами.
**Где:** `pyproject.toml`, `target-version = "py314"`. Живого примера в коде нет:
скобки снимаются только у `except` без `as`, а все многоклассовые `except` проекта
связывают исключение (`app/db/pagination.py`).

## Границы в шаблоне, выхватывающем имя из текста, — не украшение

**Что:** шаблон упоминания требовал границы с обеих сторон: `(?<![0-9A-Za-z_@])` слева и
`(?![0-9A-Za-z_])` справа.
**Почему важно:** без левой границы `alice@bob` даёт упоминание `bob` — адрес почты
превращается в адресата. Без правой `@aliceX` даёт упоминание `alice`: регулярное выражение
съедает допустимую часть ключа, и реплика молча адресуется не тому актору. Оба случая
проявляются как «уведомление пришло не тем», то есть далеко от места ошибки.
**Как правильно:** шаблон, выхватывающий имя из свободного текста, пишется с границами
с обеих сторон и проверяется тестом на «почти совпадения»: `alice@bob`, `@aliceX`,
`@@alice`. Ошибка здесь проявляется как «уведомление пришло не тому» — за десять шагов от
регулярного выражения.
**Где:** живого шаблона в коде нет — обсуждение с упоминаниями снесено задачей 20. Ближайший
родственник, `app/domain/query_language.py` (`_WORD_START_RE`, `_WORD_BODY_RE`), ту же задачу
решает разбором посимвольно, а не выражением поверх всего текста.
