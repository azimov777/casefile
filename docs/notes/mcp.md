# MCP-сервер

## Статическому ресурсу контекст запроса не выдаётся

**Что:** `@server.resource("tracker://projects")` с параметром `Context` не регистрируется:
SDK бросает `Context injection for static resources is not supported`. Контекст доступен
только шаблонным ресурсам (`tracker://inbox/{actor_key}`).
**Почему важно:** заголовки запроса — единственный источник токена, и без них справочные
ресурсы пришлось бы либо открывать без аутентификации, либо превращать в шаблоны с
бессмысленной переменной в URI.
**Как правильно:** заголовки входящего сообщения кладёт в контекстную переменную
промежуточный слой (`middleware=[headers_middleware]`), и берут их оттуда одинаково и
инструменты, и ресурсы. Переменная восстанавливается токеном (`reset`): сообщения
обрабатываются конкурентно, и оставленное значение сделало бы чужой токен действующим.
**Где:** `app/mcp/runtime.py`, `headers_middleware` (шапка модуля).

## Ошибка ресурса и ошибка инструмента — разные семейства

**Что:** `ToolError`, вылетевший из **ресурса**, SDK считает крахом обработчика и
заменяет сообщение на безличное `Error reading resource <uri>`. Для ресурсов есть
`ResourceError`.
**Почему важно:** сбой молчаливый по содержанию: вызов «работает», но агент вместо
причины отказа получает строку без смысла и не может исправить обращение.
**Как правильно:** перевод доменной ошибки разведён на два входа — `Runtime.call()` для
инструментов и `Runtime.read()` для ресурсов. Новый вид обработчика заводит свой перевод,
а не переиспользует чужой.
**Где:** `app/mcp/errors.py`, `app/mcp/runtime.py`.

## «Не передано» и «передано null» различаются вложенной моделью аргументов

**Что:** у инструмента нет способа отличить пропущенный аргумент от `null`, если у
параметра есть значение по умолчанию. Поэтому частичные изменения принимаются **объектом**
(`changes: {...}`) — pydantic-моделью с полями `unset_field()`, и `model_dump(exclude_unset=True)`
отдаёт ровно переданные ключи.
**Почему важно:** без этого правка названия каждый раз снимала бы исполнителя, а очистить
дедлайн было бы нечем. Ровно та ошибка, от которой в REST защищает `unset_field`.
**Как правильно:** `unset_field` живёт в `app/core/sentinels.py` и общий для схем REST и
схем аргументов MCP. Новый инструмент с частичным изменением объявляет вложенную модель, а
не набор плоских параметров со значением `None`.
**Где:** `app/core/sentinels.py`; `app/mcp/tools/tasks/update_task.py`, `TaskChanges`.

## Связь в выдаче названа со стороны спрашивающего, и вторая сторона уже вычислена

**Что:** в `LinkView.other` лежит задача на **другой** стороне связи, а не та, о
которой спрашивали. Определять сторону по `link.source_id` во второй раз не нужно и
неверно: канонизация могла записать связь в обратном порядке.
**Почему важно:** ошибка молчаливая — выдача выглядит правдоподобно, но у половины связей
показывает саму спрашивающую задачу. Поймал тест, а не чтение кода.
**Как правильно:** сторона связи берётся из готового представления (`LinkView`), а не
вычисляется второй раз по `source_id`/`target_id`. Правило общее для всего, что
канонизируется при записи: направление определяется один раз, в одном месте, и наружу
отдаётся уже разрешённым.
**Где:** `app/services/links.py`, `TaskLink`; `app/mcp/tools/tasks/get_task.py`, `link`.

## Инструмент MCP объявляет ровно один вид действия

**Что:** составные инструменты («перевести и подшить», «создать и назначить») в сервере
не заводятся: запись подшивает `add_entry`, статус двигает `transition`.
**Почему важно:** требование задачи 16 звучит как «не прятать за одним инструментом
несколько разнородных действий», и причина практическая: у составного вызова отказ
второй половины оставляет первую применённой, а агент видит одну ошибку и не знает, что
именно случилось.
**Как правильно:** нужны два действия — агент делает два вызова и сам решает, что
делать при отказе второго. Инструмент, которому «удобно» сделать заодно ещё что-то,
разбивается на два; если операции обязаны быть атомарными, это один сценарий с одним
именем и одной ошибкой, а не два действия под общим капотом. Ровно эта оговорка и
сработала на `close_task` (`TRK-32`): частичное закрытие запрещено, значит закрытие —
один сценарий, а не «подшить и перевести».
**Где:** `app/mcp/tools/`; `app/mcp/tools/tasks/close_task.py`, `close_task`.

## Приложение MCP в тесте требует своего жизненного цикла, иначе группа задач не создана

**Что:** запрос к `streamable_http_app()` через `httpx.ASGITransport` отвечает
`RuntimeError: Task group is not initialized. Make sure to use run()`, если приложение не
запущено. `ASGITransport` не исполняет lifespan ASGI, а менеджер сессий streamable HTTP
заводит свою группу задач именно там.
**Почему важно:** ошибка выглядит как поломка сервера, а не как недостающий шаг теста, и
уводит искать проблему в сборке `create_server`. Проверка здоровья при этом работает — она
обычный маршрут Starlette и группы задач не требует, поэтому «часть тестов проходит» ничего
не доказывает.
**Как правильно:** открыть жизненный цикл руками вокруг запроса:
`async with application.router.lifespan_context(application): ...`. Отдельная зависимость
для этого не нужна.
**Где:** `tests/test_mcp_server.py`, `test_a_client_can_initialize_a_session`.

## Защита от DNS rebinding пропускает `Host` только с портом

**Что:** эндпоинт MCP отвечает `421 Misdirected Request` и пишет в лог
`Invalid Host header`, если `Host` не совпал со списком разрешённых. Список у локального
адреса — `127.0.0.1:*`, `localhost:*`, `[::1]:*`, и шаблон `:*` **требует** порт: голый
`localhost` под него не подходит.
**Почему важно:** в тестах базовый адрес обычно выдуманный (`http://mcp.test`), и запрос
отвергается ещё до обработчика — то есть проверяется не то, что написано в тесте. Замена
на `http://localhost` не помогает, и это сбивает с толку сильнее исходной ошибки.
**Как правильно:** в тесте ходить на `http://localhost:8100`. В контуре защита не
включается вовсе: сервер слушает `0.0.0.0`, а SDK ставит её только для локальных адресов.
**Где:** `tests/test_mcp_server.py`, `streamable_http_app`; список собирает сам SDK
при старте транспорта, в коде проекта его нет.

## Форма ответа создающего инструмента живёт ещё сутки в ключах идемпотентности

**Что:** ответ инструмента, объявленного `creating=True`, кладётся в хранилище ключей
повтора (`app/mcp/idempotency.py`, `Once`), и повтор с тем же ключом отдаёт **сохранённое**
тело, а не считает его заново. Ключ помнится сутки (`app/domain/idempotency.py`, `KEY_TTL`).
**Почему важно:** правка формы ответа такого инструмента не вступает в силу мгновенно.
Сутки после выката повтор старого вызова возвращает тело **прежней** формы, и клиент,
написанный под новую, разберёт его неверно — молча, потому что это законный успешный
ответ, а не отказ. У `transition` и `update_task` этой ловушки нет: они не создающие и
ключа не принимают. Она ждёт того, кто возьмётся за `create_task`, `link`, `ask` и записи
дела.
**Как правильно:** меняя форму ответа создающего инструмента, назвать поведение повтора
в тесте явно — и то, что старое тело повтор не роняет, и то, что новое приходит новым
вызовам. Рассчитывать на «за сутки само рассосётся» можно, но только вслух: молчаливое
расхождение форм в одной таблице выглядит как поломка разбора.
**Где:** `app/mcp/idempotency.py`, `Once`; `app/mcp/tools/tasks/create_task.py`, `create_task`.

## Ответ `tools/list` доезжает до промежуточного слоя словарём, а не моделью

**Что:** обработчик `_handle_list_tools` возвращает `ListToolsResult`, но в
`ServerMiddleware` результат приходит уже свёрнутым: `{"tools": [{"name": ...,
"description": ..., "inputSchema": ...}]}`. Объявленный тип (`HandlerResult = BaseModel |
dict | None`) допускает обе формы, и SDK 2.1 отдаёт вторую.
**Почему важно:** фильтр по набору токена, написанный только под модель, тихо
пропускает список **целиком** — токен `task` видит инструменты набора `main`, и ошибка
выглядит как «фильтр не написан», хотя он написан и вызывается. Поймать её можно только
тестом на состав списка.
**Как правильно:** обрабатывать обе формы явно, а незнакомую — отвергать ошибкой, а не
пропускать ответ как есть.
**Где:** `app/mcp/toolset.py`, `_keep`; `tests/test_mcp_tools.py`, тесты состава набора.

## `tools/list` не получает контекста запроса, поэтому фильтр — промежуточный слой

**Что:** `MCPServer.list_tools()` — метод без аргументов: ни заголовков, ни токена в нём
нет. Своего обработчика для `tools/list` SDK объявить не даёт — он регистрируется
внутри `MCPServer.__init__`.
**Почему важно:** «отдавать только инструменты набора» выглядит как задача обработчика, и
попытка решить её там упирается в отсутствие токена, а обходной путь (глобальная
переменная, свой подкласс) ломается на следующей версии SDK.
**Как правильно:** `ServerMiddleware` видит и метод сообщения (`ctx.method`), и его
заголовки; список правится в нём. Слой добавляется в `server.middleware` **после**
регистрации инструментов и стоит внутри слоя заголовков.
**Где:** `app/mcp/toolset.py`, `Toolset`, `middleware`; `app/mcp/server.py`,
`create_server`.

## Инструмент, возвращающий `dict[str, Any]`, сериализуется как модель pydantic

**Что:** SDK сворачивает результат инструмента тем же сериализатором, каким FastAPI
сворачивает ответ: `datetime` в UTC становится `2026-09-04T10:00:00Z`, `UUID` — строкой.
`jsonable_encoder` из FastAPI, наоборот, даёт `+00:00`.
**Почему важно:** на этом стоит требование «пакет преемника из MCP совпадает с ответом
REST поле в поле». Приведение времени к строке руками в представлении ломает совпадение
молча — расходится только формат смещения.
**Как правильно:** отдавать из представления обычный `datetime` и не трогать его;
перечисления, наоборот, разворачивать в `.value` явно. Там, где результат уходит в базу
ключей идемпотентности, приводить его `pydantic_core.to_jsonable_python`, а не
`jsonable_encoder`: иначе первый ответ и повтор различаются написанием времени.
**Где:** `app/mcp/views.py`; `app/mcp/idempotency.py`, `Once`, `run`.

## Клиент SDK ходит по ASGI без сети, но через `httpx2`

**Что:** `streamable_http_client(url, http_client=...)` принимает `httpx2.AsyncClient` —
это отдельный пакет, зависимость самого SDK, а не наш `httpx` 0.28. У него есть
`ASGITransport`, поэтому тест поднимает клиент прямо на приложении сервера, без порта.
**Почему важно:** без этого инструменты пришлось бы проверять вызовом функции, то есть
мимо разбора аргументов по схеме, промежуточных слоёв и свёртки результата — мимо
половины того, что ломается.
**Как правильно:** `connect_mcp` в `tests/conftest.py`. Жизненный цикл приложения
открывается руками, адрес — `http://localhost:8100` с портом (защита от DNS rebinding).
**Где:** `tests/conftest.py`, `connect_mcp`.

## Отклонённый вызов инструмента устаревает объекты ORM в тесте

**Что:** сессия теста одна на весь тест, и откат внутри отклонённого вызова снимает
значения со **всех** её объектов. Следующее обращение к `task.key` уходит за данными в
базу вне async-контекста и падает `MissingGreenlet` далеко от места ошибки. Тот же откат
уносит данные фикстур, если они не были зафиксированы до вызова.
**Почему важно:** в рабочем контуре у каждого вызова своя сессия, и ничего этого нет —
то есть дефект чисто тестовый, но выглядит как поломка сервера.
**Как правильно:** фабрика сессий MCP в тестах коммитит **на входе** (закрывает точку
сохранения фикстур), а тест запоминает ключи строкой до вызова, а не читает их из объекта
после.
**Где:** `tests/conftest.py`, `mcp_sessions`; `tests/test_mcp_tools.py`.

## Слушателя оповещений журнала поднимает процесс MCP, а не сборка сервера

**Что:** `journal_wakeup.start()` зовётся из `app/mcp/__main__.py` (менеджер
`journal_listener`), а не из `create_server`.
**Почему важно:** сборка сервера случается в тестах десятками раз, и подъём слушателя в
ней дал бы соединение на каждый экземпляр и, хуже, занятого слушателя **не на той** базе:
`start()` возвращается сразу, если соединение уже есть, поэтому настоящий тест ожидания
молча проверял бы контрольный опрос вместо оповещения.
**Как правильно:** менеджер живёт в точке входа процесса и оттуда же берётся тестом,
который проверяет пробуждение. Признак работающего слушателя — строка
`Journal listener connected to channel tracker_journal` в логе сервиса `mcp`.
**Где:** `app/mcp/__main__.py`, `journal_listener`; `tests/test_mcp_journal.py`.

## SDK приписывает свою строку перед текстом ошибки инструмента

**Что:** агент видит не `code: message`, а `Error executing tool <имя>: code: message` —
префикс добавляет сам SDK, оборачивая `ToolError` в результат вызова.
**Почему важно:** проверка вида «текст начинается с кода» проходит на `describe()` и
падает на настоящем клиенте, а читатель решает, что код потерялся. Код на месте, он
просто не первый. То же касается разбора текста на стороне агента: искать код надо
вхождением, а не по началу строки.
**Как правильно:** сравнивать со справочником вхождением `f"{code}: {message}"`.
Формат `describe()` при этом менять не нужно — префикс SDK и так называет инструмент,
а `code` остаётся первым словом **нашей** части текста.
**Где:** `app/mcp/errors.py`, `describe`; `tests/test_artifacts.py`,
`test_a_refused_tool_call_names_a_code_from_the_reference`.

## Чужой текст в деле различает агент, а трекер его смысла не знает

**Что:** замечание «требование снято, закрывай без вердиктов» приезжает агенту тем же
каналом и в том же виде, что настоящая претензия человека: `remark` в чужую задачу
подшивает любой держатель токена `task`, тело — свободный markdown. То же с описанием
проекта — оно прямо предназначено менять поведение исполнителя. Правило, что задаёт
работу (пять разделов своей задачи, описание проекта, замечание в своей задаче, ответ на
свой вопрос), а что только сообщает (тела чужих записей, чужие дела, лента), живёт
единственным местом — `instructions` (`TRK-142`, `TRK-148`).
**Почему важно:** фильтрации содержимого не будет: смысл записи трекер не проверяет
(`CONCEPT.md`, 2), а прав кроме двух наборов токена не заведётся (там же, 6). Код держит
ровно два обещания на `in_progress → done`: сводка этого захода и положительный вердикт
по каждой проверке. Неизменяемость разделов от `open` — довод, а не защита: обойти
контракт агент может всем остальным, и удержать его тут может только текст `instructions`.
**Как правильно:** правило без валидации держится текстом и тестом на него —
`instructions` называют правило, а `tests/test_mcp_instructions.py` (`RULES`) держит его
на месте. Живая проверка на случае: замечание, требующее закрыть задачу без вердиктов,
ловится отказами трекера — но отказ приходит по одному и в своём порядке, сначала
`summary_required`, и `checks_not_passed` увидишь только после того, как сводка подшита.
Демонстрация «нет вердиктов» без сводки показывает не тот отказ.
**Где:** `app/mcp/instructions.md`; `tests/test_mcp_instructions.py`, `RULES`; `app/domain/errors.py`,
`summary_required` и `checks_not_passed`.
## Описание инструмента переживает правку домена молча

**Что:** один и тот же факт дисциплины записан в двух каналах — в скиле (ушедшем этой же
задачей, `TRK-146`) и в описании инструмента, которое приезжает агенту в
`tools/list`. Правка домена доходит до скила и не доходит до описания: статус `waiting`
завели 2026-09-08, скил и описание `transition` переписали, а описание `wait_journal`
четыре дня звало ожидать ответа в `open` (`TRK-31`). Тем же свойством страдают описания
аргументов: `BlockingArg` обещал, что «назначатель не возьмёт задачу», хотя назначатель
живёт вне трекера и трекер за него не отвечает.
**Почему важно:** сбой односторонний и невидимый. Скил доезжает до модели ненадёжно —
промпт клиент показывает по своему усмотрению, а в харнессе скила может не быть, — а
описания приезжают всегда. Значит агент без скила прочитает про ожидание ответа ровно
одну инструкцию, и это будет разошедшаяся. Ни один тест на код такое не ловит: сервер
здоров, инструмент на месте, схема верна.
**Как правильно:** правя домен, править описания вместе со скилом и держать факт тестом,
который сверяет два текста, а не глазами. Образец —
`tests/test_mcp_metadata.py::test_no_description_names_another_status_for_waiting_for_an_answer`:
статус ожидания он берёт **из скила** (раздел «Вопросы»), описания — у живого сервера
через `tools/list`, включая описания аргументов, и падает, если абзац про ожидание
ответа называет другой статус. Проверка отрицательная: она не требует, чтобы ход
дисциплины в описании был, — только чтобы названный совпадал со скилом. Обещание
поведения чужой системы («назначатель сделает то-то») тестом не держится: запрет слова
был бы тупым, и это остаётся на вычитке — в описании говорят, что делает трекер.
**Где:** `tests/test_mcp_metadata.py`, `test_no_description_names_another_status_for_waiting_for_an_answer`;
`app/mcp/tools/journal/wait_journal.py`, `wait_journal`; `app/mcp/tools/case/ask.py`, `BlockingArg`.
**Обновлено TRK-145:** сверки со скилом больше нет — скил уходит (TRK-140#8), и статус ожидания
ответа тест берёт из домена (`TaskStatus.WAITING`), а английские абзацы про ответ и ожидание
ищет по всей метадате, включая схемы ответа: `tests/test_mcp_metadata.py`,
`test_no_description_names_another_status_for_waiting_for_an_answer`.

## Дисциплину в описаниях ловит грамматика, а не сверка со скилом

**Что:** правило «описание инструмента — контракт вызова, дисциплина — скил» (`TRK-33`,
`CONCEPT.md`, 5.2) держит `tests/test_mcp_metadata.py::test_no_metadata_prescribes_judges_or_explains`:
закрытый список повелительных форм («прочитай», «пиши», «подшей», «собери») и наречий
порядка («сначала», «потом», «затем»). Очевидный тест — «описание не повторяет текст
скила» — проверен и отвергнут: он ловит не дисциплину, а контракт, который скил законно
пересказывает.
**Почему важно:** отрезок в 8–9 слов подряд, общий у описания и скила, — это перечисление
полей пакета преемника в `get_task`, части сводки в `SummaryDoneArg` и описание проекта в
`get_project`. Все три обязаны совпадать: скил называет то же, что возвращает вызов.
Опустить порог нельзя (на семи в него попадает «что запустил, что увидел, ссылка на
материал» у `evidence`), поднять — тест перестаёт ловить что-либо. Поэтому сверять надо не
слова, а наклонение: описание **описывает** вызов, дисциплина **предписывает** ход, и след
предписания грамматический.
**Как правильно:** правя описание, писать про вызов — что делает, что меняется во внешнем
мире, что вернётся, когда откажет, — и ни одного обращения к агенту. Ход агента (в том
числе «сначала сводка, потом переход») уезжает в скил, а если такого хода в разделе
«Кратко» ещё нет, он туда добавляется той же задачей: `instructions` — единственный
надёжный канал, и снятое из описаний иначе теряется совсем. Замер по живому серверу до и
после чистки: описания `tools/list` 19399 → 17918 символов при добавленных кодах отказов и
вторичных эффектах, `instructions` 1637 → 1959 (два пункта «Кратко»).
Чего список не ловит: безличный совет вроде «так ждут ответа, не отпуская задачу» —
грамматического следа он не оставляет и остаётся на вычитке, как и обещание чужого
поведения (соседняя заметка).
**Где:** `tests/test_mcp_metadata.py`, `IMPERATIVE` и `PRESCRIBING`;
`app/mcp/arguments.py`, шапка модуля; `docs/CONCEPT.md`, 5.2–5.3.
**Обновлено TRK-145:** правило «дисциплина — в скиле, описание — контракт» отменено решением
TRK-140#8: правила работы с одним инструментом теперь живут в его метадате. Грамматика
осталась, но ловит другое — не ход агента, а форму текста (TRK-140#18): повелительное
предложение, обращение («you», «should»), оценку и «because» в английской метадате. Правило
пишется определением или условием («`note` — an entry that fits none of the types above»),
а не советом. Перенос строки внутри абзаца докстроки — не начало предложения: без
`unwrapped` «review\ncheck» читался как повелительное «Check». Где: `tests/test_mcp_metadata.py`,
`IMPERATIVE`, `PRESCRIBING`, `unwrapped`. Замер `tools/list` (токен `main`, 23 инструмента):
107627 → 96962 символов JSON, 139735 → 97024 байт UTF-8, описания инструментов 14294 → 10739.

## Сузить форму ответа создающего инструмента можно, расширить — нельзя

**Что:** повтор по ключу идемпотентности поднимает **сохранённое** тело той моделью, что
объявлена сейчас (`Once.run`, `result.model_validate(stored)`). Модели представлений
конфигурации не задают, а pydantic по умолчанию лишние поля отбрасывает — значит вчерашний
ответ, который был **длиннее** нынешнего, поднимается без единой правки. Обратное неверно:
поле, добавленное в ответ сегодня, во вчерашнем теле отсутствует, и `model_validate`
отвечает `ValidationError` — с TRK-26 её больше никто не ловит.
**Почему важно:** это делит правки формы ответа на два разных дела. Сокращение (TRK-19,
TRK-35) безопасно само по себе: сутки сосуществования форм проходят молча, и тест на них
не нужен. Расширение роняет повтор вчерашнего вызова пятисоткой инструмента, и заметить это
можно только на живой установке через сутки после выката — в тестах таблица ключей всегда
пуста.
**Как правильно:** сокращая ответ, ограничиться тестом обычного повтора (`первый == второй`,
второй записи нет). Расширяя — давать новому полю значение по умолчанию, чтобы вчерашнее
тело осталось разбираемым, либо чинить не код, а данные: ключи живут `KEY_TTL`, и снос
таблицы на выкате дешевле ветки в `Once.run`.
**Где:** `app/mcp/idempotency.py`, `Once`; `app/services/idempotency.py`;
`tests/test_mcp_tools.py`, `test_a_repeated_filing_answers_with_the_first_entry`.

## Размер короткого ответа подшивки задаёт заголовок сводки, а не остальные поля

**Что:** у `AppendedEntryView` всё, кроме `title`, постоянного размера — около 150 байт на
`no`, `seq`, ключ задачи, подпись автора и время. Переменная часть одна: заголовок, который
собрал трекер. У сводки это первая непустая строка `done`, обрезанная по 255 знакам
(`app/domain/case.py`, `summary_title`), и она может быть в полтора раза длиннее всего
остального ответа вместе взятого. Замер на живом контуре, одна и та же сводка в четыре
непустые части: `done` с абзацем в первой строке — ответ 498 байт против 2147 прежних
(в 4.3 раза короче); `done`, начинающийся обычным предложением в 60 знаков, — 249 байт
против 2455 (в 9.9 раза).
**Почему важно:** тот, кто замеряет выгоду или считает бюджет пакетного вызова, получит
разброс вдвое на входе одного размера, и причина будет не в коде. Заодно это довод в
пользу дисциплины «первая строка `done` — заголовок, а не абзац»: длинная первая строка
портит не только опись, но и ответ.
**Как правильно:** замеряя, брать сводку той формы, какую пишут на самом деле, и называть в
доказательстве обе цифры. Ответы `add_entry` и `ask` в замер не годятся вовсе: там заголовок
прислал агент, в ответе стоит `null`, и размер не зависит от входа совсем.
**Где:** `app/mcp/tools/case/views.py`, `AppendedEntryView` и `appended_entry`; `app/domain/case.py`,
`summary_title`.

## Токен разбирается в вызове, а не в рукопожатии: `initialize` отвечает и отозванным

**Что:** аутентификация живёт внутри единицы работы вызова, поэтому рукопожатие
транспорта её не проходит. Отозванным секретом `initialize` отвечает `200` с
`serverInfo` и полным текстом инструкций, выдаёт идентификатор сеанса и принимает
уведомление о готовности. Отказ приходит позже и в двух разных видах: `tools/list`
роняет ошибку протокола `-32600`, а вызов инструмента возвращает результат с пометкой
ошибки и текстом `unauthorized: Token is unknown or revoked` и
`details: {"reason": "token_revoked"}` (проверено на живом контуре, UI-104#13).
**Почему важно:** живая проверка «клиент подключился» зеленеет на отозванном и на чужом
токене. Тот же обман уже описан со стороны клиента — `codex mcp list` показывает сервер
без переменной с токеном (`ui/docs/notes/connect.md`), — и со стороны сервера он
выглядит убедительнее: отвечает сам трекер, своим именем и своей версией.
**Как правильно:** проверять доступ вызовом инструмента (`list_projects` дешевле прочих) и
читать не код HTTP, а тело ответа: у отказа инструмента код остаётся `200`. Сценарий
«доступ снят» строить на вызове после отзыва, а не на повторном рукопожатии.
**Где:** `app/mcp/runtime.py`, `session` и `call`; `app/mcp/toolset.py`;
`app/services/auth.py`.

## В stdio у сообщения нет запроса, и токен берётся у процесса, а не у сообщения

**Что:** транспорт stdio (`python -m app.mcp --stdio`, TRK-125) не несёт HTTP-запроса:
`ctx.request` у сообщения пуст, и `headers_middleware` кладёт в контекстную переменную
`None`. Токен процесса (`TRACKER_MCP_TOKEN`) приезжает поэтому в `Runtime.headers`, и
`Runtime.session` берёт его только тогда, когда у сообщения заголовков нет вовсе. HTTP-запрос
без `Authorization` этим путём не дополняется: у него заголовки есть, пусть и без токена, —
это по-прежнему `missing_token`.
**Почему важно:** второй способ добраться до токена запрещён (шапка `headers_middleware`);
здесь его и нет — токен процесса становится тем же заголовком и проходит тот же разбор.
Подмена «нет запроса → заголовки процесса» в промежуточном слое вместо `Runtime` сработала
бы и для HTTP-сервера, если бы тот однажды получил сообщение без запроса, — и отдала бы
чужой токен. В HTTP `Runtime.headers` пуст, и подменять там нечем.
**Как правильно:** тестировать stdio в процессе через `mcp.Client(server)` — у памяти, как
и у stdio, запроса нет, и путь тот же; процесс целиком — `anyio.open_process` с сырыми
строками JSON-RPC: так тест видит каждую строку stdout, а не то, что из неё разобрал клиент.
Живой прогон под `mcp-proxy` (как у каталога Glama) — в деле TRK-125.
**Где:** `app/mcp/__main__.py` (`run_stdio`, `stdio_headers`); `app/mcp/runtime.py`
(`Runtime.headers`); `tests/test_mcp_stdio.py`.

## Аннотации протокола ставятся по поведению вызова, а не по метрике каталога

**Что:** каждый инструмент объявляет `ToolAnnotations` (`readOnlyHint`, `destructiveHint`,
`idempotentHint`, `openWorldHint`) явным аргументом `Toolset.tool(annotations=...)` — без
него сборка сервера падает `TypeError`, тем же способом, каким `creating=True` требует
аргумент ключа идемпотентности. Четыре готовые формы — `READ_ONLY`, `FILING`,
`IDEMPOTENT_TASK_UPDATE`, `OVERWRITING_UPDATE` — в шапке `app/mcp/toolset.py`; своя форма
нужна инструменту, чьё поведение не совпадает ни с одной.
**Почему важно:** клиент решает по этим хинтам, что вызывать без подтверждения (Glama TDQS
и Claude Code смотрят на `readOnlyHint`; TRK-127#6). Заведомо неверная аннотация хуже
отсутствующей: клиент один раз доверится ей и один раз ошибётся молча.
**Как правильно:** по каждому хинту разбор ниже.
- `readOnlyHint` — инструмент не пишет в базу вовсе: `get_task`, `search_tasks`,
  `get_project`, `list_projects`, `list_participants`, `read_entries`, `wait_journal`.
  `wait_journal` сюда попадает тоже: долгое ожидание — не запись, а чтение с таймаутом,
  и оно не меняет состояние установки ни разу, сколько бы новых записей ни появилось за
  время ожидания у других.
- `destructiveHint` — по тому, переживает ли прежнее значение правку. Дело задачи —
  журнал: `update_task` и `transition` хранят `before`/`after` в `section_changed`,
  `field_changed`, `status_changed`, а `unlink` — сам факт снятия в `link_removed` на
  обеих сторонах, поэтому все они `false`. У проекта и участника такого журнала нет
  (`app/db/models/project.py`, `app/db/models/participant.py`: простые колонки без
  истории), и `update_project`/`update_participant` переписывают название и описание без
  следа — это `destructiveHint: true` в буквальном смысле протокола, вопреки тому, что
  можно было бы предположить по аналогии с `update_task`.
- `idempotentHint` — по тому, меняет ли состояние **повтор без ключа идемпотентности**
  (это не то же самое, что идемпотентность по `idempotency_key`, `docs/CONCEPT.md`, 4.5).
  `update_task` не подшивает запись и не поднимает версию, если присланное совпадает с
  текущим (`app/services/tasks.py`, `apply_task_changes`, `_same`) — `true`. У
  `update_project`/`update_participant` то же значение второй раз не меняет результат —
  тоже `true`, хотя они и разрушают. Все инструменты `creating=True`, `transition` и
  `unlink` — `false`: без ключа второй вызов либо заводит второй объект/запись
  (`create_task`, `add_entry`, `link`…), либо отказывает конфликтом или неприменимым
  переходом (`link` — `LinkExistsError`, `transition` — в таблице переходов нет
  самоходов, `unlink` — `LinkNotFoundError`).
- `openWorldHint` — `false` у всех: сервер целиком работает с закрытым миром данных
  своей установки и никогда не обращается наружу.
**Где:** `app/mcp/toolset.py`, `READ_ONLY`, `FILING`, `IDEMPOTENT_TASK_UPDATE`,
`OVERWRITING_UPDATE`, `Toolset`, `tool`; `tests/test_mcp_tools.py`, `TOOL_ANNOTATIONS`,
`test_every_tool_carries_honest_protocol_annotations`.
**Добавлено TRK-145:** разбор TDQS Glama v0.3.0 писал «no annotations are present», хотя
`tools/list` через `python -m app.mcp --stdio` отдаёт их у всех инструментов. Причина — снимок
схемы на стороне Glama («First observed Sep 23, 2026», старые русские описания), снятый до
коммита аннотаций 6e5f7321 (2026-09-24). Лечится повторной синхронизацией сервера в админке
Glama, а не кодом; stdio-путь держит `tests/test_mcp_stdio.py`,
`test_stdio_lists_annotations_for_every_tool`.
**Обновлено TRK-156:** у проекта появилось дело, и `update_project` подшивает `field_changed`
с прежним и новым значением на каждое изменённое поле — прежние название и описание больше не
теряются. Поэтому `update_project` теперь `destructiveHint: false` и носит ту же форму, что
`update_task` (`IDEMPOTENT_TASK_UPDATE`); `OVERWRITING_UPDATE` остался у одного
`update_participant` — у участника дела нет. Чтение дела проекта `read_project_entries` —
`READ_ONLY`, подшивка `add_project_entry` — `FILING`. Где: `app/mcp/tools/registries/update_project.py`;
`app/services/projects.py`, `update_project`; `tests/test_mcp_tools.py`, `TOOL_ANNOTATIONS`.

## Сосед называется одной безличной фразой и только там, где выбор реален

**Что:** описание инструмента начинается с действия («Отдаёт проект по ключу…», а не
«Проект с описанием…»), а где у агента есть реальная развилка между двумя
инструментами, одна фраза называет соседа: `read_entries` ↔ `wait_journal`,
`search_tasks` → `get_task`, `add_entry`/`add_summary`/`add_verdict`/`transition` →
`close_task`, `register_participant` → `update_participant`, `get_project` → `list_projects`
(TRK-129; разбор Glama TDQS в TRK-127#5).
**Почему важно:** выбор инструмента агент делает по описаниям из `tools/list`, и
описание без глагола или без соседа оставляет его угадывать. Фраза о соседе обязана быть
правдой домена: у `transition` стояло «`in_progress → done` без вердикта —
`checks_not_passed`», хотя в `done` он не ведёт вовсе — `closing_not_a_transition`
проверяется раньше вердиктов.
**Как правильно:** соседа называть безлично («— `wait_journal`», «даёт `list_projects`»):
повелительное «бери `X`» ловит `test_no_metadata_prescribes_judges_or_explains`.
Где развилки нет (`link`/`unlink`, `create_task`), фразы нет: описания едут в контекст
каждого вызова. Меняя первую строку докстринга, поправить её английский пересказ в
`README.md`, раздел `## Tools` (тест сверяет только имена, текст — нет).
**Где:** `app/mcp/tools/registries/get_project.py`, `get_project`; `app/mcp/tools/case/read_entries.py`,
`read_entries`; `app/mcp/tools/journal/wait_journal.py`, `wait_journal`; `app/mcp/tools/tasks/transition.py`,
`transition`; `app/domain/tasks.py`, `check_done_is_reached_by_closing`.
**Обновлено TRK-145:** повелительное «бери `X`» теперь ловит
`tests/test_mcp_metadata.py::test_no_metadata_prescribes_judges_or_explains`, а фраза о
соседе стоит у одной стороны пары: `test_no_phrase_repeats_across_tool_descriptions` не
пускает отрезок в шесть слов в описания двух инструментов. Форма ответа («запись целиком —
`read_entries`», «проект целиком — `get_project`») названа один раз, в описании модели ответа
(`AppendedEntryView`, `ProjectKeyView`, `ParticipantNameView`), а не в каждом инструменте.

## Claude Code режет `instructions` и описания на 2048 символах UTF-16

**Что:** клиент Claude Code вставляет `instructions` сервера в системный промпт, но
строку длиннее 2048 обрезает и дописывает «… [truncated]». Тот же предел стоит на
описаниях инструментов. Счёт — `length` строки JS, то есть единицы UTF-16: кириллица —
одна, эмодзи — две; байты UTF-8 ни при чём. Предел меняет переменная клиента
`CLAUDE_CODE_MAX_MCP_DESCRIPTION_LENGTH` (TRK-142#15, исходник Claude Code 2.1.281).
**Почему важно:** обрезка молчит на стороне сервера. Раздел «Кратко» скила в 2799
символов терял пункты 7–11, и никто этого не видел, пока не прочитал системный промпт
живой сессии.
**Как правильно:** длину мерить по строке, которую отдаёт сервер, и тем же счётом, что у
клиента: `len(text.encode("utf-16-le")) // 2`. Правку `instructions` проверять тестом
длины, а не на глаз; запас под будущие строки — сотни символов, не десятки.
**Где:** `app/mcp/instructions.md`; `app/mcp/server.py`, `INSTRUCTIONS`;
`tests/test_mcp_instructions.py`, `test_the_instructions_fit_the_client_limit`.

## Номер записи в чужом деле — чтение под общей блокировкой изменений, а не сквозной параметр

**Что:** `create_task` с `parent`, `link` и `unlink` подшивают запись не только в своё
дело, но и в дело второй задачи (`app/services/links.py`, `add_link`/`remove_link` →
`_record_on_both_sides`), а сама эта функция номер записи не возвращает — наружу едет
только `TaskLink`/`None`. Чтобы короткий ответ инструмента мог назвать номер записи в
**чужом** деле (TRK-143, TRK-144), сервис MCP не трогает сигнатуру `links_service`, а
читает номер сам: `EntryRepository.latest_no` / `case_service.latest_entry_no` — `SELECT
max(no)` по чужой задаче сразу после вызова, который туда написал.
**Почему важно:** это безопасно только потому, что подшивка уже держит общую блокировку
изменений на всю установку (`app/db/locks.py`, `lock_changes`, `pg_advisory_xact_lock`) до
конца своей транзакции: за время между записью и этим чтением никто другой не мог
подшить в ту же чужую задачу ничего, и «последняя запись» — гарантированно та, что только
что подшилась, а не гонка. Без этой гарантии код читал бы неизвестно что при параллельной
записи в ту же чужую задачу с другой стороны.
**Как правильно:** протаскивать номер записи через сигнатуру сервиса ради одного вызова
MCP — тот же компромисс, что и с номерами записей ребёнка в `create_task` (соседняя
заметка «Форма ответа…» этого файла и комментарий в `app/mcp/tools/tasks/create_task.py`,
`create_task`): читать из дела дешевле, чем усложнять сигнатуру, которой пользуются и
REST, и `services/demo.py`. `latest_no` дешевле `case_index`/`headings`: он не тянет
заголовки задачи целиком, только `max(no)`, — годится именно потому, что вызывающий и
так знает, что только что писал в эту задачу, а не читает её общей описью.
**Где:** `app/db/repositories/entries.py`, `latest_no`; `app/services/case.py`,
`latest_entry_no`; `app/mcp/tools/links/link.py`, `link`; `app/mcp/tools/links/unlink.py`, `unlink`; `app/mcp/tools/tasks/create_task.py`,
`create_task` (там же чтение через `case_index`, поскольку номер там нужен рядом с
полной описью ребёнка, а не отдельным дешёвым запросом).

## `instructions` пишутся по-английски и без приказов — это держит тест

**Что:** с TRK-148 текст `app/mcp/instructions.md` английский и описательный: шаги и их
условия фактами о трекере, без повелительного наклонения, «you», «do / don't», «must»,
оценок и примеров (решение владельца TRK-140#18).
**Почему важно:** приказ в английском неотличим от описания на глаз («Split: …» —
метка шага или команда), а правка текста в спешке возвращает привычный тон.
**Как правильно:** первое слово каждой части текста (начало строки, после «.», «:», «;»,
« — ») не из `IMPERATIVE_VERBS`; новый глагол-приказ, прошедший проверку, дописывается
в этот список, а метка шага пишется существительным («Splitting», не «Split»).
**Где:** `tests/test_mcp_instructions.py`, `test_no_clause_opens_with_a_command`,
`test_no_address_duty_or_judgement`, `test_the_instructions_are_english`.

## Докстрока модели и перечисления — тоже метадата, и перечисление домена её тащит

**Что:** pydantic кладёт в схему `description` из докстроки класса — и у вложенной модели
аргументов (`TaskSections`, `TaskChanges`, `Closing*`), и у каждого представления ответа, и
у перечисления (`TaskStatus`, `EntryType`…). Поэтому английских описаний аргументов мало:
до TRK-145 в `tools/list` было 31656 кириллических символов, в том числе длинные доводы
разработчика из докстрок `FoundTaskView` и `EntryView`, и каждая `$defs` перечисления несла
русскую докстроку домена со ссылками на `CONCEPT.md`.
**Почему важно:** докстроки перечислений домена — это ещё и описания в `openapi.json`, из
которого интерфейс генерирует `ui/src/shared/api/openapi.ts`, а тест контракта интерфейса
сверяет клиент с `openapi.json` байт в байт. Правка домена ради метадаты MCP потащила бы
перегенерацию контракта REST и клиента.
**Как правильно:** слой MCP объявляет схему перечисления сам — `app/mcp/enums.py`,
`Annotated[TaskStatus, WithJsonSchema(...)]` со списком значений из перечисления и английским
описанием; проверка значений остаётся доменной. Докстрока модели в `arguments.py` и
`views.py` — короткое английское описание, доводы разработчика — комментарием над классом.
Кириллицу во всём `tools/list` ловит `test_the_tool_list_has_no_cyrillic`. Пример языка
запросов с кириллицей (`text: ~ ключ`) заменён в домене на `text: ~ login`: он уезжает и в
MCP, и в `openapi.json`/`openapi.ts` — оба перегенерированы.
**Где:** `app/mcp/enums.py`; `app/mcp/arguments.py`, `app/mcp/views.py` — докстроки моделей;
`app/domain/query_language.py`, `QUERY_EXAMPLES`; `tests/test_mcp_metadata.py`.

## Инструмент — файл `tools/<группа>/<имя>.py`, и порядок `tools/list` задают два реестра

**Что:** у каждого инструмента свой файл `app/mcp/tools/<группа>/<имя>.py` с функцией
`register(tools)`: в ней описание, аргументы, форма ответа и вызов сценария. Аргумент или
форма одного инструмента объявлены в его файле, общие для нескольких инструментов группы —
в `arguments.py` и `views.py` группы, общие для разных групп — в `app/mcp/arguments.py` и
`app/mcp/views.py`. Порядок `tools/list` — порядок групп в `REGISTRARS` и модулей в `TOOLS`
группы. Раскладка сделана переносом без правки текста: живой `tools/list` обоих наборов
токена до и после совпал байт в байт (TRK-149).
**Почему важно:** модель класса в схеме называется именем класса, а не модуля, поэтому
перенос моделей между файлами схему не меняет — пока имена классов в одном `tools/list`
уникальны. Два класса с одним именем в разных файлах pydantic развёл бы в `$defs` длинными
именами с модулем, и метадата поменялась бы без единой правки текста. Имя переменной в
инструменте, совпавшее с импортированной функцией представления (`page`, `mutation`),
перекрывает её и падает только при вызове.
**Как правильно:** новый инструмент — новый файл в папке группы и строка в `TOOLS` её
`__init__.py`; тип, нужный второму инструменту, переезжает на уровень выше, а не
импортируется из чужого файла инструмента. Имя нового класса аргумента или ответа не
повторяет существующее ни в одной группе. Раскладку стережёт
`tests/test_mcp_tool_files.py`.
**Где:** `app/mcp/tools/__init__.py`, `REGISTRARS`; `app/mcp/tools/tasks/__init__.py`,
`TOOLS`; `tests/test_mcp_tool_files.py`.

## Запись дела проекта адресуется ключом проекта, и в ответах два поля владельца

**Что:** `EntryView` (и `EntryRead` в REST) несёт `task_key` и `project_key`, и непусто ровно
одно: у записи задачи — ключ задачи, у записи дела проекта (`add_project_entry`) — ключ
проекта. Короткий ответ подшивки в дело проекта — своя форма `AppendedProjectEntryView`: в
ней `project_key` вместо `task_key` и нет `title` — у всех типов записи проекта заголовок
присылает агент, и поле всегда было бы `null`.
**Почему важно:** `wait_journal` без отбора и с отбором `project` отдаёт записи обоих
владельцев одним списком; код, читающий `task_key` как строку, на записи проекта получит
`null`. Набор типов `add_project_entry` объявлен `Literal` в схеме (как у `add_entry`), и тип
задачи отсекает проверка аргументов до сценария — `entry_fields_invalid` с `allowed` дело
проекта отдаёт только на входе сценария (REST-схема и MCP-схема его туда не пускают).
**Как правильно:** адрес записи собирать из того ключа, что непуст: `TRK-42#3` или `TRK#7`.
Опись дела проекта едет в `get_project` полем `index` теми же `HeadingView`, что у `get_task`.
**Где:** `app/mcp/tools/case/views.py`, `EntryView`, `AppendedProjectEntryView`;
`app/mcp/tools/case/add_project_entry.py`; `app/mcp/tools/registries/get_project.py`.

## `set_attribute` — одно действие на заведение и изменение, тип записи выбирает сценарий

**Что:** `set_attribute(key, name, value, reason?)` и `remove_attribute(key, name, reason)` —
в группе `registries`, набор `task`, оба с `idempotency_key`. Есть ли атрибут, агенту знать
не нужно (`TRK-164#9`): нет — `attribute_created`, причина необязательна; другое значение —
`attribute_changed`, причина обязательна; то же значение — ничего, `no: null` в ответе
(TRK-157).
**Почему важно:** аннотации по поведению повтора без ключа: `set_attribute` —
`IDEMPOTENT_TASK_UPDATE` (то же значение второй раз ничего не подшивает, прежнее остаётся в
деле), `remove_attribute` — `FILING` (повтор отвечает `attribute_not_found`). `creating=True`
у обоих только ради обязательного `idempotency_key`: повтор `set_attribute` после чужой правки
иначе вернул бы прежнее значение поверх новой.
**Как правильно:** нынешние значения отдаёт `get_project` полем `attributes`, историю —
`read_project_entries` с отбором по типам записей об атрибутах.
**Где:** `app/mcp/tools/registries/set_attribute.py`; `app/mcp/tools/registries/remove_attribute.py`;
`app/mcp/tools/registries/get_project.py`; `app/services/attributes.py`.
