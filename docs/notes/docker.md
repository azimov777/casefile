# Docker

## Зависимости отдельным слоем требуют заглушки пакета

**Что:** `pip install -e ".[dev]"` в образе падает, если каталога `app/` ещё нет: hatchling
собирает колесо и проверяет, что описанный в `pyproject.toml` пакет существует.
**Почему важно:** зависимости ставятся до копирования кода — иначе каждая правка исходника
переустанавливает все пакеты, и сборка образа растягивается на минуты.
**Как правильно:** перед установкой создать пустышку — `RUN mkdir -p app && touch
app/__init__.py && pip install --no-cache-dir -e ".[dev]"`. Реальный код приезжает томом
(dev) или `COPY` (prod) и заменяет пустышку.
**Где:** `docker/Dockerfile.dev`, `docker/Dockerfile.prod`.

## Прод-образ ставит зависимости, но не сам проект

**Что:** в builder-стадии выполняется `pip install .`, а сразу за ним `pip uninstall -y
tracker`: в виртуальном окружении остаются только зависимости.
**Почему важно:** код в рантайм приезжает файлами (`COPY app ./app` + `PYTHONPATH=/app`).
Если оставить проект установленным колесом, в образе будет две копии кода, и правка
скопированной ничего не изменит — импортируется та, что в site-packages.
**Как правильно:** держать единственный источник кода. Зависимости — в `/opt/venv`, код — в
`/app`, `PYTHONPATH=/app`.
**Где:** `docker/Dockerfile.prod`.

## Compose интерполирует переменные до сборки

**Что:** `docker compose -f docker-compose.prod.yml build` падает с
`required variable POSTGRES_USER is missing a value`, хотя сборка образа переменных не требует.
**Почему важно:** конструкция `${VAR:?сообщение}` в прод-контуре разворачивается при разборе
файла, а не при запуске сервиса. Собрать образ «просто проверить» без окружения не выйдет.
**Как правильно:** для любой команды прод-контура сначала `cp .env.example .env` и заполнить
значения, либо передать переменные в окружении команды.
**Где:** `docker-compose.prod.yml`, блок `x-app-environment`.

## Проверка здоровья прод-образа обходится без curl

**Что:** в прод-образе нет `curl` — он не нужен приложению и тянет лишние пакеты.
**Почему важно:** healthcheck с `curl` в прод-контуре тихо переводит контейнер в `unhealthy`,
а зависящие сервисы — в бесконечное ожидание.
**Как правильно:** проверять эндпоинт средствами Python:
`python -c "import urllib.request; urllib.request.urlopen('http://localhost:8000/health')"`.
**Где:** `docker-compose.prod.yml`, healthcheck сервиса `api`.

## Виртуальное окружение хоста прячется анонимным томом

**Что:** `./:/app` монтирует в контейнер и `.venv` с бинарниками, собранными под macOS.
**Почему важно:** содержимое окружения хоста для контейнера бесполезно и сбивает с толку при
отладке путей импорта.
**Как правильно:** добавить вторым томом `- /app/.venv` — анонимный том затеняет каталог хоста.
**Где:** `docker-compose.yml`, якорь `x-app-service`.

## Фоновый процесс стартует раньше миграций — и обязан это пережить

**Что:** воркер событий поднимается вместе с контуром (`depends_on: db healthy`), а
миграции применяются отдельной командой и позже. Первые секунды он работает на базе без
своих таблиц и получает `UndefinedTableError`.
**Почему важно:** сбой поймала только живая проверка. Воркер ходит в базу с первой
секунды, и без обработки ошибок цикла он падал насмерть: в дев-контуре `restart` не
задан, и события копились, пока кто-нибудь не заметил бы. Тесты этого не видят никогда: у
них схема уже накатана. С задачи 13 то же касается и API — он синхронизирует реестр
правил в lifespan, то есть тоже идёт в базу при старте.
**Как правильно:** у любого нового фонового процесса исключение внутри цикла — повод
подождать и попробовать снова, а не завершиться (база может ещё и перезапуститься, и
потерять соединение). Паузу делать заметно длиннее интервала опроса. Ошибку писать в лог
целиком — кроме непромигрированной базы, см. следующую заметку.
**Где:** `app/worker.py`, обработка исключения в `run`.

## «Схемы ещё нет» — не сбой, и в логе оно обязано выглядеть иначе

**Что:** `schema_is_missing` (`app/db/session.py`) отличает SQLSTATE `42P01`
(`undefined_table`) от всего остального. Воркер, планировщик и lifespan API пишут на него
одну строку предупреждения, а на любую другую ошибку — трассировку целиком.
**Почему важно:** до миграций в базу идут все три процесса — воркер и планировщик каждые
пять секунд, API один раз в lifespan. Полноэкранная трассировка на каждый круг давала
десяток трассировок за минуту при каждом подъёме контура с нуля, и настоящую ошибку
старта в такой простыне не находят. Молчать при этом тоже нельзя: строка в логе —
единственное, что объясняет пустой список правил.
**Как правильно:** признак — SQLSTATE, а не текст сообщения: текст меняется с версией
драйвера и локалью сервера. Проверка узкая намеренно — отсутствующая колонка означает
миграции, применённые не до конца, то есть настоящую поломку, и трассировку у неё
отбирать нельзя. Новый фоновый процесс, ходящий в базу при старте, обязан делать то же
самое.
**Где:** `app/db/session.py`, `schema_is_missing`; `app/worker.py`, `app/scheduler.py`,
`app/main.py`.

## Автоперезапуска по правке кода у воркера нет

**Что:** `--reload` есть только у uvicorn, и следит он за своим процессом. Воркер
запускается как `python -m app.worker` и правку файла не замечает.
**Почему важно:** выглядит как «подписчик не работает»: код исправлен, контейнер
запущен, поведение старое.
**Как правильно:** `docker compose restart worker` после правки кода подписчиков.
**Где:** `docker-compose.yml`, сервис `worker`.

## Сигнал остановки доходит до процесса только при exec-форме команды

**Что:** команда воркера задана списком (`command: python -m app.worker`), поэтому Python
становится первым процессом контейнера и получает `SIGTERM` сам.
**Почему важно:** обёртка `sh -c "..."` сигнал не пробрасывает, и остановка каждый раз
доходила бы до `SIGKILL` через 10 секунд — с оборванной посреди работы транзакцией.
Проверяется по времени: `docker compose stop worker` должен занимать секунду, а не
весь `stop_grace_period`.
**Где:** `docker-compose.yml` и `docker-compose.prod.yml`, сервис `worker`.
