## Назначение процесса защищено границей очереди

**Что:** `queue_issue_types.workflow_id` обязателен и входит вместе с `queue_id` в составной
внешний ключ на `workflows(id, queue_id)`.
**Почему важно:** простой внешний ключ только по `workflow_id` позволил бы назначить типу задачи
процесс из другой очереди при обходе сервисного слоя.
**Как правильно:** назначать процесс через workflow-сервис и сохранять составной ключ при любых
изменениях схемы привязок.
**Где:** `app/db/models/queue.py`, `app/db/models/workflow.py`.

## Статус и резолюция изменяются вместе

**Что:** переход в `done` принимает резолюцию в той же операции, а выход из `done` очищает её;
прямое изменение этих полей не может создать промежуточное противоречивое состояние.
**Почему важно:** раздельные запросы оставляют закрытую задачу без исхода или открытую задачу с
устаревшей резолюцией, а журнал фиксирует уже некорректную пару значений.
**Как правильно:** менять статус через переход workflow; при массовом переносе передавать
резолюцию для целевого `done`, а при переносе из `done` полагаться на автоматическое очищение.
**Где:** `app/services/issues.py`, `app/services/workflow.py`, `app/services/catalogs.py`.

## Живой граф проверяется целиком

**Что:** и полная замена графа, и точечное редактирование сначала строят будущий граф и целиком
проверяют достижимость, путь в `done`, отсутствие недопустимых тупиков и совместимость назначений.
**Почему важно:** локально корректное удаление одного ребра может сделать недостижимым другой
статус или оставить существующие задачи без исходящих переходов.
**Как правильно:** не обновлять строки `workflow_statuses` и `transitions` напрямую; использовать
workflow-сервис и показывать клиенту его `impact` со счётчиками затронутых задач.
**Где:** `app/domain/workflows.py`, `app/services/workflow.py`.

## Миграция нормализует старые резолюции

**Что:** миграция workflow создаёт для старых очередей совместимый процесс, добавляет локальный
`done` при его отсутствии, выдаёт техническую резолюцию закрытым задачам без исхода и очищает
резолюцию у незакрытых задач.
**Почему важно:** новый инвариант резолюции нельзя включить только ограничением схемы — старые
строки могли быть созданы до появления workflow и не обязаны ему соответствовать.
**Как правильно:** при изменении правил статуса и резолюции проверять миграцию на данных обеих
аномальных форм, а не только на пустой базе.
**Где:** `app/db/migrations/versions/20260828_1200_workflows.py`.

## Статус очереди по умолчанию связан с её графом в обе стороны

**Что:** статус по умолчанию обязан входить в процесс каждого разрешённого типа задачи и не
может быть категории `done`. Шаблон при создании очереди берёт в граф именно его, а не свой
предпочтительный ключ; смена статуса по умолчанию проверяет все назначенные графы.
**Почему важно:** задача без явного статуса попадает именно в него. Граф без этого статуса даёт
очередь, в которой нельзя завести ни одной задачи (`status_not_in_workflow`), а `done` по
умолчанию требовал бы резолюцию при каждом создании. Оба состояния создавались настройкой
очереди, а проявлялись при первой задаче — далеко от места ошибки.
**Как правильно:** новое умолчание очереди и новый шаблон процесса проверять вместе, на очереди
с нестандартным стартовым статусом, а не только на `open`: совпадение умолчаний скрывает разрыв.
**Где:** `app/services/queues.py` (`_ensure_default_status_usable`),
`app/services/workflow.py` (`create_from_template`, `ensure_queue_default_status_supported`).
