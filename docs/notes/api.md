# HTTP-слой

## `HTTPBearer` со значениями по умолчанию отвечает 403 в чужом формате

**Что:** `HTTPBearer()` без `auto_error=False` при отсутствии заголовка сам возвращает
`403 {"detail": "Not authenticated"}` — мимо единой оболочки ошибки и с неверным статусом
(по соглашениям отсутствие токена — это `401 unauthorized`).
**Почему важно:** ошибка приходит из библиотеки, а не из кода эндпоинта, поэтому переопределённые
обработчики исключений её не видят. Заметит это фронтенд, получив ответ неизвестной ему формы.
**Как правильно:** `HTTPBearer(auto_error=False)` и собственная проверка на `None`. Схема при
этом всё равно попадает в OpenAPI, и в `/docs` работает кнопка Authorize.
**Где:** `app/api/deps.py`, `bearer_scheme`.

## Аутентификация висит на роутере, а не на эндпоинтах

**Что:** `api_router = APIRouter(prefix="/api/v1", dependencies=[Depends(get_actor), ...])`.
**Почему важно:** новый маршрут защищён по умолчанию. Забыть авторизацию на эндпоинте
невозможно — её можно только осознанно снять. Обратный порядок (навешивать зависимость на
каждый роутер) держится на внимательности семнадцати задач подряд.
**Как правильно:** новые роутеры подключать в `app/api/router.py`. Если понадобится публичный
маршрут, выносить его за префикс, как это сделано с `/health`.
**Где:** `app/api/router.py`.

## `Query()` в значении аргумента ловится линтером

**Что:** `limit: int = Query(default=50)` даёт `B008` — вызов функции в значении по умолчанию.
**Почему важно:** правило не придирка: такой объект создаётся один раз на весь процесс.
**Как правильно:** современный стиль FastAPI — `Annotated`:
`limit: Annotated[int, Query(ge=1, le=200)] = 50`. Повторяющиеся параметры удобно вынести
псевдонимом типа (`LimitQuery`, `CursorQuery`).
**Где:** `app/api/deps.py`, `LimitQuery` и `CursorQuery`; `app/api/routes/journal.py`.

## Отзыв токена идемпотентен и отвечает 204

**Что:** `DELETE /api/v1/tokens/{token_id}` на уже отозванном токене снова отвечает `204`.
**Почему важно:** место выглядит как недоработка («почему не 409?»). Это решение: клиент,
не получивший ответ и повторивший запрос, не должен получать ошибку на выполненное действие.
Сама строка при этом не удаляется — у неё проставляется `revoked_at`, и токен остаётся виден
в списке. Наружу это выглядит удалением, внутри остаётся следом в истории.
**Как правильно:** клиент повторяет отзыв без опаски и не считает `204` доказательством
того, что токен был живым. Новое удаляющее действие устраивается так же — повтор отвечает
`204`, а не `404`, — и «удаляет» отметкой в строке, если запись нужна истории.
**Где:** `app/api/routes/tokens.py`, `revoke_token`; `app/services/tokens.py`.

## «Не передано» и «передано как null» различаются типом поля, а не валидатором

**Что:** поле схемы `PATCH` объявляется своим настоящим типом и получает значение по умолчанию
`UNSET` через `unset_field()` из `app/api/schemas/common.py`: `display_name: str =
unset_field(...)`, а не `display_name: str | None = None`.
**Почему важно:** соблазн — объявить поле как `T | None` и отбросить `null` через
`model_dump(exclude_none=True)`. Это молчаливый сбой: клиент отправил `{"display_name": null}`,
получил 200 и уверен, что поле изменено, а не изменилось ничего. Валидатор, отвергающий `null`,
уже лучше, но в OpenAPI поле всё равно остаётся nullable, и сгенерированный клиент разрешает
фронтенду отправить то, что сервер отвергнет.
**Как правильно:** `null` осмыслен («очистить исполнителя») — объявлять `T | None` с тем же
`unset_field()`: тогда различимы все три состояния. `null` не осмыслен — объявлять `T`, и схема
отвергнет его сама. В `unset_field` намеренно `default_factory`, а не `default`: значение по
умолчанию Pydantic пытается положить в JSON-схему, а сентинел не сериализуется, и генерация
схемы сыплет предупреждениями.
**Где:** `app/api/schemas/common.py`, `UNSET` и `unset_field`.

## `operation_id` задаётся генератором на всё приложение

**Что:** `FastAPI(generate_unique_id_function=generate_operation_id)` в `create_app`;
идентификатором операции становится имя функции-обработчика.
**Почему важно:** по умолчанию FastAPI склеивает имя с путём и методом
(`read_actor_api_v1_actors__actor_key__get`). В сгенерированном TypeScript это нечитаемо, а
главное — меняется при любой правке пути: фронтенд ломается на переезде маршрута, хотя контракт
не менялся.
**Как правильно:** ничего не делать руками — генератор действует на все маршруты, включая
подключённые мимо `api_router`. Следить только за именами обработчиков: они становятся именами
функций клиента, а уникальность FastAPI не гарантирует. Её стережёт `tests/test_openapi.py`.
**Где:** `app/api/router.py`, `generate_operation_id`; `app/main.py`.

## Границы размера страницы проверяются дважды, и это не дубль

**Что:** пределы объявлены в параметре запроса (`Query(ge=..., le=...)`) и ещё раз в
`resolve_limit` внутри `app/db/pagination.py`.
**Почему важно:** параметр запроса работает только для HTTP. MCP и фоновые вызовы идут прямо в
сценарий, и без второй проверки один и тот же `limit=100000` REST отверг бы, а MCP выполнил.
Расхождение интерфейсов на одном входе — то, что проект запрещает в первую очередь.
**Как правильно:** выход за границы — ошибка `invalid_page_size`, а не тихое срезание до
потолка. Срезание выглядит дружелюбнее, но вызывающая сторона не может отличить «выдали
меньше, чем просили» от «больше и не было».
**Где:** `app/db/pagination.py`, `resolve_limit`; `app/api/deps.py`, `LimitQuery`.

## Адресация мягкая, создание строгое

**Что:** ключ, которым адресуют существующий объект (путь, фильтр, ссылка в теле), приводится
к каноническому виду: `/api/v1/queues/trk` и `/api/v1/tasks/trk-42` работают.
Ключ, который придумывают при создании, проверяется шаблоном в схеме и кривым быть не может.
**Почему важно:** соблазн поставить `pattern` и на параметр пути велик, но тогда один и тот же
ввод REST отвергает, а MCP, идущий мимо схем FastAPI, выполняет — ровно то расхождение
интерфейсов, которое проект запрещает отдельным правилом. Плюс ошибка домена полезнее:
она объясняет в `details`, какой формат ожидался, а нарушение шаблона — нет.
**Как правильно:** `pattern` только в схемах создания; параметры пути и фильтры — без него.
**Где:** `app/api/routes/queues.py` (`QueueKeyPath`), `app/api/deps.py` (`TaskKeyPath`).

## С FastAPI 0.141 подключённые роутеры не лежат в `app.routes`

**Что:** `include_router` кладёт в `app.routes` объект `_IncludedRouter`, а не разворачивает
маршруты. Отбор `[r for r in app.routes if isinstance(r, APIRoute)]` возвращает пустой список.
**Почему важно:** проверка, написанная по такому отбору, продолжает проходить — на пустом
множестве. Тест уникальности `operation_id` полгода «работал» бы, ничего не стерегя.
**Как правильно:** проверять контракт по схеме OpenAPI (`get_openapi(...)`) — её собирает тот
же код, который отдаёт `/openapi.json` фронтенду. Заодно любая такая проверка обязана
утверждать, что множество непустое.
**Где:** `tests/test_openapi.py`, `_operation_ids`.

## Ошибки валидатора значений отдаются все сразу, в `details.fields`

**Что:** `task_fields_invalid` и `entry_fields_invalid` несут список замечаний целиком:
`[{"field": "title", "reason": "required"}, ...]`. Первое замечание не прерывает проверку.
**Почему важно:** фронт подсвечивает всю форму за один ответ, а агент исправляет запрос за одну
попытку, а не за пять кругов «исправил одно — вылезло другое».
**Как правильно:** причины замечаний — стабильные строки в `snake_case` (`required`,
`too_long`, `not_allowed`), они часть контракта наравне с кодом ошибки. Уточнения, которым
нужна база (`unknown_entry`, `not_a_question`), добавляет сценарий поверх доменных, и
уточняющий запрос идёт только по ветке отказа.
**Где:** `app/domain/fields.py`, `FieldProblem` и `FieldProblems` (шапка модуля).

## Упавший коммит доходит до клиента только с областью зависимости `function`

**Что:** `SessionDep` объявлен как `Depends(get_session, scope="function")`
(FastAPI 0.141). Без этого параметра исключение, вылетевшее при коммите, приходит в
обработчик ошибок с уже отправленным ответом, и Starlette превращает его в
`RuntimeError: Caught handled exception, but response already started`.
**Почему важно:** сбой полностью незаметен для тестов сервисного слоя — падает только
живой запрос, и клиент получает оборванный ответ вместо оболочки ошибки. Воспроизводится
на отложенном ограничении (`DEFERRABLE INITIALLY DEFERRED`), где отказывает не вставка,
а `COMMIT`.
**Как правильно:** FastAPI держит два стека завершения зависимостей — видно в
`fastapi/routing.py`, функция `request_response`: обычный стек закрывается **после**
`await response(...)`, стек с областью `function` — до. Границу транзакции это не
раздваивает, она по-прежнему одна в `session_scope`; сдвигается только момент. Снимать
`scope="function"` нельзя — тест
`tests/test_transactions.py::test_failing_commit_reaches_the_client_as_a_conflict`
падает ровно этим `RuntimeError`.
**Где:** `app/api/deps.py`, `SessionDep`; `app/db/session.py`, `commit`.

## `route_class` родительского роутера не наследуется подключёнными

**Что:** `APIRouter(prefix="/api/v1", route_class=Custom)` не действует на маршруты
роутеров, подключённых через `include_router`. `dependencies` и `responses` при этом
переносятся, а класс маршрута — нет.
**Почему важно:** сбой молчаливый: приложение собирается, маршруты работают, а логика в
`get_route_handler` просто не выполняется. Проверка «в `app.routes` лежат нужные классы»
тоже не спасёт — с 0.141 там `_IncludedRouter`, а не маршруты.
**Как правильно:** сквозное поведение выражать поддерживаемыми параметрами роутера
(`dependencies`, `responses`) или областью зависимости, а не своим классом маршрута.
Если класс всё же нужен — задавать его на каждом роутере предметной области и стеречь
тестом, который делает настоящий запрос.
**Где:** `app/api/router.py`.

## Выбор возвращаемых полей — это `exclude_unset`, а не `dict` в ответе

**Что:** у поиска задача в выдаче описана моделью, где все поля кроме ключа
необязательны, собирается только из запрошенных, а маршрут объявлен с
`response_model_exclude_unset=True`.
**Почему важно:** соблазн отдать `dict[str, Any]` велик и запрещён соглашениями: весь
блок приехал бы на фронт как `Record<string, unknown>` и убил бы смысл генерации
клиента. Обратный соблазн — отдавать всегда полную задачу — ломает требование задачи 12:
сто задач с полным набором полей съедают контекст агента целиком.
**Как правильно:** непрошенное поле остаётся **не установленным**, а не `null`: FastAPI
сериализует модель через `model_dump(exclude_unset=True)`, поэтому значение по умолчанию
до ответа не доезжает. У поля обязан быть дефолт, иначе оно всегда «установлено».
**Где:** `app/api/schemas/search.py`, `TaskSearchRead`; `app/api/routes/tasks.py`,
`list_tasks`.

## Маршрут с фиксированным сегментом объявляется до маршрута с параметром

**Что:** маршрут с постоянным сегментом на одном уровне с параметром пути обязан быть
объявлен **выше** него.
**Почему важно:** FastAPI сопоставляет пути в порядке объявления, и при обратном порядке
постоянное слово уехало бы в параметр пути, не разобралось и превратилось бы в отказ
разбора вместо ответа. Столкновения в нынешнем наборе маршрутов нет ни одного, и это не
везение: `/stream` стоит рядом с `""`, а не с параметром. Первый же сосед вида
`/tasks/summary` рядом с `/tasks/{task_key}` ловушку откроет.
**Как правильно:** новый маршрут с постоянным сегментом (`/summary`, `/stats`)
объявляется в файле **выше** соседа с параметром на том же уровне, а порядок закрепляется
тестом: перестановка функций местами при уборке — ломающее изменение, и без теста об этом
никто не узнает.
**Где:** `app/api/routes/tasks.py`, порядок объявления вокруг `task_key`;
`app/api/routes/journal.py`, `stream_journal`.

## Ответы маршрута замещают ответы роутера по коду, а не дополняют их

**Что:** `responses={422: {"description": "..."}}` на маршруте **вытесняет**
`422: {"model": ErrorResponse, ...}`, объявленный на `api_router`. Уточнив одно
описание, маршрут теряет схему тела ошибки целиком.
**Почему важно:** сбой молчаливый и ровно там, где его меньше всего ждут: маршрут
выглядит документированным лучше соседей, а сгенерированный клиент видит `422` без
формы. У потока событий так потерялись и `422`, и `429`.
**Как правильно:** уточняя описание кода на маршруте, повторять `model`:
`{"model": ErrorResponse, "description": "..."}`. Стережёт
`tests/test_api_contract.py::test_errors_are_described_with_the_common_envelope`.
**Где:** `app/api/routes/journal.py`, `responses` у `stream_journal`.

## Тип содержимого всех ответов операции берётся из `response_class`

**Что:** FastAPI подставляет `route.response_class.media_type` и в успешный ответ, и в
ошибки. Свой класс с типом потока (задача 15) описал в OpenAPI **каждый** ответ маршрута
как `text/event-stream` — в том числе `401`, который на самом деле приходит обычным
JSON-конвертом ошибки. У значения по умолчанию (`JSONResponse`) обработчик, возвращающий
готовый `Response`, получает `200` с **пустой** схемой `application/json` — то есть
маршрут, который генератор клиента видит возвращающим `unknown`.
**Почему важно:** три варианта, и два из них плохи. Фронтенд генерирует клиент из схемы:
на своём классе он разбирал бы ошибку не тем кодом, которым разбирает её у всех
остальных маршрутов, а на значении по умолчанию не разобрал бы успех вовсе. Заметить это
чтением кода почти невозможно — маршрут выглядит правильно.
**Как правильно:** `response_class=Response` — у базового класса Starlette
`media_type = None`, поэтому FastAPI не добавляет к `200` ничего, а ошибкам
подставляет `application/json`. Экземпляр при этом не создаётся: обработчик возвращает
свой `Response`. Тип содержимого нестандартного ответа задаётся вручную в `responses`
(`{"content": {"text/event-stream": {"schema": {"$ref": ...}}}}`). Стережёт
`tests/test_openapi.py`, проверяющий, что `401` описан через `application/json`.
**Где:** `app/api/routes/journal.py`, `stream_journal` и `JournalStreamResponse`.

## Исключения из оболочки перечислены кодом, а не только прозой

**Что:** `app/api/contract.py` (`ENVELOPE_EXEMPT`) — список маршрутов, чей успешный
ответ не завёрнут в `data`, с причиной у каждого. Сплошная проверка сверяет с ним
**множество фактических отклонений**, а не «пропускает известные».
**Почему важно:** сравнение множеств ловит обе стороны сразу. Новое отклонение падает
как незаявленное; исчезнувшее — как исключение, выданное неизвестно кому. Список,
который только «пропускает», ловит одну сторону и молча гниёт.
**Как правильно:** новое исключение заводится строкой в `ENVELOPE_EXEMPT` с причиной и
правкой `docs/CONVENTIONS.md`. Проза и код обязаны совпадать; какие исключения есть
сейчас — говорит сам `ENVELOPE_EXEMPT`, а не эта запись.
**Где:** `app/api/contract.py`; `tests/test_api_contract.py`.

## Справочник кодов ошибок собирается обходом, но только по пакету `app`

**Что:** `error_catalog()` идёт по наследникам `AppError`, отбирая тех, чей
`__module__` начинается с `app.`.
**Почему важно:** обход видит **любой** класс, объявленный в процессе, — в том числе
`tests/test_errors.py::SampleNotFound` с кодом `sample_not_found`. Без отбора прогон
одного файла и прогон всего набора давали бы разные справочники, и тест на дубли падал
бы только на полном прогоне.
**Как правильно:** класс ошибки может лежать в трёх местах (`app/domain/errors.py` —
предметные, `app/db/*` — механизменные, `app/core/errors.py` — базовые), и модуль,
объявляющий свой, обязан быть импортирован до чтения справочника. Полноту стережёт
тест, обходящий весь пакет `pkgutil`.
**Где:** `app/api/contract.py`, `_error_classes`.

## Общий параметр пути объявляется в `deps.py`, а не в роутере

**Что:** `TaskKeyPath` живёт в `app/api/deps.py`, потому что ключ задачи принимают два
роутера — задачи и связи. `QueueKeyPath` остался в своём роутере: его больше никто не
принимает.
**Почему важно:** объявленный по месту дважды, один и тот же параметр приезжает в схему
двумя описаниями, и в сгенерированном клиенте выглядит по-разному. Поймал тест, а не
чтение кода.
**Как правильно:** параметр, который принимает второй роутер, переезжает в `deps.py`;
пока роутер один — остаётся у него. Стережёт
`tests/test_api_contract.py::test_every_path_parameter_is_described`.
**Где:** `app/api/deps.py`, `TaskKeyPath`; `app/api/routes/queues.py`, `QueueKeyPath`.

## Имя и ключ канонизируются на создании, а не отвергаются по регистру

**Что:** шаблон `ParticipantCreate.name` и `QueueCreate.key` принимает **обе** раскладки
(`^[A-Za-z]...`), а канонический вид считает домен: имя в нижний регистр, ключ очереди в
верхний.
**Почему важно:** соглашения требуют уникальности без учёта регистра. Если поставить в схему
шаблон «только нижний регистр», то `Alice` при существующем `alice` даст `422` — разговор о
форме строки вместо ответа «имя занято». Проверка задачи 21 требует ровно `409`.
**Как правильно:** новому идентификатору с уникальностью без учёта регистра давать пару
`normalize_*` / `validate_*` в домене, хранить уже канонизированное значение и держать
уникальность обычным `UNIQUE` — функциональный индекс по `lower()` не нужен. Правило
«адресация мягкая» при этом действует и на создание: разница только в том, что кривую строку
создание всё-таки отвергает.
**Где:** `app/domain/participants.py`, `app/domain/queues.py`.

## Метку временного агента проверяет домен, а не схема заголовка

**Что:** у `ActorLabelHeader` в `app/api/deps.py` намеренно **нет** параметра `pattern`,
хотя место для него есть.
**Почему важно:** с `pattern` одна и та же кривая метка получала бы в REST общий
`validation_error` от Pydantic, а в MCP — предметный `invalid_actor_label` с шаблоном в
подробностях: заголовок приезжает в MCP мимо схем FastAPI. Расхождение интерфейсов на одном
входе проект запрещает отдельным правилом.
**Как правильно:** форму значения, приходящего обоими интерфейсами, проверять в домене, а в
объявлении заголовка описывать её текстом. То же относится к любому будущему заголовку.
**Где:** `app/api/deps.py`, `ActorLabelHeader`; `app/domain/authors.py`, `validate_actor_label`.

## Метка не сверяется с реестром участников, и это решение

**Что:** `X-Actor-Label: owner` пройдёт, даже если участник `owner` существует: подпись
временного агента может совпасть с именем постоянного.
**Почему важно:** выглядит как дыра — временный агент «выдаёт себя» за участника. Сверка
стоила бы запроса в реестр на каждый вызов агента с общим токеном, а защищала бы от того, от
чего защищаться нечем: общий агентский токен по своей природе доверенный, и тот, у кого он
есть, всё равно может завести участника с любым именем, если у токена набор `main`.
**Как правильно:** нужна неподделываемая подпись — выпускать именной токен: у него подпись
всегда своя, и метка молча игнорируется.
**Где:** `app/services/auth.py`, `_author`.

## Токены — ресурс верхнего уровня, а не подресурс участника

**Что:** `/api/v1/tokens`, а не `/api/v1/participants/{name}/tokens` (как было у акторов).
**Почему важно:** у общего агентского токена участника нет вовсе, и в подресурсе его путь
нечем заполнить. Держать два маршрута выпуска — именной и общий — значит развести один
сценарий на два, а `participant` в теле остаётся обычным необязательным полем.
**Как правильно:** ресурс кладётся в подресурс только тогда, когда родитель есть у
**каждого** его экземпляра. Есть вид без родителя — ресурс верхнего уровня, а связь с
родителем становится необязательным полем тела, а не сегментом пути.
**Где:** `app/api/routes/tokens.py`.

## Модель Pydantic в параметрах запроса раскладывается, только если она там одна

**Что:** `filters: Annotated[TaskFilters, Query()]` рядом с `query`, `sort`, `fields`,
`limit` и `cursor` **не** превращается в набор параметров: FastAPI раскладывает модель на
поля только тогда, когда она единственный параметр запроса у маршрута
(`_get_flat_fields_from_params`, `len(fields) == 1`). Иначе она остаётся одним параметром
с именем аргумента.
**Почему важно:** сбой молчаливый и очень убедительный. Схема OpenAPI показывает параметр
`filters`, запрос `?assignee=release_bot` проходит с кодом 200, а фильтр не применяется — ответ
выглядит как «под условие подошло всё». Поймал это только тест, сравнивавший выдачу с
ожидаемой; проверка «эндпоинт отвечает 200» его пропускала.
**Как правильно:** группу параметров запроса объявлять датаклассом через `Depends()` —
`Annotated[TaskFilters, Depends()]`. Поля датакласса аннотируются `Query(...)` как обычно,
попадают в схему по отдельности с описаниями и работают рядом с любыми другими
параметрами. Модель через `Query()` годится только маршруту, у которого других параметров
запроса нет.
**Где:** `app/api/schemas/search.py`, `TaskFilters`; `app/api/routes/tasks.py`, `list_tasks`.

## Список имён принимается и повтором параметра, и через запятую

**Что:** `?fields=title&fields=status` и `?fields=title,status` — одно и то же;
разделение делает `split_names` в домене, а не схема HTTP.
**Почему важно:** первую форму пишет сгенерированный клиент, вторую — человек и агент,
набирающие адрес руками. Признавать только одну значило бы отвечать «поля `title,status`
нет» на запись, которая выглядит совершенно законной.
**Как правильно:** новый параметр-список пропускать через ту же функцию; она же
применяется к `sort`, и потолок числа ключей считается уже после разделения.
**Где:** `app/domain/search.py`, `split_names`.

## Идемпотентность обёрнута вокруг работы обработчика, а не навешана слоем

**Что:** создающий маршрут отдаёт свою работу замыканием в `Once.run`
(`app/api/idempotency.py`), а не помечается декоратором или промежуточным слоем.
**Почему важно:** ключ обязан быть занят **до** работы, а ответ записан **после** неё, и
всё это внутри транзакции запроса. Зависимость FastAPI закрывается уже после сборки
ответа, промежуточный слой видит только байты и про транзакцию не знает — ни то, ни
другое в рамку не помещается. Декоратор, поставленный «поверх», разошёлся бы с
транзакцией молча: ключ фиксировался бы отдельно от объекта.
**Как правильно:** новый создающий маршрут берёт `OnceDep`, кладёт тело обработчика в
локальную функцию и возвращает `await once.run(Модель, request=..., build=...)`. Всё, что
может отказать (поиск очереди, задачи, участника), делается **до** `once.run`: иначе
отклонённый запрос тратит ключ и освобождает его только откатом транзакции.
**Где:** `app/api/idempotency.py`; `app/api/routes/tasks.py`, `create_task`.

## Отпечаток запроса собирается из разрешённых значений пути, а не из адреса

**Что:** в отпечаток уезжает `task.key` и `queue.key`, а не то, что было в URL.
**Почему важно:** адресация в проекте мягкая (`trk-1` находит `TRK-1`), и отпечаток по
сырому адресу считал бы два одинаковых вызова разными — повтор получал бы `409
idempotency_key_reused` вместо первого ответа.
**Как правильно:** сначала разрешить объект, потом строить `request` для `once.run` из
его канонических полей.
**Где:** `app/api/routes/tasks.py`, `create_task_entry`; `app/api/routes/links.py`.

## Ключ идемпотентности проверяется доменом, а не схемой заголовка

**Что:** у `IdempotencyKeyHeader` нет ни `max_length`, ни шаблона; пустоту и длину ловит
`normalize_idempotency_key` (`app/domain/idempotency.py`).
**Почему важно:** тот же ключ приезжает в MCP аргументом `idempotency_key`, мимо схем
FastAPI. С проверкой в заголовке REST отвечал бы общим `validation_error`, а MCP —
предметным `invalid_idempotency_key` с потолком в подробностях: один и тот же вход,
два разных ответа. То же правило и по той же причине действует у метки временного агента.
**Как правильно:** значение, которое приходит и в REST, и в MCP, проверяется функцией
домена, а схема FastAPI объявляет его свободной строкой. Ограничение, записанное в
`max_length` или `pattern` заголовка, действует только на одном из двух входов — и
расхождение ответов заметит не тест, а агент, получивший другой код на тот же ввод.
**Где:** `app/api/idempotency.py`, `IdempotencyKeyHeader`.

## Сплошная проверка требует ключ идемпотентности у каждого маршрута с `201`

**Что:** `tests/test_api_contract.py` роняет прогон, если операция объявляет ответ `201`
и не принимает заголовок `Idempotency-Key`.
**Почему важно:** забыть `OnceDep` у нового создающего маршрута ничего не ломает и не
видно ни в одном тесте самого маршрута — заголовок просто перестаёт действовать. Признак
«создающий» взят из статуса ответа: другого признака у схемы нет.
**Как правильно:** новый создающий маршрут получает параметр `once: OnceDep` и зовёт
его так же, как соседи; отвечать `201` без ключа нельзя. Если создание идемпотентности
не требует по смыслу, ответ у него не `201` — переубеждать проверку исключением в тесте
не нужно.
**Где:** `tests/test_api_contract.py`, `test_every_creating_route_accepts_an_idempotency_key`.

## `openapi.json` лежит в репозитории, и его свежесть держит тест, а не дисциплина

**Что:** до задачи 29 схема была в `.gitignore` с объяснением «вторая копия отстанет».
Теперь она коммитится, а расхождение с кодом роняет прогон.
**Почему важно:** аргумент про отставание верен ровно до тех пор, пока отставание нечем
поймать. Фронтенд живёт отдельным репозиторием, и без файла в git генерация клиента
требовала бы поднятого Docker с чужим бэкендом. Тот же приём уже работал на
`docs/ERRORS.md` — сравнение с выгрузкой, — и его просто распространили на схему.
**Как правильно:** поменял маршрут или схему — `docker compose run --rm schema`, и оба
файла едут тем же коммитом. Забыл — падает `tests/test_artifacts.py` с этой командой в
сообщении.
**Где:** `.gitignore`; `tests/test_artifacts.py`, `test_the_committed_schema_matches_the_code`.

## Документ фронтенду живёт в интерфейсе и сверяется оттуда

**Что:** карта контракта (`ui/docs/FRONTEND.md`) сверяется тестом интерфейса
(`pnpm check` в `ui/`): каждый путь `/api/v1/...` — с `openapi.json`, каждый код из
таблицы частых ошибок — с `docs/ERRORS.md`. Обе выгрузки интерфейс читает из корня
репозитория по относительному пути `..`.
**Почему важно:** документ читают до того, как поднимут бэкенд, и строки из него уезжают
прямо в код интерфейса. Так в нём дожили до задачи 29 `question_not_found` и
`question_already_answered` — коды, которых в трекере нет и не было, — и путь
`/api/v1/tasks/{key}` вместо настоящего `{task_key}`. Ни то ни другое не видно ничем,
кроме сравнения с кодом: выглядит как настоящее и не появляется никогда.
**Как правильно:** переименовав маршрут или сняв код ошибки, помнить, что сторож стоит
в наборе интерфейса и упадёт там, а не в `pytest`. Выгрузки — `openapi.json` и
`docs/ERRORS.md` — обязаны оставаться на своих путях в корне: тест интерфейса ищет их
по `..`.
**Где:** `openapi.json`; `docs/ERRORS.md`.

## Нарушение целостности переводится в `conflict` на границе транзакции

**Что:** `IntegrityError` становится `409 conflict` в двух местах одной функцией:
`transaction` в `app/db/session.py` (обе ветки) плюс `handle_integrity_error` как
страховка для того, что случилось мимо границы. Наружу уходит только имя ограничения
(`details.constraint`), а не текст драйвера — в нём бывают значения строк.
**Почему важно:** обработчик HTTP закрывал только REST. MCP и командная строка получали
сырой `IntegrityError`: агент — безличный крах вызова без кода и подробностей, оператор —
трассировку вместо сообщения.
**Как правильно:** ответ клиента не изменился (`409 conflict`, `details.constraint`), и
менять его нельзя — но новый интерфейс поверх сценариев ничего для этого не делает, ему
достаточно открыть транзакцию общим способом.
**Где:** `app/db/session.py`, `transaction`; `docs/notes/db.md`.

## Отбросить пустые поля в ответе — значит потерять схему у клиента

**Что:** `@model_serializer(mode="wrap")`, выбрасывающий `None`, заменяет схему
**сериализации** модели на «словарь чего угодно». В `openapi.json` она становится
`{"additionalProperties": true}`, а `openapi-typescript` печатает клиенту
`Record<string, unknown>` — то есть ровно то, ради отсутствия чего схема и выгружается.
**Почему важно:** в коде всё выглядит правильно, тесты зелёные, ответ короче. Изъян
виден только на генерации клиента интерфейса (`ui/`) — то есть после того, как
работа считалась сделанной.
**Как правильно:** необязательные поля отдавать как `null` и платить размером, если
модель нужна клиенту типизированной. Маршрутные `response_model_exclude_none` и
`exclude_unset` не годятся по той же причине с другой стороны: они действуют на весь
ответ, а `null` в других его местах значим («исполнителя нет» — не то же самое, что
«поля нет»).
**Где:** `app/api/schemas/entries.py`.

Довод верен и сейчас, а вот вывод «значит, платим размером» верен не всегда: если поля
пусты **не случайно, а по типу**, платить не нужно — см. следующую заметку. Именно так
и оказалось с `EntryFactsRead`, на котором эта заметка была написана: 339 байт на строку
описи он стоил не из-за генерации клиента, а из-за того, что описывал не свои данные.

## Поля, пустые по типу, — это размеченное объединение, а не длинный объект

**Что:** `EntryFactsRead` — факты записи для строки описи дела — был одним объектом из
шестнадцати полей, из которых у любой записи заполнено одно-три: у `status_changed` свои
три, у ссылки свои два, у записи агента — ни одного. Остальные ехали как `null`. Строка
описи весила **339 байт вместо ста**, и опись входит в каждый пакет `get_task`, самый
частый вызов агента.
**Почему важно:** дороже байтов было второе. Состав полей каждого типа **нигде не был
назван**: и агент, и фронтенд узнавали его из того, какие ключи пришли непустыми, то есть
из побочного эффекта сериализации. Схема при этом описывала не данные, а объединение всех
полей всех типов — и потому не могла ничего запретить.
**Как правильно:** разметить по типу, как размечена нагрузка записи. Своя форма фактов на
каждый состав полей, у каждой свой `type: Literal[...]`, объединение
`Annotated[..., Field(discriminator="type")]`.
Схема получает `oneOf` с `discriminator.mapping` на все типы `EntryType`,
`openapi-typescript` разворачивает это в дискриминированный union с именами полей, а не в
`Record<string, unknown>`, — то есть третий путь снимает противоречие, а не выбирает
сторону. Замер на живом контуре: строка описи 502 → 243 байта в среднем, факты записи
305 → 15–87 байт по типу, ответ `GET /api/v1/tasks/DEMO-1` (19 записей) 12 701 → 7 723
байта. Дублирование `type` внутри фактов (17–28 байт на запись) осознанно: без него
`facts` нельзя истолковать, не заглянув в соседнее поле, а его передают отдельным
значением.

Правило шире одного места: **если набор полей зависит от другого поля того же объекта,
это размеченное объединение**, и один плоский объект тут не экономия схемы, а её
отсутствие. Проверяется так же, как здесь: сплошным перебором словаря типов, где у
каждого члена перечисления либо своя форма, либо явно объявленное «формы нет».
**Где:** `app/domain/case.py`, формы фактов и `FACTS_BY_ENTRY_TYPE`;
`app/api/schemas/entries.py`, `EntryFactsRead`; `app/mcp/tools/case/views.py`, `FactsView`;
`tests/test_case_index_facts.py`.

## Молчаливо проглотить присланное — один класс ошибок на три двери

**Что:** трекер принимает данные тремя дверьми, и каждая по-своему решала, что делать с
тем, чего в контракте нет. Тело REST отвечало отказом (`extra="forbid"` в схемах), а две
другие молчали: FastAPI игнорировал неизвестный параметр запроса, SDK MCP — неизвестный
аргумент инструмента. Пойманное живьём: `create_task` с `goal`, `context`, `constraints`,
`output` и `checks` верхним уровнем вместо вложенного `sections` отвечал успехом и заводил
задачу с пятью **пустыми** разделами; `GET /api/v1/tasks?stauts=open` отвечал `200` и
отдавал все задачи установки.
**Почему важно:** это худший вид сбоя — не отказ, а успех. Агент уверен, что прислал
понятое, и узнаёт правду ходов через пять, когда данные оказались не те. Обратной связи у
него нет никакой: короткий ответ изменяющего инструмента (`TRK-12`) даже пустые разделы
показывать перестал. Отбор без условия при этом выглядит убедительнее всего — ответ
читается как «под условие подошло всё».
**Как правильно:** запрет объявляется по разу на дверь, там, где дверь устроена, а не
повторяется в каждой подписи.

- **Тело REST** — `model_config = ConfigDict(extra="forbid")` в модели. Что запрет стоит у
  **каждой** модели тела, включая вложенные, стережёт обход схемы OpenAPI, а не `grep`:
  поиск строки показывает те модели, где запрет есть, и молчит о той, где его нет. Именно
  так нашлась `ResolutionPayload` — единственная нагрузка без запрета среди своих соседей.
- **Параметр запроса** — зависимость на роутере `/api/v1`, рядом с аутентификацией и по той
  же причине: маршрут, заведённый завтра, получает правило сам. Список допустимого берётся
  из дерева зависимостей самого маршрута, то есть из той же схемы, по которой FastAPI
  разбирает параметры; второго перечня имён в проекте нет. Исключений для служебных имён
  (`utm_*` и метки переходов) не заведено: они ездят на переходах браузера по страницам, а
  в `/api/v1` ходят кодом.
- **Аргумент инструмента MCP** — `extra="forbid"` на `ArgModelBase`, базовой модели, от
  которой SDK производит модель аргументов каждого инструмента. Промежуточный слой для
  этого не годится, и это проверено: он сидит выше диспетчера инструментов, и `ToolError`
  оттуда доезжает до клиента протокольной ошибкой JSON-RPC, а не результатом `is_error` с
  текстом, каким приходят все прочие отказы трекера.

Отказ у всех трёх дверей говорит одно и то же слово — `extra_forbidden` — и называет
присланное. Нового кода ошибки под это не заведено.
**Где:** `app/mcp/toolset.py`, `ArgModelBase.model_config`; `app/api/deps.py`,
`reject_unknown_query_params`; `app/api/router.py`, `api_router`;
`tests/test_openapi.py`, `test_every_request_body_refuses_a_field_it_does_not_declare`.

## `meta.total` объявлен у всех коллекций, а заполняет его одна

**Что:** `total` стоит в общем `PageMeta`, поэтому приезжает в `meta` **каждой**
коллекции API, но считает его только `GET /api/v1/tasks`. У остальных там `null` — «не
считали»; `0` означает «по отбору не нашлось ничего» и приходит только от того, кто
считал.
**Почему важно:** соблазн заполнить поле заодно везде велик — оно же объявлено, — но
подсчёт это второй запрос на каждый список, а у ленты дела и журнала он ещё и
бессмыслен: их читают хвостом по `seq` и курсором, номеров страниц там нет. Обратная
ошибка дороже: отдать `0` вместо `null` значит сказать клиенту «задач нет» там, где их
не считали, — и интерфейс честно нарисует пустой список рядом с непустой страницей.
**Как правильно:** коллекции, которой число понадобилось, — попросить его у сценария
(`with_total=True`) и передать в `CollectionResponse.of`; остальным не трогать поле
вовсе. Сплошная проверка оболочки следит за тем, что заполнен он ровно у списка задач.
**Где:** `app/api/schemas/common.py` (`PageMeta`, `CollectionResponse`),
`tests/test_api_contract.py`.

## Сеанс входа — токен со сроком в базе, а окна попыток — в памяти процесса

**Что:** вход по почте и паролю выпускает токен набора `main` со сроком
(`tokens.expires_at`), секрет едет в куку, а `GET /api/v1/session` отдаёт его вкладке
(TRK-113). Отдельной таблицы сеансов нет. Окна неудачных попыток — поля объекта
`PasswordLogin` в `app.state` приложения API. До TRK-113 в памяти процесса жили и сами
сеансы (TRK-90#9): перезапуск API гасил их все, а реплики разнесли бы сеансы по процессам —
вход «то работает, то нет», похожий на поломку куки.
**Почему важно:** с людьми, у каждого из которых свой токен, сеанс обязан пережить
перезапуск и отзываться точечно (выход, смена пароля, отключение), — этого память процесса
не даёт, а строка `tokens` даёт даром: хеш, отзыв, участник. Окна попыток по-прежнему в
памяти: `uvicorn --workers N` или вторая реплика `api` умножили бы разрешённое число
попыток на число процессов.
**Как правильно:** служба `api` запускается одним процессом, это записано рядом с её
командой в `docker-compose.prod.yml`. Понадобятся реплики — переносить в базу окна, а не
сеансы. Отозвать сеанс — отозвать токен; «выйти везде» — `TokenRepository.list_live_sessions_of`
(отключение отзывает больше — все свои токены человека, `list_live_owned_by`, TRK-114). Тесты собирают приложение своё на каждый случай (`create_app`), поэтому
окна соседних тестов не делятся, а сеансы видны любому приложению на той же базе.
**Где:** `app/services/login.py`, `PasswordLogin`; `app/services/accounts.py`, `_revoke_sessions`;
`app/main.py`, `create_app`; `tests/test_password_login.py`,
`test_a_session_survives_a_restart_of_the_api`.

## Адрес клиента для окна попыток: API верит `X-Real-IP` только названному собеседнику

**Что:** окно попыток входа считается на адрес клиента (TRK-98) и на почту (TRK-113); адрес берёт
`ClientAddresses` в `app/api/client_address.py`: собеседник TCP, а если он назван в
`TRACKER_REAL_IP_FROM` — его `X-Real-IP`. `X-Forwarded-For` API не читает вовсе: цепочку
разбирает nginx интерфейса, и только от прокси из `CASEFILE_TRUSTED_PROXIES`. Прод-контур
называет доверенным имя службы `ui`; имя разрешается при попытке входа и помнится
несколько секунд, потому что `ui` поднимается после API и при пересоздании получает новый
адрес. Не разрешилось — доверия нет.
**Почему важно:** заголовок с адресом пишет кто угодно; окно на адрес, которое верит
заголовку по его присутствию, перебирающий обходит новым адресом на каждой попытке.
Второй разбор `X-Forwarded-For` здесь стал бы вторым правилом доверия рядом с nginx. Ещё
одно доверие сидит в самом uvicorn: `--proxy-headers` включён по умолчанию и верит
`X-Forwarded-For` от `127.0.0.1` (`--forwarded-allow-ips`), подменяя `request.client`.
В контейнерах установки на петле к API не ходит никто, кроме проверки здоровья, поэтому
`request.client` — это собеседник TCP; прокси внутри контейнера `api` это бы сломало.
**Как правильно:** адрес клиента брать из `ClientAddresses.of`, а не из заголовков.
Нужен ещё один доверенный собеседник — дописать его в `TRACKER_REAL_IP_FROM` контура,
а не расширять разбор. Счётчики адресов и почт в `PasswordLogin` предела не имеют и не
должны: строка живёт, пока у ключа есть неудача в окне или идущая попытка, а каждая из них
занимает место общего потолка — отдельный предел ниже потолка дал бы перебирающему сбросить
своё окно, наводнив таблицу чужими адресами.
**Где:** `app/api/client_address.py`, `ClientAddresses`; `app/services/login.py`,
`client_key`, `PasswordLogin`; `docker-compose.prod.yml`, `TRACKER_REAL_IP_FROM`;
`tests/test_password_login.py`, `test_the_counters_never_hold_more_keys_than_the_ceiling`.
